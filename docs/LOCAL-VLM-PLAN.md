# CK 조사에 로컬 비전 모델 도입 계획

작성: 2026-09-30. 개정: 2026-09-30(외부 검토 1·2차 반영 — §14). 상태: **실험 스킬로 시운전 중** — §5-A 타협안을 `ck-local` 로 따로 만들었다. 기존 ck-research 는 그대로.

## 0. 한 줄 요약

**찾는 일은 추가 API 비용이 없는 로컬 비전 모델이, 읽고 판단하는 일은 Claude 가 한다.**
롤 화면이 확실히 없는 VOD 는 Claude 를 부르지 않고, 롤이 있는 VOD 는 로컬이 결과창 후보를 모아
Claude 에게 넘긴다. 경기 수·경계·승패·참가자·KDA 판독과 기록은 지금처럼 Claude 가 한다.

가장 먼저 단단히 할 곳은 모델 선택이 아니라 두 가지다.
1. **언제 Claude 를 건너뛰어도 되는가(skip 조건)** — 조용한 누락을 만들지 않게(§6-4).
2. **"롤이 보이는 구간"과 "경기 한 판"을 혼동하지 않기** — 경기 경계는 Claude 가 정한다(§6-3).

## 1. 왜 하나 — 토큰이 어디에 쓰이는가 (실측)

2026-09-28~30 이상호·김민교 백필로 끝낸 VOD **220개** 기준:

| 결과 | 수 | 비율 |
|---|---|---|
| 롤 경기가 연결됨 | 16 | **7%** |
| 후보는 있었으나 전부 대상 아님(FC·LCK 시청·듀오 랭크 등) | 166 | 75% |
| 후보조차 없음(토크·일상) | 38 | 17% |

세션 하나(= VOD 하나)의 비용(백필 자식 세션 237개, 중앙값):

| 모델 | 출력 토큰 | 캐시 읽기 | 캐시 쓰기 | 연 사진 |
|---|---|---|---|---|
| Sonnet 5 (169세션) | 5.1만 | **655만** | 49만 | 19장 |
| Opus 5.5 (40세션) | 1.9만 | 344만 | 32만 | 20장 |
| Haiku 4.5 (16세션) | 3.3만 | 274만 | 29만 | 12장 |
| Sonnet 5.5 (11세션) | 2.8만 | 268만 | 60만 | 22장 |
| 기타(모델 표시 없음, 1세션) | 2.0만 | 289만 | 48만 | 21장 |

비용의 대부분은 사진이 아니라 **캐시 읽기**다 — 도구를 부를 때마다 긴 스킬 문서와 이전 대화 전체를
다시 읽는다. 그래서 절약할 곳은 두 가지다.

1. **세션을 안 여는 것** — 롤 없는 VOD 는 Claude 를 부르지 않는다.
2. **세션 안의 왕복을 줄이는 것** — 결과창을 찾으려고 "5분할 → 5분할 → 2초 간격"으로 여러 번 오가는
   부분(경기 있는 VOD 한 세션에 사진 112장 연 사례)을 로컬로 넘긴다.

⚠ **세션 수 감소 ≠ 비용 감소.** 줄이는 건 주로 롤 없는 VOD 세션인데, 이런 세션은 원래 짧다. 비싼 건
경기 있는 VOD 다. 절감액은 §10 의 방법으로 같은 VOD 묶음에서 **토큰 총량**으로 잰다.

## 2. 검토했다가 버린 대안과 이유

| 대안 | 버린 이유 |
|---|---|
| **Claude Code 를 통째로 로컬 모델로 교체** | 조사는 도구 수십 번 호출 + 엄격한 JSON 제출(`ck:merge`) + 기존 경기 대조의 긴 에이전트 작업이다. 2026-09-29 김민교 9월을 **Haiku 4.5** 로 돌렸을 때 `candidates[].at 은 [시작초,끝초]`, `linked 인데 같은 파일에 match 제출 없음`, `허용되지 않은 필드: note` 로 제출이 반복 거부됐고, 한 VOD 는 "4경기 확인"이라 요약했지만 DB 에 후보 0건이 남았다. 이것이 모든 작은 모델의 가능성을 판정하지는 않지만, **지금의 에이전트 흐름**은 작은 모델에 맞지 않는다는 근거다. 작은 한글 닉네임·KDA 판독 오류는 틀린 경기로 남는다(CLAUDE.md 원칙 3·10). |
| **AirLLM(층을 디스크에서 하나씩 올림)** | 토큰마다 모델 전체를 디스크에서 다시 읽어 토큰당 수 초~수십 초. 비전 모델 미지원, OpenAI 호환 서버 없음. 70B 원본 약 140GB 인데 C: 여유 38GB. |
| **더 큰 로컬 모델(32B 비전)** | 4bit 로도 약 21GB. 지금 장비(VRAM 8GB·RAM 16GB)로는 안 올라간다. |
| **썸네일 거름망만으로 판정** | docs/CK-COLLECTION.md §4 실측: 밝기·채도 규칙은 롤과 FC 를 못 가른다(**오탐 67%**), LCK 시청은 원리상 못 거른다. |

**함께 볼 대안(로컬과 별개, 병행 가치 있음)** — 비용 주원인이 긴 문맥 재독이므로
스킬 문서 축소, 도구 출력 축소, 반복 탐색의 스크립트화만으로도 절감될 수 있다. 로컬 모델 도입과 충돌하지 않는다.

## 3. 지금 조사는 어떻게 도나

```
ck:probe (VOD 1개)
 ├ 기본 지점: 30분 간격(--interval 1800), 거름망과 무관하게 항상  ← 6시간 VOD ≈ 13곳
 ├ 거름망 추천: 썸네일 시트(약 3초 간격, 5시간에 시트 60장·약 6,000칸)의 밝기·채도 → 최대 12곳 추가
 └ 위 지점만 원본 해상도로 받음(HLS 세그먼트 약 6MB/장)
Claude
 ├ 받은 사진을 전부 열어 판정
 └ 롤이 보이면 결과창을 찾으려고 --between/--divide 로 반복해서 좁힘  ← 비용이 큰 곳
```

거름망(`detect` in `scripts/lib/soop-vod.mjs`)의 실력(CK-COLLECTION §4): 정답 경기 5건 전부 탐지 구간 안
(표본 작음), 게임 종류는 못 가름, 경기 끝 경계 3~8분 끌림, 이상호·김민교 두 명으로 맞춘 규칙.

## 4. 설계 원칙

1. **역할 분리.** 로컬 = 찾기(어디에 롤이 있나, 결과창 후보는 어디인가). Claude = 경기 수·경계·대상 여부·
   판독·기록. 로컬 라벨은 **"어디를 볼지"의 힌트**이지 경기 데이터의 근거가 아니다.
2. **놓치지 않는 쪽으로 기운다.** 롤 화면을 "롤 아님"으로 보는 비용(영구 누락)이 반대(세션 하나 낭비)보다 훨씬 크다.
   롤 한 장이라도, 또는 **애매하면** Claude 로 넘긴다.
3. **실패를 "없음"으로 해석하지 않는다.** 사진을 못 받았거나 판정이 실패하면 "롤 없음"이 아니라 "확인 못 함"이다(§6-4).
4. **탐색 실패를 판정으로 바꾸지 않는다.** docs/CK-RESULT-SEARCH-QUEUE-PLAN.md §2 — 결과창을 못 찾았다고
   경기가 아닌 게 아니다.
5. **30분 간격 기본 지점은 유지한다.** 거름망이 놓친 구간을 잡는 안전장치다.
6. **관문은 하나.** Riot(`RiotClient`)·SOOP(`soopFetch`)처럼 로컬 모델 호출도 한 모듈만 통과한다.
7. **로컬이 없거나 실패하면 지금 방식으로 돈다.** 멈추거나 건너뛰지 않는다.
8. **누가 무엇을 봤는지 남긴다.** Claude 가 본 것(`opened`)과 로컬이 본 것(`local_opened`)을 섞지 않고,
   로컬 판정은 실행마다 모델·프롬프트·입력 사진을 보존한다.
9. **분류는 최소로.** 필요한 건 결과창뿐이다(2026-09-30 결정). 밴픽·로딩·인게임·로비는 "롤"로 묶는다.

## 5. 목표 흐름

```
1. 귀 대보기 (기존)
   └ 썸네일 시트 거름망 → "게임 같은 구간" + 30분 간격 기본 지점
2. 로컬 판정 (신규)
   └ 그 지점들의 원본 프레임을 5분류: 롤 결과창 / 롤 / FC / 그 외 / 애매함
   └ skip 조건(§6-4)을 모두 만족할 때만 → "대상 아님(로컬 판정)" 기록, Claude 안 부름
   └ FC 단서 처리는 FC 스킬 개편 때 정한다(§6-4)
3. 로컬 탐색 (신규, 3단계)
   └ 롤이 보이는 "롤 탐색 구간"들 — 경기 한 판이 아니다
   └ 구간 **전체**에서 결과창 후보를 모음(끝만 보지 않음) — 결과창은 판마다 한 번씩 나오므로 후보 수가 판 수의 단서
   └ 시각이 가까운 후보끼리 묶고 묶음마다 대표 사진 2~3장 — 판 구분은 Claude 가 한다
4. Claude 에게 전달
   └ 요약 파일: 롤 탐색 구간 + 결과창 후보 사진(시각 포함)
5. Claude 판독·기록 (기존)
   └ 경기 수·경계 확정, 같은 판인지, 대상 경기인지, 승패·참가자·챔피언·KDA → ck:merge
   └ 후보가 안 보이면 ck:local-find 로 재탐색(최대 2~3회) → 그래도 없으면 기존 방식(5분할)
```

### 5-A. 타협안 — 실험 스킬 `ck-local` 로 먼저 돌려 본다 (2026-09-30 결정)

§5 를 그대로 만들려면 원본 프레임을 촘촘히 받아야 해서 한 달 치가 30시간을 넘는다. 그래서
**원본 대신 SOOP 썸네일 시트(192×108, 약 3초 간격, 5시간에 45MB)를 로컬 모델에 먹인다.**
그리고 오프라인 평가를 더 쌓는 대신 **별도 스킬로 만들어 실제 VOD 에 돌리며 고친다.**

```
① 썸네일 2분 간격 전체 → 5분류 (롤 결과창 / 롤 / FC / 그 외 / 애매)
② 롤·결과창·애매·실패 칸 앞뒤 2분을 10초 간격으로 다시 분류
③ 결과창 칸을 60초 이내끼리 묶어 후보 → 묶음마다 처음·가운데·끝을 ck:probe --at 으로 원본 수신
④ ① 전체를 몽타주로 → Claude 가 항상 열어 검산 (모델이 놓친 롤 화면 확인)
⑤ 판독·기록은 ck-research 규칙 그대로. 결과창 묶음이 없는 롤 구간은 기존 5분할로
```

| 기존 계획(§5·§6)과 다른 점 | 이유 |
|---|---|
| 원본 30분 격자 대신 썸네일 2분 | 원본은 장당 6MB. 썸네일은 이미 받는 것이고 촘촘하다 |
| skip 기록(Claude 안 부름)을 하지 않는다 | 첫 판은 Claude 가 몽타주로 항상 검산한다. 몽타주는 이미지 몇 장이라 싸다 |
| `local_opened`·`signals` 확장 등 core 수정 없음 | 언제든 지울 수 있게. 기록은 `scan.version = "ck-local/1"` 로만 구분한다 |
| `ck:local-find` 없음 | 결과창 묶음이 없으면 기존 5분할로 간다. 필요해지면 그때 만든다 |

- 구현: `scripts/ck-local/`(scan·vlm·image), 스킬 `.claude/skills/ck-local/SKILL.md`, `npm run ck:local`.
  백필은 `CK_BACKFILL_SKILL=ck-local scripts/ck-backfill.sh …`. **DB 에는 도구가 아무것도 쓰지 않는다.**
- 지우는 법은 스킬 문서 「지우기」. 실험 결과가 좋으면 §6 의 정식 구조(core 관문·skip 조건)로 옮긴다.
- 볼 것: VOD 당 로컬 시간, Claude 가 연 이미지 수, 모델이 놓친 롤·헛본 결과창(스캔 기록 `note`에 적는다).

## 6. 구성요소

### 6-1. 로컬 모델 관문 — `packages/core/lib/localvlm/client.ts` (신규)
- Ollama `/api/chat` 한 곳만 부른다. `temperature 0`, 응답 형식은 JSON 스키마로 강제(`format`).
  ⚠ 스키마는 **답의 형식**만 보장한다. 판정이 맞다는 보장이 아니다([Ollama 문서](https://docs.ollama.com/capabilities/structured-outputs)).
- 이미지는 가로 960px 로 줄여 보낸다(시험 조건).
- 동시 1건(GPU 하나), 요청당 시간 제한. 서버 꺼짐·시간 초과·형식 오류는 **예외**로 올려 호출부가 판단한다.
- 결과에 모델 식별값(이름 + digest)·프롬프트 버전을 함께 돌려준다.

### 6-2. 화면 분류기 — 5분류
| 라벨 | 뜻 | 처리 |
|---|---|---|
| `LOL_RESULT` | 경기 종료 후 롤 클라이언트 결과 창('승리'/'패배' + 점수판·그래프·룬 탭) | 결과창 후보 |
| `LOL` | 그 밖의 롤 화면(인게임·밴픽·로딩·로비). 게임 중 화면의 점수판은 결과창이 아니다 | 롤 있음 |
| `FC` | FC 온라인/축구 게임 | 롤 아님 + FC 단서 |
| `OTHER` | 그 외 | 롤 아님 |
| `UNSURE` | 판단이 애매함 | **Claude 로 넘김** |
- `UNSURE` 는 "애매하면 Claude"를 표현할 자리다. 작은 모델은 자기 확신을 잘 표현하지 못하므로 실제 사용률은 시험으로 확인한다.
- FC 와 OTHER 는 헷갈려도 게이트에는 상관없다. 중요한 건 **롤 → 롤 아님** 오분류다.
- 프롬프트는 버전을 매겨 코드에 둔다. 바꾸면 §11 회귀 시험.

### 6-3. 사전 조사 명령 — `npm run ck:local-scan -- --vod <번호>` (신규)
1. 기존 `ck:probe` 와 같은 지점(30분 격자 + 거름망 추천)의 원본 프레임을 받는다(이미 있으면 재사용).
2. 전부 분류. skip 조건 판정(§6-4).
3. (3단계) 롤 프레임이 이어지는 **롤 탐색 구간**을 만든다.
   - ⚠ 기존 `mergeRuns` 는 **일정 간격 썸네일의 장수**로 끊김을 센다. 30분 격자·추천 지점처럼 **불규칙한 시각**에는
     그대로 못 쓴다 — 초 단위 거리로 다시 설계한다.
   - ⚠ **롤 탐색 구간 ≠ 경기 한 판.** 연속으로 여러 판을 하면 하나의 긴 구간이 되고(끝만 보면 마지막 판 결과창만 찾는다),
     한 판 중 알트탭·광고가 나오면 여러 조각이 된다. 그래서 결과창 후보는 **구간 전체**에서 모은다.
4. 결과창 후보 탐색은 **다운로드 예산** 안에서 한다 — 6시간 전체를 30초 간격 원본으로 보면 720장·약 4.3GB·추론 약 22분.
   - 우선 **썸네일(3초 간격, 시트 60장 약 45MB)** 로 결과창을 찾을 수 있는지 시험하고, 되면 원본은 후보 몇 장만 받는다.
   - ⚠ 썸네일은 **다운로드만 줄인다.** 5시간 방송의 약 6,000칸을 하나씩 추론하면 장당 1.8~2.9초로 **약 3~5시간**이다.
     롤 탐색 구간 안의 칸만 보거나, 여러 칸을 한 장으로 묶어 보내는 방식(대신 칸이 작아져 탐지율이 떨어질 수 있음)을
     시험해야 한다. 시험에는 입력 방식·추론 횟수·전체 시간·결과창 탐지율을 함께 잰다.
   - 안 되면 구간 안에서만, VOD 당 원본 N장 상한을 둔다.
   - **다운로드 예산과 추론 예산(횟수·시간)을 둘 다 둔다.** 예산을 다 써서 멈춘 경우는 "결과창 없음"과 구분해 기록하고 Claude 에 알린다.
5. 요약 파일 `out/ck/<vod>/local-scan.json` — **실행마다 추가**(덮어쓰지 않음):
```json
{
  "runs": [{
    "at": "2026-10-01T02:00:00Z", "model": "qwen3-vl:8b-instruct", "model_digest": "0533d74300e4",
    "prompt_version": "gate5/1", "gate": "send", "gate_reasons": [],
    "frames": [{"at": 1800, "path": "out/ck/…/g0001800.jpg", "label": "FC", "source": "grid"}],
    "regions": [{"from": 4210, "to": 8400, "result_candidates": [{"at": 6152, "path": "…"}, {"at": 8120, "path": "…"}]}]
  }]
}
```
- DB 에는 쓰지 않는다. 기록은 `ck:merge` 한 창구(기존 원칙).

### 6-4. skip 조건과 백필·자동 조사 연결

**skip(= Claude 생략)은 아래를 모두 만족할 때만:**
1. 계획한 필수 프레임(30분 격자 + 거름망 추천)을 **전부** 받았다. 빈 목록·일부 다운로드 실패는 skip 금지.
   **거름망 자체도 정상 완료**여야 한다 — `scanSheets` 는 시트 JPEG 해석에 실패하면 오류 없이 그때까지 받은 칸만
   돌려준다(scripts/lib/soop-vod.mjs). 그러면 추천 지점이 조용히 적게 나온다. 시트 수가 영상 길이에 맞는지 확인한다.
2. 받은 프레임의 분류가 **전부 성공**했다(시간 초과·형식 오류 0).
3. `LOL`·`LOL_RESULT`·`UNSURE` 가 한 장도 없다.
4. 못 본 파일·실패 구간이 없다(분할 파일 전부 처리).
5. 이 VOD 의 이전 기록에 대상 경기나 미해결 후보가 없다.
6. 제목 규칙(`titleExclusion`)과 무관하게 적용한다(제목 제외는 그 전에 이미 걸러짐).

하나라도 어기면 `gate: send` 이고 이유를 `gate_reasons` 에 남긴다. **"실패"는 "롤 없음"이 아니다.**

**FC 단서 — FC 스킬 개편 때 결정(보류)** — 지금 자동 조사는 Claude 가 FC 화면을 보면 `fco:context clue` 를 남긴다
(이상호 96건, 김민교 64건). 로컬이 FC VOD 를 skip 하면 이 단서가 끊긴다. 로컬 분류로 대신 남기는 방안이 있지만
로컬은 FC 를 자주 "그 외"로 본다(§8-1: FC 증거 40장 중 18장만 FC). 그래서 FC 온라인 VOD 탐색 스킬을 고칠 때 함께 정한다.
그 전까지 skip 된 VOD 의 FC 단서는 생기지 않는다(알려진 공백).

**연결 방식 — 백필과 자동 조사가 다르다**
- 백필(`scripts/ck-backfill.sh`): VOD 하나당 Claude 세션 하나. `next` 로 고른 VOD 에 `ck:local-scan` → skip 이면
  기록하고 다음 VOD, send 면 요약 파일 경로를 프롬프트에 넣는다.
- 자동 조사(`scripts/ck-auto.sh`): **큐 전체를 세션 하나**에 넘긴다. 그래서 큐를 만든 뒤 각 VOD 에 게이트를 돌려
  skip 된 VOD 를 큐에서 빼고, 남은 VOD 의 요약 파일 경로를 큐 파일에 붙인다.
- 로컬 실패 → 게이트 없이 지금처럼 Claude(원칙 7). **정상 전달(send)** 과 **장애 폴백**은 따로 센다.
- `ck:merge` 저장 성공 **그리고** `vodWork` 완료 확인 뒤에만 큐에서 뺀다.
- 요약 파일은 실행마다 안정적인 `run_id` 로 참조하고, 중단돼도 깨지지 않게 임시 파일에 쓴 뒤 바꿔 넣는다.
- 로컬 호출 동시 1건은 **프로세스를 넘어서** 지켜야 한다(Ollama 는 서버 차원에서 병렬 요청을 받고, 병렬은 메모리를 늘린다).

### 6-5. 다시 찾기 명령 — `npm run ck:local-find -- --vod <번호> --around <초> --want result` (신규)
- Claude 가 "이 근처에서 결과창 다시 찾아와"라고 시킬 때 쓴다. 로컬이 주변을 훑어 후보 사진·시각을 돌려준다.
- Claude 는 명령 한 줄 + 사진 몇 장. VOD·경기당 2~3회까지, 그 뒤엔 기존 방식.

### 6-6. 기록 규칙 — `event_lead.raw.scan`
로컬 게이트로 끝낸 VOD(새 테이블·마이그레이션 없음). 기존 입력 검증을 통과하는 형태로:
```json
{
  "scan": {
    "status": "done", "requested": [[0, 12345]], "sampled": [[0, 12345]],
    "local_opened": [0, 1800, 3600, 4210],
    "signals": ["local-vlm"], "version": "local-gate/qwen3-vl:8b-instruct@0533d74300e4/gate5/1",
    "note": "로컬 판정: 롤 화면 없음 (28장). 요약: out/ck/<vod>/local-scan.json runs[0]"
  },
  "candidates": [
    {"id": "local-gate-1", "at": [0, 12345], "conclusion": "not_target", "why": "로컬 판정: 롤·애매함 0장 / 28장"}
  ]
}
```
- 후보에는 `id` 필수, `note` 는 후보 필드가 아니다(설명은 `why`). 기존 검증: `scripts/ck-merge.mjs` 후보 검사,
  `packages/core/lib/db/ck.ts` 허용 필드 검사.
- **`local_opened`(결정, 2026-09-30)**: 로컬이 본 시각. `opened` 는 "Claude·사람이 실제로 연 시각" 그대로 둔다.
  - `LeadScanState` 에 `local_opened?: number[]` 추가, `mergeScan` 에서 누적 병합.
  - `signals` 타입에 `"local-vlm"` 추가.
  - `vodWork` 의 "연 화면이 있다" 조건을 `opened` 또는 (`signals` 에 `local-vlm` 이 있을 때) `local_opened` 로 넓힌다.
  - `ck:merge` 입력 검증에 새 칸 허용, 스킬 「기록의 뜻」에 한 줄 추가.
- **실행별 출처**: `version` 은 재실행 때 덮이고 열람 시각은 누적되므로, 여러 모델로 다시 돌리면 어느 모델이 어느
  사진을 봤는지 DB 만으로는 흐려진다. 그래서 실행 단위 기록은 요약 파일 `runs[]` 에 보존하고, `scan.note` 가
  그 실행을 가리킨다. 모델을 바꿔 재조사할 때는 `version` 접두어(`local-gate/`)로 골라낸다.

### 6-7. 스킬 수정 — `.claude/skills/ck-research/SKILL.md`
- 요약 파일이 있으면 거기서 출발한다. 30분 간격으로 처음부터 다시 훑지 않는다.
- 로컬 라벨은 탐색 힌트다. **경기 수·경계는 Claude 가 확정한다**(롤 탐색 구간은 판이 아니다).
- 결과창이 안 보이면 `ck:local-find` → 그래도 없으면 기존 5분할. 결과창을 못 찾아도 경기가 아닌 게 아니다.
- 「기록의 뜻」에 `local_opened` 한 줄.

## 7. 구현 순서 — 단계마다 측정 후 다음으로

| 단계 | 내용 | 다음 단계로 가는 조건 |
|---|---|---|
| **0. 오프라인 평가** | 과거 데이터 전체로 게이트 검증(§8-4). 추가 토큰 0 — 실시간 비교 운영을 대신한다 | 경기 VOD 누락 0, 어려운 사례 포함 |
| **1. skip 조건 + 기록 계약** | §6-1 관문, §6-2 분류기, §6-4 skip 조건·FC 단서, §6-6 기록, 가짜 Ollama 검증(§11) | 실패 주입 시험에서 "실패 → send"가 전부 성립 |
| **2. 제한적 자동 skip** | 백필부터 적용. skip 기록에 버전이 남아 나중에 골라 재조사 가능. 자동 조사는 그다음 | 운영 중 skip VOD 표본 재확인 + 토큰 총량 비교(§10) |
| **3. 결과창 탐색 + 전달** | §6-3 롤 탐색 구간·후보 수집(썸네일 우선), 요약 파일, §6-5, §6-7 | **실제 경기마다** 결과창을 찾은 비율(후보 중 결과창 비율이 아니라), 다운로드량, 세션 토큰 |

**실시간 비교 운영(로컬이 skip 이라 해도 한동안 Claude 로 계속)을 하지 않는 이유**: Claude 는 이미 수백 개 VOD 를
조사해 정답을 남겼다. **분류 성능**은 그 데이터로 추가 토큰 없이 검증한다(0단계). 과거 데이터가 못 보여 주는
**운영 문제**(새 VOD 의 다운로드 실패, 큐 처리, 완료 기록)는 실패 주입 시험(§11)과 제한적 운영(2단계)으로 확인한다.

**평가 명세** — 평가 입력은 **1차 탐색 지점만**이다. `scan.probes.extra` 와 `probe.json` 은 Claude 가 나중에 좁히며 본
지점까지 누적하므로, 저장된 사진을 전부 쓰면 실제 게이트보다 유리해진다(§8-2 에서 실제로 그랬다). 운영할 **최종 프롬프트**로
평가한다. VOD·경기 단위로 개발용/평가용을 나누고, 정답 근거(어느 기록으로 경기 유무를 판정했는지)를 목록에 남긴다.

### 8-2. VOD 단위 게이트 — ⚠ 유리하게 계산됨(무효)
VOD 45개 · 1,244장, 롤 1장이라도 있으면 send. **입력에 Claude 가 나중에 좁히며 본 지점이 섞였다**(`scan.probes.extra` 누적).
실제 1차 조사는 VOD 당 최대 약 25장인데 경기 VOD 는 중앙값 30장·최대 129장이었다. 아래 수치는 참고만 하고 §8-4 로 대체한다.

| | Qwen2.5-VL 7B | Qwen3-VL 8B instruct |
|---|---|---|
| 경기 VOD 15 → send | **15/15** | **15/15** |
| 대상 아님 30 → skip | 20 (67%) | 21 (70%) |
| 경기 VOD 최소 롤 프레임 비율 | 28% | 27% |
| 추론 시간 | 1.81초/장 | 2.90초/장 |

- 시간은 추론만이다. 프레임 다운로드를 포함한 처리 시간은 따로 잰다.
- 이 비율을 백필 실적(대상 아님 93%)에 곱하면 전체 VOD 의 약 62% 가 skip — **세션 수 추정**이지 비용 추정이 아니다(§1).

### 8-3. 결과창 구분
- **1차 시험은 무효.** 정답으로 쓴 `kind='result'` 사진이 대부분 **멸망전 공식 중계 화면**이었다. 중계 화면은 경기 내내 아래에
  10명 KDA 점수판이 떠 있고, 멸망전은 클라이언트 결과창을 보여 주지 않는다. 찾아야 할 건 **스트리머 CK 방송의 클라이언트 결과창**이다.
  - 그래도 성향은 보였다: Qwen2.5 는 점수판만 보이면 결과창이라 하고(게임 중 화면 52/80, FC 5/30 을 결과창으로), Qwen3 는
    정의를 지켰다(게임 중 6/80, FC 0/30).
- **2차 시험(CK 만)**: 결과창 158장(경기 65판·채널 8개) + 결과창 직전 1~15분 60 + 직후 5~15분 60 + FC 30.

  | | Qwen2.5-VL 7B | Qwen3-VL 8B |
  |---|---|---|
  | 결과창 → 결과창 | **152/158 (96%)** | 146/158 (92%) |
  | 결과창 아님 → 결과창 | 29/150 | **16/150** |
  | FC → 결과창 | 5/30 | **0/30** |
  | 추론 시간 | **1.8초/장** | 4.1초/장 |
  - 직접 확인: "결과창" 정답에도 게임 도중 관전 화면·넥서스 파괴 후 승리 연출이 섞여 있다(모델이 "아님"이라 한 게 맞음).
    두 모델 모두 롤 로비 위 메모장을 결과창으로 봤다.
  - 해석: 두 모델 모두 CK 결과창을 90% 넘게 찾는다. Qwen2.5 는 넓게(놓침 적고 오탐 많음), Qwen3 는 깐깐하게.
    결과창 탐색은 놓치는 쪽이 더 비싸므로(재탐색) Qwen2.5 가 약간 유리하지만, 정답 잡음을 감안하면 차이는 작다.
  - 이 시험은 **분류** 시험이다. 실제 **탐색** 평가(3단계)는 따로 한다 — 결과창이 있는 경기 중 후보를 확보한 비율,
    그 후보로 Claude 가 필요한 정보를 읽은 비율, 결과창 없음·예산 소진·탐색 실패를 나눠 센다. 전환 직전·직후 수십 초
    (종료 연출, 결과창 진입 과정, 가려진 결과창)도 음성 표본에 넣는다.

### 8-4. 오프라인 평가 (0단계)

**1차 — 30분 격자만, 5분류(`UNSURE` 포함), 두 모델 (진행 중)**: VOD 198개(경기 31 · 대상 아님 167) · 1,621장.
거름망 추천 지점은 기록에서 Claude 추가 지점과 분리할 수 없어 뺐다 — **실제 게이트보다 불리한 조건**이다.
§8-2 의 45개는 개발용으로, 나머지는 평가용으로 따로 채점한다. (결과가 나오면 여기에 채운다.)

**이후 계획**:
- 1차 프레임이 온전한 **경기 VOD 32개 + 대상 아님 VOD 133개** 전체. 경기 VOD 32개 누락 0 이면 95% 상한 약 9%.
- **어려운 사례를 일부러 넣는다**: 긴 방송 중 짧은 단판, 게임 화면이 작거나 가려진 VOD, 짧은 꼬리 파일.
- 모델 선택·프롬프트 수정에 쓰지 않은 VOD 로 채점한다(8-2 의 45개와 분리).

## 9. 우려와 대응

| 우려 | 왜 문제인가 | 대응 |

| **태그 없는 LCK 시청** | 롤 화면이라 send(비용만 듦) | 제목 규칙(`#LckWatchParty`)이 먼저 거름. 나머지는 Claude 판단 |
| **결과창을 잘못 짚음**(직전·직후·가려짐) | Claude 가 못 읽음 | 후보 2~3장, `ck:local-find`, 최종 폴백은 기존 5분할 |
| **로컬 판정이 경기 데이터로 새어 들어감** | 7B 는 작은 글씨를 틀린다 | 로컬은 라벨·시각만 낸다. 경기 필드는 로컬 코드 경로에 없다 |

| **자동 조사 구조가 백필과 다름** | 큐 전체를 세션 하나에 넘긴다 | 큐 필터링 + 요약 파일 경로 첨부(§6-4) |
| **Ollama 꺼짐**(WSL 재시작 — 2026-09-30 실제 발생) | 게이트가 멈추면 조사가 멈춤 | 원칙 7 폴백 + 서버 자동 기동 |
| **모델·프롬프트 교체 시 결과가 달라짐** | 예전 skip 판정의 신뢰도가 바뀜 | 실행별 출처 보존(`runs[]`), `version` 으로 재조사, 회귀 시험 |

| **비용 절감 과대평가** | 세션 감소 ≠ 토큰 감소 | §10 방법으로 실측 |

## 10. 비용 측정 방법

같은 VOD 묶음에서 기존 방식과 새 방식을 비교한다.
- **Claude 토큰 총량** — 모델별로 일반 입력·출력·캐시 읽기·캐시 쓰기를 **나눠서**, 재시도 세션까지 합산한다.
  세션 로그(`~/.claude/projects/…/*.jsonl` 의 `usage`)에서 VOD 별로 모은다.
  과거 세션이 있으니 "롤 없는 VOD 세션이 전체 토큰의 몇 %였나"는 지금도 계산할 수 있다.
- 전체 소요 시간(다운로드 + 로컬 추론 + Claude), 다운로드량, **send 비율과 장애 폴백 비율을 따로**.
- "무료"라고 쓰지 않는다 — 로컬은 **추가 API 비용이 없을** 뿐 전기·시간·디스크를 쓴다.

## 11. 검증

- **가짜 Ollama**: `verify:ingest` 의 가짜 Riot 처럼 HTTP 경계만 가짜로 두고 게이트·폴백·기록을 끝까지 돌린다.
  **실패 주입**: 빈 프레임 목록, 일부 다운로드 실패, 시간 초과, 형식 오류, 서버 꺼짐 → 전부 `send` 또는 폴백이어야 한다.
- **정확도 회귀 명령** `npm run verify:localvlm`: §8 정답 세트(사진 180 · VOD 45 · CK 결과창 308 + 0단계 세트).
  모델·프롬프트를 바꿀 때마다 돌린다. 기준: 경기 VOD 누락 0.
- **기록 계약**: §6-6 형식이 `ck:merge` 검증을 통과하는지, `vodWork` 가 완료로 보는지, `version` 으로 골라 재조사 가능한지 단위 테스트.

## 12. 운영

- **설치(완료, 2026-09-30)**: Ollama 0.35.0 을 `~/.local/ollama` 에 sudo 없이 풀었다(공식 `curl … | sh` 는 sudo 필요).
  모델은 `~/.ollama/models`. 서버: `~/.local/ollama/bin/ollama serve`.
  받은 모델: `qwen2.5vl:7b`(6.0GB), `qwen3-vl:8b-instruct`(6.1GB) — 결정 후 하나만 남긴다.
- **재시작**: WSL 이 재시작되면 서버가 꺼진다. 자동 기동이 필요하다.
- **하드웨어**: RTX 2070 8GB / Ryzen 7 3700X / RAM 16GB(WSL 9.7GB) / NVMe 512GB 하나(C:, WSL 가상 디스크 포함).
  7~8B 비전 모델이 한계다. 게이트·결과창 탐색에는 이 사양으로 충분하다(§8).
- **디스크**: 조사 프레임은 검수 증거(`match_evidence_frame`·`fco_context_evidence`·`raw` 안 경로)와 **요약 파일 `runs[]` 가 참조하는 사진**을 영구 보존.
  조사가 끝난 VOD 의 미참조 프레임은 지워도 된다(2026-09-30 에 3.3GB 정리). WSL 안에서 지워도 C: 는 가상 디스크를 압축해야 줄어든다.

## 13. 결정이 필요한 것 / 결정된 것

- ✅ 로컬이 본 시각은 별도 칸 `local_opened`(§6-6).
- ✅ 분류는 결과창 중심(롤 세부 분류 안 함).
- ✅ 실시간 비교 운영 대신 오프라인 평가(0단계).
- ⏳ **모델**: 게이트(§8-4 재시험)와 결과창 탐색(§8-3)을 **각각의 목적**으로 평가해 정한다. 운영 단순성을 위해 하나로 가는 것을 우선한다.
- ⏳ **FC 단서**: FC 온라인 VOD 탐색 스킬 개편 때 결정(§6-4).
- ⏳ **3단계 착수 여부**: 0~2단계 결과와 썸네일 결과창 시험을 보고 결정.
- ⏳ **스킬 문서 축소 등 병행 대안(§2)** 을 함께 진행할지.
