# FC 온라인 경기 맥락 조사 스킬 계획

상태: 구현 반영 중 (2026-09-24). 구현 순서 1~5와 6의 FC API 일일 수집까지 구현됐다 —
실측 [FCO-TIME-SAMPLES](FCO-TIME-SAMPLES.md), 스키마 0032, `fco:context` CLI 와
`verify:fco-context`, `fco-match-context` 스킬, `ck-research` 교차 단서, 워커 `engine_e_fco`.
남은 것: 공통 VOD 목록의 일일 스케줄 연결(계약 1), 검수 화면(admin). `skill-creator` 검증기는
이 환경에 없음을 확인했고 스킬 등록·실제 VOD 사례 검증으로 대신했다.

## 결정

**기존 `ck-research`는 작게 수정하고, `fco-match-context` 스킬을 새로 만든다.**

- `ck-research`: 요청 범위의 LoL VOD를 계속 전부 조사한다. 이미 읽은 화면에 FC 온라인이 보이면 `VOD ID·채널·VOD 전체 초·관찰`을 가벼운 교차 단서로 남긴다. FC 경기의 분류나 행사 조사를 그 자리에서 끝낼 의무는 없다.
- `fco-match-context`: API로 확인한 스트리머 간 경기에서 출발한다. 관련 VOD·공지의 필요한 부분만 확인해 단순 친선/CK/대회 맥락과 행사 메타데이터를 기록한다.
- 공통 도구: SOOP VOD 목록, 실제 재생 길이·분할 파일의 전체 시간축, 선택 지점의 프레임·채팅·음성. 두 스킬이 같은 VOD를 독립적으로 전량 재조사하지 않는다.

핵심은 LoL의 **필수 수행·기록 / 자율 해석** 경계를 계승하되, FC에서는 경기 발견과 승패 판독을 VOD의 임무에서 빼는 것이다. [`ck-research`](../.claude/skills/ck-research/SKILL.md), [`CK-RESEARCH-PLAN`](CK-RESEARCH-PLAN.md), [`MULTI-GAME-FCONLINE-PLAN`](MULTI-GAME-FCONLINE-PLAN.md)을 기준으로 삼는다.

다만 `MULTI-GAME-FCONLINE-PLAN`의 세 항목은 이 문서가 대체한다 — 「친선은 우선 `friendly`로 둔다」(§Phase 1), 「경기당 수락 후보 하나」(§Phase 2), 「matchDate ±N분만 확인한다」(§Phase 3). 매치 타입의 이름 표시는 그대로 두되 행사 맥락의 증거로 쓰지 않으며, `±N분`은 판정 규칙이 아니다. 경기당 하나로 관리하는 것은 현재 최종 맥락 판단이고, 확인된 VOD 근거는 여러 개를 허용한다. 원문에도 개정 표시를 남겨 기준 문서 둘이 서로 반대말을 하지 않게 한다.

## 두 스킬의 경계

| 상황 | 담당 | 남길 것 | 하지 않을 것 |
|---|---|---|---|
| LoL 전체 탐색 중 FC 화면 발견 | `ck-research` | 실제 읽은 화면의 VOD 위치와 짧은 관찰, FC 후보로 넘겼는지 | FC 경기·대회 확정, LoL 탐색의 나머지 범위 생략 |
| API에 새 스트리머 간 FC 경기 등장 | `fco-match-context` | `matchId` 기준 조사 상태, VOD/공지 후보와 결과 | VOD를 처음부터 전량 훑어 경기 찾기 |
| VOD와 API 경기가 맞아 보임 | `fco-match-context` | 화면에서 본 사실, 연결 판단과 이유, 남은 의문 | 시각·닉네임만으로 자동 확정 |
| FC 화면이 없거나 VOD가 없음 | `fco-match-context` | 찾은 범위, 접근 실패, 맥락 미확인 | 경기가 없었다거나 단순 친선이라고 단정 |

교차 단서는 **추가 입력 경로**다. FC 조사 대상을 LoL 스캔 결과만으로 제한하지 않는다. FC API에만 존재하는 경기와 LoL 조사 범위 밖의 방송도 FC 조사 후보로 남아야 한다.

## 정보의 소유권과 분류

- **넥슨 API 정본:** `matchId`, OUID, 매치 타입, 경기 시각 원문, 승무패, 점수, 스쿼드·선수별 지표. VOD 화면을 읽어 이 값을 다시 덮어쓰지 않는다. OUID와 스트리머 연결은 닉네임 일치가 아니라 확인된 계정 관계를 쓴다.
- **VOD·공지 근거:** 실제 진행/중계/다시보기 여부, 경기와 방송의 대응, 단순 친선/CK/대회 여부, 행사명·주최자·참가자·진행 방식·시리즈·출처. 관찰과 해석, 미해결을 구분한다.
- **모드와 맥락은 별개:** API의 친선 매치 타입에서도 CK·대회를 진행할 수 있다. `mode_key=60`을 `단순 친선`의 증거로 쓰지 않는다. `event_id IS NULL`도 `친선`의 뜻이 아니다. 미조사·근거 부족을 표현할 수 있어야 한다.
- **시각은 후보 생성용:** `matchDate`가 경기 시작인지 종료인지 확인되지 않았다. SOOP 목록의 종료 시각과 API duration만으로 방송 시작을 확정하지 않는다. 실제 HLS 길이, 분할·중단·재시작을 기록하고 실측 표본으로 시간 대응을 보정한다. 고정된 `±N분`은 도구 초기값일 수 있어도 판정 규칙이 아니다.
- **검수 보존:** 공급자 재수집은 API 소유 필드를 갱신하되 사람이 확인한 행사·시리즈 연결, 맥락 판단, 숨김과 근거를 덮지 않는다.

## FC 조사 스킬의 필수와 자율

| 반드시 수행·기록 | 조사자가 정한다 |
|---|---|
| 확인된 공개 스트리머 계정의 API 경기와 기존 조사/행사 연결을 조회한다 | 어느 경기·VOD·방송 시점부터 볼지 |
| 실제로 연 VOD 지점, 사용한 공지, 못 연 범위와 시간 대응의 불확실성을 남긴다 | 후보 시간창, 추가 프레임·채팅·음성의 필요성과 범위 |
| 같은 경기의 중복 기록을 `matchId`로 막고, 여러 시점의 근거를 보존한다 | 후보 VOD가 같은 실제 경기인지 |
| 친선/CK/대회의 결론 **또는 미해결 사유**를 남긴다 | 근거를 종합한 행사 분류·메타데이터·시리즈 경계 |
| 반영 결과와 충돌·검수 보호로 건너뛴 항목을 구별해 보고한다 | 추가 자료의 가치가 낮을 때 조사 중단 위치 |

`N장 확인`, `N개 단서`, `다른 POV 필수`, `연속 경기면 대회`, `VOD 미발견이면 친선` 같은 합격선을 만들지 않는다. 대신 없는 행사명·상대·결과를 지어내지 않으며, 분류 근거가 부족하면 `맥락 미확인`으로 남긴다. 조사 수행 완료와 분류 성공은 별개다.

## 최소 실행 흐름

```text
확인된 스트리머 OUID의 FC API 경기 수집
  → 공개 스트리머 간 1:1 경기 추림 · matchId 중복/기존 맥락 조회
  → 경기 시각·참가자·SOOP VOD 목록으로 후보 제안
     ↖ LoL 전체 스캔에서 실제 읽은 FC 화면 단서도 합류
  → 조사자가 후보 VOD의 해당 구간과 필요한 공지/채팅/음성을 확인
  → 관찰 · 맥락 판단 · 미해결 항목 · 행사 메타데이터를 한 창구로 반영
  → 실제 저장 결과와 공개 화면/검수 큐 확인
```

FC에서는 API의 경기 사실이 이미 있으므로 결과 화면을 찾는 LoL 절차는 복제하지 않는다. VOD가 없어도 API 경기는 남고, 맥락만 미확인이다. 반대로 VOD에 FC 화면이 보여도 API `matchId`와 일치하는지 확인하기 전에는 그 경기로 묶지 않는다.

## 필요한 도구·데이터 계약

1. **공통 VOD 목록:** 와치리스트의 새 VOD를 제목·방송 카테고리로 사전 배제하지 않고 한 번만 수집한다. 현재 구형 `ck:collect`는 `listBroadcasts`가 받은 목록을 LoL 카테고리로 거르므로 이를 일일 전체 검수의 유일한 입력으로 쓰면 FC 방송이 빠진다. 카테고리 필터의 원래 목적은 후속 조사 대상의 노이즈 차단이었다. 이 필터는 응답 수신 뒤 로컬에서 적용되므로 같은 채널·기간의 목록 API 페이지 호출 수는 필터 제거 전후가 같다. 증가하는 비용은 필터를 통과한 VOD의 상세 조회·프레임 추출·음성 확보·판독이며, 이를 일일 처리 예산에 계상한다. 현재 `ck:probe`의 전역 초·HLS 길이 계산과 실제 열람 구분은 재사용한다.
2. **FC API 지속 수집:** 현행 `fco:sync`는 수동 실행이다. 일일 수집을 하려면 FC 전용 커서·재조회/실패 정책과 워커 작업을 추가한다. Riot 수집 루프에 FC 요청을 끼워 넣지 않는다. API 수집 실패, 조회 성공 후 `경기 0건`, 지원 범위 밖을 구분해 남긴다. 첫 구현은 현재 계획대로 스트리머 간 1:1 경기로 한정하고, 일일 수집의 matchtype별 조회·저장 지원 여부와 제외 사유를 명시한다. 현행 기본값은 30·40·50·60이며 감독모드(52)는 빠져 있다. 감독모드 포함 여부는 실응답과 저장 모델의 대응을 확인해 정한다. 공식 목록에는 볼타 친선(204)·공식(214)·AI대전(224)·커스텀(234)도 있다([넥슨 메타데이터](https://open.api.nexon.com/static/fconline/meta/matchtype.json), 2026-09-24 확인). 현재 저장기는 참가자가 정확히 두 명인 경기만 받고 `side_no`도 1·2로 제한하므로 다인 경기 지원에는 별도 모델 변경이 필요하다. 이런 모드의 교차 단서는 지원 밖으로 보존하며, 수집 실패나 경기 부재로 처리하지 않는다. 다인 모드 확대는 후속 범위로 두고 넥슨 매치 목록의 과거 조회 가능 범위는 커서 설계 전에 실측한다.
3. **맥락 후보:** `matchId`와 VOD ID/채널/후보 전체 초를 연결하되 후보 점수는 탐색 우선순위에만 쓴다. **경기당 현재 최종 맥락 판단은 하나, 그 판단을 뒷받침하는 확인된 VOD 연결은 여러 개**로 관리한다. 판단 변경 이력도 보존한다. 같은 경기의 두 번째 POV를 확인했을 때에도 독립된 근거로 연결할 수 있어야 하므로 VOD 후보/근거 테이블에 경기당 `accepted` 하나라는 제약을 적용하지 않는다. 후보·근거·최종 판단의 정확한 테이블/필드 구성은 기존 `event_lead`, `match_evidence_frame`, `review_record`, `match_series` 소유권을 검토해 정한다. `event.kind` CHECK(`ck·scrim·tournament·showmatch·other`, 0001·0031)에는 `unknown`이 없으므로 미확인 값을 그대로 event에 저장할 수 없다. `ck`(승패·보상이 걸린 스트리머 매치)와 `scrim`(대회 준비 연습게임)은 0031에서 갈랐다. 0013은 이 승격 원칙을 설명하는 주석이며 별도의 승격 차단 제약이나 트리거를 추가한 것은 아니다. `맥락 미확인`을 임의의 event 종류로 치환하지 않고 **event 밖의 조사 상태**로 기록한다. `event_lead`는 채널·VOD 단서 구조라 matchId 기준 상태와 모양이 다르므로 옛 계획 §Phase 2의 `match_context_candidate` 스케치를 출발점으로 삼되, VOD 연결과 현재 최종 판단의 유일성을 구분해 설계한다.
4. **단일 반영 경로:** `dry-run`/멱등 재전송, 실제로 읽은 근거, 기존 행사와의 충돌 확인, 사람이 고친 필드 보호, 사후 교정 경로를 제공한다. 현재 `fco:link-event`는 확인 URL을 요구하지만 `event.kind='tournament'`로만 저장하므로 CK·단순 친선·미해결을 다루는 경로로 그대로 쓰지 않는다. 같은 slug의 기존 event 이름을 경고 없이 덮어쓰는 현행 upsert(`ON CONFLICT … SET name`)도 답습하지 않는다 — 충돌은 확인 대상이지 덮어쓰기 대상이 아니다. 시리즈에 속한 세트의 행사는 `match_series.event_id`가 정본이다.
5. **가벼운 교차 단서:** `ck-research`가 실제로 열람한 FC 화면의 위치만 남길 수 있는 저장/인계 형식을 만든다. 프레임 파일 생성만으로 `읽음`이나 FC 매치 연결을 표시하지 않는다. LoL 조사 결과 파일에 FC 행사를 억지로 넣거나, LoL 조사 완료를 FC 맥락 완료로 간주하지 않는다.

## 구현 순서와 완료 기준

1. **표본·시간 대응 검증:** 이미 수집된 FC 맞대결과 VOD 몇 건을 읽기 전용으로 대조한다. `matchDate` 의미, VOD 시작·종료 오차, 방송 중단·분할 사례를 기록한다. CK·대회·단순 친선·VOD 없음 사례를 포함한다.
2. **맥락 상태 데이터 모델 확정:** 미조사/근거 부족/단순 친선/CK/대회를 담을 저장 구조를 **도구보다 먼저** 정한다. 조사 진행 상태와 행사 분류의 의미를 구분하고, 경기당 하나의 현재 최종 판단에 여러 확인된 VOD 근거를 연결할 수 있게 한다. 미확인 표현, 부재≠부정 증거, 교정 보존이 이 결정 위에 서 있다. 데이터 계약 3의 스키마 제약과 1의 실측을 입력으로 쓴다.
3. **후보·근거·반영 도구:** 위 데이터 계약과 검수 화면/CLI를 구현한다. 근거 없이 자동 행사 연결하지 않고, 재실행·다른 POV·수동 교정 후 재수집을 시험한다. 데이터 무결성과 필드 소유권은 DB 제약·저장 코드가 실행 시 강제한다. `verify:fco-context` 류 스크립트는 이 보호가 유지되는지 회귀 검증한다(`verify-fco.ts` 전례). 검증 항목은 재수집 후 사람 교정 보존, 같은 경기의 복수 POV 근거 보존과 현재 최종 판단의 유일성, API 소유 필드 보호, 수집 실패·조회 0건·지원 밖의 구분이다. 근거의 의미나 CK/대회 여부를 검증기의 고정 합격선으로 정하지 않는다.
4. **새 스킬 작성:** 실제로 동작하는 명령만 `fco-match-context/SKILL.md`에 넣는다. 본문은 목적, 필수/자율 경계, 최소 흐름, 반영·미해결 계약에 집중한다. API·스키마·SOOP 시간축 세부는 필요할 때 읽는 참조 문서에 둔다.
5. **기존 스킬 소폭 수정:** `ck-research`의 전체 탐색·후보 기록 부분에 FC 화면 교차 단서의 관찰/인계만 추가한다. 현재 LoL 결과 화면 탐색·중복 조회·단일 쓰기 창구의 의미는 바꾸지 않는다.
6. **일일 운영 연결:** 공통 VOD 목록과 FC API 수집을 스케줄에 연결하고, LoL 조사에서 FC 단서가 있으면 FC 후보 큐로 넘긴다. VOD 판독을 서버에서 구독형 대화 계정으로 무인 호출하는 방식은 별도 권한·비용 검토 없이 도입하지 않는다.

완료는 문구 작성이 아니라 다음의 통과로 판단한다: API 경기 사실이 VOD 분류로 덮이지 않음; 혼합 방송에서도 LoL 전체 범위를 놓치지 않음; FC 화면 부재가 부정 증거가 되지 않음; 같은 경기의 여러 POV 근거를 보존하면서 현재 최종 판단을 하나로 관리함; CK/대회 안의 연습 경기와 실제 행사 경기를 구별해 미확인은 미확인으로 남김; 재수집 후 사람의 교정이 보존됨; 프레임 추출과 실제 열람이 구분됨; 수집 실패·조회 0건·지원 밖이 구분됨. 기계로 확인 가능한 데이터 계약은 DB·저장 코드가 강제하고 verify 스크립트로 회귀 검증한다(구현 순서 3). 새 스킬은 실제 VOD 사례로 행동을 검증하고, 형식 검사는 `skill-creator` 검증기의 설치 여부를 먼저 확인한 뒤 쓴다 — 저장소 밖의 에이전트 스킬 경로도 확인한다.

## 이번 계획의 범위 밖

가격·이적시장 시세, FC API가 제공하는 경기 지표의 VOD 재판독, LoL 조사 파이프라인의 전면 재작성, 모든 FC VOD의 별도 전량 스캔, 볼타 등 다인 경기의 저장 모델 확대는 포함하지 않는다. 지원 밖 모드에서 발견한 교차 단서는 사유와 함께 보존한다.
