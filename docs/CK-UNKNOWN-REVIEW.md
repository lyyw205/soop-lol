# 미확인 참가자 공개·일괄 연결 재검토

검토일: 2026-09-22. 대상은 현재 작업 디렉터리의 0022, 공개 계약, 공용 로스터 UI, 미확인 관리자 화면과 저장 함수다. 아래 A~F는 구현 전 검토 기록이며, 현재 구현 결과는 바로 아래에 적는다. 운영 DB에는 쓰지 않았다.

## 구현 완료 기록 — 2026-09-22

검토에서 확인한 다섯 문제를 수정했다.

- 관리자 연결을 자동 identify와 분리했다. 화면에서 선택한 `(match_id, participant_id)`와 당시의 이름·검수 시각을 서버가 잠금 뒤 다시 비교한다.
- 선택한 경기 전체를 하나의 트랜잭션으로 저장한다. 중간 제약 오류는 참가자·검수 표시·파생 통계를 모두 되돌린다.
- 성공한 경기는 `reviewed_at`을 기록하여 자동 재수집이 연결을 지우지 못한다. 자동 identify는 기존처럼 이 표시를 남기지 않는다.
- 이름은 목록의 그룹·검색 단서로만 사용한다. 다른 시리즈, 숨긴 경기, 화면을 연 뒤 새로 생긴 동명 자리는 자동으로 포함하지 않는다.
- 0023에서 공개 뷰 끝에 `participant_id`를 추가했다. 로스터의 React key는 `match_id + participant_id`를 사용한다. 적용된 0022는 수정하지 않았다.

검증 결과:

- 단위 검사 129개, 전체 typecheck, verify:db 164개, verify:ingest, verify:modules, production build 통과.
- PGlite에서 신규 설치와 0022 설치 후 0023 업그레이드의 뷰 정의·열 순서가 같고, 기존 참가자 데이터와 자리 ID가 보존되며 0023 재적용도 안전함을 확인했다.
- 실제 PostgreSQL에서 두 운영자의 동시 연결은 한 건만 커밋되고 다른 한 건은 충돌했다. 네 자리 일괄 연결 후 재수집 보호, 숨긴/다른/늦게 추가된 자리 제외, 중간 실패 전체 롤백도 통과했다.
- 실제 Next 앱과 Chromium에서 데스크톱·모바일 선택/저장/실패 후 재시도, 두 탭 충돌 후 선택과 slug 보존, 공개 로스터의 동명 미확인 두 자리와 링크 없음, 연결된 네 세트 표시를 확인했다.

운영 DB의 0023 적용과 실제 운영 데이터 확인은 이 로컬 구현에서 수행하지 않았다.

## A. 최종 판정

**수정 후 구현 가능.** 미확인 참가자를 공개 로스터에 포함하는 방향과 뷰 중심의 공개 정책은 유지한다. 관리자 일괄 연결에는 검수 보존·동시성·대상 범위·부분 실패 문제가 남아 있어 현재 상태를 완료로 승인하기는 어렵다. “0022 WHERE만 유일한 위험 지점”이라는 평가는 맞지 않는다.

이름 공개는 전달된 운영 정책을 전제로 검토했다. 새 승인 단계나 공개 대기 상태를 추가할 이유는 없다.

## B. 반드시 수정할 문제

### 1. 관리자 연결이 재수집으로 사라진다 — 높음

- 근거: `apps/web/app/admin/ck/actions.ts:335` → `packages/core/lib/db/ck.ts:1325` → `linkParticipants`(`:1067`). 이 함수는 자동 identify용이어서 reviewed_at을 기록하지 않는다. `upsertMatchFromScan`은 `:701`에서 그 표시만 확인하고 `:732`에서 참가자를 교체한다.
- 재현: 미확인 자리를 A에게 일괄 연결 → reviewed_at=null → 원래 조사 입력을 재수집하면 true 반환, streamer_id는 다시 null.
- 수정: 자동 identify와 사람의 검수 저장을 구분한다. 관리자 일괄 연결은 기존 검수 저장 계약을 사용하여 대상 경기의 reviewed_at을 기록한다. 자동 identify의 동작을 전역으로 바꾸지 않는다.
- 필요한 검사: 관리자 연결 뒤 재수집 거부·연결과 판독값 보존·통계 유지. 자동 identify는 기존처럼 reviewed_at을 찍지 않는다는 검사도 유지한다.
- 범위: 현재 모델은 경기 단위 검수 보호다. 이 보호를 쓰면 해당 경기의 후속 자동 판독 보강도 멈추며, 이는 기존 관리자 검수와 같은 계약이다. 이를 피하려고 이번에 참가자별 검수 상태를 별도로 도입하지 않는다.

### 2. 두 운영자의 일괄 연결이 모두 성공하며 서로 덮는다 — 높음

- 근거: `ck.ts:1313`에서 미확인 자리 ID를 트랜잭션 밖에서 수집한다. 잠금 후 실행되는 `linkParticipants`는 최신 값을 읽지만(`:1084`), 여전히 같은 observed_name이며 streamer_id/puuid가 비어 있는지 비교하지 않고 `:1118`에서 갱신한다.
- 재현: 실제 PostgreSQL에서 경기 행을 잠근 뒤 동일 미확인 이름을 A/B에게 연결하는 두 요청을 시작했다. 두 요청의 잠금 대기를 확인하고 풀자 둘 다 linked=1을 반환했으며 최종 값은 한 사람으로 덮였다.
- 수정: 관리자 요청에 대상 자리 ID와 기대값을 포함한다. 경기 잠금 획득 후 이름·사람·계정 등 편집 기준을 다시 비교한다. 이미 다른 사람에게 연결됐거나 다른 자리로 바뀌었으면 충돌/건너뜀 사유를 명확히 반환한다. 잠금만으로 기대값 검사를 대신하지 않는다.
- 필요한 검사: 실제 두 연결의 동시 저장, 자동 재판독과의 경쟁, 자리 삭제/교체, 동일 요청 재시도. 두 번째 요청은 첫 연결을 바꾸지 않아야 한다.

### 3. 화면에 표시한 자리와 실제 변경 대상이 다르다 — 높음

- 근거: 목록은 `ck.ts:1269`에서 공개 경기만 읽지만 저장은 `:1314`에서 전체 match_participant를 이름으로 다시 찾는다. 폼은 대상 자리 없이 observed_name만 전송한다(`LinkUnknownForm.tsx`).
- 재현: 같은 이름의 공개 경기 두 개·숨긴 경기 한 개를 만들면 화면 집계는 2자리인데 실제 연결은 숨긴 경기까지 3자리다.
- 추가 구조 문제: 표시 이름은 식별자가 아니다. 다른 날짜·시리즈의 동명이나 화면에 없는 신규 유입도 같은 문자열이면 묶인다. “한 내전 네 세트의 동일인”이라는 조사 결과가 전 기간의 같은 이름 전체에 대한 판단을 뜻하지는 않는다.
- 수정: 이름은 검색·그룹 표시용으로 유지하되, 저장 대상은 화면에서 확인하고 선택한 `(match_id, participant_id)` 목록으로 고정한다. 세트/시리즈별 일괄 선택을 제공하여 네 자리를 네 번 저장할 필요는 없게 한다. 확인하지 않은 다른 시리즈·숨긴 경기·나중에 추가된 자리는 자동 포함하지 않는다.
- 필요한 검사: 동일 이름의 서로 다른 시리즈, 숨긴 경기, 화면을 연 뒤 추가된 경기. 선택한 네 자리만 바뀌는지 정확한 ID 집합으로 비교한다.

### 4. 중간 실패 시 일부만 저장되고 응답은 전체 실패다 — 중간

- 근거: `ck.ts:1324`는 경기마다 별도 linkParticipants 트랜잭션을 커밋한다. 뒤의 호출이 실패하면 `actions.ts:348`은 오류만 반환하고 앞에서 저장한 결과와 영향 범위를 잃는다.
- 재현: 첫 경기는 연결 성공, 두 번째 경기에는 대상 스트리머가 이미 다른 자리에 있어 `match_participant_streamer_uq` 충돌. 함수 전체는 예외지만 첫 경기 연결은 남고 두 번째는 미확인이다.
- 수정: 이 규모에서는 사용자가 선택한 일괄 연결을 한 트랜잭션으로 처리한다. 경기 ID 순으로 잠그고, 대상과 기대값을 확인한 뒤 연결·reviewed_at·조우·before∪after 챔피언 통계를 함께 반영한다. 기존 검수 경기를 건너뛰는 방침은 결과에 명시한다. 도중 제약 위반은 이번 배치 변경을 전부 롤백한다.
- 구현 주의: 기존 공개 함수가 새 트랜잭션을 여는 구조라면 바깥 트랜잭션에서 그대로 호출하지 않는다. 필요한 내부 처리만 tx를 받는 함수로 공유한다.
- 필요한 검사: 두 번째 경기 실패 시 첫 경기의 참가자·검수 표시·파생 통계까지 불변. 성공 시 정확한 변경/건너뜀 ID와 개수를 반환한다.

### 5. 새 React key도 중복될 수 있다 — 중간

- 근거: `packages/ui/match-details.tsx:60`은 이름/사람+팀+챔피언으로 key를 만든다. 바로 위 주석은 “자리 번호가 유일하다”고 설명하지만 실제 key에는 자리 번호가 없다. 공개 DTO도 participant_id를 반환하지 않는다.
- 재현: DB가 허용하는 두 미확인 자리에 동일한 관찰 이름·팀·챔피언을 저장하고 실제 listMatchRosters로 읽었다. 행은 2개인데 key는 둘 다 `same-label-100-34`다. 실제 브라우저에서 행이 사라지는 현상까지 재현한 것은 아니다.
- 수정: 기존 자리 식별자인 participant_id를 공개 뷰/DTO에 전달하고 `match_id + participant_id`를 사용한다. 이름·챔피언 교정이나 세트 전환에도 식별자가 안정적이어야 한다.
- 필요한 검사: 동명·챔피언 미상 참가자 둘, 세트 전환, 이름/챔피언 교정 시 두 행을 모두 유지하고 key 충돌이 없어야 한다.

## C. 권장 개선과 보고 정정

- `scripts/verify-db.ts:1499`의 “여러 자리를 한 번에” 검사는 실제로 한 자리만 준비하고 `linked >= 1`을 확인한다. 현재 164개 통과를 네 자리 일괄 저장·동시성·원자성의 증거로 사용할 수 없다. 정확히 네 자리와 서로 다른 경기들을 준비한다.
- 전체 단위 테스트 128개는 앞선 검수 수정 등을 포함한 합계다. 이 변경만의 회귀 검사 수와 전체 합계를 구분한다. 공용 로스터 모델 검사에는 nullable identity 사례를 추가한다.
- `0022:57`의 “숨긴 계정은 행째로 빠진다”는 설명은 부정확하다. 직접 연결한 공개 streamer_id가 있으면 숨긴 계정이어도 참가 기록은 남고 식별자만 제거하는 0021 정책이 유지된다. 이 동작은 결함으로 되돌리지 않는다. 이미 적용된 0022 본문 대신 후속 마이그레이션의 COMMENT와 문서를 고친다.
- “다른 질의는 전부 특정 UUID 필터”도 정확하지 않다. `db/public.ts:219`의 챔피언 이름 조회는 champion_id만 비교한다. 다만 경기 수·승률의 합계는 별도 champion_stat에서 읽으므로, 미확인 로스터 추가가 그 합계에 영향을 주지 않는다는 결론은 유지된다.
- `/admin/ck/unknown`의 경기 ID는 검수 화면 링크로 연결하고, 전체 자리 수와 현재 일괄 연결 가능한 자리 수를 구분하면 건너뜀 뒤의 복구가 쉬워진다.

## D. 확인한 올바른 부분과 검증 범위

- 0022는 기존 열을 유지하고 observed_name을 끝에 추가한다. 새 저장 테이블 없이 원본 참가자에서 미확인 목록을 파생한다.
- 실제 `listMatchRosters` 호출에서 사람·slug·표시명이 null인 미확인 행의 관찰 이름, Anivia, 3/8/7이 반환됐다. 공개 조회의 LEFT JOIN이 이 행을 다시 지우지 않는다.
- 동일 경기 visibility를 hidden으로 바꾸면 공개 로스터는 빈 배열이었다. 숨긴 스트리머의 행도 빈 배열이었다.
- 숨긴 계정에 직접 연결된 공개 사람이 있는 경우 참가 기록은 유지되고 observed_name은 null이었다. 이는 0021의 기존 정책과 맞는다. 공개 뷰는 원본 mp.puuid 대신 공개 계정 조인의 sa.puuid를 선택한다.
- 로스터 UI에는 미확인 행의 인게임명·미등록 표시, 프로필/상대전적 링크를 만들지 않는 분기, nullable 이름 정렬이 있다. 이번에는 해당 UI의 실제 브라우저 클릭을 새로 시험하지 않았다.
- `npm test`: 128개 통과. 전체 `npm run typecheck`: 통과.
- 별도 폐기용 실제 PostgreSQL에 마이그레이션을 적용하고 위 B의 네 저장 현상, 중복 key, 공개 조회 경계를 재현했다. 외부 DATABASE_URL과 운영 데이터를 사용하지 않았다.
- 전체 verify:db 164개 및 이전 브라우저 검증은 앞선 작업의 통과 기록이다. 이번 미확인 일괄 연결의 동시 저장·실패 복구까지 포함한 검사로 해석하지 않는다.

## E. 최종 수정 범위와 순서

1. 기존 `verify:ck`와 실제 PostgreSQL 동시성 검사에 B1~B4 재현을 추가한다. 일괄 검사의 fixture를 실제 네 자리로 확장한다.
2. `ck.ts`에 관리자용 선택 자리 일괄 검수 계약을 구현한다. 자동 identify는 유지한다. 잠금·기대값·원자 저장·검수 보호·파생 계산을 연결한다.
3. `unknown/page.tsx`, `LinkUnknownForm.tsx`, `actions.ts`에서 같은 선택 ID 집합과 기준값을 전달한다. 부분 성공처럼 보이는 일반 오류를 없애고 변경/건너뜀/충돌을 구분한다.
4. 적용된 0022는 수정하지 않는다. 다음 번호의 마이그레이션으로 공개 뷰 끝에 participant_id를 추가하고 부정확한 COMMENT를 바로잡는다. 이미 같은 번호가 생겼다면 그 다음 번호를 사용한다. 데이터 재적재는 필요 없다.
5. `contract/index.ts`, 공용 로스터 UI와 fixture에 participant_id를 연결한다. 새 테이블·identity 사본·작업 큐·승인 상태는 추가하지 않는다.
6. 신규 DB와 0022 적용 DB의 업그레이드를 각각 확인한다. 정책 조합(숨긴 경기/사람/계정, 직접 연결 여부)과 전체 계약·수집·모듈·타입·단위 검사를 실행한다.
7. 폐기용 DB를 연결한 실제 Next 브라우저에서 네 자리 선택→연결→공개 로스터→재수집 보호, 두 탭 경쟁, 실패 후 재시도, 동명 두 자리·모바일 표시를 확인한다.

최소 수정은 목록/저장의 공개 필터 정렬과 key 보완이지만, 이것만으로 검수 유실·동시 덮어쓰기·반쪽 저장은 해결되지 않는다. 따라서 이번에는 위 저장 계약까지 완성하는 것이 필요한 수정 범위다.

## F. 개발자 전달문

미확인 참가자를 인게임명으로 공개하고 공개 정책을 뷰에 모으는 결정은 유지한다. 관리자 일괄 연결은 자동 identify와 분리해, 확인한 자리 ID/기대값을 대상으로 한 트랜잭션에서 검수 보호와 파생 계산까지 저장한다. 이름은 검색 단서이며 전 기간의 동일인 키로 쓰지 않는다. 화면에 없는 숨긴 경기·나중에 추가된 자리는 포함하지 않는다. 공개 로스터 key는 기존 participant_id를 전달해 만든다. 완료 조건은 네 자리 실제 일괄 저장, 재수집 보존, 두 요청 충돌, 중간 실패 전체 롤백, 숨김 경계, 브라우저 왕복 검사다.
