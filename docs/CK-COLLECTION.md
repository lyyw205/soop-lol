# 내전(CK) 수집 — 실측으로 알아낸 것

> 이 문서는 **참고자료**다. 절차가 아니다.
> 조사를 어떻게 돌리는지는 [`.claude/skills/ck-research`](../.claude/skills/ck-research/SKILL.md) 에 있고,
> 여기에는 **화면에서 무엇이 읽히고 어디서 틀리는지**만 둔다. 필요할 때 필요한 절만 연다.
>
> 숫자는 전부 실제로 돌려서 나온 값이고, 날짜는 그걸 확인한 날이다.
> ⚠ 옛 판에는 「수집 순서」·「하루 파이프라인」·「판독할 때 이 순서로 묻는다」 같은
> **강제 절차표**가 있었다. 도구가 바뀌면서 걷어냈다 — 판단을 표로 대신하면
> 표를 통과시키는 일이 판단을 밀어낸다.

내전은 이 프로젝트의 존재 이유에 가장 가까운 데이터다. "스트리머끼리 누가 누구를
이겼나"의 절반이 여기 있다. 그런데 **Riot API 로는 거의 안 잡힌다.**

## 1. 경로는 둘뿐이다

| | 잡히는 것 | 상태 |
|---|---|---|
| **A. 토너먼트 코드** (`queue 3130`) | 주최자가 코드로 연 방만 | **코드 완성.** 다만 최근 물량이 없다 |
| **B. 방송 VOD** | 방송한 내전 전부 | **도구화 완료** — `ck:probe` → `ck:listen` → `ck:merge` |

그냥 만든 사용자 설정 방(`queue 0`)은 match-v5 로 **사후 조회가 불가능하다**.
이건 우리 구현 문제가 아니라 Riot 의 제약이다 (CLAUDE.md 제약 1).

## 2. 경로 A — 토너먼트 코드

### 되는 것

match-v5 로 **승패·KDA·포지션까지 전부** 나온다. Production Key 도 스트리머 협조도
필요 없다. 읽기는 키 등급과 무관하다.

```
queueId=3130 gameType=CUSTOM_GAME tournamentCode=KR050c3-aad2ff79-…
저장: inserted=true 조우=3 후보=7
match 행: { source: 'tournament_code', queue_id: 3130, tournament_code: 'KR050c3-…' }
```

### 물량 — 로스터를 늘리자 19배가 됐다

| | 스트리머 93명일 때 | 418명일 때 |
|---|---|---|
| 잡히는 내전 | 112경기 | **2,147경기** |
| 경기당 아는 참가자 | 1.2명 | **2.8명** |
| 김민교 | 0경기 | 49경기 |
| 이상호 | 0경기 | 58경기 |

경기당 시점이 늘어나는 게 중요하다. 한 판을 여러 방송에서 중복 수집하게 되므로
**한 사람만 놓쳐도 다른 시점이 메운다.**

### ⚠ 그런데 시한이 지났다

```
김민교   2025-07 ███████ 7      2025-12 ██████████████████████ 42   마지막 2025-12-15
이상호   2025-06 ████ 4  07 █ 1  2025-12 ██████████████████████ 53   마지막 2025-12-19
```

**2025-12 이후 0건이다.** 안 한 게 아니라 코드를 안 쓰는 내전으로 바뀌었다.
2026-08 한 달만 봐도 김민교 CK VOD 8건, 이상호 시그니처ck·멸망전 스크림이 있다.

→ **경로 A 는 과거 백필용이고, 앞으로를 위해서는 경로 B 가 필요하다.**

## 3. 경로 B — 방송 VOD

### 물량 (등록 채널 418개, 최근 7일 실측)

```
롤 본방 VOD      925건 · 5,944시간   →  849h/일
그중 내전/CK     183건 · 1,270시간   →  181h/일
동시 내전 방송   평균 6.1개 (중앙 4, 최대 26)
```

**동시 6.1개**가 비용을 가른다. 같은 내전을 평균 6명이 방송하므로 한 판을 두 곳에서
확인하면 충분하다 → 처리량이 1/3(59h/일)로 떨어진다.

### 접근 경로 (인증·로그인 불필요, 2026-08-11 확인)

```bash
# 채널의 VOD 목록
https://chapi.sooplive.co.kr/api/<채널>/vods/all?page=1&per_page=60&orderby=reg_date
#   ucc.vod_category = 40019 (롤) · ucc.file_type = 'REVIEW' (본방) / 'CLIP' (편집본)

# VOD 상세 — ★ POST 여야 한다. GET 은 "This VOD does not exist" 를 돌려준다
POST https://api.m.sooplive.co.kr/station/video/a/view
     nTitleNo=<번호>&nApiLevel=10&nPlaylistIdx=0
#   files[].duration 은 **밀리초** · files[].snapshot / .chat / .file
#
# ⚠ **`duration` 을 시간축으로 믿지 마라** (2026-08-19 실측)
#   실제 받을 수 있는 영상(HLS)보다 길게 보고하는 VOD 가 있다.
#     멸망전 공식채널 188993475 — API 4.00h vs HLS 2.18h (전 화질 동일)
#   이게 두 가지를 동시에 틀어놓는다:
#     ① 시트 훑기가 잡은 뒷구간의 **프레임을 영영 못 받는다** (결과화면 6장 실패)
#     ② `ended_at - duration` 으로 계산한 **방송 시작 시각이 어긋난다** —
#        실제 경기는 17:00 에 시작했는데 19:00 으로 잡혔다. 참가자 POV 를
#        시간대로 찾을 때 엉뚱한 창을 보게 된다.
#   → 그래서 `ck:probe` 는 **HLS 로 잰 실제 길이**로 전역 시간축을 쌓고,
#     API 가 더 길다고 하면 그 초과분을 '못 본 범위' 로 남긴다.

# 썸네일 시트 — 1920×1080 에 10×10=100 프레임, 3초 간격, 장당 ~750KB
https://videoimg.sooplive.co.kr/php/SnapshotLoad.php?rowKey=<…_t>&column=0..N
#   시간당 12장. 5시간 방송 전체가 60장 45MB
#   ★ column 0 은 column 1 과 **같은 이미지**다. 파일 로컬 t 초 = column 1+floor(t/300) 의 칸 floor(t/3)%100.
#     칸 수는 ceil(길이/3) ±1. 끝나면 **HTTP 500 + 빈 본문** — 오류와 모양이 같아 칸이 끝까지 덮었나로 판정한다.
#     (2026-09-30 실측. 옛 계산은 파일 앞쪽 시각을 최대 5분 늦게 냈다. 단일 출처: scripts/lib/vod-timeline.mjs,
#      검증: node scripts/verify-sheet-axis.mjs --vod <번호>)

# 채팅 — ★ startTime 없이 부르면 404. 300초 창으로 끊어서 준다
https://videoimg.sooplive.co.kr/php/ChatLoadSplit.php?rowKey=<…_c>&startTime=0

# 영상 — HLS. 6초 세그먼트 하나만 받아 프레임을 뽑는다 (1080p 세그먼트당 ~6MB)
files[].file → manifest.m3u8 → 1080p 변형 → seg-N.m4s
```

### 무엇이 읽히나 (이상호 시그니처ck, 2026-08-09, 4.9h 로 실측)

선별기가 지목한 12곳의 1080p 프레임을 **사람이 직접 판독**한 결과:

| 화면 | 건수 | 얻은 것 |
|---|---|---|
| 메모 대진표 | 5 | **10명 전원** + 라인별 매치업 + 챔피언(밴 3개씩인 것도) |
| 로딩 화면 | 1 | **10명 + 챔피언 10개** — 규격 배치라 판독이 제일 쉽다 |
| Tab 스코어보드 | 2 | **10명** + 챔피언 + KDA |
| 게임 화면 | 3 | 1~5명 (체력바 라벨·이벤트 로그) |
| 무용 | 1 | — |

**11장 중 7장이 10명 전원.** 그리고 거의 모든 프레임 오른쪽에 SOOP 오버레이로
**시리즈 스코어**가 떠 있다.

읽은 인게임 닉네임을 DB 에 넣어보니 6명 중 5명이 붙었다:

```
사나이묵직한주먹 → 김민교 (사나이묵직한주먹#산 본)
이상호93        → 이상호 (이상호93#KR1)
JustLikeThatKR → 저라뎃 (JustLikeThatKR#KR1)
7halsakeN      → 트할_ (7halsakeN#1004)
Radiohead      → 클리드1 (Radiohead#KR1)
한샘            → ✖ DB 에 없음
```

롤 클라이언트 채팅이 뜬 프레임에서는 **태그까지** 나온다
(`사나이묵직한주먹 #산 본 님이 로비에 참가`, `뀨 삐 #1999 님이 로비에 참가`).
이름 추측이 아니라 라이엇 ID 그 자체다.

### ⚠ 밴픽 화면은 절반만 준다

사용자 설정 방의 챔피언 선택 화면은 **적 팀을 `1번 적` ~ `5번 적` 으로 가린다.**
우리 팀 5명만 나온다. 10명 전원이 필요하면 **로딩 화면**이나 **Tab 스코어보드**를
잡아야 한다. 밴픽 프레임은 "5명 + 라이엇 ID 태그" 로는 여전히 값지지만 한 판을
채우지는 못한다.

### 승패 — 종료 화면이 **정본이다** (2026-08-12 정정)

> 이 절은 원래 "종료 화면이 필요 없다"였다. **틀렸다.** 그 믿음 때문에 실제로
> 승자가 뒤집힌 채 사이트에 올라갔다. 무엇이 어떻게 틀렸는지 그대로 남긴다.

**처음 근거.** 오버레이 시리즈 스코어의 *변화*가 곧 직전 경기의 승자이고,
프레임에서 읽은 흐름이 채팅 `!공지` 와 4건 전부 일치했다:

```
프레임에서 읽음                    채팅 !공지
  1:17:33  0:1 ← 성훈팀 승        1:04:46  0:1  성훈팀 승  ✓
  1:45:07  0:2 ← 성훈팀 승        1:39:55  0:2  성훈팀 승  ✓
  3:05:37  1:0 ← 상호팀 승        3:01:59  1:0  상호팀 승  ✓
  4:14:51  1:1 ← 성훈팀 승        3:58:10  1:1  성훈팀 승  ✓
```

**함정.** 오버레이는 독립된 증거가 아니다 — **채팅 공지를 그대로 비추는 위젯**이다.
둘이 일치하는 건 당연하고, 아무것도 검증하지 못한다. 게다가 위 표에는 **5세트가 없다.**
둘이 어긋난 유일한 판이 하필 빠져 있었다.

**실제로 일어난 일** (2026-08-08 시그니처CK 2부 3세트):

```
4:45:33  이상호 화면에 결과창 '패배' (30:29)      ← 진짜
4:45:37  [하늘하늘_] !공지 상호팀 2 : 1 성훈팀     ← 오기
4:46:04  [상구미]    !공지 상호팀 1 : 2 성훈팀     ← 27초 뒤 정정
```

직전이 1:1 이라 `2:1` 과 `1:2` 가 **둘 다 '한 칸 전진'** 이다. 점수 진행만으로는
못 고르는데 파서가 먼저 온 것을 채택했다. 승자가 반대로 들어갔다.

**그래서 규칙.**

| | 무엇 | 지위 |
|---|---|---|
| 채팅 `!공지` | 사람이 친다. 틀리고, 몇십 초 뒤에 고친다 | **단서** — 어디를 볼지 알려준다 |
| 오버레이 스코어 | 공지를 비추는 위젯 | 증거 아님 (공지의 사본) |
| **LoL 최종 결과 화면** | 승리/패배 · 10명 챔피언 · KDA · 게임 길이 | **우선 근거 — 있으면 직접 확인** |

종료가 의심되는 곳에서는 마지막 게임 진행 화면과 첫 종료 후 화면 사이를 후보 구간으로 잡고
5분할을 반복해 좁힌다. **확실한 진행 화면과 확실한 종료 후 화면만** 새 기준점으로 쓰며,
브라우저·로딩·판단하기 어려운 리플레이는 안 연 구간을 버리는 근거가 아니다. 더 나눌 새 정수
초가 없거나 확정 기준점만으로 더 좁힐 수 없는 마지막 짧은 구간만 초 단위로 모두 연다. 결과 화면 발견을 경기 인정이나 조사 완료의
조건으로 강제하는 것은 아니다. 강제 종료·중계 전환·화면 가림·소스 누락이면 확인한 범위,
대신 사용한 근거, 읽지 못한 값을 적고 멈출 수 있다.

⚠ **결과 화면을 잡았다고 라인업을 읽을 수 있는 게 아니다** (실측 2026-08-19, 이상호 02-28 스크림)

종료 화면은 탭이 둘이고, 스트리머가 어느 탭에 있었느냐로 회수량이 갈린다:

| 탭 | 보이는 것 | 쓸모 |
|---|---|---|
| **점수판** | 10명의 인게임명·챔피언·KDA·골드 + 팀 합계 | 전부 읽힌다 |
| **그래프** | 승리/패배 와 막대그래프뿐 | **승패만** — 사람도 챔피언도 없다 |

02-28 스크림은 결과창 클러스터가 8개나 잡혔는데 그중 **2개만 점수판**이었다.
나머지 6판은 승패 말고 아무것도 못 넣었다. 프레임 수로는 성공처럼 보이지만 아니다.

→ **"결과화면 N장 확보" 는 탭까지 보장하지 못한다.** 열어서 탭을 확인하고,
   그래프뿐이면 승패만 넣고 그렇게 적는다.

⚠ **공식 중계 재송출에는 결과 화면이 아예 없다** (실측 2026-08-19, 03-12 멸망전 4강)

중계는 게임이 끝나면 해설 카메라로 넘어간다. 프레임 35장 전부 인게임·밴픽·클립뷰어였다.
대신 중계 HUD 좌우 사이드바에 **10명의 챔피언 초상화와 스트리머 이름**이 붙어 있어
챔피언과 로스터는 회수할 수 있다 — 최종 KDA 는 못 얻는다.

★ 반대로, **참가자가 남의 방송을 보던 화면**에서 결과창이 통째로 잡히기도 한다.
  03-11 4강 1경기 1세트는 이상호가 무잔(봉준) 방송을 보던 화면에서 나왔다.
  본인 경기가 아니어도 시청 구간을 버리지 말 것.

코드가 막아 주는 자리:
- `ck:merge` · `seed:tournament` — 승패를 무엇으로 정했는지(`result_evidence`) 없이는
  경기를 **거부한다** (마이그레이션 0015). 결과 화면을 못 찾았으면 그 사실을 적으면 된다
- `ck:merge` — **승자를 모르면 경기로 안 받는다.** 후보에 `unresolved` 로 남긴다

**오프셋은 실측이다** (같은 방송 5세트):

```
공지 대비 결과 화면 위치   1세트 +12~+21 · 2세트 +10 · 3세트 +5~+11 · 4세트 −4 · 5세트 −4~+22
화면이 떠 있는 시간        9초(1세트) ~ 27초(5세트) — 스트리머가 바로 리플레이를 켠다
```

→ `RESULT_OFFSETS = [-6, 0, 6, 12, 18, 24]`. 처음엔 `[-6, +8, +22]` 셋이었는데
1세트를 놓쳤다(+8 은 이르고 +22 는 1초 늦었다). 제일 짧은 9초보다 촘촘해야 한다.

**시트 판독의 경기 구간 끝은 종료 지점으로 쓰지 않는다.** 스트리머가 끝나고 리플레이를
켜면 그것도 '롤 화면'이라 구간이 늘어난다 — 실측에서 구간 끝이 실제 종료보다 5~8분
뒤였다. 공지가 없는 방송에서만 차선으로 쓴다.

## 3.5 경기 진행 방식 — 결과 화면만 보면 틀린다 (운영자 구술, 2026-08-13)

결과 화면은 "그 판 누가 이겼나"만 말한다. **그 판이 전적에 들어가는 판인지**, 들어간다면
**어느 시리즈의 몇 세트인지**는 판 진행 방식을 알아야 정해진다. 세 가지가 있다.

### 3.5-1. CK — 승부가 나면 끝, 그 뒤는 **덤**이다

3판 2선승·5판 3선승처럼 승부가 정해지는 방식으로 간다. **문제는 승부가 난 뒤다.**
누가 못했는지 가리는 장난식 추가 경기를 몇 판 더 한다.

```
본선   3판 2선승 → 2:0 으로 끝남
추가   "미드 바꿔서 단판"  "범인찾기"   ← 시리즈 전적이 아니다
```

→ **시리즈가 끝난 뒤의 판을 세트로 이어 붙이면 전적이 틀어진다.** 2:0 으로 끝난 3판
2선승이 갑자기 2:2 가 된다. 오버레이 스코어가 안 올라가는 것이 신호다 — 본선은
`3/2) 상호팀 2:0 …` 처럼 스코어가 붙어 있고, 추가 세트는 스코어가 멈추거나
문구가 통째로 바뀐다.

**⚠ 추가 세트를 부르는 말은 정해져 있지 않다.** 방송마다 다르게 부른다.
**찾을 때마다 여기에 적는다** — 이 목록이 곧 판별 근거다.

| 본 말 | 뜻 | 처음 본 곳 |
|---|---|---|
| 미드 바꿔서 단판 | 승부 후 자리 바꿔 한 판 | (운영자 구술) |
| 범인찾기 | 진 팀에서 누가 못했나 가리기 | (운영자 구술) |
| **원딜바꿔서 단판** | 위와 같은데 자리가 원딜 | 2026-04-05 염상교CK (VOD 191906571) |
| **본경승 / 정글바에서 단판** | 승부 후 단판 | 2026-06-26 깐부CK |

★ 실측 팁: 추가 세트로 넘어갈 때 오버레이가 **`염상교CK 0 : 3 패` 처럼 승패를 확정해 적고
그 아래 줄에 추가 세트 이름을 단다.** 스코어가 멈추는 것보다 이게 더 또렷한 신호였다.

### 3.5-2. 랜드 — 팀이 매 판 바뀐다. **시리즈가 아니다**

정해진 10명이 **매 판 팀을 섞어서** 한다. 그래서 같은 판에 있던 두 사람이
다음 판엔 적이 된다. **팀 단위 승패가 없고 사람마다 전적이 다르다.**

```
잘못    "랜드 5판" 을 한 시리즈로 묶고 팀 승패를 센다   ← 팀이 매 판 다른데 무의미
맞음    판마다 그때의 두 팀을 그대로 기록한다
        랜드 전체는 사람별 n승 m패로만 묶는다
```

→ 스키마상 `series_key` 는 **묶음 식별용**으로만 쓰고, "팀이 몇 대 몇으로 이겼다" 는
계산을 하면 안 된다. `streamer_encounter` 는 판 단위라 그대로 맞는다 —
같은 사람과 아군이었다가 적이었다가 하는 게 정상이고, 그게 이 사이트가 보여줄 것이다.

**⚠ 예외 — 로스터가 중간에 바뀐다.** 10명으로 시작했다가 길어지면 4명쯤 빠지고
새로 구해서 다시 10명으로 이어 간다. 그래서 **랜드 묶음 하나에 고정 명단을 가정하면 안 된다.**
로스터는 판마다 결과 화면에서 새로 읽는다.

**⚠ 반대 방향도 성립하지 않는다 — 팀이 두세 판 같았다고 랜드가 아닌 것은 아니다** (운영자 지적, 2026-10-07).
랜드는 판마다 **랜덤으로** 팀을 정하므로 같은 구성이 연달아 나올 수 있다. 실제로 깐숙 방송 "2부 롤랜드" 2판이
팀이 같다는 이유로 3판2선 시리즈로 잘못 묶였다. 오버레이는 `2부 롤랜드 !멤버 깐숙 0 VS 0 야옹민지` —
**맞라인 두 사람의 개인 스코어**였다. 랜드인지 시리즈인지는 팀 구성이 아니라 **방송이 말한 형식**
(제목·오버레이의 "랜드/롤랜드", 맞라인 개인 스코어 vs 팀 스코어 `3/2) 상호팀 1:1 성훈팀`)으로 정한다.
팀 구성은 후보를 찾는 단서일 뿐 판정 근거가 아니다.

### 3.5-3. 스크림 — **마지막 판은 버린다**

멸망전 같은 대회 연습이다. **2시간 단위로 상대 팀이 미리 정해져 있다.**

```
20:00~22:00  vs A팀   보통 2판, 시간 남으면 3판째
22:00~24:00  vs B팀
```

마지막 타임은 상호 합의로 3판 이상 가기도 한다. 문제는 **경계**다 —
시간이 남아 한 판 더 시작했는데 다음 스크림 시간이 되면 **하던 게임은 전원 탈주**한다.

→ **그 중간에 끊긴 마지막 판은 전적에 넣지 않는다.** 넣으면 실제로 진 적 없는
패배가 생긴다. 신호: 경기 시간이 유난히 짧고(10~20분대), 끝나는 시각이 정각에 붙어 있고,
바로 다음 판의 상대 팀이 바뀐다.

### 이게 왜 중요한가

진행 방식에 따라 **같은 결과 화면이 다른 뜻**이 된다 — 같은 "만식팀 승" 이라도
CK 본선이면 시리즈 스코어가 오르고, 승부가 난 뒤의 추가 세트면 안 오른다.
랜드면 애초에 팀 단위 승패가 없다.

⚠ **순서표를 만들지 마라.** 옛 판에는 "판독 전에 카테고리부터 확정한다" 는 절차가 있었는데,
잘못 확정한 카테고리에 결과를 끼워 맞추면 세트 수와 승패가 통째로 틀어진다.
무엇인지 애매하면 **애매한 채로 두고** 근거를 적는다 — 그게 미해결 후보의 쓸모다.

## 4. 선별기 — 비용이 여기서 갈린다

시트 60장을 통째로 LLM 에 태우면 VOD 하나에 $0.11 이다. 그런데 시트에서 할 일은
"이 구간에 롤 경기가 있나" 뿐이라 **코드로 된다.** `detect()` in `scripts/lib/soop-vod.mjs`.
⚠ 지금은 이걸 **추가로 볼 자리를 제안하는 신호**로만 쓴다 — 기본 탐색 범위를 깎는 데 쓰지 않는다.

판정 규칙은 프레임 6,000장의 통계를 **채팅이 알려준 정답과 맞춰가며** 골랐다:

```
협곡 화면 = 어둡고 알록달록  → 밝기 < 75 && 채도 > 28
            (게임 중 밝기 56~70 / 채도 30~40, 브라우저·메모는 밝기 84~230)
밴픽/로딩 = 챔피언 일러 10장 → 채도 > 45 && 밝기 < 110
            (전체 중앙 34, 99%tile 48)
```

### ⚠ 이건 분류기가 아니라 거름망이다 — 게임 종류는 못 가른다 (2026-08-12)

위 규칙이 답하는 건 **"게임 같은 화면이 얼마나 있었나"** 지 **"롤이었나"** 가 아니다.
192×108 썸네일에는 그걸 가를 정보가 없다. 이상호 8월 표본 7개를 네 구역으로 실측 —

```
구역 밝기/채도        미니맵     아이템바    우상단
롤  시그니처CK        60/94     83/107     43/86
FC  공허한새벽 밤      61/96     63/100     24/98    ← 사실상 같다
FC  덕몽어스          66/97     70/158     66/105
```

FC온라인은 잔디가 어둡고 유니폼이 알록달록해서 `밝기<75 && 채도>28` 을 그대로 통과한다.
**실측 오탐률 67%** — 이상호 8/1~8/12 단서 6건 중 4건이 롤이 아니었다.
`gameRatio 89%` 짜리가 덕몽어스(오리게임) 투표 화면이었다.
임계값을 조이면 진짜 롤을 버린다. 어느 구역에도 깨끗한 분리선이 없었다.

**→ 판정은 원본 해상도 프레임이 한다.** 거름망이 후보를 줄이고(60채널 12일 → 6건),
경기 구간마다 한 장(6MB)씩 뽑은 확인 프레임이 게임 종류를 확정한다.
그래서 `ck:probe` 는 거름망과 **독립적으로** 시간축 전체에 대표 프레임을 깔고,
거름망이 짚은 자리는 거기에 **더한다**.

**VOD 하나에 한 장으로 줄이지 마라.** 5시간 방송이면 게임을 갈아탄다 — 실제로
2026-08-08 "이상호 피파" VOD 안에 롤 내전이 두 개 들어 있었다. 가장 긴 구간
한 장만 봤으면 FC온라인으로 판정하고 통째로 버렸을 것이다.

**세 번째 부류가 있다 — 롤 화면인데 우리 경기가 아닌 것.**
`203884619` 는 한 VOD 안에 덕몽어스 두 구간과 **LCK 시청**(KT vs DK ·
"LCK WATCH PARTY" 오버레이) 한 구간이 같이 있었다. 시청 방송은 협곡 화면이라
어떤 픽셀 규칙으로도 안 걸러진다. 프로 선수 이름(`KT Bdd`)과 방송사 오버레이가
보이면 시청이다 — 확인 프레임에서만 보인다.

### 한계를 그대로 적는다

- **경기 종료 시각은 못 맞춘다.** 종료 화면과 로비도 어둡고 알록달록해서 구간이
  3~8분 더 끌린다. 정답 5건이 전부 탐지 구간 '안'에는 들어왔지만 경계는 아니다.
  (다행히 §3 에서 보듯 종료 화면이 필요 없어졌다)
- **후보 밀도가 스트리머마다 다르다.** 이상호 12곳/4.9h, 김민교 24곳/5.6h.
  오버레이 구성이 달라서다. 두 명으로만 맞춘 규칙이다.
- **끊김을 이어 붙여야 한다.** 상점·Tab·잠깐 딴짓으로 한 판이 256조각까지 부서진다.
  40프레임(2분) 이하 끊김은 잇는다.

### 채팅 — 있으면 최고, 없는 게 대부분

진행자가 `!공지` 로 시리즈 스코어를 갱신하는 방송이 있다. 텍스트라 공짜이고
**종료 시각과 승자를 동시에** 준다. `loadChat()` · `gameEndsFromNotice()` in `scripts/lib/soop-vod.mjs`.

```
★ !공지 8건 (앞뒤 안 맞아 버린 것 1건) → 경기 종료 5건
   1:04:46  0:1   성훈팀 승
   1:39:55  0:2   성훈팀 승
   …
```

작성자가 아니라 **점수 진행이 말이 되는지**로 거른다 — 시청자가 장난으로 올린
반대 점수(2:1 다음에 1:2)가 실제로 있었고 이 규칙이 걸러냈다.

⚠ **10개 채널 중 1개에만 있었다.** 대형 조직 내전의 습관이지 규격이 아니다.
그래서 선별기가 본체이고 채팅은 보너스다.

### 백필 — ⚠ **VOD 는 시한부가 아니다** (2026-08-18 정정)

여기 원래 *"SOOP VOD 는 3~5개월치가 남아 있다"* 라고 적혀 있었다. **틀렸다.**
그 숫자는 `chapi /vods/all` 이 10,000건 하드 상한에 걸려 6개월치밖에 못 보던 시절의
관측이고, 본방만 받는 `/vod/all/streamer` 로 바꾼 뒤로는 훨씬 멀리 간다
(`scripts/lib/soop-vod.mjs` 의 주석이 이미 그렇게 적고 있었다 — 이상호 **5,272건 ·
2017-06-24 부터**).

실측(이상호 `lshooooo`, 2026-08-18):

```
2021-01  전체 251건 · 롤 213건        2024-06  전체  45건 · 롤  36건
2023-01  전체 145건 · 롤  81건        2025-01  전체  73건 · 롤  58건
```

**스트리머가 직접 지우지 않는 한 계속 남는다.** 그러니 VOD 수집은 시한부가 아니다 —
서두를 이유는 없고, 대신 **몇 년치를 거슬러 올라갈 수 있다**는 뜻이다.
(시한부인 것은 여전히 `rank_snapshot` 과 match-v5 2년 보존이다. CLAUDE.md 참조)

⚠ **빈 날짜를 보존 만료로 읽지 마라.** 이상호 2026-03-05~14 에 VOD 가 3건뿐인데,
이건 사라진 게 아니라 그날 방송을 안 했거나 본인이 지운 것이다. 실제로 그 기간
그는 멸망전 2경기를 뛰었지만 개인 방송 기록이 없다 — 그런 판은 **공식 채널**
(`lolbjmatch`)이나 다른 참가자 POV 로 간다.

채널의 반복적인 VOD 보존 성향은 `streamer_channel.vod_availability`에 기록한다.
`npm run watch -- --vod-usually-unavailable <이름또는채널>` 등으로 바꿀 수 있다. 이 값은
다른 POV 선택 비용을 가늠하는 힌트일 뿐이다. `usually_unavailable`이어도 목록 조회를
생략하지 않고, 특정 날짜에 VOD가 없다는 사실을 불참 근거로 사용하지 않는다.

다른 POV에서 경기 후보를 만나면 근사 절대시각으로 `ck:merge --find-match`를 먼저 실행한다.
정확한 시작 시각은 필요하지 않다(기본 앞뒤 90분). 조회 결과의 로스터·미확인 자리·챔피언/KDA
공백·결과 프레임·최종 판정 근거·남은 질문을 보고, 참여만 확인할지 빈칸을 겨냥해 더 볼지
판단한다. 몇 명의 POV를 봤는지는 완료 기준이 아니다. 기존 경기와 같은 판이라고 판단했다면
경기 하나의 좁은 구간만 `linked`로 남긴다. 여러 경기가 든 넓은 구간을 한 경기에 연결하면
어드민의 경기 막대와 프레임 문맥도 그 범위로 잘못 팽창한다.

백필 비용은 대상 기간을 정하고 다시 잡아야 한다. 3개월치 ≈ $141 · 155GB 였다.

전제: 이미지 1장 ≈ 1,844토큰(1920×1080 → 1568×882 리사이즈), 출력 400토큰,
내전만·시점 2개(동시 6.1개 중), 게임당 35분.

**틀릴 수 있는 것**: 제목 정규식(`ck|내전|멸망전|스크림|대회`)으로 CK 를 판별하므로
제목에 안 적고 하는 내전은 빠진다. 실제 물량은 이보다 많다.

## 5.5 지금은 어떻게 도는가

> 실행 방법의 정본은 [`ck-research` 스킬](../.claude/skills/ck-research/SKILL.md)이다. 여기는 맥락만.

```
ck:probe   전 범위 대표 프레임 (DB 에 안 쓴다 · '읽음' 안 붙인다)
ck:listen  고른 구간 음성 (보조)
  ↓ 사람이 프레임을 연다
ck:merge   기록·경기 반영 — 유일한 창구
  ↓ 곧바로 공개
/admin/ck  사후 교정·제외
```

★ **초안 단계가 없다.** 넣으면 곧 공개다. 그 대신 어드민이 고치고 뺄 수 있어야 하고,
  그래서 근거 프레임(`match_evidence_frame`)과 후보 결론(`event_lead.raw.candidates`)을
  같이 남긴다 — 검수자가 "왜 이렇게 판단했나" 를 되짚을 수 있어야 한다.

★ **뽑은 것과 읽은 것을 나눠 센다.** 파일이 생긴 것은 근거가 아니다.
  뽑아 놓고 안 열고서 단정한 사고가 실제로 있었다.

> ⚠ **구독 토큰을 서버에 올려 자동 호출하면 안 된다.** 구독 플랜은 본인이 대화형으로
> 쓰는 것이고 서버 자동화는 API 다. 서버가 필요해지면 그때 §5 의 비용으로 간다.

### 쓰기 명령의 기본값 규약

| 기본값 | 대상 | 왜 |
|---|---|---|
| **확인만, `--apply` 로 실행** | 공개 화면에 노출되는 테이블 (streamer·streamer_account) — `candidates:identify`, `repair:puuid` | 부계정 오노출은 실제 분쟁이 된다. 사람 눈을 강제로 거친다 |
| **기본 쓰기, `--dry-run` 으로 확인** | 조사 기록·경기 — `ck:merge` | 놓치면 복구가 안 된다. 안 쓰는 쪽이 더 위험하다 |

같은 성격의 새 스크립트를 만들 때 이 표를 따른다 — 규약이 갈라지면 사고가 난다.

## 6.5 사전 수집 경로 — 확인된 것 (2026-08-11 실측)

VOD 판독만으로는 수율이 낮다(§3 참고 — 26장에서 온전한 경기 하나를 못 만들었다).
그래서 역할을 나눈다.

| | 텍스트 사전 수집 | VOD 사후 검수 |
|---|---|---|
| 답하는 질문 | **언제·무엇이·누가 참가하나** | **어느 팀·누가 이겼나** |
| 비용 | 사실상 0 | 프레임당 토큰 |
| 정확도 | 조인 키가 정확 | 스트리머마다 편차 큼 |
| 놓치면 | **존재 자체를 모름 (복구 불가)** | 나중에 다시 볼 수 있다 |

```bash
# 전역 VOD 검색 — 418채널을 순회할 필요가 없다. 미등록 스트리머까지 잡힌다
sch.sooplive.co.kr/api.php?m=vodSearch&v=3.0&szKeyword=ck&nPageNo=1&szOrder=reg_date

# 지금 롤 방송 중인 사람 (00040019 = 리그 오브 레전드)
sch.sooplive.co.kr/api.php?m=categoryContentsList&v=1.0&szCateNo=00040019&szOrder=view_cnt

# ★ 게시판 — 호스트가 다르다. chapi 에는 없다
api-channel.sooplive.com/v1.1/channel/<채널>/menu           # 게시판 목록(bbsNo)
api-channel.sooplive.com/v1.1/channel/<채널>/board?…        # 글 목록·키워드 검색

# ★ 참가 신청 명단 — 이쪽은 chapi 다
chapi.sooplive.co.kr/api/<채널>/title/<글번호>/comment
```

### 게시판 댓글이 제일 정확하다

댓글은 `user_id`(SOOP 채널 아이디)를 그대로 준다. **우리
`streamer_channel.channel_id` 와 같은 키**라 이름 대조도 OCR 도 필요 없다.

```
2026-08-08 21:14  BJ댕라칸  thggftt      탑 골하 정글 골하 … 서폿 다이아벨 신청합니다
2026-08-08 21:19  기깔.     hun82825     원딜 미드 플하
2026-08-08 21:30  승욱쨩    ssw6676      저요 박권혁 맞밸ㄹ런스요
```
→ 신청자 12명 중 **8명이 즉시 매칭**됐다.

`keyword` 를 주면 게시판을 가로질러 검색된다(`bbsNo` 불필요). `startDate`/`endDate`
가 둘 다 비면 공지만 오므로 날짜나 키워드 중 하나는 줘야 한다.

### ⚠ `/board` 는 515 를 자주 뱉는다

`{"code":"CHA0002","message":"An error occurred."}`. Retry-After 도 레이트리밋
헤더도 없다. 헤더를 브라우저와 똑같이 맞춰도 재현되므로 **요청 내용이 아니라
호출 빈도 문제**로 본다. 한 번 막히면 몇 분 단위로 안 풀린다(실측 중).

→ 수집기는 채널당 호출을 최소로 잡고, **515 를 0건으로 넘기면 안 된다.**
  그러면 "그날 공지가 없었다"로 잘못 기록된다.

### 이 경로를 어떻게 찾았나

`chapi` 에서 한참 헤맸다. 답은 **헤드리스 크로미움으로 게시판 페이지를 열어
네트워크를 잡는 것**이었다 — 페이지가 Next.js SPA 라 HTML·번들 어디에도 API
주소가 없었다. 남의 API 를 찾을 때는 정적 분석보다 이쪽이 빠르다.

## 7. 미해결 — 기술이 아니라 결정

- **Riot 정책**: *"Products may not publicly display a player's match history from the
  custom match queue unless the player opts in to share this specifically for League of
  Legends."* 데이터 출처를 한정하지 않는다. **방송에서 파생한 데이터에도 미치는지가
  불명확하다.**
- **SOOP ToS·저작권**: 방송 VOD 를 자동으로 내려받아 분석하는 것의 위치.
- 둘 다 "된다"와 "해도 된다"가 다른 문제다. 공개 화면에 내보내기 전에 답이 있어야 한다.


## 결과 화면의 `1번 팀` 은 blue 가 아니다 (2026-08-21 실측)

롤 경기 결과 화면은 **보는 사람의 팀을 항상 `1번 팀` 자리에 올린다.**
김민교 시점으로 판독한 **11판이 예외 없이 `1번 팀`** 이었다 — 중간계 VIPER 의 Bo3·Bo5 는
세트마다 진영이 교차하므로 진짜 진영이라면 절반은 `2번 팀` 이어야 한다.
같은 날(2026-06-20) **로비 화면에서는 김민교가 `2팀`** 인데 결과 화면에서는 `1팀` 이다.

→ 시드의 `blue`/`red` 는 **팀 이름표**로만 쓴다. 진영이 필요하면 로비·밴픽 화면을 봐야 한다.
→ 승패·조우 집계는 영향이 없다(`winner` 는 팀 이름으로 정해진다).


## 검수 후 재조사 기록 (2026-09-22)

`ck:merge`는 검수된 경기·프레임·후보를 자동 입력으로 덮지 않는다. 후보의 안정적인 ID를 유지하고, CLI가 보고하는 검수 보존(건너뜀)을 갱신 성공과 구분한다. 입력 파일에 후보의 `reviewed_at`을 넣지 않는다.

`scan.sampled`는 대표 샘플 배치 범위다. 기존 실패는 기본적으로 보존된다. 실제 재시도 결과로 실패가 해소됐다면 아래처럼 별도 입력한다. `resolved_failed`는 VOD 전체 초의 양끝 포함 범위이며 명령으로 소비되고 누적 상태에 남지 않는다. 소수 초는 해소 범위를 넓히지 않도록 안쪽 정수 초로 축소된다.

```json
{"scan":{"status":"done","resolved_failed":[[800,800]],"failed":[]}}
```

위 조각은 기존 scan 결과 파일의 scan 필드에 합친다. 경기 생성 입력이나 단서 정보 자체를 대신하지 않는다. 새 실행에서 다시 실패한 범위는 해소보다 우선하여 남는다.

음성 `samples.json`의 `complete`는 생성된 다운로드 조각의 완료 여부다. 요청 범위 밖 구간은 `outOfRange`에 `[시작초, 끝초]`로 남는다. `plannedRanges`는 `[시작초, 길이초]`이므로 형식을 구분한다. 일부가 범위 밖이어도 유효한 조각의 전사는 허용하며, 이 기록만으로 읽음 상태를 올리지 않는다.

## 애매한 화면으로 탐색 구간을 버리면 안 되는 이유 (2026-09-23 실측, VOD 207602969)

이상호93 s1g2(1세트 2세트)의 결과 화면을 찾다가 실제로 건너뛴 사고다.

```
19400  살아 있는 게임 화면 (인게임 콤뱃로그)         ← 확실한 진행 중
19490  브라우저 탭이 뜬 화면                        ← 안 연 구간의 시작. 판단 보류
19505  검은 로딩 화면                               ← 안 연 구간의 끝. 판단 보류
19535  8배속 재생 컨트롤이 보이는 화면               ← 리플레이. 정확히 읽었다
19590  리플레이 확인
```

⚠ **19535 를 "리플레이"로 읽은 건 오독이 아니었다.** 실제로 하단에 되감기·일시정지·
8배속 재생 컨트롤과 타임라인 스크러버가 그대로 보이는, 화면 종류로는 애매할 게 없는
프레임이다(`out/ck/207602969/g0019535.jpg`). **잘못은 화면 종류를 맞힌 것과, 그 사실로
그 앞의 안 연 구간(19490~19505)까지 "이미 지나갔다"고 단정한 것을 같은 일로 취급한
데 있다.** 19535 가 리플레이라는 건 19535 시점에 대해서만 참이고, 19490~19505 사이에
무엇이 있었는지는 아무것도 말해주지 않는다. 그런데도 그 확정을 종료 후 기준점 삼아
19400(진행 중)과 19535 사이를 이분 탐색 감각으로 건너뛰고, 매치 히스토리 요약 같은
더 약한 간접 근거로 KDA 를 채웠다. **실제 결과 화면은 그 안 연 구간의 19500 에 있었다**
— 옛 조사(이 VOD 를 이전 스킬로 조사했을 때)는 찾았던 값인데 이번엔 놓쳤다.

화면 전환이 `진행 중 → 브라우저 → 결과창 → 로딩 → 리플레이`처럼 여러 상태를 거치므로,
뒤쪽 프레임 하나를 정확히 읽어냈다는 사실이 그 앞의 안 연 구간을 "다 봤다"는 근거가 되지는
않는다. 좁히기 자체가 문제가 아니라, 애매한 화면을 확정 기준점으로 삼아 구간을 버린 것이
문제였다.

재조사 때 `npm run ck:probe -- --vod 207602969 --between 19488:19510 --step 2`로
2초 간격으로 추출한 프레임을 모두 열자 `g0019500.jpg`에서 옛 조사와 정확히
일치하는 10인 점수판이 바로 나왔다. 애초에 그 구간을 열기만 했으면 놓칠 수 없었다.

→ 그래서 넓은 구간은 확실한 진행 화면과 종료 후 화면을 기준점으로 5분할해 좁히고, 마지막
짧은 구간만 초 단위로 소진한다. 브라우저·로딩·판단하기 어려운 리플레이는 기준점으로 쓰지
않는다. 화면 종류를 정확히 읽은 것을 그 앞뒤 안 연 구간까지 "이미 없다"고 단정하는 것과,
뽑은 프레임을 열지 않고 넘어가는 것은 여전히 금지 대상이다.

## 뽑고 안 읽는 것이 진짜 실패 모드다 (2026-09-23 실측, VOD 207602969)

위 사고를 고친 뒤에도 같은 VOD 의 **s2g1 과 단판에서 결과 화면을 또 놓쳤다.** 세어 보니
원인이 한 가지로 모였다.

```
뽑은 프레임   313장
실제로 연 것   48장 (15%)
안 연 것      265장
```

안 연 것이 어디 몰려 있었나 — 전부 **결과 화면을 찾겠다고 직접 돌린 `--between` 스윕**이다.

```
04:38~04:42  25장   s1g1 결과창 구간
05:23~05:29  44장   s1g2 결과창 구간  → 19500 이 여기 있었다
06:20~06:27  23장   s2g1 결과창 구간  → 23120 이 여기 있었다
08:12~08:13   5장   단판 결과창 구간  → 29500 이 여기 있었다 (0장 열었다)
```

**원인은 비용의 비대칭이다.** `--between ... --step 2` 는 명령 한 줄에 파일 수십 개가
생기고(싸다), 프레임 판독은 장당 약 1,844토큰이다(비싸다). 그래서 넓게 뽑아 두고 답 같은
것이 보이면 멈추는 습관이 붙는다. 보통 검색이면 맞는 전략인데, 결과 화면은 끝난 것처럼
보이는 화면 **사이에** 끼어 있어 먼저 보이는 것에서 멈추면 정확히 그것을 놓친다.

**그리고 이건 안 뽑은 것보다 나쁘다.** 안 뽑으면 "여긴 안 봤다"가 남는데, 뽑고 안 읽으면
`scan.sampled` 에 범위가 들어가고 파일도 디스크에 있어 **"봤다"처럼 보이면서** 기록에는
아무 흔적이 없다. 검수 화면에도 읽은 것만 올라가므로 사람이 구멍을 볼 방법이 없었다 —
실제로 세 번 다 운영자가 화면을 보고 "결과창이 없는데?"라고 해서 발견했다.

→ **`ck:merge` 가 `probe.json` 의 프레임을 전부 등록한다.** 메모가 없으면
`read_at = NULL` 로 남고, `/admin/ck` 의 경기·후보 행이 **"메모 없음 N장"** 으로 구멍을
그대로 보여 준다. 읽음을 올리는 장치가 아니라 **안 읽었다는 사실을 화면에 박는 장치**다.
