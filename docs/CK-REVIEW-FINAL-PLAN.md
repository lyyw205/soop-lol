# CK 재검토 결과와 최종 수정안

검토일: 2026-09-22. 대상: 현재 작업 디렉터리의 CK 코드.
아래 A~F는 구현 전 재검토 기록이다. 당시의 코드 줄 번호·검사 수·미검증 범위는 그 시점 기준이며, 현재 구현 결과는 바로 아래에 기록한다.

## 구현 완료 기록 — 2026-09-22

이 계획의 일곱 항목을 구현했다. 운영 DB에는 쓰지 않았으며, 이 수정 범위에서 새 마이그레이션은 추가하지 않았다.

검증은 저장소 내부 스크립트로 재현한다.

- `npm test`: 단위·CLI 산출물 검사 128개 통과.
- `npm run typecheck`, `verify:db`(현재 작업 디렉터리 기준 164개), `verify:ingest`, `verify:modules`, `verify:ck`: 통과. 기존 scan 검사의 잘못된 기대도 수정했다.
- `verify:ck:concurrency`: 폐기용 실제 PostgreSQL에서 잠금 대기를 관측한 뒤 커밋을 풀어 낡은 기대값 거부를 확인했다. 다른 필드 동시 저장, 동일 자리 동시 추가, 실제 ck:merge 호출의 후보 보존·실패 해소까지 통과했다.
- `verify:ck:browser`: 폐기용 DB에 연결한 실제 Next 앱과 Chromium에서 데스크톱·모바일 저장/새로고침, 경기 전환, 같은 경기 서버 갱신 중 입력 보존, 두 탭 충돌, 최신 값 불러오기, 후보 보존을 확인했다. 경기 이동 후 늦게 도착한 이전 저장 응답도 새 폼을 바꾸지 않는다. 공개 승패 및 챔피언 통계 반영도 검사했다.
- `npm run build`: 통과. 기존 프레임 파일 라우트의 동적 경로 추적 경고 2건은 남아 있다. 별도 출력 디렉터리로 빌드한 뒤 해당 산출물은 제거했다.

실제 PostgreSQL·브라우저 실행 준비는 [SETUP.md](./SETUP.md)의 CK 검증 절에 있다. 두 스크립트는 외부 DATABASE_URL 대신 직접 만든 임시 클러스터만 사용한다. 빠른 `verify:ck`는 PGlite를 사용하며, 별도 프로세스를 여는 CLI 왕복 검사는 실제 PostgreSQL 검사에 포함했다.

이번에 실행하지 않은 범위: 운영 DB의 백업·복구, 실제 원격 VOD 다운로드/ASR 전체 실행, 과거에 이미 소실된 기록 복구. 다른 작업에서 추가된 기능·마이그레이션 전체의 승인을 이 결과로 대신하지 않는다.

## A. 최종 판정

**수정 후 구현 가능.** 사후 검수 중심의 구조는 유지한다. 확인된 여섯 결함은 편집 상태·부분 저장·검수 보존·실패 해소 계약을 완성하면 해결된다. 음성 요청 범위 밖 기록은 별도의 낮은 우선순위 보완으로 포함한다.

앞선 피드백은 핵심 현상에 대해 맞지만 다음 표현을 조정한다.

- 프레임과 후보 폼에는 이미 ID별 `key`가 있다. 빠진 것은 경기 인스펙터와 로스터의 경기별 경계다. 모든 폼에 `key`가 없다는 설명은 부정확하다.
- `key`만 추가하면 경기 전환 문제는 막지만, 같은 경기의 props가 갱신될 때 입력값과 `prev_*`가 갈라지는 문제는 남는다.
- `ck:listen.complete=true` 자체를 오판으로 규정하지 않는다. 다운로드 대상으로 만들어진 조각의 완료 여부라는 기존 의미는 유지할 수 있다. 범위 밖 요청을 산출물에 남기지 않는 것이 보완 대상이다. 이 재현은 실제 VOD 내부의 음성을 유실했다는 증거가 아니다.
- `sampled`는 대표 샘플을 배치한 범위다. 읽음·정밀 확인·실패 해소의 증거로 승격시키면 안 된다.

## C. 최종 변경 계약

### 1. 폼의 대상·기준값·입력값을 함께 관리한다

변경: `CkReviewer.tsx`, 필요하면 같은 폴더에 CK 전용의 작은 폼 상태 보조 함수.

1. `MatchInspector`와 `RosterInspector`에 `match_id` key를 추가한다. 다른 경기로 이동하면 이전 경기의 입력과 액션 메시지를 재사용하지 않는다.
2. 편집 단위는 경기 메타 폼, 참가자 한 자리, 후보 폼이다. 각각 편집 시작 시점의 `base`와 사용자의 `draft`를 보유한다. `prev_*`를 매번 최신 props에서 계산하지 않는다.
3. 값은 controlled input으로 관리한다. 실패 응답 시 draft와 base를 보존한다. 같은 ID의 props 갱신만으로 편집 중인 base를 교체하지 않는다.
4. 저장 성공 시 서버가 반환한 정규화된 저장 결과로 base와 draft를 함께 갱신한다. 충돌 시 서버 최신값을 별도로 보여주고, 사용자의 명시적 다시 불러오기로 두 값을 함께 갱신한다.
5. 제출 중에는 해당 폼 입력과 중복 제출을 잠가, 제출 후 입력한 값을 뒤늦은 성공 응답이 지우지 않게 한다. 다른 경기의 폼에 완료 응답을 적용하지 않는다.
6. 이미 key가 있는 후보·프레임의 ID 경계는 유지한다. 새 경기 폼은 프레임·후보의 생성 문맥을 key로 삼아 제안 ID와 근거 프레임이 엇갈리지 않게 한다.

CK 액션에 필요한 반환값만 확장한다. 전역 ActionState나 다른 관리자 화면 전체를 개편하지 않는다. CK용 상태에 `saved` 또는 `conflict`를 담고, saved는 해당 폼이 편집하는 필드의 스냅샷만 포함한다.

### 2. 경기 메타에도 변경 필드와 기대값을 적용한다

변경: `actions.ts`, `ck.ts`, CK 액션 상태 타입.

- 메타 검수 입력은 `{ changes, expect }`로 받는다. 비교는 core에서 한 번 구현하고 현재 참가자 patch 경로에도 같은 비교 함수를 사용한다.
- 액션은 draft와 고정된 base를 동일한 규칙으로 정규화한 뒤 바뀐 필드만 changes에 넣는다. 변경 필드의 기대값 누락은 오류다. 파생 필드를 사용자가 보내는 비교 대상과 혼동하지 않는다.
- `undefined`는 변경 없음, `null`은 명시적 비우기, `0`은 실제 숫자 0이다. 폼의 빈 값 규칙은 필드별로 현재 UI와 일치시키고, 비교 전후에 같은 정규화를 적용한다.
- 비교 대상은 허용된 필드만 받는다. 숫자·시각은 정규화하고, 후보의 질문 배열은 원소와 순서를 구조적으로 비교한다. 모든 값을 `String()`으로 바꾸는 느슨한 비교를 배열·객체까지 확장하지 않는다.
- `SELECT ... FOR UPDATE` 후 최신 메타를 읽고 기대값을 비교한다. 다른 필드 수정은 병합하고, 같은 필드가 달라졌으면 아무 값도 쓰기 전에 충돌로 반환한다.
- 시리즈 ID·세트 번호는 합쳐진 최종 상태로 쌍 제약을 검증한다. 시각은 현재 KST 변환을 유지하고 기대값 비교에서는 같은 시간 표현으로 정규화한다.
- 참가자의 team_id도 변경 필드와 기대값 계약 안으로 넣는다. 챔피언 이름·ID는 하나의 의미 단위로 비교·정규화한다.
- 승자 변경 후 participant.win 동기화, before∪after 통계 계산, 조우 재파생은 기존 트랜잭션에 유지한다. 편집 폼마다 재계산 구현을 복제하지 않는다.
- 변경 없음은 저장·재계산 없이 성공으로 반환한다. 충돌 메시지는 필드·내 기준값·현재값을 포함한다.

### 3. 참가자 신규 추가와 기존 수정 경로를 분리한다

변경: `MatchReviewPatch`, `applyMatchReview`, `saveParticipantAction`, 관련 DB fixture.

- `participants.add`는 신규 자리만 받는다. `(match_id, participant_id)` 충돌 시 `DO NOTHING RETURNING` 결과를 보고 명확한 충돌을 반환한다.
- 중복 추가의 트랜잭션에서는 메타·reviewed_at·기존 참가자·파생 결과가 변경되지 않아야 한다. 충돌을 성공으로 응답하지 않는다.
- 기존 자리는 `participants.patch`로 수정한다. 현재 실제 앱의 upsert 호출은 신규 추가 액션이며, 다른 확인된 호출은 verify-db fixture다. 이 호출들을 add/patch로 옮기고 검수용 무조건 upsert는 제거한다.
- 응답 유실 후 같은 추가 요청을 보내도 기존 행을 덮지 않는다. 최초 수정에서는 별도 idempotency 테이블 없이 “이미 추가된 자리”와 최신 행을 응답한다.

### 4. 챔피언의 명시적 삭제를 보존한다

변경: `ck.ts`의 participant patch 정규화와 `participant.ts`의 사용 계약.

- 챔피언 필드 자체가 없으면 기존 값을 유지한다.
- 이름을 명시적으로 변경한 경우 기존 ID로 fallback하지 않는다. 이름만으로 정규화해 알려진 이름이면 ID를 채우고, 미상 이름은 현재 표현 규칙을 따른다.
- 명시적으로 비운 경우 저장값은 기존 스키마의 미상 표현인 `champion_id=0`, `champion_name=null`이다. 이 수정을 위해 champion_id를 nullable로 바꾸지 않는다.
- ID만 명시적으로 바꾸는 내부 경로도 키 존재 여부로 판단한다. `?? current_id`로 null과 생략을 합치지 않는다.
- 기존 재계산으로 옛 챔피언 통계가 정리되고 참가 기록 자체는 보존되는지 확인한다.

### 5. 후보에 검수 보존 계약을 추가한다

변경: `LeadCandidate`, `mergeLeadCandidates`, 새 `reviewLeadCandidate`, 후보 액션·폼, `ck-merge.mjs`.

- `raw.candidates[]`에 `reviewed_at`을 추가한다. 새 테이블과 마이그레이션은 필요 없다.
- 자동 입력 타입과 검수 타입을 구분한다. 자동 입력에서 reviewed_at을 주입·초기화할 수 없도록 CLI와 core에서 허용 필드를 제한한다. 관리자 권한 여부를 입력 JSON의 플래그로 판단하지 않는다.
- 자동 병합은 reviewed_at이 있는 같은 ID 후보를 그대로 보존한다. 새 후보는 추가하고 검수하지 않은 후보는 기존처럼 병합한다. 결과에 갱신·건너뜀 ID를 반환하고 CLI에서 보고한다.
- 관리자 수정은 `reviewLeadCandidate(leadId, candidateId, {changes, expect})`로 처리한다. event_lead 행을 잠근 다음 후보를 읽고 비교·수정·검수 표시까지 한 트랜잭션으로 처리한다.
- 현재 saveCandidateAction의 트랜잭션 밖 read→전체 후보 재전송을 제거한다. 관찰·판단·질문은 별도 필드로 유지한다.
- 과거 후보의 검수 여부는 현재 데이터만으로 복원할 수 없다. 기존 후보 전체를 임의로 검수 처리하지 않는다. 식별 가능한 검수 기록이 있다면 해당 후보만 별도로 확인한다.

### 6. sampled와 실패 해소를 분리한다

변경: `markLeadScan`, `ck-merge.mjs`, probe의 초안·설명, `verify-db.ts:1337` 부근.

이번 수정은 현재 실패 배열의 원인 정보가 부족하다는 점을 반영해 보수적으로 처리한다.

- `sampled`는 대표 샘플 배치 범위라는 뜻을 유지한다. `subtractRanges(prev.failed, next.sampled)`를 제거한다.
- 입력 전용 `resolved_failed`를 추가한다. 이는 이번 조사에서 실제로 해소했다고 확인한 실패 구간을 명시하는 명령이다. 누적 상태에 매번 재적용될 별도 정본으로 저장하지 않는다.
- 병합은 `failed = union(subtract(previous.failed, resolved_failed), incoming.failed)`로 처리한다. 같은 실행에 실패가 다시 보고되면 실패를 유지한다. `resolved_failed` 생략 또는 빈 배열은 이전 실패를 지우지 않는다.
- CLI가 `resolved_failed`를 읽어 markLeadScan의 옵션으로 전달한다. 유한한 VOD 전체 초·정렬된 구간 등 형식은 검사하되 판단을 점수나 문구로 심사하지 않는다.
- probe가 샘플 주변 구간이나 프레임 한 장 성공만으로 resolved_failed를 생성하지 않게 한다. 현재 failed에는 프레임·음성·접근 실패가 섞일 수 있으므로, 자동으로 실패 원인을 추정해 지우지 않는다.
- 조사자는 실제 재시도 결과를 근거로 명시적으로 해소를 전달한다. 자동 해소가 나중에 필요하면 그때 실패의 매체·원인·시점 식별을 모델링한다. 이번에 일반 작업 큐나 실패 이력 테이블을 만들지 않는다.
- 기존 정수 초·양끝 포함 구간 연산은 유지한다. ASR의 소수 초 범위를 전달한다면 해소 범위를 넓히지 않는 정수화 규칙을 적용한다. 기존 구간 연산에 소수 초를 그대로 넣어 ±1 연산으로 구간을 지우지 않는다.
- 기존 회귀 검사는 sampled와 opened 한 점만으로 600~900초 실패가 해소된다고 기대한다. 이 기대를 “명시적 해소 없으면 보존”으로 바꾸고, resolved_failed를 준 별도 성공 검사를 추가한다.

### 7. 음성 범위 밖 요청을 manifest에 남긴다

변경: `ck-listen.mjs`, 범위 분할·manifest 생성 검사.

- 기존 complete는 생성된 다운로드 대상 조각의 완료 여부로 유지한다. ASR이 이 필드를 읽는 계약을 깨지 않는다.
- `outOfRange`를 VOD 전체 초 `[start,end]` 배열로 samples.json에 기록한다. requested/plannedRanges는 기존 `[start,duration]` 형식임을 명시해 서로 혼동하지 않게 한다.
- 일부 요청만 범위 밖인 경우 유효 조각 전사는 허용하고, 출력에서 요청 일부 제외를 알린다. 범위 밖 요청 때문에 정상 조각 전사를 새 승인 단계로 막지 않는다.
- 전체 요청이 범위 밖이면 네트워크 호출 없이 요청·outOfRange·빈 clips·complete=false를 manifest로 기록한 뒤 종료한다. 이전 실행의 samples.json이 최신 결과처럼 남지 않게 한다.
- downloaded/읽음/조사 완료의 의미를 합치지 않는다. 이 변경으로 transcript_read나 DB 상태를 자동으로 올리지 않는다.

## D. 유지할 부분과 검증 현황

이번 재실행에서 확인한 결과:

- `npm test`: 118개 통과. 앞선 보고의 117개는 이전 실행 수치다.
- 전체 `npm run typecheck`: 통과.
- `verify:db`: 154개 검사 통과. 6번의 잘못된 기대가 들어 있으므로 통과 자체가 해당 계약의 올바름을 보장하지는 않는다.
- 추가 DB 재현에서도 identify 후 챔피언/KDA 보존, 프레임 없는 경기 조회·집계, 이전 참가자 통계 정리, 부분 KDA 제외, 기존 ID 수동 생성 거부, 수동 생성 경기 재수집 보호를 확인했다.
- `verify:ingest`, `verify:modules`, 운영 DB 개수·식별자 노출 및 신규/업그레이드 비교는 앞선 검토 결과이며 이번 재검토에서 반복하지 않았다.

미검증: Next 전체 저장 E2E, 실제 PostgreSQL 동시 트랜잭션, 백업 복구. 이번 테스트 실행을 해당 검증까지 통과한 것으로 표현하지 않는다.

## E. 구현 순서와 완료 조건

1. 현 재현을 프로젝트 내부 테스트로 옮겨 먼저 실패시킨다. `/tmp` 스크립트나 다른 저장소의 Playwright 설치를 영구 검증 의존성으로 삼지 않는다.
2. core의 메타 patch·신규 add·챔피언 정규화를 수정한다. 기존 FOR UPDATE와 파생 계산 경로를 유지한다.
3. 액션의 base/draft 파싱·저장 결과 반환과 UI의 ID 경계·고정 기준값을 함께 연결한다.
4. 후보 검수 계약과 CLI 건너뜀 보고를 추가한다.
5. 실패 해소 명령과 음성 범위 밖 manifest를 추가하고 기존 잘못된 검사 기대를 수정한다.
6. 단위·DB·수집·모듈·typecheck를 실행한다. 폐기 가능한 실제 PostgreSQL에 두 연결을 열어 대기/커밋을 제어하는 동시성 검사도 실행한다. 운영 연결을 받는 기본값은 두지 않는다.
7. 폐기 가능한 DB를 연결한 Next 앱에서 데스크톱·모바일 선택→수정→저장→새로고침을 검증한다. 중요한 메타·참가자 변경은 공개 조회의 승패·챔피언 통계까지 확인한다.

## F. 개발자 전달문

현재 구조를 유지한다. 경기 폼의 ID 경계와 고정된 편집 기준값을 도입하고, 메타에도 changes/expect를 적용한다. 참가자 추가는 insert-only, 챔피언 삭제는 0/null로 정규화한다. 후보는 raw 안에 검수 표시를 남겨 재수집을 막고, sampled를 실패 해소 근거로 사용하지 않는다. 해소는 명시적인 resolved_failed 입력으로 처리한다. 음성 complete 의미는 유지하면서 outOfRange를 manifest에 기록한다.

새 승인 단계·범용 폼 프레임워크·작업 큐·이력 테이블은 추가하지 않는다. 여섯 결함 재현과 음성 경계 기록 검사를 회귀 테스트로 고정하고, 실제 브라우저 저장 및 폐기 가능한 PostgreSQL 동시성 검사를 완료 조건으로 삼는다.
