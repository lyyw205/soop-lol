> **검증 방법(조사 품질 비교)은 별도로 정한다** — 이 문서는 구조와 순서, 품질을 지키는 장치까지 다룬다.
>
> **2026-10-16 개정(Codex 검토 반영, 7건 모두 코드 대조로 사실 확인).** 바뀐 것:
> ① 첫 분리는 **필수 읽기 범위를 그대로** 둔다 — 조건부 읽기 전환은 품질 검증 대상인 별도 변경(§5.5.1·§5.5.9).
> ② 품질 검증 방법이 정해지기 전에는 스킬 분리를 **운영에 넣지 않는다**(§7 4단계).

> ④ 롤 자동 조사는 목록 확인·조사를 **다른 작업**으로 등록하고 화면에서만 묶는다. 조사 정상 판정에 대기·진척을 쓴다(§5.1·§5.6).

> ⑥ 검증 조건 충돌 해소 — 프롬프트 출력 경로 신설, 의도한 중복 허용 목록, 파일 이동과 내용 변경을 다른 단계로(§5.5.7·§5.5.8·§7).
> ⑦ 스킬 교체는 조사 세션이 하나도 없을 때만, 조사 잠금을 잡고 한다(§5.5.10).

## 0. 한 문단 요약

조사 판단(스킬의 규칙)은 **한 글자도 바꾸지 않고 자리만 옮긴다.** 바꾸는 것은 그 바깥이다 —
① 모든 자동화를 한 곳에 선언하는 **등록부**, ② 어떤 작업이든 같은 형식으로 남기는 **실행 기록**(시작·생존·진척·멈춘 이유),
③ 등록부를 읽는 **운영 화면**, ④ 같은 규칙이 다섯 군데에 복사된 것을 **한 곳**으로 모으는 것,
⑤ 500줄에 닿은 스킬을 **핵심 + 참고 파일**로 나누는 것(첫 분리는 파일 정리일 뿐 읽는 범위는 지금과 같다). 실행 방식(조사 세션·워커·타이머)은 업무별로 그대로 둔다.
순서는 정합성 수리 → 등록부 → 실행 기록·화면 → 백필 정식화 → 스킬 구조 → (측정된 병목만) 조사 분리다.
스킬 분리·프롬프트 변경·실행기 공통화는 **각각 따로 검증하는 별개 변경**이다.
★ 파일이 짧아졌다는 사실만으로 비용·속도·정확도가 좋아졌다고 판단하지 않는다 — 그런 주장은 측정(§9-6) 뒤에만 한다.

## 1. 목표와 하지 않는 것

### 목표

1. **빼기 쉽게** — 자동화 하나를 없애려면 등록부 한 항목과 그 파일들만 지우면 되고, 남은 흔적은 검사가 잡는다.
2. **무엇이 돌고 왜 멈췄는지 한 곳에서** — 자동·수동·백필·보관 작업 모두. "살아 있음"과 "진척 있음"을 구분한다.
3. **스킬을 가볍게** — 세션이 매번 읽는 양을 줄이되, 필요한 상황에서 필요한 규칙을 **반드시** 읽게 한다.
4. **규칙은 한 곳** — 스킬·실행기 프롬프트·재개 요약이 서로 다른 버전의 규칙을 말하지 않게 한다.

### 하지 않는 것 (근거는 §2)

- 전문 오케스트레이터(Airflow·Dagster·Temporal) 도입 — 한 대·작업 15개·운영자 1명 규모에 과하다.
- 모든 작업을 하나의 대기열로 통합 — 긴 VOD 조사가 당일 수집을 밀어낸다.
- 조사 세션을 단계별 에이전트로 쪼개기 — 맥락이 끊기고 원본을 다시 읽어 비용·품질이 나빠질 수 있다. 측정 전에는 하지 않는다.
- 스킬 규칙 문장의 재작성·요약 — 4단계에서는 **원문 그대로 이동**과 **똑같은 문단의 중복 제거**만 한다.
- 공개·검수 정책 변경 — CK 판독은 저장 즉시 공개, FC 화면 경기는 숨긴 채 저장 후 검수 공개, 편성표 분석은 검토 후보까지. 그대로 두고 등록부에 명시만 한다.

## 2. 근거 — 표준 원칙과 이 계획의 대응

### 3.3 이미 잘 돼 있는 것 — 보존 대상 (§6에 불변식으로 고정)

- 진척의 단일 출처: `event_lead.raw.scan`/`fco_scan`을 `vodWork`(`packages/core/lib/metrics/ck-vod-status.ts:91-123`)로 읽는다. 커서 없음 → 재실행이 멈춘 곳부터 잇고 빈틈도 메운다.
- 자동·백필이 `vodWork`·`madeProgress`·반복 방지 가드·`recordVodAccess`를 공유한다.
- 저장 관문이 코드에 있다: `ck:merge`(제출 형식·근거·재송출·검수 잠금), `fco:context scan --status done`의 음성 필수 창 관문(`scripts/fco-context.ts:522-542`).
- 같은 API 출처끼리 잠금 공유(`out/locks/*.lock`), 채널당 한 프로세스.
- 무인 세션 안전장치: `</dev/null`, `--no-session-persistence`, 자동 메모리 끔, 세션별 `--model`, 이미지 예산 훅.
- 모듈 구조의 선례: `module.json` + 생성 등록부 + `verify:modules`(AST 기반, 자가시험 포함).

### 5.1 등록부 (빼기 쉽게)

**근거:** P5·P6. 표준 도구는 모두 작업을 코드로 선언한다. 우리에겐 이미 `module.json` + `verify:modules` 선례가 있다.

**방법**

1. 작업마다 파일 하나: `ops/jobs/<id>.json`(저장소 안, 사람이 고친다). 생성 색인 `packages/core/lib/ops/jobs.generated.ts`는 `npm run ops:sync`가 만든다(`modules:sync`와 같은 방식, 손으로 고치지 않는다).

### 5.2 실행 기록 공통화 (실행됐나·살아 있나·진척·왜 멈췄나)

**근거:** P5·P8, 데드맨·SRE 원칙. Codex 표의 "살아 있음 ≠ 진척", "종료 코드 0만으로 정상 표시 금지".

**방법**

1. **감싸는 실행기 하나** `scripts/ops/run-job.ts --job <작업 ID> -- <원래 명령>`:
   - 시작할 때 **실행 ID**(`run_id`, uuid)를 만들어 자식에게 환경 변수 `OPS_RUN_ID`·`OPS_RUN_DIR`(`out/ops/runs/<작업 ID>/<run_id>/`)로 넘긴다.
     **작업 ID**(등록부 `id` — "무엇")와 **실행 ID**("이번 한 번")는 다른 것이다.
   - 시작 기록, 자식 프로세스가 살아 있는 동안 60초마다 **생존 신호**(heartbeat), 끝나면 종료 코드와 **실행기가 남긴 멈춘 이유**(3)를 기록한다.
   - 원래 명령은 그대로 실행한다(인자·환경·종료 코드 투명 전달). 유닛의 `ExecStart` 앞에만 붙인다.
2. **진척은 작업이 직접 알린다** — 작업이 원할 때 `$OPS_RUN_DIR/progress.json`에 `{done, total, unit, last_item, at}`을 원자적으로 쓴다(**실행마다 다른 경로** — 앞 실행의 진척이 다음 실행 것으로 읽히지 않는다). 감싸는 실행기가 생존 신호와 함께 읽어 기록한다. 백필은 이미 `run.log`·`current.json`이 있으므로 `ck-backfill.sh`가 VOD 하나 끝날 때마다 한 줄 쓰게 한다(조사 로직 무변경).
3. **멈춘 이유는 종료 코드에서 번역하지 않는다 — 실행기가 그 분기에서 직접 남긴다.**
   종료 코드는 지금 그대로 두되(호출자·유닛이 쓴다), 같은 코드가 여러 이유를 뜻한다. 실제 예:
   - `ck-auto.sh`의 **3**: DB 관문(`:90`) · STOP(`:107`, `:278`) · abort(`:108`) · 실행 시간 상한(`:109`) · 디스크 부족(`:112`) · 쓰기 차단 플래그(`:115`) · 세션별 DB 관문(`:116`).
   - `ck-auto.sh`의 **0**: 조사 완료 · 중복 실행 생략(`:50`) · FC 대상 없음(`:97`) · 미리보기(`:79`).
   - `ck-backfill.sh`의 **0**: 기간 완료(`:154`) · 요청으로 멈춤(`:145`) · 세션 수 상한(`:264`).
   그래서 각 분기에서 종료 직전에 `$OPS_RUN_DIR/stop.json`에 `{reason, detail}`을 쓰는 한 줄 함수(`ops_stop <이유> <설명>`)를 부른다.
   감싸는 실행기는 이 파일을 읽고, **없거나 형식이 틀리면 `unknown`**으로 기록한다(추측해서 채우지 않는다). 감싸기 없이 돌면(수동 실행) 함수는 아무것도 안 한다.
   분류(화면 표시용):
   `completed`(할 일 끝) · `no_work`(대상 0 — 실패 아님) · `skipped`(이전 실행이 돌고 있어 생략) · `user_stop`(STOP·--stop) · `time_cap`(실행 시간·세션 수 상한 — 다음 회차가 잇는다) · `blocked_external`(DB 관문·DB 쓰기 차단·디스크·HLS 차단·사용량 한도 — `detail`에 어느 것인지) · `no_progress`(반복 가드) · `budget`(세션 예산 — 정상 인계) · `lock_busy`(75) · `error` · `killed`(130·TERM) · `unknown`.
   "대상 0"과 "대상을 못 찾음(목록 잘림 등)"은 다른 이유다 — 목록 잘림은 `error`다.
   `verify:automation`이 등록된 실행기 셸의 모든 `exit` 줄 근처에 `ops_stop`이 있는지 본다(빠진 분기 = 실패, 의도한 예외는 주석 표시).
4. **기록의 주인은 하나 — 감싸는 실행기.** 지금 워커의 `runJob()`(`apps/worker/src/job.ts:55`)도 `job_run`에 시작·종료를 쓰므로, 정하지 않으면 한 실행에 행이 둘 생기거나 최종 상태가 둘이 된다.
   - 감싸기 아래에서(`OPS_RUN_ID`가 있으면) `runJob()`은 **새 행을 만들지 않고** 같은 `run_id` 행에 엔진 값(`processed`·`api_calls`·`detail`·`error`)만 갱신한다. 최종 `state`·`stop_reason`·`finished_at`은 감싸는 실행기만 쓴다. 부분 실패는 지금처럼 종료 3 + `stop.json`의 `error`(부분 실패 N건).
   - 감싸기 없이(`OPS_RUN_ID` 없음) 돌면 `runJob()`은 지금 동작 그대로 — 손 실행·`worker loop`가 깨지지 않는다.
   - 시험: 같은 실행에 `job_run` 행이 정확히 하나, 최종 상태 작성자가 하나인지.
5. **저장 위치:** `job_run`을 넓힌다(새 마이그레이션 — 번호는 착수 때 `db:migrate --status`로 확인):
   `run_id uuid UNIQUE, ops_job text, trigger text, host text, heartbeat_at timestamptz, progress jsonb, stop_reason text, exit_code int`, 그리고 `state` CHECK에 `stopped`·`skipped`·`lost`(감싸기가 최종 기록 없이 죽음 — 다음 실행이 생존 신호 끊김으로 판정) 추가.
   기존 `job` 칸(엔진 이름)은 그대로 두고 `ops_job`이 등록부 작업 ID다. `state`를 읽는 곳(`packages/core/lib/ops/collector.ts:75-87`)도 같은 변경에서 고친다 — 사용자 정지를 `ok`·`failed`로 뭉개지 않는다.
   ★ **DB가 막혀도 기록은 남아야 한다**(10월 디스크 가득 참 사고) — DB 쓰기 실패 시 `out/ops/runs.jsonl`에 `{run_id, seq, ...}` 사건 단위로 쓰고 다음 성공 때 옮긴다.
   옮기기는 **`run_id`로 upsert, `seq`가 더 큰 사건만 반영** — 여러 번 옮겨도, 일부가 이미 DB에 있어도 같은 실행이 두 번 생기지 않는다. 옮긴 줄은 옮김 표시 뒤 지운다. DB 관문으로 멈춘 작업이 자기 멈춤을 DB에 못 쓰는 상황이 정확히 이것이다.
5. **외부 데드맨** — 같은 PC가 꺼지면 화면도 멈춘다. 등록부 `freshness`를 가진 작업은 끝날 때 외부 감시에 성공·실패 신호를 보낸다. 후보: Healthchecks.io(무료 등급 또는 직접 설치), 또는 배포 후 EC2 쪽 작은 감시. **운영자 결정 필요(§9).** 결정 전에는 신호 전송부를 꺼 두고 내부 기록만 쓴다.

**보존할 것:** `job.ts`의 부분 실패 = `failed` + 종료 3, 운영 화면의 "관측 소실을 해소로 처리하지 않음"(`storage.ts:18`), `--work`가 바쁜 `daily.lock`을 기다리는 동작(`ck-auto.sh:44-47`, 안 그러면 .path가 무한 재시작), STOP 존중.

**확인:** 가짜 명령(0·3·4·75·130 종료, 무한 대기, 진척 파일 갱신 멈춤)으로 감싸는 실행기 시험 — 각 경우 화면 상태가 기대대로인지.
특히 **같은 종료 코드 3을 DB 관문·STOP·시간 상한으로 각각 내면 화면 이유가 셋 다 다르게** 나오는지, `stop.json` 없이 3으로 끝나면 `unknown`인지.
DB 막힘 흉내(쓰기 거부) 때 파일로 떨어지고, 복구 후 두 번 옮겨도 행이 하나인지. 워커 작업을 감쌌을 때 `job_run` 행이 하나인지.

**되돌리기:** `ExecStart` 앞의 감싸기를 지우면 원래대로. 넓힌 칼럼은 남아도 무해.

### 5.3 대기열·자원 (밀림 방지)

**근거:** 벌크헤드·우선순위 대기열 원칙, Codex "신규만 우선하면 백필이 영원히 안 돈다".

**방법**

1. 등록부 `resources`로 자원 등급을 선언한다: `riot`, `nexon`, `fc-site`, `soop-board`, `soop-vod`(HLS·목록), `asr`(전사 GPU, `.local/ck-listen/prepare.lock`), `claude`(5시간 사용량 창), `disk`. 잠금 파일은 지금 것을 그대로 쓴다 — 이름을 등록부에 적어 화면이 "누가 잡고 있나"를 보여 준다.
2. **조사 대기열은 둘로 둔다** — 자동(당일) · 백필. 정책:
   - 자동이 먼저다(당일 VOD는 보존 기간·차별점 때문에 급하다).
   - 백필은 **최소 몫**을 보장한다: 자동 대기열이 비었을 때 + 자동이 N시간 이상 점유했으면 VOD 하나 끝날 때 한 번 양보(값은 운영자 결정, §9).
   - 경보는 대기 건수가 아니라 **가장 오래 기다린 항목의 나이**로 건다(백필 요청 후 X일 진척 0 → 알림).
3. 지금처럼 같은 채널은 한 프로세스만(채널 잠금) — 유지.

**보존할 것:** 채널 잠금, `ck-backfill-par.sh`의 `SOOP_PACE=$JOBS`, `--work`의 잠금 대기, 음성 준비 잠금 대기 시간(백필 4시간).

**확인:** 대기열 시뮬레이션 단위 시험(자동이 계속 들어와도 백필이 정해진 몫을 받는다).

**되돌리기:** 정책 함수만 원래(자동 독점)로.

### 5.4 수동 백필을 정식 작업으로

**근거:** P3(스킬은 대기 작업 금지, 실제는 대기 유닛), P5(백필이 화면에 없다), 05:19 멈춤 3시간 놓침.

**방법**

1. 템플릿 유닛 `scripts/systemd/ck-backfill@.service`: 인스턴스 이름 = 요청 id, 인자는 `out/ck/backfill/requests/<id>.env`(채널·게임·기간·모델·환경)에서 읽는다. `ExecStart`는 `run-job.ts --job ck-backfill --instance %i -- scripts/ck-backfill.sh …`.
2. **잠금 대기는 실행기 안의 정해진 동작으로** — 지금 임시 유닛의 `until flock -n …; sleep 60` 고리를 `ck-backfill.sh --wait-lock`(최대 대기 시간 지정)으로 옮긴다. 기다리는 동안 상태는 `lock_busy`로 화면에 보인다.
   → `ck-backfill` 스킬의 "종료 75면 대기 작업을 만들지 않는다"를 "사용자가 요청하면 `--wait-lock`으로 기다리게 할 수 있다"로 **이 한 줄만** 고친다(운영 정책 변경이라 운영자 확인 후).
3. 시작 명령 `npm run ck:backfill -- start --streamer … --from … --to … [--game] [--wait-lock]` — 요청 파일을 만들고 `systemctl --user start ck-backfill@<id>`. `--stop`·`status`는 지금 명령 그대로.
4. 운영 화면: 백필 요청마다 기간·VOD 총수·완료·남음·접근 불가·현재 VOD·마지막 진척 시각·생존 — `ck:backfill status`가 이미 계산하는 값(`total/complete/remaining/unavailable`)을 진척 파일로 내보낸다.

**보존할 것:** 진척 = DB 도장(요청 파일은 기간 기본값일 뿐), 종료 코드 0/4/5/75/130 뜻, `CK_BACKFILL_LOCKED` 규약, 채널 잠금, `--stop`이 저장 경계에서 멈추는 동작, 클립 제외(10/15 수정).

**확인:** 짧은 기간(VOD 1~2개)으로 시작·중지·재시작·잠금 대기·재부팅 후 재개를 실제로 돈다. 지금 돌고 있는 두치와뿌꾸 FC 백필은 끝난 뒤 새 방식으로 옮긴다(중간에 갈아타지 않는다).

**되돌리기:** 템플릿 유닛 삭제, 기존 `scripts/ck-backfill.sh` 직접 실행은 그대로 동작.

### 5.5 스킬 구조 — 핵심 + 참고 파일, 규칙은 한 곳

**근거:** P1·P2·P3, Anthropic 단계별 노출 원칙. 품질 보호가 최우선 — Codex "운영 구조 변경과 조사 판단 변경을 한 번에 하지 않기".

#### 5.5.1 원칙 (4단계 전체에 적용)

1. **문장은 옮기기만 한다.** 재작성·요약·"더 명확하게 다듬기" 금지. 허용되는 편집은 ① 위치 이동, ② **똑같은 문단**이 여러 번 있을 때 하나만 남기고 나머지를 링크로, ③ 새 파일 머리의 "언제 읽나" 한 줄, ④ 본문의 "필수로 읽을 때" 색인. 규칙 내용을 바꿔야 할 일이 생기면 **별도 커밋·별도 검증**으로 뺀다.
2. **세션은 하나 그대로.** 파일만 나눈다 — 판독·해석이 한 세션 안에서 이어진다(Codex "자료 확보·판독·해석이 밀접하면 같은 세션").
3. **첫 분리는 읽는 범위를 한 줄도 줄이지 않는다**(2026-10-16 Codex 검토 1). "문장이 어딘가 남아 있다"와 "그 문장을 지금과 같은 때에 읽는다"는 다르다.
   지금 실제로 읽히는 범위를 기준으로 삼는다:
   - 스킬을 부르면 `SKILL.md` **전체**가 맥락에 들어온다. 그러니 지금은 495줄 전부가 매번 읽힌다.
   - `ck-local` 세션은 3단계에서 `ck-research/SKILL.md`를 열라는 지시를 받는다. 이름은 "네 절"이지만 파일을 열면 **전체**를 읽는다. 그래서 `handoff`(재개)·`modes`(`game_mode` 필수)도 지금 읽히고 있다.
   - 「같은 경기의 다른 시점」 절은 기존 경기가 있을 때만의 규칙이 아니다. `pov.source`·`pov.link_basis` 필수, 재송출 조건, 신원, `vod_availability`가 들어 있고 **모든 제출**에 해당한다.
   그래서 첫 분리에서 참고 파일은 **세션 시작(또는 지금 그 파일을 열던 시점)에 전부 읽는 필수 파일**이다. 본문 색인은 "이 스킬로 조사하는 세션은 다음 참고 파일을 **모두** 읽고 시작한다"로 쓴다.
   → 첫 분리의 이득은 **유지보수(어디에 무엇이 있나·같은 규칙 한 곳)**이고, 읽는 양·비용은 거의 그대로다. 이것을 숨기지 않는다.
   **조건부 읽기 전환**("이 상황이 되면 읽는다")은 읽기 범위가 실제로 바뀌는 **조사 판단 변경**이다. 품질 검증 방법이 정해진 뒤 파일별로 따로 한다(§5.5.9).
4. **참고는 본문에서 한 단계만.** 참고 파일이 다른 참고 파일을 다시 부르지 않는다.
5. **스킬 이름은 바꾸지 않는다.** 실행기·문서·사용자 습관이 이름을 쓴다. 설명(description)만 실제와 맞춘다.

- **프롬프트 출력 경로**를 만든다. 지금 `ck-auto.sh --dry-run`은 대상 목록만 만들고 `:79`에서 끝나서 프롬프트가 생기지 않는다. 그래서 0단계의 "프롬프트 비교"가 성립하지 않는다.
  `ck-auto.sh --print-prompt <vod> [--prep ok|fail] [--listen <코드>]`와 `ck-backfill.sh --print-prompt <vod> ...`를 둔다. 실제 실행과 **같은 함수**(`lol_prompt` 등)로 프롬프트를 만들어 표준 출력에 내고 끝낸다. 대기열·잠금·Claude·DB 쓰기는 하지 않는다.

#### 5.5.8 `verify:skills` (새 검사)

- 각 SKILL.md: frontmatter(name·description), 본문 500줄 이하(목표 200 내외), 링크가 실제 파일, 참고는 한 단계만(참고 파일이 다른 참고를 부르면 실패), 모든 참고 파일이 본문 색인에 등장(고아 파일 금지).
- **문장 보존 검사(4단계 전용):** 옮기기 전 스킬 전 문장의 목록을 기준선으로 저장 → 옮긴 뒤 본문+참고 전체에 같은 문장이 있는지 대조. 하나라도 사라지면 실패. 첫 분리는 지우는 문장이 없으므로 허용 목록이 비어 있어야 한다.
- **필수 읽기 범위 검사:** 지금 세션이 읽는 문장 집합(스킬 본문 전체, `ck-local` 세션은 여기에 `ck-research` 전체)이 분리 뒤 "필수로 읽는 파일"의 문장 합집합에 모두 들어 있다. 문장 보존만으로는 이것을 못 잡는다(Codex 검토 1).
- **중복 문단 검사:** 스킬·프롬프트 사이에 같은 문단(정규화 해시)이 두 번 이상이면 실패 — P1 재발 방지.
  **의도한 중복은 `ops/skills-duplicates.json`에 명시**한다(본문에도 남기는 핵심 규칙, 첫 분리에서 남겨 둔 `ck-local` 재송출 문단). 항목마다 위치들과 이유를 적는다.
  허용된 중복은 **모든 위치가 글자까지 같아야** 통과한다. 한 곳만 고치면 실패한다. 중복을 허용하되 어긋남은 막는 것이 P1의 진짜 원인(복사본이 따로 늙음)에 대한 방어다.
- 실행기 프롬프트가 부르는 스킬·절 이름이 실제로 있다.
- 한계를 적어 둔다: 이 검사들은 **글이 그대로 있고 읽히는가**까지만 본다. 필요한 순간에 규칙을 적용했는지, 어려운 사례에서 빠뜨리지 않았는지는 보지 못한다. 그것은 품질 검증(§9-6)의 몫이다.

#### 5.5.9 조건부 읽기·중복 정리 (조사 판단 변경 — 품질 검증 방법이 정해진 뒤)

- 대상: §5.5.2·§5.5.4 표의 "나중 조건부 후보", `ck-local` 재송출 문단의 가리킴 전환, 프롬프트 (나), `multi-pov.md`를 "모든 제출 규칙"과 "기존 경기와 맞추기"로 다시 나누기.
- **한 번에 하나씩**, 파일 하나 = 변경 하나 = 품질 비교 한 번. 비교 방법은 §9-6에서 정한다.
- 이득(읽는 양·비용 감소)은 이 단계에서만 생긴다. 측정한 값으로만 주장한다.

#### 5.5.10 교체 시점 — 진행 중 세션을 건드리지 않는다

- 참고 파일은 세션 **도중에** 읽힌다. 스킬 본문도 세션이 다시 열 수 있다. 그래서 "다음 세션부터 적용"이 아니다. 조사 중에 파일을 옮기거나 지우면 진행 중 세션이 없는 경로를 열거나 절반만 바뀐 규칙을 읽는다(Codex 검토 7).
- 스킬 구조 변경은 **작업 트리 밖(git worktree·별도 브랜치)**에서 만들고 검증한다. 운영 작업 트리에 합치는 순간만 문제가 된다. 조사 세션이 쓰는 작업 트리가 곧 운영 작업 트리이기 때문이다.
- 합치기는 `scripts/ops/swap-skills.sh`로만 한다. 이 스크립트는 다음 순서로 동작한다.
  1. 조사 잠금(`out/ck/auto/daily.lock`·`fc.lock`, 백필 `.lock`)을 **비차단으로 모두** 잡는다. 하나라도 바쁘면 거부하고 끝낸다.
  2. 잡은 상태에서 조사 `claude` 프로세스가 없는지 한 번 더 확인한다.
  3. 합친다(`git merge --ff-only` 등).
  4. `verify:skills`를 실행한다.
  5. 잠금을 놓는다.
  잠금을 잡고 있는 동안 새 세션은 시작하지 못한다.
- 실행마다 스킬 묶음을 복사해 고정하는 방법도 검토했다. Claude Code는 작업 디렉터리의 `.claude/skills`를 읽기 때문에 실행마다 별도 작업 트리가 필요해져 무겁다. 그래서 채택하지 않는다.

### 5.6 운영 화면

**근거:** Codex 표(알고 싶은 것 7개), SRE "증상 중심·사람이 할 일".

**방법:** `model.ts`의 하드코딩 `JOBS`를 생성 등록부로 바꾸고, 각 작업 카드가 아래를 답하게 한다.

| 질문 | 표시 | 데이터 |
|---|---|---|
| 오늘 할 일이 실행됐나 | 예정·실제 시작·마지막 성공 | 등록부 `freshness` + 실행 기록 |
| 지금 실제로 움직이나 | 실행 중·마지막 생존 신호·마지막 진척 | heartbeat · progress |
| 무엇이 얼마나 남았나 | 대기 건수·가장 오래된 항목 나이·백필 남은 VOD | 대기열·진척 파일 |
| 왜 멈췄나 | 멈춘 이유 분류(§5.2-3) | stop_reason |
| 서비스 영향 | 빠진 회차(시한부 수집: 랭크·구단가치)·오래된 데이터·**롤 자동 조사 정지 = 차별점 위험** | 등록부 `critical`·`freshness` |
| 내가 할 일 | 자동 재시도 예정 / 재개 필요 / 검토 필요 / 설정 수정 | 이유 → 조치 표 |
| 이 표시를 믿어도 되나 | 마지막 관측 시각·관측 불가 | 수집 시각, 외부 데드맨 |

**정상 판정은 작업 종류마다 다르다.**
- 주기 수집(랭크·구단가치 등): 최근 성공이 `freshness` 안에 있으면 정상이다.
- **조사 작업**(`ck-auto-lol-work`·`ck-auto-fc`·백필): 최근 실행만으로는 정상이 아니다. 등록부 `health` 세 가지로 판정한다.
  - 대기 건수
  - 가장 오래된 대기 항목의 나이
  - 실제 진척(`vodWork` 완료 수가 늘었나)
  
  판정:
  - 대기가 있는데 진척이 정해진 시간 동안 없으면 **"조사 정지"**다. 목록 확인이 성공하고 있어도, 감싸기 생존 신호가 있어도 마찬가지다.
  - 대기 0 + 진척 0은 "할 일 없음"이다. 정지가 아니다.
- 그룹 카드(`display_group`)는 소속 작업 중 **가장 나쁜 상태**를 보인다. 목록 확인 정상 + 조사 정지면 그룹은 "조사 정지"다.

**보존할 것:** 아직 안 돈 작업에 성공 시각을 만들지 않음, 관측 소실 ≠ 해소, 처리 0건 ≠ 실패, STOP 존중.

## 6. 품질 불변식 — 어떤 단계도 이것을 바꾸지 않는다

구조 변경 커밋마다 이 목록을 대조한다. 바꿔야 하면 별도 결정·별도 커밋.

### 6.1 진척·완료

1. 진척의 출처는 `event_lead.raw.scan`/`fco_scan` 하나, 판정은 `vodWork` 하나. 롤·FC 도장은 따로.
2. `done` = 필수 탐색 완료이지 값 확정이 아니다. `opened` 비었거나 요청 범위가 끝 5초 전까지 안 닿으면 `partial`.
3. 예산 소진·"더 볼 것 없음" 메모는 `done` 조건이 아니다. 미해결을 `not_target`으로 바꾸거나 지우지 않는다.
4. 결과 진척 없는 세션 3회 → 멈춤(가드), 재실행에도 유지.
5. FC `done`은 음성 필수 창 관문을 통과해야 한다(`fco-context.ts:522-542`).

### 6.2 근거

6. 뽑은 프레임은 읽은 프레임이 아니다. 연 것만 근거(`scan.opened`/`frames[].read`). 뽑은 프레임은 전부 연다.
7. 결과창 탐색은 판마다 네 종료 사유 중 하나에 닿을 때까지. 가려진 결과창은 앞쪽 보완 탐색까지.
8. 결과 판독의 우선 근거는 최종 결과 화면. 공지·오버레이·전사는 탐색·맥락용. 음성은 화면 판독값을 덮지 않는다.
9. 다른 시점은 이 화면에서 직접 읽은 칸만 낸다. 생략 = 안 읽음, `0` = 읽은 값, `null` = 철회. 일치는 도구가 계산한다.
10. 재송출은 방송 주인이 그 경기·같은 시리즈·같은 대회 참가자일 때만. 무관한 방송은 `not_target` + 관찰만.
11. 합격선("N장이면 됐다")·자동 결론("후보 둘이면 제외")을 만들지 않는다.
12. 경기 0 ≠ 경기 없음. FC 화면 부재 ≠ 부정 증거.

### 6.3 저장·공개

13. `ck:merge`·`fco:context apply/screen/scan`이 유일한 저장 창구. 한 파일 = 한 트랜잭션. 재전송은 중복을 만들지 않는다.
14. 검수된 경기·admin 판단은 자동 수집이 못 덮는다(⏭를 성공으로 세지 않는다).
15. 새 경기 `match`는 `game_mode` 필수(칼바람 `ARAM`), `played_at_precision` 필수, `result_evidence` 필수, 승자 모르면 경기로 넣지 않는다.
16. 랜드·보너스 판 규칙, `event.name`에 날짜 금지, 기존 대회는 slug만, 새 대회는 name+kind 필수.
17. FC: 초안부터(빈 파일 금지), 닉네임 한 글자씩, 결과 화면 필수, `best_of`는 화면·공지 근거로만, 상대가 바뀌면 시리즈 아님.
18. 공개 정책: CK 즉시 공개 · FC 화면 경기 숨김 후 검수 · 편성표 검토 후보까지.

### 6.4 실행 안전

19. 채널당 한 프로세스, API 출처별 잠금 공유, `fco-club` 잠금 순서, 루프와 타이머 동시 금지.
20. 무인 세션: `</dev/null`, `--no-session-persistence`, 자동 메모리 끔, 세션별 `--model`(전역 설정 불변), 세션 예산·이미지 예산.
21. 예산 한도·이미지 플러시(20)는 정상 인계, 진척은 DB로 재판정. DB 관문은 회차 시작과 세션마다, 쓰기 차단 플래그는 실행 중 세션도 멈춘다.
22. `--work`는 바쁜 `daily.lock`을 기다린다. 실패·정지는 `pause`로 wake를 지운다.
23. 시한부 수집(랭크·구단가치·넥슨 30일)은 `Persistent=true` 유지.

| 참고 파일로 옮긴 규칙을 세션이 안 읽는다 | 첫 분리는 참고 전부를 시작 때 필수로 읽음(§5.5.1-3), 필수 읽기 범위 검사, 첫 VOD 세션 기록에서 실제 열람 확인, 핵심 규칙은 본문에도 남김(뽑음≠읽음·종료 사유·결과 화면 필수·근거=연 것 전부) |
| 옮기다 문장이 빠진다 | 문장 보존 검사(기준선 대조) |
| 문장은 다 있는데 조사 품질이 떨어진다 | 검사로 증명할 수 없음을 인정한다 — 스킬 구조 변경은 품질 검증 방법이 정해지기 전에는 운영에 넣지 않는다(§7 4단계) |
| 같은 종료 코드를 잘못 해석해 장애를 "사용자 정지"로 보인다 | 이유는 실행기 분기가 직접 남김, 없으면 `unknown`(§5.2-3), 검사가 빠진 분기를 잡음 |
| 목록 확인 성공이 조사 정지를 가린다 | 작업을 나눠 등록, 조사는 대기·진척으로 판정, 그룹은 나쁜 쪽(§5.1·§5.6) |
| 한 실행에 기록이 둘 생기거나 최종 상태가 엇갈린다 | 실행 ID, 기록 주인은 감싸는 실행기 하나, 파일 기록은 `run_id` upsert(§5.2-4·5) |
| 조사 도중 스킬 파일이 바뀐다 | 작업 트리 밖에서 준비, 조사 잠금을 모두 잡고 교체(§5.5.10) |
| 파일이 짧아진 것을 개선으로 착각한다 | 비용·속도·정확도 주장은 측정 뒤에만(§0) |
| 등록부가 또 하나의 손으로 맞추는 목록이 된다 | 설치기·운영 화면이 등록부를 **읽게** 하고, 주인 없는 유닛을 검사가 실패시킨다 |
| 감싸는 실행기가 원래 종료 코드·신호를 바꾼다 | 투명 전달 시험(0·3·4·75·130·TERM) |
| DB 막힘 때 기록이 사라진다 | 파일 대체 기록 |
| 공통 고리 추출이 자동/백필의 미묘한 차이를 지운다 | 생성 프롬프트·명령 줄 diff, 기존 셸 시험 |
| 이전이 중간에 멈춰 두 벌이 남는다 | 단계마다 옛 경로 제거를 완료 기준에 포함 |

## 9. 운영자 결정이 필요한 것

1. **외부 데드맨** — Healthchecks.io 무료 등급 / 직접 설치 / 배포 후 EC2 감시 / 당분간 없음.
2. **백필 몫** — 자동 대기열이 빌 때만 / 자동이 N시간 넘게 점유하면 VOD 하나마다 양보(N=?).
3. **백필 잠금 대기** — 75일 때 기다리게 하는 것을 정식 동작으로 인정(스킬 한 줄 변경).
4. **`ck-local` 설명 변경** — "기본 롤 조사 스킬"로 바꾸면 사람의 수동 롤 조사 요청도 ck-local로 간다.
5. **`soop-community` 설치 시점** — 가입을 열 때(현행 계획) 유지 여부.
6. **품질 검증 방법** — 스킬 구조 변경(4다·4라)을 운영에 넣는 관문(평가 VOD 세트 등). 이 문서 밖에서 정한다. **정해지기 전에는 4다·4라를 운영에 넣지 않는다.** 0~3단계와 4가·4나는 이것 없이 진행할 수 있다.
