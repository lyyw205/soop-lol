# SOOP SEEK 출시 전 검증 — 2026-10-15

## A. 최종 판정

**수정 후 출시 가능 — 현재 출시 승인 불가.** 깨끗한 환경의 npm ci가 lockfile 누락으로 실패하며, 도메인·실제 OAuth·문의 수신·AWS/로컬 작업 소유권이 아직 확정되지 않았고, 의존성 보안 경고와 운영 도구의 안전성/검증 공백이 남아 있다. 코드 구조 전체를 다시 설계할 근거는 발견하지 않았다.

사용자 결정: LoL·FC·커뮤니티 가입 모두 출시 범위. AWS에는 웹 및 서버 실행 가능한 수집을 올리고 CLI 의존 조사는 로컬 유지. 도메인은 `soopseek.com` 또는 `soop-seek.com` 검토 중. Supabase는 유료 전환 완료. 문의는 기존 hotplace-map의 도메인 메일 전달 방식을 차용하며 최종 주소는 나중에 확정한다.

### 범위와 해석

- 현재 미커밋 변경을 포함한 작업 트리를 기준으로 조사했다. 기존 변경은 보존했고, 커밋·배포·운영 DB 쓰기·파일 대량 삭제는 하지 않았다.
- Git 추적 및 ignore되지 않은 미추적 파일 **2,695개**, 텍스트 **1,077개 / 141,617줄**을 목록화·해시·참조/위험 패턴 검색했다. 이는 모든 줄의 의미를 수작업으로 증명했다는 뜻이 아니다. 인증·공개 경계·수집·병합·마이그레이션·보관·운영 진입점은 코드를 따라 정밀 검토했다.
- 문서·시안 자료·스크립트 **454개**의 역할/보존 분류: [FILE-REVIEW.tsv](FILE-REVIEW.tsv). 문서 본문·목차·상태·관련 코드와 실행 명령을 교차 확인했다. 참조 수 0은 자동 삭제 근거가 아니다(수동 호출·문자열 조립 가능).
- `node_modules`, `.git`, 빌드 캐시, ignored 원본/모델의 내부 전체는 코드 전수 목록에서 제외했다. 이들은 용량·의존성·배포 포함 여부·보존 위험으로 별도 조사했다. 심볼릭 링크 밖 외장 원본 전체의 무결성은 검사하지 않았다.
- 로그·초기 파일 상태·SHA256 목록·읽기 전용 DB 결과·스크린샷: `out/release-audit/`. 이 경로는 gitignore이므로 장기 증거가 필요하면 별도 보관한다. 감사용 production 서버/임시 DB와 임시 clean-install 폴더는 종료·정리했고, 별도 빌드 캐시 약 314MB도 제거했다. 인증 정보/DB 연결 문자열을 보고서에 싣지 않는다.
- [원본+확장 체크리스트](CHECKLIST.md)는 원본 1~8절을 보존하고 9~15절을 추가했다(총 115개 점검 항목). 아래 결과표가 이번 실행의 판정 정본이다.

## B. 출시 전 필수 해결 및 검증

### B0. 새 서버에서 npm ci 실패 — workspace lock 누락

- 근거: `packages/modules/cam_link/package.json`에는 `@soop-lol/module-cam_link@0.1.0`이 있지만 `package-lock.json`에는 대응 workspace/link 항목이 없다.
- 재현: 현재 소스와 manifests/lock을 환경파일·node_modules 없는 임시 디렉터리에 복사해 `npm ci` 실행 → **EUSAGE, Missing: @soop-lol/module-cam_link@0.1.0 from lock file**, 종료코드 1. `clean-install.log`, `clean-checks.json`.
- 기존 node_modules로 production build가 통과하는 것과 별개다. fresh build는 설치 실패로 진입하지 못했다. 임시 디렉터리는 정리했다.
- 수정 방향: 기존 버전이 뜻하지 않게 갱신되지 않도록 lockfile의 workspace 항목을 동기화하고 diff를 검토한다. B1 보안 패치와 변경 이유를 구분한다.
- 완료 조건: node_modules 없는 임시 복사본에서 npm ci → typecheck/test/build. 원본 작업 폴더의 의존성은 이번 감사에서 재설치하지 않았다.

### B1. 의존성 경고 — 설치 패키지 3개, critical 1 / high 2

- 근거: `apps/web/package.json:18`의 Next 16.3.0, `package-lock.json`; `out/release-audit/npm-audit.json`.
- `npm audit`는 Next, sharp, source-map-js를 보고했다. Next에는 여러 advisory가 묶여 있다. **취약 버전 탐지와 이 서비스에서의 공격 성공은 다르다.** 공격 재현은 수행하지 않았다.
- 유지보수자 공지 대조: [AVIF 최적화 RCE](https://github.com/vercel/next.js/security/advisories/GHSA-2xp9-vwfh-vxw4), [next/og RCE](https://github.com/vercel/next.js/security/advisories/GHSA-vcvr-r3jv-pc5j), [Windows 서버 RCE](https://github.com/vercel/next.js/security/advisories/GHSA-p293-qw3h-jr36), [이미지 SSRF](https://github.com/advisories/GHSA-cjq9-62q9-8jv4), [sharp](https://github.com/advisories/GHSA-rgj7-g3m4-5g8c), [source-map-js](https://github.com/advisories/GHSA-68fv-2mgg-jv7q).
- 현재 `remotePatterns`는 비어 있어 해당 SSRF 공지의 영향 조건에 해당하지 않는다. `next/og`, draftMode/use-cache 사용은 검색에서 발견하지 않았다. Windows 서버 항목은 Linux 배포라면 해당 조건이 아니다. 반면 `next/image` 및 관리자 sharp 축소 경로는 사용한다.
- 수정 방향: 현행 minor의 보안 수정 버전 및 전이 의존성을 검토해 **명시적인 버전/lock 변경**으로 처리한다. 자동 `npm audit fix --force`는 하지 않는다. 당시 audit 범위상 Next 16.3.8 이상, sharp 0.35.5 이상, source-map-js 1.2.2 이상이 필요하지만 실제 선택 시 다시 공지를 확인한다.
- 완료 조건: 깨끗한 설치, production build, 관리자 인증/이미지, 공개 화면, OAuth/서버 액션 회귀 및 audit 재실행. 경고를 수용한다면 영향 조건과 수용 이유를 남긴다.

### B2. 실제 가입은 아직 열 수 없는 설정 상태

- 근거: `packages/core/lib/auth/oauth.ts:31`, `apps/web/lib/site-origin.ts:13`, 두 auth route, `out/release-audit/env-presence.json`.
- 로컬 설정에서 카카오·구글 client ID와 SITE_ORIGIN 모두 미설정. 관리자 비밀번호는 설정됨. 이는 AWS 설정 상태를 확인한 결과는 아니다.
- 발생 조건: 현재 환경 그대로 배포하면 로그인 제공자 버튼이 없다. production SITE_ORIGIN 누락 시 `siteOrigin()`은 경고 후 요청 origin으로 대체한다.
- 수정 방향: 대표 도메인 하나 확정 → HTTPS → 제공자 앱 등록/승인 → 정확한 callback → 역할별 환경변수 주입. 개발용 가짜 제공자 설정이 운영에 들어가지 않게 배포 검사한다.
- 완료 조건: 실제 두 제공자로 가입·취소·재로그인·탈퇴·재가입 제한, 다른 브라우저, 프록시 뒤 Server Action Origin/쿠키를 확인한다. 로컬 가짜 OIDC 시험은 아래 D절과 구분한다.

### B3. 공개 문의·정책 문구 미완성

- 근거: `apps/web/app/privacy/page.tsx:30` 위탁 문구, `:32` 연락처 placeholder. `components/site-footer.tsx:22`는 문의를 안내하지만 실제 연락 경로가 없다.
- 사용자 결정: 개인 주소를 곧바로 공개하지 않고 최종 도메인의 문의 주소로 전달받는다.
- 차용 근거: 인접 저장소 `hotplace-map/docs/apps-in-toss-console-fields.md:390`에 `help@hotplacemap.kr`의 ImprovMX 수신 확인 기록이 있다. 이 기록은 당시 설정이며 현재 서비스 요금/발신 기능을 보장하지 않는다.
- 수정 방향: `help@<대표 도메인>` 같은 최종 주소를 정한 뒤 전달·수신·답장 경로 시험 → 약관/방침/푸터 단일 설정으로 연결. AWS 사용을 포함한 실제 위탁/처리 구조와 공개 문구를 대조한다.
- 완료 조건: placeholder 0건, 실제 수신 확인, 계정 비노출/정정 요청 처리 가능. 법률 적합성 전문 검토는 이번 코드 감사의 통과 판정에 포함하지 않았다.

### B4. AWS/로컬 실행 소유권과 근거 파일 접근 미확정

- 근거: `scripts/systemd/*.service`의 `%h/repos/soop-lol`, `scripts/systemd/install.sh`, `apps/worker/src/main.ts:143`, `scripts/lib/soop-board-gate.mjs:4`, `app/admin/ck/frame/[...path]/route.ts:39`, `app/admin/office/status/route.ts`.
- 발생 조건: AWS에서 worker loop를 켠 채 로컬 데이터 타이머를 유지하면 같은 잡이 두 호스트에서 돈다. flock·쿨다운은 로컬 파일이라 호스트 간 중복을 막지 못한다. AWS에는 로컬 CK 파일과 systemd 관측 결과가 없다.
- 권장 배치: AWS = 웹, Riot/FC 일반 수집, 커뮤니티 파기; 로컬 = Claude CLI/VOD/ASR/공지 분석. SOOP 게시판 관문을 공유해야 하는 조사들은 한 호스트에 둔다. 최종 배치는 실행 주기·키 예산과 함께 확정한다.
- 완료 조건: 잡별 담당 호스트/주기/잠금 표, 서버 이동 후 해당 로컬 타이머 중지, 중단/복귀 시험. 관리자 검수는 로컬 유지 또는 인증된 비공개 파일 전달 중 선택한다. 공개 `public/`에 판독 근거를 넣지 않는다. 오피스 스냅샷도 출처·시각을 보존해 전달한다.

### B5. 개발 시안이 공개 배포 경로에 있음

- 근거: `apps/web/public/design-lab/` **약 37MB**. 임시 production 서버에서 `/design-lab/arena.html` **200** 재현.
- 내용: 디자인 비교 HTML/JS, 가상 전적 데이터, 참조 화면·프롬프트/출처 파일. 운영 앱의 TS/TSX에서 이 경로에 대한 직접 의존은 발견하지 않았고 디자인 문서에는 링크가 있다.
- 수정 방향: 별도 로컬 preview 디렉터리/서버로 옮기고 참조를 갱신하거나 배포 staging에서 제외한다. 출처·라이선스 원본은 비공개 개발 자료로 보존한다.
- 완료 조건: production `/design-lab/*` 404, 실제 `/images` 및 폰트 정상, 디자인 검토 재현 경로 유지. 파일을 바로 삭제하지 않았다.

### B6. 마이그레이션 CLI의 읽기/인자/동시 실행 계약

- 근거: `scripts/migrate.ts:39`~`:42`, `:52`, `:90`, `:118` 및 이후 적용 루프.
- `--status`도 먼저 CREATE/ALTER를 실행한다. 따라서 진짜 읽기 전용 검사로 사용할 수 없다. 이번 실제 DB 조회는 별도 READ ONLY 트랜잭션으로 수행했다.
- `--baseline`만 주고 값을 빠뜨리면 baseline이 undefined가 되어 일반 적용 분기로 간다. 알 수 없는 플래그도 거부하지 않는다. `--status --adopt`는 adopt 분기가 먼저 실행된다. 코드 흐름으로 확인했으며 운영 DB에서 재현하지 않았다.
- 러너 전체를 직렬화하는 잠금도 없어 두 배포가 동시에 pending을 읽고 DDL을 실행할 가능성이 있다(이번에 경합 재현은 하지 않음).
- 수정 방향: DB 연결 전 엄격한 인자 검증/상호 배타 옵션, status 전용 SELECT 경로, 마이그레이션 실행 직렬화. 테스트는 폐기 가능한 DB에서 실제 CLI로 수행한다.
- 완료 조건: 잘못된 인자에서 DB 접속 0회, READ ONLY에서 status 성공, 동시 실행 한 쪽 대기/거부, 중간 실패 후 재시도와 장부 일치.

### B7. 백필 통합 시험의 파일 상태 격리 실패

- 근거: `scripts/verify-ck-backfill.ts:77`~`:96`, `scripts/lib/soop-http.mjs:147`, `scripts/lib/soop-board-gate.mjs:4`.
- 실제 결과: 초기 plan CLI가 종료코드 1, 33.8초에 실패. child에는 30초 제한이 있다. HTTP 응답은 대체하지만 새 boardGate는 저장소의 실제 `out/locks/soop-board`를 공유하고 최소 20초 간격을 강제한다. SOOP_PACE를 줄여도 이 하한은 남는다.
- 이 구조는 운영 중 조사와 시험이 같은 쿨다운 파일을 갱신하게 한다. 실제 HTTP 요청을 했다는 뜻은 아니다.
- 수정 방향: 테스트 전용 디렉터리/시계 또는 주입 가능한 관문 경계를 제공하되 production의 20초 보호는 유지한다. child 실패의 stdout/stderr를 assertion에 포함한다.
- 완료 조건: 운영 lock/state 파일 해시 변화 0, 가짜 HTTP 외 네트워크 요청 0, 백필 전체 왕복 통과. 이 시험은 아직 실패이며 통과로 계산하지 않는다.

### B8. 원본 보관 도구의 경쟁·실패 복구

- 근거: `scripts/ck-archive.ts:76`~`:103`. 완료 여부를 한 번 조회한 뒤 파일 목록을 만들고, 크기만 대조해 rename→symlink→원본 삭제. 자동/백필의 채널 잠금을 취하지 않는다.
- 발생 조건: 복사 동안 재조사/다른 프로세스가 파일을 추가·수정하면 목록 밖 파일 또는 복사 이후 변경이 삭제될 수 있다. symlink 실패 시 원본은 `.archiving`에 남지만 기존 경로는 사라지고 다음 실행은 숫자 디렉터리만 찾으므로 자동 복구하지 않는다. 조건부 코드 위험이며 실제 원본으로 파괴 시험하지 않았다.
- 수정 방향: 수집기와 동일한 잠금, DB 상태 재확인, 내용 hash/원본 변경 검증, `.archiving` 복구 journal. 이미 보관된 근거의 링크도 확인한다.
- 완료 조건: 쓰기 경합·중간 종료·마운트 이탈·symlink 실패 주입 시험에서 근거 유실 0. 이 개선 전에는 이번 25GB out 폴더 정리에 일괄 사용하지 않는다.

### B9. 실제 동시성·부하·배포 복구 검증 공백

- 실제 PostgreSQL의 initdb/pg_ctl과 CK_PG_BIN이 이 환경에 없어 `verify:ck:concurrency`, `verify:ck:browser`는 실행하지 않았다. PGlite를 대체 통과로 표시하지 않는다.
- 커뮤니티 계획의 동시 글쓰기/탈퇴/신고·파기 시험은 실제 PostgreSQL 다중 연결 검증이 별도로 필요하다. 현행 `verify:ck:concurrency`는 CK 경합 시험이며 커뮤니티 경합까지 보장하지 않는다.
- AWS 실배포, 프록시 Origin, 실제 OAuth, 부하 p95/DB 풀 대기, 백업 복원 및 롤백은 미검증. 단일 사용자·작은 fixture의 200 응답을 이 항목의 통과로 보지 않는다.
- 완료 조건: 폐기 가능한 PostgreSQL 설치/CI 작업으로 동시성 시험, 배포 환경에서 부하/복원 훈련, 실제 사용 규모와 허용 응답시간 기록.

## C. 권장 개선

1. **UUID 입력 검증**: `schedule-public.ts:82,89`, `opponent-history-action.ts:8`의 `/^[0-9a-f-]{36}$/`는 하이픈 36개를 통과시킨다. PGlite에서 같은 입력의 UUID cast가 `22P02`임을 재현했다. 표준 UUID 형식 검사로 404/잘못된 조건 응답을 내고 DB 오류로 흘리지 않게 한다. 개인정보 유출은 확인되지 않았다.
2. **검색·공유 메타데이터**: 현재 metadataBase/canonical/OG/sitemap/robots 파일을 발견하지 않았다(관리자 layout noindex는 있음). 도메인 확정 후 공개 범위를 정해 추가한다. 데이터가 숨겨졌을 때도 생성 경로가 같은 공개 정책을 써야 한다.
3. **버전/실행 정본**: 루트 package는 고정 버전 원칙을 쓰지만 PGlite 2개는 `^` 범위다. worker 설명은 Node 24, README는 22.23+, 실제 검증은 22.23.2다. 지원 버전/engines와 lock 재생성 정책을 정리한다.
4. **검증 자동화**: npm test는 TS 테스트만 포함한다. Python 6개 파일과 `.test.mjs`, 통합/browser는 별도다. CI/검증 명령 목록에 포함하되 동일 시험을 중복 실행하지 않는다. lint 명령/설정은 없어서 lint 통과를 주장하지 않는다.
5. **현재 상태 문서**: SETUP의 2026-08-09 표(15개 테이블/57개 테스트), CLAUDE의 최신 운영 표와 오래된 '내전은 2단계' 문장, FC 구단가치 계획의 '타이머는 배포 때'와 현재 systemd가 충돌한다. 날짜별 이력은 남기고 현재 운영 지침과 분리한다.

### 연결된 DB 읽기 전용 대조

- `BEGIN READ ONLY` + statement_timeout 20초 안에서 SELECT만 실행했다(`live-readonly.json`). 마이그레이션 CLI의 --status는 쓰기가 있어 사용하지 않았다.
- 파일/장부 **88개 일치**, pending 0, checksum 차이 0. public 테이블 **69개**, RLS 비활성 0. core_public 뷰 **39개**. public/core_public SECURITY DEFINER 함수 0.
- DB 자체 **532,499,603 bytes**. default_transaction_read_only=off. 사용자 유료 전환 확인 및 로컬 운영 `DB_QUOTA_MB=8000` 확인. 무료 한도 초과로 출시 차단이라고 판정하지 않는다.
- 이 크기는 현재 DB만이며 템플릿·WAL·물리 디스크·대시보드 사용량 전체가 아니다. Supabase 실제 요금/프로젝트 설정이나 AWS 환경 주입값을 이번 조회로 증명하지 않는다.
- RLS ON은 앱 소유자 연결의 공개 정책 검사를 대신하지 않는다. 공개 뷰/DTO 회귀 결과와 함께 해석한다. 실제 anon REST 권한 공격 시험은 하지 않았다.

## F. 개발자 전달용 완료 기준

전체 재설계보다 현행 공개 정책·공용 계산·검수 모델을 유지하면서 경계를 보완한다. 단위/빌드 통과만으로 출시 완료로 처리하지 않는다. B0~B9의 해결 또는 명시적 수용 근거, 실제 두 OAuth 가입 왕복, 공개 정책 문구·수신 확인, 호스트별 잡 소유권, 백업 복원 증거가 필요하다. 폴더는 운영 코드 / 현행 문서 / 역사·시안 / 로컬 원본·상태 / 재생성 캐시로 나누되, 유일한 판독 근거와 현재 미커밋 작업을 먼저 보존한다.
