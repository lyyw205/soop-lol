# 출시 전 전체 아키텍처 점검표 — SOOP SEEK

> 원본 작성: 2026-09-21 · 프로젝트 적용: 2026-10-15  
> 용도: 기능 계획안·대규모 수정·마이그레이션·수집 파이프라인 변경을 구현 전과 구현 후에 검토한다.

원본: `onair-map/docs/plans/architecture-review-checklist.md`. 원본 1~8절을 보존하고, 아래 9~15절을 추가했다. 원본의 코스·음식·좌표 예시는 이 프로젝트에서는 경기·참가자·계정·VOD·일정에 대응한다. 원본 파일은 수정하지 않았다.

이번 실행 결과와 미완료 항목은 [검증 보고서](REVIEW-2026-10-15.md)에 기록한다. 체크박스는 다음 검증에도 재사용하는 기준이며, 공란을 실패 또는 미실행으로 일괄 해석하지 않는다.

## 사용 원칙

- 계획안만 읽고 판단하지 않는다. 실제 호출자, 타입, API, DB/RPC, 마이그레이션, 수집 도구, UI, 테스트까지 따라간다.
- 계획에 적힌 파일만 보지 않는다. 값을 만드는 곳부터 손님 화면에 보이는 곳까지 추적한다.
- “이미 해결됨”, “영향 없음”, “안전함”은 코드·테스트·실제 데이터 중 하나로 확인된 경우에만 쓴다.
- 추측은 추측이라고 표시한다. 확인하지 않은 실 DB 상태나 브라우저 동작을 사실처럼 말하지 않는다.
- 작은 수정이라도 기존 규칙을 복제해 새 문지기를 만들지 않는지 본다.
- 발견만 하고 끝내지 않는다. 문제마다 수정 방향과 필요한 검증을 적는다.

## 1. 근본 해결 여부

- [ ] 증상만 가리는 조건문·예외 처리가 아니라, 데이터 모델 또는 책임 분리가 원인을 해결하는가?
- [ ] 같은 문제가 import, 관리자 직접 수정, 공개 API, 캐시, 배치 스크립트 등 다른 경로에서 다시 생기지 않는가?
- [ ] 한 개념에 정본(source of truth)이 하나인가? 예: 코스 공개 상태, 음식의 소속, 장소의 공개 상태.
- [ ] 같은 업무 규칙을 화면·API·RPC·공개 조회가 각각 다시 판단하지 않는가?
- [ ] 업무 규칙과 데이터 안전장치를 구분했는가? 공개 정책은 중복하지 않고, FK·권한·형식·트랜잭션 보호는 유지하는가?
- [ ] 기능을 위해 새 상태·테이블·사본을 추가했다면 기존 모델로 표현할 수 없는 사실이 무엇인지 설명되는가?

## 2. 전체 데이터 흐름

각 변경은 아래 흐름을 실제 파일과 함수 이름으로 한 줄씩 연결한다.

```text
입력/조사 → 파싱 → 병합 → 저장/RPC → DB → 관리자 검수/수정 → 공개 API/캐시 → 공개 UI
```

- [ ] 입력 타입과 파서가 새 값·null·빈 배열을 정확히 구분하는가?
- [ ] 병합·재가져오기에서 사용자가 고친 값, 명시적으로 비운 값, 아직 모르는 값을 구분하는가?
- [ ] 저장 결과가 호출자에게 충분히 반환되는가? 새 ID, revision, 상태, 영향 받은 캐시 키 등.
- [ ] API 요청 타입·서버 매퍼·DB JSON/RPC 인자·공개 DTO의 필드명이 일치하는가?
- [ ] 공개 조회가 저장된 상태를 몰래 뒤집거나, 관리자 화면과 다른 기준으로 숨기지 않는가?
- [ ] 값이 조용히 버려지는 `undefined`, 누락 select, fallback, `continue`, no-op 비교가 없는가?
- [ ] 캐시 무효화가 실제 변경 범위를 덮되, null ID나 다른 편의 키를 보내지 않는가?

## 3. DB·마이그레이션·동시성

- [ ] NOT NULL, UNIQUE, FK, CHECK, trigger, RLS/권한이 현재 제품 규칙과 맞는가?
- [ ] DB 제약이 화면의 편의 규칙을 중복해서 심사하는 것이 아니라, 데이터가 깨지는 경우만 막는가?
- [ ] 기존 설치에서 새 마이그레이션을 순서대로 적용할 수 있는가?
- [ ] 신규 설치와 기존 DB 업그레이드가 같은 스키마가 되는가?
- [ ] 기존 데이터 이관은 ID, 순서, 판정, 사용자 메모, 외래키를 보존하는가?
- [ ] 이관은 재실행해도 안전한가? 중간 실패 후 재시도할 수 있는가?
- [ ] 삭제·재추가·이름 변경·순서 변경·재조사에서 키와 연결이 불필요하게 새로 발급되지 않는가?
- [ ] revision/낙관적 동시성은 실제 동시 편집만 막는가? 행 수만큼 revision이 오르지는 않는가?
- [ ] 트리거·RPC·권한 변경 뒤 오래된 함수, 인덱스, 권한, 테스트 fixture가 충돌하지 않는가?

## 4. UI·API·도메인 규칙의 일관성

- [ ] 관리자에서 “포함”이라고 보이는 데이터가 공개 화면에서도 동일하게 보이는가?
- [ ] 화면의 경고는 안내인지 실제 저장 차단인지 명확한가? 안내가 별도 문지기가 되지 않았는가?
- [ ] 공개 여부, 지도 표시 가능 여부, 검색 가능 여부처럼 다른 의미의 상태를 하나의 조건으로 묶지 않았는가?
- [ ] 예: 코스 공개와 좌표 존재, 음식 공개와 장소 연결, 목적지 필터와 경유지는 각각 독립적으로 판단되는가?
- [ ] null/미상 데이터가 정상일 때 화면이 빈 제목, 깨진 링크, 가짜 지도 점, 잘못된 자동 선택을 만들지 않는가?
- [ ] 데스크톱·모바일·키보드·딥링크에서 같은 항목을 같은 ID로 선택하는가?
- [ ] 목록·상세·지도·공유 페이지가 같은 순서와 동일한 공개 데이터를 사용하는가?

## 5. 부작용과 예외 상황

- [ ] 빈 값, 명시적 삭제, 중복, 재방문, 이름 변경, 시간 교정, 순서 변경을 확인했는가?
- [ ] 장소 미상, 좌표 미상, 여러 영상, 기내식·간식처럼 연결할 코스가 없는 음식도 정상값으로 다뤄지는가?
- [ ] 이미 공개된 데이터의 재검수·재가져오기에서 사람의 제외·포함·메모가 되돌아가지 않는가?
- [ ] 부분 조사·부분 실패가 기존 데이터를 삭제하거나 판정을 무르는가?
- [ ] 네트워크 재시도·응답 유실·중복 요청에서 중복 행 또는 반쪽 저장이 생기지 않는가?
- [ ] 다른 탭·다른 운영자의 동시 편집에서 원인을 알 수 있는 충돌 응답이 나오는가?
- [ ] 기존 공개 데이터와 새 데이터가 다른 규칙으로 동작하지 않는가?
- [ ] 비공개 장소·검수 근거·운영 메모가 공개 API, 캐시, sitemap, 검색 결과로 새지 않는가?

## 6. 성능·보안·운영

- [ ] 변경 한 번에 전체 삭제·재삽입, N+1 조회, 불필요한 전체 캐시 삭제가 생기지 않는가?
- [ ] 반복 import가 필요한 행만 갱신하고, DB 트리거가 행 수만큼 비용을 만들지 않는가?
- [ ] 공개 API가 필요한 최소 컬럼만 읽으며 내부 키·근거·관리자 상태를 싣지 않는가?
- [ ] service role, RPC 실행 권한, RLS, 관리자 인증의 경계가 유지되는가?
- [ ] 실패 메시지가 운영자가 원인과 복구 방법을 알 수 있을 만큼 구체적인가?
- [ ] 운영 DB에 fixture를 쓰는 테스트를 실행할 가능성을 기술적으로 막았는가?
- [ ] 실 DB 이관 전 백업, 대상 개수 대조, 실패 시 복구 절차가 있는가?

## 7. 테스트 검증

- [ ] 새 규칙을 먼저 실패하는 단위 테스트로 재현했는가?
- [ ] 파서 → import → DB → 관리자 저장 → 공개 읽기까지 한 번은 왕복 시험했는가?
- [ ] 새 설치와 기존 버전에서의 업그레이드 마이그레이션을 모두 시험했는가?
- [ ] 기존 동작의 핵심 수치(공개 코스·음식 수, 순서, ID, 지도 점)를 전후 비교했는가?
- [ ] UI 변경은 실제 브라우저에서 데스크톱·모바일로 확인했는가?
- [ ] 테스트가 실제 운영 DB가 아닌 폐기 가능한 DB에서 실행되도록 보장되는가?
- [ ] 타입체크·lint·관련 단위·스키마·상호작용 테스트 결과를 구분해 기록했는가?
- [ ] 통과하지 못한 검사가 있다면 범위와 이유를 명시했는가?

## 8. 오버엔지니어링 검토

- [ ] 현재 문제에 꼭 필요하지 않은 테이블, 필드, 상태, RPC, 컴포넌트가 추가되지 않는가?
- [ ] 미래에만 필요할 가능성을 위해 정밀도 점수, 승인 단계, 큐, 별도 사본을 미리 만들지 않는가?
- [ ] 같은 정보를 여러 테이블·계층에 복제해 새 정본이 생기지 않는가?
- [ ] 기존 ID, 상태, 저장 경로, UI 부품을 재사용할 수 있는데 별도 시스템을 만들지 않는가?
- [ ] 유지보수·마이그레이션·테스트·운영 비용이 해결하려는 문제의 가치에 맞는가?
- [ ] 최소 수정안과 근본 수정안을 비교했는가?
- [ ] “지금 반드시 필요”, “실제 사례가 생기면 확장”, “불필요”를 구분했는가?
- [ ] 코드 줄 수가 늘었다는 이유만으로 데이터 정합성·안전성 개선을 과하다고 판단하지 않았는가?

## 9. 게임 기록의 논리적 정합성

- [ ] LoL/FC, 공개 큐/수기, CK/대회/랜드/보너스/칼바람의 포함 범위가 목록·상세·통계에서 같다.
- [ ] 사람 ID·계정 ID·외부 경기 ID·시리즈 ID·VOD ID를 혼용하지 않는다.
- [ ] 승패 미상·무승부·날짜만 아는 경기·불완전 KDA를 패배/0/정확한 시각으로 둔갑시키지 않는다.
- [ ] 맞라인은 추론 일치 여부를 확인하고, 계정 숨김·연결 변경은 과거 조우와 공개 목록에도 반영한다.
- [ ] 다시점 병합·중복 거부·distinct_from·칸별 검수 보호가 서로 충돌하지 않는다.
- [ ] 보너스 세트는 행사 소속을 유지하면서 공식 시리즈 승패·수상 계산에서 정해진 대로 제외한다.
- [ ] 커서 동률·날짜 경계·타임존·정렬 전환·마지막 페이지에서 누락/중복이 없다.
- [ ] FC 구단 스냅샷의 시도/성공/실패/오래됨과 실제 가격 관측일을 구별한다.

## 10. 커뮤니티 가입·권한·파기

- [ ] 카카오/구글 실제 앱 등록·scope·callback·운영 HTTPS 쿠키를 확인한다. 가짜 OIDC 통과로 대체하지 않는다.
- [ ] state·nonce·PKCE·콜백 재사용·취소·다른 제공자·외부 next 경로를 검증한다.
- [ ] 로그인→동의·닉네임→원래 글쓰기까지 site/game/s 문맥이 유지된다.
- [ ] 작성자 본인·관리자·비회원·제재·탈퇴 계정 권한을 서버에서 검사한다.
- [ ] HTML/링크·서버 액션 Origin·입력 크기·횟수 제한·중복 추천을 검증한다.
- [ ] 글쓰기/탈퇴, 신고/파기, 제재/로그인 연결 정리를 실제 PostgreSQL 동시 트랜잭션으로 검증한다.
- [ ] 삭제·신고 스냅샷·탈퇴 연결의 보존 기간이 공개 문구와 정리 잡에서 일치한다.
- [ ] 실제 가입 전 샘플 게시물 제거 대상과 실제 사용자 데이터를 구별한다.
- [ ] 문의·비노출 요청 경로가 실제 수신되고, 운영 정책 미완성 문구가 없다.

## 11. AWS 웹·워커 / 로컬 CLI 분리

- [ ] 웹·일반 API 수집·커뮤니티 정리는 AWS, CLI/ASR/VOD 조사는 로컬이라는 소유권 표를 만든다.
- [ ] 동일 작업을 AWS loop와 로컬 systemd가 동시에 실행하지 않는다. 로컬 flock은 다른 호스트를 막지 못한다.
- [ ] 로컬 PC 종료·인터넷 단절·절전·외장 드라이브 이탈을 실제로 구별해 표시한다.
- [ ] CK_OUT_ROOT/CK_ARCHIVE_ROOT의 로컬 근거를 AWS 관리자 화면에서 읽을지, 검수 자체를 로컬에 둘지 결정한다.
- [ ] 운영 오피스 스냅샷은 호스트별 출처·갱신 시각을 보존한다. AWS systemd만 보고 로컬 조사 상태를 추정하지 않는다.
- [ ] DB·API 키·관리 토큰은 역할별로 주입하고 배포물·로그·브라우저에 포함하지 않는다.
- [ ] 대표 도메인 하나를 정하고 HTTPS·리다이렉트·SITE_ORIGIN·OAuth callback을 일치시킨다.
- [ ] 도메인 문의 주소 전달 설정, 수신 시험, 답장 주소를 확인한다.

## 12. 배포 재현성·의존성·복구

- [ ] 깨끗한 checkout + npm ci + 고정 Node 버전으로 빌드된다. 기존 node_modules 통과와 구분한다.
- [ ] npm audit 경고는 설치 버전·수정 버전·실제 도달 가능한 사용 경로로 분류한다.
- [ ] standalone에 public/static을 명시적으로 넣고, design-lab·out·환경파일·학습 모델은 제외한다.
- [ ] 빈 DB/이전 버전 업그레이드/실제 장부 checksum을 각각 확인한다.
- [ ] 마이그레이션 잘못된 인자·중복 실행·중간 실패·status 읽기 전용 계약을 확인한다.
- [ ] 백업 복원 연습과 이전 앱 버전 복귀 절차가 있고, DB 되돌리기와 앱 롤백을 구분한다.
- [ ] health/readiness·프로세스 재시작·SIGTERM·DB 단절·외부 API 429/5xx 처리를 확인한다.
- [ ] CI 또는 단일 검증 절차가 단위·TS·모듈·DB·브라우저·Python 시험 누락을 막는다.

## 13. 성능·웹 품질

- [ ] 실제 데이터 규모에서 EXPLAIN, 응답시간 p50/p95, DB 풀 대기, 웹 동시 접속을 측정한다.

- [ ] 임시 SQL·하드코딩 /tmp·개인 경로·고정 날짜·옛 baseline을 실제 호출자와 대조한다.

- [ ] 문서 이동 후 상대 링크·npm 경로·systemd·CLI 스킬·import 경로를 다시 검사한다.

## 15. 검증 도구도 검증한다

- [ ] fixture가 현행 중복·공개·검수 규칙을 만족해 실제 본 시험까지 도달한다.
- [ ] 임시 DB뿐 아니라 파일 잠금·쿨다운·로그·포트·환경변수도 운영 상태와 분리한다.
- [ ] URL 비교는 쿼리 문자열 순서 대신 의미를 확인하고, 꼭 보존해야 할 문맥은 별도 assert한다.
- [ ] PGlite 직렬 시험을 실제 PostgreSQL 동시성 통과라고 보고하지 않는다.
- [ ] 제한시간 종료·환경 누락·검사 미진입·제품 실패·fixture 오류를 따로 기록한다.
- [ ] PASS에는 명령·종료코드·로그·기준 상태를 붙인다. 미실행/미확인은 통과로 표시하지 않는다.

## 검토 결과 형식

계획 또는 구현 검토 결과는 아래 형식으로 남긴다.

### A. 최종 판정

`그대로 구현 가능` / `수정 후 구현 가능` / `재설계 필요` 중 하나와 한 문장 이유.

### B. 반드시 수정할 문제

각 항목에 문제, 실제 코드 근거(파일·줄), 발생 조건, 수정 방향, 필요한 테스트를 쓴다.

### C. 권장 개선사항

필수는 아니지만 구조·운영·사용성을 개선하는 사항을 쓴다.

### D. 이미 올바르게 반영된 부분

실제 코드·테스트·데이터로 확인한 사실만 쓴다.

### E. 변경 파일과 작업 순서

변경 대상, 마이그레이션/이관 순서, 테스트 순서를 적는다.

### F. 개발자 전달용 최종 피드백

바로 복사해 전달할 수 있게 결정·수정 범위·완료 조건을 짧게 정리한다.
