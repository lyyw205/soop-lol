- 소급 추정선은 지금 카드가 **전부** 시세를 가진 날부터만 그린다. 최근 출시 카드가 있으면 짧다(호날두: 9/10부터).

등록 스트리머의 FC 온라인 구단을 **자산처럼** 다룬다.

1. **구단가치 순위**: 공식 구단가치 순으로 줄 세운다. 1일·7일·30일 등락도 같이 보여 준다.
2. **스쿼드 등록 선수**: 스쿼드 6개에 등록된 카드 전부와 카드별 가치.
3. **가치 변동 차트**: 시세 그래프처럼, 스트리머 구단의 가치가 날마다 어떻게 움직였는지 보여 준다.
   "시세가 올라서 오른 것"과 "선수를 바꿔서 오른 것"을 나눠 보여 준다.

## 1. 데이터는 어디서 오나 (실측)

넥슨 Open API 에는 구단가치·스쿼드·시세가 **없다.** 거래 기록(`/fconline/v1/user/trade`)은
NEXON Open ID 로그인(유저 본인 동의) 전용이라 API 키로는 400 이다.
전부 **공식 홈페이지(fconline.nexon.com) 내부 요청**으로 얻는다. 형식이 예고 없이 바뀔 수 있다.
약관 검토는 하지 않기로 했다(2026-10-02 사용자 결정).

| 무엇 | 요청 | 응답 |
|---|---|---|
| 감독명 → 넥슨 회원번호 | `GET /profile/common/PopProfile?strCharacterName={감독명}` | 있으면 302 `Location: /profile/squad/popup/{회원번호}`. 없으면 200 + `alert('구단주 정보가 존재하지 않습니다.')` |
| 회원번호 → 캐릭터ID | `GET /profile/squad/popup/{회원번호}` | HTML 안 `SquadProfile.SetSquadInfo("1", "1", "{회원번호}", "{캐릭터ID}")`. 캐릭터ID(24자 hex)는 ouid 와 **다른 값** |
| 공식 구단가치 | `POST /Profile/Common/ToolTip/{회원번호}` | HTML. `<span class="name" …> 감독명</span>`, `<div class="value" alt="12,222,552,300">` |
| 스쿼드 | `GET /datacenter/SquadGetUserInfo?strTeamType={1 대표팀·0 클럽팀}&n1Type={1~3 A/B/C}&n8NexonSN=…&strCharacterID=…` | **JSON**. 캐릭터ID 없거나 틀리면 빈 응답 |
| 카드 시세 이력 | `POST /datacenter/PlayerPriceGraph` 본문 `spid=…&n1strong={강화}` | HTML. `현재가 <strong alt="…">` + `json1 = { time: ["10.02", …], value: ["263000", …] }` |

### 실측 결과 (2026-10-02)

**구단가치**
- 연결 계정 16개 **전부** 받았다. 랭킹(상위 1만 명) 밖 7명도 된다.
- 랭킹 화면에 있던 9명은 회원번호·구단가치가 랭킹 값과 **정확히 같았다**(9/9).
- 구단주 검색은 **대소문자를 무시한다**(`뀨뀨RR` → `뀨뀨rr`). 앞뒤 공백이 있으면 못 찾는다.
- 커뮤니티에서 회원번호를 따로 알던 사람(`너억파지` 1575664508)으로 대조했다.

**스쿼드**
- 스쿼드는 **6칸**(대표팀 A/B/C × 클럽팀 A/B/C). 칸마다 18명(선발 11 + 교체 7).
- 선수마다 `spid`·`pid`·`name`·`season`·`position`·`role`(교체는 대문자)·`ovr`·`pay`,
  `price`(현재가), `eachPrice`(강화 0~13단계 현재가, `|` 구분). `totalPrice` = 선발 11명 현재가 합(직접 더해서 확인).
- **강화 단계 필드는 비어 있다**(`lv: ""`). `price` 가 `eachPrice` 몇 번째와 같은지로 구한다.
  저창FC 18명이 9/29 경기 상세의 `spId`·`spGrade` 와 **18/18 일치**.
- 메시연(이상호)은 6칸이 전부 달랐다: 대표A 1,313억 · 대표B 229억(2군) · 대표C(A와 선발 같고 배치·교체만 다름) ·
  클럽A 996억 · 클럽B 1,128억 · 클럽C 713억. 합집합 34장(카드+강화), 1,790억.
  9/24 경기 8건 중 대표A/C 선발 11/11 3건, 대표B 11/11 1건 — 1군·2군 운영이 그대로 잡힌다.
- 저창FC 는 클럽 A/B/C 가 같았다(하나만 쓰는 것으로 본다).
- 창고(스쿼드에 안 넣은 카드)는 **보이지 않는다.**
- 공식 구단가치 > 스쿼드 합집합: 메시연 2,274억 / 1,790억. 차이가 창고일 수 있지만 **확인하지 않았다.**

**시세 이력**
- 스쿼드 JSON 의 `price` = 시세 그래프의 **현재가**(3/3 정확히 일치).
- 그래프는 카드×강화마다 **최대 365일치 일별 값**을 한 번에 준다. 출시가 그보다 늦으면 출시일부터.
- **일별 값 ≠ 현재가.** 해리 케인 26TOTS 11강: 현재가 428억, 그래프 10.01 값 411.9억.
  일별 평균 거래가로 보이지만 **확인하지 않았다.** → 두 숫자를 한 선에 섞지 않는다(§2).
- 원본: `out/fconline/club-value/` (gitignore. 테스트 fixture 는 저장소로 옮긴다).

## 2. 근본 설계 — 원본 셋, 나머지는 전부 계산

기능이 셋(순위·스쿼드·차트)이고 나중에 맞대결 스쿼드 비교까지 붙는다. 기능마다 테이블을 만들면
같은 사실이 여러 곳에 갈라져 어긋난다. 그래서 **서로 독립인 원본 사실 셋**만 저장하고,
나머지는 전부 그 셋에서 계산한다. 주식으로 치면 "공시 시가총액", "보유 종목", "종목 시세" 셋이다.

| 원본 | 무엇 | 왜 따로 두나 |
|---|---|---|
| ① **공식 구단가치** | 계정 × 날짜 → 넥슨이 주는 값 | 헤드라인 숫자. 계산식을 몰라 우리가 재현할 수 없다 |
| ② **보유(스쿼드)** | 계정 × 날짜 × 6칸 × 18자리 → 카드·강화·그날 현재가 | 누가 무엇을 들고 있었나. **지나간 날은 다시 구할 수 없다** |
| ③ **카드 시세** | 카드 × 강화 × 날짜 → 일별 값 | 스트리머와 무관한 **시장 데이터**. 365일까지 소급해서 받을 수 있다 |

③을 스트리머와 떼어 두는 게 핵심이다. 같은 시세표 하나로:
- 가치 변동 차트 = ② × ③
- 맞대결 스쿼드 비교 = 경기 상세의 `spId`·`spGrade`·경기 날짜 × ③ (스냅샷이 없던 과거 경기까지 된다)
- 나중에 다른 무엇이든 카드 가치가 필요하면 ③

**계산(파생) — 저장하지 않고 원본에서 언제든 다시 만든다** (코딩 원칙 5).
계산식은 `packages/core` 한 곳에 둔다(원칙 6). 순위 화면·차트·맞대결이 같은 함수를 쓴다.

| 계산 | 식 |
|---|---|
| 스쿼드 등록 선수 | 그날 6칸의 합집합. 중복 기준 **카드(spid)+강화**. 같은 선수 다른 시즌 카드는 별개 |
| 등록 선수 현재가 합 | 합집합의 그날 현재가 합 (② 안의 값만 쓴다) |
| **실제 가치 이력** | 날짜 t 마다 Σ(그날 보유 카드의 t 일별 시세). 스냅샷을 쌓기 시작한 날부터 |
| **현재 스쿼드 소급 추정** | 오늘 보유 카드를 과거 365일 시세로 평가. "지금 스쿼드를 1년 전부터 들고 있었다면" — 실제 이력이 아니라 **추정**으로 표시 |
| 변동 분해 | Δ(t) = **시세 효과**(이틀 다 보유한 카드의 시세 차) + **교체 효과**(새로 들어온 카드 − 빠진 카드) |
| 등락률 | 1일·7일·30일. 공식 구단가치 기준과 실제 가치 이력 기준을 따로 |

**숫자 두 종류를 섞지 않는다.**
- 오늘 숫자(순위표·보유 목록)는 **현재가**로 계산한다. 넥슨 스쿼드 화면 합과 맞는다.
- 차트 선은 **일별 시세**로만 그린다. 마지막 날만 현재가로 바꾸면 차트 끝이 가짜로 튄다.
- 공식 구단가치는 별도 선 또는 별도 숫자로 둔다. 창고가 포함됐을 수 있어 스쿼드 가치와 수준이 다르다.

### 그 밖의 결정

| 결정 | 내용 | 이유 |
|---|---|---|
| 수집·저장·계산은 **core** | 원본 셋과 계산 함수 | 사실과 공용 계산은 core (ARCHITECTURE.md) |
| 화면은 **새 모듈 `fc_club_value`** | `/fc/club-value`(순위·차트·보유 선수 통합) | 순위·차트·보유 목록으로 커져서 리더보드 탭 하나로는 안 맞는다. 모듈째 떼어낼 수 있다(core 데이터는 남는다). 앞 계획의 "리더보드 탭"을 바꾼다 |
| 감독명은 **조회 직전에 API 로 갱신** | `user/basic` | 감독명은 바뀐다 |
| 툴팁 감독명 **완전 일치**일 때만 저장 | 대소문자까지 | 구단주 검색이 대소문자를 무시한다 |
| 회원번호가 바뀌면 저장하지 않고 알린다 | 같은 ouid 의 이전 값과 비교 | 감독명이 남에게 넘어간 경우 |
| 형식이 깨지면 실패로 남긴다 | 행을 만들지 않고 잡 결과에 | 엉뚱한 값이 조용히 쌓이는 것을 막는다 |
| 못 찾음도 남긴다 | 상태 `missing` | "없다"와 "못 봤다"를 구분한다 |
| 스트리머당 계정이 여럿이면 | 공식 구단가치가 가장 큰 계정 기준, 어느 계정인지 표시 | 부계정으로 순위를 매기면 오해 |
| 홈페이지 호출은 **게이트웨이 하나** | `datacenter-client.ts`, 초당 1회 | 원칙 4 를 이 출처에도 |

## 3. 시한부인 것 — 순서를 정하는 기준

- **② 보유와 ① 공식 구단가치는 지나간 날을 다시 구할 수 없다.** 랭크 스냅샷과 같다. 하루 늦으면 하루 구멍이다.
- **③ 시세는 365일까지 소급된다.** 급하지 않다.

→ ①② 수집을 **가장 먼저** 돌리고, 화면은 그다음이다.

## 4. 단계

### 1단계 — 스키마 `db/migrations/0060_fco_club_value.sql`
```sql
-- ① 공식 구단가치 + 조회 근거. 계정 × 조회 시각.
CREATE TABLE fco_club_snapshot (
  id           bigserial PRIMARY KEY,
  ouid         text NOT NULL REFERENCES fco_account(ouid) ON DELETE CASCADE,
  captured_at  timestamptz NOT NULL DEFAULT now(),
  status       text NOT NULL CHECK (status IN ('ok', 'missing')),
  nickname     text NOT NULL,          -- 조회에 쓴 감독명(근거)
  nexon_sn     bigint,
  club_value   bigint,                 -- 공식 구단가치
  CHECK ((status = 'ok') = (nexon_sn IS NOT NULL AND club_value IS NOT NULL))
);
CREATE INDEX ON fco_club_snapshot (ouid, captured_at DESC);

-- ② 보유. 스냅샷 하나에 6칸, 칸마다 18자리.
CREATE TABLE fco_squad_snapshot (
  snapshot_id  bigint NOT NULL REFERENCES fco_club_snapshot(id) ON DELETE CASCADE,
  team_type    smallint NOT NULL CHECK (team_type IN (0, 1)),    -- 1 대표팀, 0 클럽팀
  slot         smallint NOT NULL CHECK (slot BETWEEN 1 AND 3),   -- A/B/C
  total_price  bigint NOT NULL,                                  -- 넥슨이 준 선발 합
  coach_id     text,
  PRIMARY KEY (snapshot_id, team_type, slot)
);
CREATE TABLE fco_squad_player (
  snapshot_id  bigint NOT NULL,
  team_type    smallint NOT NULL,
  slot         smallint NOT NULL,
  idx          smallint NOT NULL,      -- 응답 순서 0~17
  role         text NOT NULL,          -- 선발 자리(소문자) / 교체(대문자)
  is_starter   boolean NOT NULL,
  spid         bigint NOT NULL,
  grade        smallint,               -- eachPrice 로 구한 강화. 못 구하면 null
  price        bigint,                 -- 그날 현재가
  name         text NOT NULL,
  season       text,
  ovr          smallint,
  PRIMARY KEY (snapshot_id, team_type, slot, idx),
  FOREIGN KEY (snapshot_id, team_type, slot) REFERENCES fco_squad_snapshot ON DELETE CASCADE
);

-- ③ 카드 시세. 스트리머와 무관한 시장 데이터.
CREATE TABLE fco_card_price_daily (
  spid        bigint NOT NULL,
  grade       smallint NOT NULL CHECK (grade BETWEEN 0 AND 13),
  day         date NOT NULL,
  price       bigint NOT NULL,          -- 그래프 일별 값
  fetched_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (spid, grade, day)
);
```
- 적용 전 `npm run db:migrate -- --status` 로 대기 번호부터 확인한다.

### 2단계 — 수집기 (core) `packages/core/lib/games/fconline/club/`
- `datacenter-client.ts` — fconline.nexon.com 전용. 초당 1회, 리다이렉트 수동, 실패를 숨기지 않는다.
- 파서(순수 함수, fixture 테스트): 구단주 검색 응답 / 프로필 HTML(캐릭터ID) / 툴팁 / 스쿼드 JSON(+강화 추정) / 시세 그래프.
  - 시세 그래프의 `"10.02"` 는 연도가 없다. 마지막 점이 조회 전날이라는 가정으로 거꾸로 날짜를 붙이고,

#### 운영 주기 (서버 배포 때)

| 잡 | 주기 | 이유 | 예산(초당 1회) |
|---|---|---|---|
| F `fco-club` ①② | **2시간마다** | 조사 대상이 소수 스트리머라 감당된다. 선수 사고팔기가 하루 안에서 보인다 | 16계정 × 8 = 128회/회(약 2분) → 하루 1,536회(약 26분) |
| G `fco-prices` ③ | **하루 한 번**(F 다음) | 시세 그래프가 일별 값이다. 하루 빠져도 365일까지 소급된다 | 보유 카드 수(지금 379장, 약 7분) |

할 일:
- 설정 `FCO_CLUB_INTERVAL_MIN`(기본 120)을 만들고, `loop` 에서 F 는 그 간격으로, G 는 `FCO_HOUR_KST` 에 하루 한 번만 돌게 나눈다.
- G 는 카드마다 DB 왕복이 3번이라 카드당 1초를 넘는다(첫 수집 379장 6분 50초). 카드 목록의 "오늘 받았나" 조회를 한 번으로 묶는다.
- **저장량**: 2시간 간격이면 스쿼드 자리 행이 하루 약 2만(16 × 12회 × 6칸 × 18), 1년 약 750만이다.
  스쿼드가 직전 스냅샷과 같으면 자리 행을 다시 쓰지 않고 "직전과 같음"만 남기는 방식을 그때 정한다
  (① 구단가치 행은 매번 쓴다). 조회(`playersOf`)가 그 참조를 따라가게 같이 고친다.
- 화면의 날짜별 값은 그날 마지막 스냅샷을 쓴다(지금 `dailySnapshots` 그대로). 2시간 값은 나중에 "오늘 중 변동" 에 쓸 수 있다.
- 공식 구단가치가 실제로 얼마나 자주 바뀌는지 아직 모른다(§1). 2시간 기록을 며칠 쌓아 보고, 하루 한 번만 바뀌면 ① 은 줄이고 ② 만 2시간으로 둔다.
- 서버 시간대는 KST 가 아닐 수 있다 — 스케줄은 `nextKstHour` 처럼 KST 로 계산한다.
- 참고: FC 경기 수집(Engine E)도 운영에서 9/25 이후 돌지 않았다. 같은 배포에서 함께 살린다.

### 5단계 — 화면 (모듈 `fc_club_value`)

**`/fc/club-value` 한 화면에서 고른다**(2026-10-02 개편). 선택은 주소에 담는다: `?s=스트리머&p=카드,카드`(카드 = `spid:강화`).
- 위: **차트 패널** — 고른 스트리머(기본 1위)의 공식 구단가치·등락, 스쿼드 등록 선수 현재가 합, 가치 차트.
- 아래 왼쪽: 순위표. 이름을 누르면 페이지 이동 없이 위 차트가 그 구단으로 바뀐다(선수 선택은 비운다).
- 아래 오른쪽: 그 구단의 스쿼드 등록 선수. ＋ 를 누르면 그 선수 시세가 차트에 **더해진다**(최대 4명, 칩의 × 로 뺀다).
- 차트는 축 하나. 선수가 없으면 금액(실제 보유 실선 · 소급 추정 점선), 선수를 더하면 **등락률(%)** 로 바뀐다 —
  구단(수천억)과 카드(수억)를 금액 축에 같이 그리면 선수 선이 바닥에 깔리고, 이중 축은 쓰지 않는다.
  기준은 **모든 선이 함께 있는 첫날 = 0%**. 선마다 자기 첫날을 기준으로 하면 출시 직후 싼 값 때문에 수만 % 로 튄다
  (이언 라이트 SPT 11강: 출시일 0.9억 → 두 달 뒤 306억).
- 색: 구단 #3987e5, 선수 #d95926 · #199e70 · #c98500 · #d55181 고정 순서(dataviz 검증 통과, 다크). 그래서 4명까지.
- 좁은 화면: 차트를 실제 폭으로 다시 그리고, 선 끝 이름표 대신 칩이 정체를 맡고, 툴팁은 차트 아래 고정 칸.
- 별도 상세 페이지는 중복 화면이라 제거했다. 구단 선택은 `/fc/club-value?s=스트리머`에서 처리하며, 스쿼드·변동 원본 데이터는 유지한다.
- 금액은 `2,274억 5,879만`, 정확한 숫자는 `title`. 등락은 빨강 ▲ / 파랑 ▼(색만으로 구분하지 않는다). 기록이 모자라면 "—".
- 출처 표기: "FC온라인 공식 홈페이지 기준 · {조회 시각}". 창고 미포함이라는 점을 보유 목록 위에 적는다.

연결만 되면 "이 선수를 언제 얼마에 사고팔았나"를 그 선수 시세 선 위에 찍어 보여 줄 수 있다.

### 무엇을 보여 주나
- 선수 시세 차트(그 카드×강화의 일별 시세, **금액 축**) 위에 거래 점: 매수 ▲ · 매도 ▼(모양으로 구분, 색만 쓰지 않는다).
- 툴팁: "매수 12.3억 · 그날 시세 13.1억(−6%)". 그날 시세가 없으면 비교하지 않는다.
- 카드별 요약: 평균 매수가, 현재가 대비 평가 손익, 매도까지 했으면 실현 손익. 표본이 1건이면 1건이라고 쓴다.
- 지금 비교 모드(%)의 선수 선과는 따로 — 거래 가격은 금액이라 "선수 하나 + 내 거래" 는 금액 축 차트로 그린다.

### 연동 방법 — **Open ID 하나뿐이다** (2026-10-02 확인)
| | 결과 |
|---|---|
| A. 본인 API 키(피온북 방식) | **막혀 있다.** 지금 FC Open API 문서(키 방식)는 계정·매치·랭커·메타데이터·이미지 5개뿐이고 거래가 없다. `/fconline/v1/user/trade` 는 Open ID "데이터 항목"(`fconline.trade`) 표에만 있고 `Authorization: Bearer {액세스 토큰}` 으로 부르라고 돼 있다. 우리 키로는 어느 계정이든 400(`OPENAPI00004`) — 스트리머 계정, 그리고 사용자가 준 `휴면61796609155`(→ 현재 감독명 `달머제이크`, 레벨 1, 등급 기록 없음)도 400. 피온북 안내는 이 변경 전 방식으로 보인다 |
| **B. NEXON Open ID** | 사용자가 "넥슨으로 로그인" → `fconline.trade` 동의 → 액세스 토큰(30분)·리프레시(14일)으로 호출. 앱 등록이 필요하다 |

**검수 전에도 시작할 수 있다.** Open ID 는 "테스트 단계: 제작자와 지정된 테스트 사용자만 로그인 가능" — 검수 전이라도
제작자 본인과 우리가 등록한 테스트 사용자(협조하는 스트리머)는 쓸 수 있다. 모든 사람에게 여는 프로덕션 전환에만
검수가 필요하고, 검수에는 서비스 URL·로고와 로그인 버튼·제공 정보 화면 캡처가 필요하다(→ 배포 뒤).
- 테스트 사용자 수 제한은 아직 모른다 — 앱 등록할 때 확인한다.
- 리다이렉트 URI 가 필요하다. 로컬(`http://localhost:3000/...`)이 허용되는지 확인한다.

### 설계 원칙
- **토큰은 오래 들고 있지 않는다.** 첫 버전은 로그인한 그 세션 동안만 쓰고 버린다. 로그·오류 메시지에 남기지 않는다.
  넥슨 호출은 서버에서 한다. 거래 API 는 키 대신 Bearer 토큰을 쓰므로 NexonClient 에 토큰 호출 경로를 하나 더한다(게이트웨이는 그대로 하나).
- **거래는 기본 비공개다.** 첫 버전은 저장 없이 그 자리에서 그려 주기만 한다.
  저장(다음 방문에 다시 보기)은 사용자가 고를 때만, 스트리머 화면에 공개하는 것은 본인이 따로 켤 때만 —
  계정 매핑과 같은 원칙(근거·visibility·삭제 경로).
- 저장한다면 표: `fco_user_trade (ouid, sale_sn PK, trade_type, trade_date, spid, grade, value, fetched_at)` + 공개 여부.
- **거래한 카드의 시세가 없을 수 있다.** 지금 시세는 스쿼드에 있는 카드만 받는다(이미 판 카드는 없다).
  연결할 때 거래한 카드×강화의 시세 그래프를 받아 ③ 에 넣는다 — ③ 은 스트리머와 무관한 시장 데이터라 그대로 쓴다.
  그래프는 365일까지라 그보다 오래된 거래는 시세 비교 없이 점만 찍는다.
- 넥슨이 거래를 몇 건·며칠까지 주는지 모른다(게임 안 화면은 최근 100건). A/B 확인 때 같이 잰다.

### 순서
1. 넥슨 Open API 에서 Open ID 앱 등록(테스트 단계): scope `fconline.trade`, 리다이렉트 URI, 테스트 사용자 제한 확인.
2. 제작자 본인 계정으로 로그인 → 거래 기록을 받아 응답 필드·건수·기간을 기록한다(게임 안 화면은 최근 100건).
3. 서버: OAuth 콜백 → 토큰은 세션 동안만(저장한다면 암호화, 리프레시 14일) → 거래 받기 → 거래 카드 시세 보충(③) → 카드별 거래·시세 묶기(core 계산, 단위 테스트).
4. 화면: 선수 시세(금액) + 거래 점 차트, 카드별 요약 표. 로그인 버튼은 넥슨 디자인 가이드대로.
5. 협조하는 스트리머를 테스트 사용자로 등록해 써 본다.
6. 배포 뒤 검수 신청 → 프로덕션(누구나).
7. (선택) 저장·스트리머 화면 공개 — 본인이 켤 때만.

### 공식경기 점수 (2026-10-02)

스트리머 표의 `공경 점수`는 공식 홈페이지 `/datacenter/rank_inner?rt=1vs1&n4seasonno=0&strCharacterName=...`의 **현재 시즌 1대1 랭킹점수(ELO)**다. 구단가치 TOP 50 순위와 별개다. `rank_r_win_point`의 소수점을 보존하고, 응답의 기준 시각(KST)과 함께 `fco_rating`(0066)에 저장한다. 공식 홈페이지는 1시간 단위 갱신이라고 안내하며, 우리 수집 주기는 구단 엔진 실행 주기를 따른다.

조회 행의 구단주명과 회원번호를 최신 성공 구단 스냅샷에 대조한다. 명시적 검색 결과 없음은 NULL(`—`), 요청 실패·형식 변경·신원 불일치는 기존 성공 데이터를 보존한다. 공개 조회는 현재 계정명과 맞는 관측만 노출한다. 점수에 마우스를 올리면 출처와 기준 시각을 확인할 수 있다.

- 구단 엔진 `worker -- fco-club`에서 계정별로 함께 갱신한다.

### 등급과 헤더 정렬 (2026-10-02)

- 사용자가 요청한 직전 시즌의 **최고 ELO**는 확인한 공식 자료에서 제공되지 않았다. 사용자 선택에 따라 **직전 시즌 최고등급**으로 변경했다. 시즌별 랭킹 조회 ELO를 최고점수로 대체하지 않는다.
- `/Profile/Stat/TeamInfo/{회원번호}?n1Type=50`의 `season_grade_info__current .grade_current`는 현재 등급, `season_grade_info__last .grade_last`는 직전 시즌 최고등급이다. 지난 시즌의 `grade_current`(최종 등급) 또는 역대 최고와 혼동하지 않는다. 조회 직전 툴팁 감독명·회원번호를 대조한다.
- 등급명과 순서는 공식 `/datacenter/rank`의 `list_grade` 및 `update_2026/ico_rank{n}.png` 매핑을 따른다. 2026 등급표에는 마스터 1~3부가 포함된다. 이미지 번호를 구형 Open API division ID로 추정하지 않는다.
- 0067에 현재·직전 최고등급과 별도 조회 시각을 추가했다. ELO의 원본 집계 시각과 등급 조회 시각은 툴팁에서 구분한다.
- 헤더 클릭 정렬: 스트리머 순위·공식 구단가치 순위는 오름차순, 구단가치·현재 등급·직전 최고등급은 내림차순으로 시작하며 다시 누르면 반전한다. 누락은 항상 마지막. 현재 스트리머와 선수 선택, 페이지 스크롤을 바꾸지 않는 클라이언트 정렬이며 스트리머를 바꿔도 정렬은 유지한다.

- 티어 표시: 현재 공식경기도 점수를 숨기고 38px 등급 아이콘과 작은 등급명 라벨만 표시한다. ELO 수집 데이터는 보존한다. 헤더는 행과 같은 스크롤 영역의 sticky 헤더로 배치하여 스크롤바 폭과 무관하게 중심선이 일치한다.

### 총 구단가치 차트로 통일 (2026-10-02)

선수 미선택 차트는 `account.history`의 공식 총 구단가치 일별 관측만 그린다. 현재 스쿼드 소급 추정·실제 보유 평가 곡선과 그 범례를 제거했다. 선수 선택 시에는 카드별 가격 비교와 선택 선수 범례만 표시한다. 총 구단가치는 수집된 날짜만 표시하며 과거 시세로 역산하지 않는다. 첫날 기록 하나만 있을 때에는 점으로 표시한다.

### 초기 이력 부족 기간의 추정 차트 복원 (2026-10-02 사용자 결정)

공식 총 구단가치 이력이 하루뿐이므로, 사용자 요청에 따라 선수 미선택 차트는 현재 스쿼드의 과거 시세 합산(`backcast`)을 다시 표시한다. 실제 총 구단가치는 상단 요약에 표시하고, 추정 곡선은 점선과 `현재 스쿼드 기준 추정 · 실제 총 구단가치와 다를 수 있습니다` 안내로 구분한다. 선수 선택 시에는 이 안내를 숨기고 선수별 가격만 비교한다. 공식 구단가치 수집·보존은 유지한다.

### 추정/수집 구간 구분 (2026-10-02)

현재 선수의 과거 시세 합산은 연한 점선으로 유지하고, 저장된 스쿼드의 해당 날짜 시세 합산(`actual`)은 진한 실선/점으로 겹쳐 표시한다. 같은 날짜는 수집 스쿼드 평가액을 우선하며 툴팁도 한 값만 표시한다. 수집이 빠진 날짜를 실선으로 잇지 않는다. 스쿼드의 전일 기준 날짜를 유지한다. 이 두 계열 모두 스쿼드 평가액이며 공식 총 구단가치와 이어 붙이지 않는다. 최초 하루만 수집된 상태는 진한 점으로 나타난다.


### 과거 경기 명단 기반 추정 (2026-10-02 사용자 결정)

기존 현재 스쿼드 역산을 대체한다. 계정별 최초 홈페이지 스쿼드 수집일 이전 30일 창에서 저장된 가장 오래된 1대1 경기(40·50·60)의 명단을 읽는다. 창은 최초 수집일에 고정하며, API 최장 조회 가능 경기라고 보장하지 않는다. 중간 경기를 새로 수집하지 않는다.

- 근거 경기 날짜부터 최초 홈페이지 스쿼드 기준일 전날까지 명단을 유지했다고 가정해 날짜별 시세를 합산한다. 근거 날짜 이전은 그리지 않는다.
- 모든 카드의 양수 시세가 있는 날만 추정한다. 빠진 카드를 0원으로 합산하거나 현재 선수로 대체하지 않는다. 시세가 부족해 추정이 없는 계정은 화면에 이유를 표시한다.
- 추정은 연한 점선, 수집 스쿼드는 진한 점·실선으로 표시하고 두 계열은 연결하지 않는다. 전환일에는 ‘수집 기준 전환’을 표시한다. 과거 경기 명단과 홈페이지 6개 스쿼드 합집합은 비교 범위가 다르며 영입·판매 시점을 확정하지 않는다.
- 수집 구간도 카드/강화 또는 시세 확인 범위가 바뀌면 연결선을 끊는다. 창고를 포함한 공식 총 구단가치와 별개이며, 공식 총 구단가치는 상단 요약으로 유지한다.
- 30계정 실데이터 확인: 모두 과거 명단 18명, 24계정 추정 생성. 6계정은 과거 시세 부족으로 제외. 으네 9월 3일 128.883808억으로 보고서와 일치.
- 검증: club-value.test.ts, price-history.test.ts, verify:fco-club의 원본 경기→공개 조회 검증(근거 날짜 고정·모드 제외·현재 목록 분리 포함).


### 과거 시세 부분 반영 (2026-10-02 보정)

전원 시세 조건을 해제했다. 0강·0원 또는 누락 시세 카드는 제외하고 양수 시세가 있는 선수만 합산한다. 차트 안내에는 최근 추정일의 반영 인원, 툴팁에는 해당 날짜의 반영 인원/전체 명단 수와 제외 수를 표시한다. 반영 카드 구성이 달라진 날은 선과 면적을 이어 그리지 않으며 전원 미확인인 날은 점을 만들지 않는다. 임의로 1강 시세를 대입하지 않는다.


### 현재 스쿼드 소급 추정으로 복원 (2026-10-02 사용자 결정)

과거 경기 명단 기반 추정 및 부분 반영을 화면에서 철회했다. 현재 스쿼드의 과거 일별 시세 합산으로 복원하고, 수집 날짜는 관측 스쿼드 평가액을 우선해 진한 점·실선으로 표시한다. 명단 전환 표시와 반영 인원 표시는 제거했다. 수집된 과거 경기·카드 시세와 비교 보고서는 보존한다.
