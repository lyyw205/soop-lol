## 요약

- **플랫폼(로비) 공간의 모듈 `community`.** 주소는 `/community` 하나이고, 게임은 필터(`?game=`)다. 편성표와 같은 자리, 같은 규칙
- **분류는 두 축** — 게임(`game_code`: `lol`·`fconline`·없음=공통) × 말머리(자유·질문·정보·경기 이야기·공지). 게시판을 게임마다 쪼개지 않는다
- **나눔도 편성표와 같다.** 회원·글·댓글·신고·제재는 core(표·공개 뷰·쓰기 접근자·관리자 화면), 모듈은 공개 화면만. 모듈을 지우면 화면이 사라지고 기록은 남는다
- **공개 경계는 `core_public` 뷰다.** 숨긴 글·숨긴 스트리머·탈퇴 회원 이름이 새지 않는 것을 `verify:db` 가 **돌려서** 확인한다
- **차별점은 엮기다** — 글을 스트리머·맞대결·편성 일정·대회에 붙인다. 프로필·상대전적에서 들어오는 길은 첫 출시에 넣는다
- **모듈 시스템은 고치지 않는다.** 새로 생기는 규칙은 하나 — 계약에 회원용 쓰기 함수를 연다(§1)

## 왜 이 모양인가

### 한 문장 정의와의 관계

CLAUDE.md 의 정의("스트리머끼리 누가 누구를 이겼나")에서 커뮤니티는 벗어난 기능이다. 일반 게시판만 만들면
SOOP 방송국 게시판·갤러리·에펨의 열화판이 된다 — 프로필만 예쁘게 만들면 lolsoop 의 열화판이 된다는 것과 같은 구조다.
그래서 **글이 이 사이트의 사실에 붙는 것**을 처음부터 넣는다(스트리머 태그와 프로필·맞대결 링크는 2단계, 일정·대회는 3단계, 승부예측은 후속).

### 왜 플랫폼 공간인가

PLATFORM-LAYER-PLAN 의 기준: **게임마다 계산 규칙이 달라지면 게임 층, 게임이 속성이면 플랫폼 층.**
글에서 게임은 속성이다 → 플랫폼. 롤·FC 머리말 끝의 "커뮤니티" 메뉴는 기존 규칙대로 `?game=<그 게임>` 을 달고 로비로 온다.

### 왜 편성표 방식인가 (2차 개정에서 바꾼 이유)

처음 판은 글·댓글을 모듈 스키마(`mod_community`)에 뒀다. core 는 모듈 안을 볼 수 없다(계약 4조). 그 결정 하나 때문에
편성표에는 없던 장치 다섯 개가 따라 붙었다.

| 따라 붙은 장치 | 왜 필요했나 |
|---|---|
| 관리자 화면 안에 모듈 화면을 띄우는 자리 | core 관리자 화면이 모듈 표를 읽을 수 없다 |
| 관리자 판정을 계약으로 옮기기 | 모듈 서버 액션이 `requireAdmin` 을 부를 수 없다 |
| 모듈 안의 공개 뷰 | `core_public` 이 하는 일을 모듈 안에서 한 번 더 |
| 모듈 표 검사를 `verify:db` 에 따로 붙이기 | `verify:db` 는 core 만 올린다(`scripts/verify-db.ts:64`). 로더에 `includeModules` 옵션은 있지만 켜고 검사를 따로 더해야 한다 |
| 로비·프로필에 모듈 조각을 싣는 장치 | 로비·프로필이 모듈 표를 읽을 수 없다 |

편성표 방식이면 다섯 개가 모두 필요 없다. 검증은 기존 `verify:db` 경로를 그대로 쓰고(`verify-schedule-db.ts` 처럼), 관리자 화면은
`/admin/schedule` 옆에 놓이고, 로비의 "새 글" 은 core 가 바로 읽는다. 대가는 둘이다.

- **계약에 쓰기 함수가 처음 생긴다.** 회원이 모듈 화면에서 글을 쓰기 때문이다. 세션 확인·검증·저장은 core 접근자 하나가 다 하고, 모듈은 폼 값을
  넘기기만 한다 — 편성표 관리자 액션과 `saveScheduleEntry` 의 관계와 같다
- **모듈을 지워도 기록은 남는다.** 편성표도 같다

처음 판의 반대 근거("core 에 두면 모듈이 껍데기가 된다")는 편성표 모듈이 바로 그 모양으로 잘 돌고 있어서 약했다.
ARCHITECTURE 의 core 정의("사실의 저장과 수집·**검수**")에도 신고 처리가 들어간다.

### 왜 Supabase Auth 가 아닌가

① 앱은 supabase-js 를 전혀 안 쓰고 `postgres.js` 로 직결한다 ② Supabase Auth 를 쓰면 인증 서버(GoTrue)가 하나 더 생긴다 —
자체 호스팅으로 옮길 수는 있지만 그 서버를 직접 운영해야 한다 ③ 그 서버는 PGlite 에 올릴 수 없다.
→ 별도 인증 서버 없이 지금의 Postgres·PGlite 검증 구조("가짜는 HTTP 경계 하나뿐")를 그대로 쓰려고 직접 관리한다.

### 단순함의 기준 — 확장 지점 (4차 개정, 5차에서 기준을 좁힘)

첫 출시의 기능 범위는 작게 둔다. 단순함은 표·파일 개수가 아니라 **다음 기능을 붙일 때 기존 데이터와 호출 경로를 얼마나 바꿔야 하는가**로 판단한다.
**기존 데이터의 의미를 잃지 않고 명확한 기본값으로 전환할 수 있으며, 변경 범위가 정해져 있는 기능은 필요한 시점까지 미룬다.**
미룬 것은 넓힐 자리와 함께 바꿔야 할 범위를 여기 적어 둔다.

| 축 | 지금 | 넓힐 때(바꿔야 할 범위) | 지금 만들지 않는 이유 |
|---|---|---|---|
| 신원 확인 진입점 | 웹 쿠키 → 세션 토큰 → 접근자 | 앱은 요청 헤더로 같은 세션 토큰을 보낸다. 접근자는 그대로 | 이미 나뉘어 있다(§1 계약) |
| 게시 공간(게시판) | 하나 — 칸 없음 | `community_board` 표 + 글의 `board_id`. 기존 글은 기본 게시판으로 | 기존 글의 의미가 기본 게시판으로 그대로 옮겨진다. 팬 공간·비공개 게시판은 아직 계획에 없다 |
| 게임 · 말머리 | `game_code` · `topic` | 값을 늘린다 | — |
| 읽기 범위 | 전부 공개 — 칸 없음 | 범위 칸 + 권한 판정 + 목록·상세·검색·캐시가 모두 그 범위를 따르게. **상태(`published`)와는 다른 축이다** | 칸 하나로 끝나지 않는다 — 공개 아닌 공간이 실제로 생길 때 범위 전체를 함께 설계한다. 그때까지 `core_public` 은 **누구나 읽어도 되는 것만** 낸다 |
| 작성자 · 공지 | 공지 = 작성자 없음(운영자). 관리자는 Basic 인증 하나 | 운영자가 **여럿이 되기 전에** 기록 방식을 바꾼다 — 공지 작성자 = 실제 운영자 회원, 화면 표시("운영자")는 역할로, 권한 검사도 함께. 과거 공지(작성자 없음)를 새 운영자 개인의 글로 소급해 해석하지 않는다 | 실제 운영자가 한 명(Basic 인증 하나)인 동안은 기록할 작업자가 늘 같다 |
| 본문 형식 | 일반 텍스트 | `body_format` 칸(기본 `plain`). 칸을 더하는 순간 기존 글이 `plain` 으로 채워져 **새 문법으로 다시 해석되지 않는다** | 기존 글을 모두 `plain` 으로 해석하면 된다 — 의미가 그대로다 |
| 부가 데이터(첨부·투표·승부예측) | 스트리머 태그 | 글 id 에 표로 연결한다. **본문이나 JSON 한 칸에 몰지 않는다** | 기능마다 표가 느는 건 정상 비용이다 |
| 후속 작업(알림·검색 색인) | 없음 | 저장과 **같은 트랜잭션**에 할 일을 남기고, 재시도해도 한 번만 처리한다. 삭제·숨김·파기도 같은 접근자에서 따라가게 한다 | 모든 쓰기가 이미 접근자 경로 하나를 지난다. 이벤트 장치는 필요한 곳에만(ARCHITECTURE §4) |
| 화면 경로 | 2개 + `?write=1`·`?edit=1` | 독립 화면이 늘면(내 활동·게시판 관리 등) 이름 있는 경로를 지원한다 | 이번 출시엔 모듈 시스템을 넓히지 않는다 |

### 계약 — 쿠키는 계약에서, 판단은 접근자에서

```
모듈 화면 → 계약 함수 → lib/auth/request.ts 가 쿠키에서 세션 토큰을 읽는다
                      → lib/db/community.ts 접근자가 그 토큰으로 세션을 확인하고 저장한다
```

- **접근자는 Next 를 모른다.** 토큰을 인자로 받는다. 그래서 `verify:db` 가 실제로 발급한 세션 토큰으로 **같은 접근자**를 부른다 — 검사를 건너뛰는
  시험용 함수가 없다. (`cookies()` 는 Next 요청 밖에서 부르면 오류다 — 확인함)
- **작성자는 언제나 토큰에서 정한다.** 모듈이 보낸 회원 id 를 쓰지 않는다
- 토큰을 읽는 곳만 진입점마다 다르다 — 웹은 쿠키, 나중의 앱은 요청 헤더. 같은 세션 표로 확인하고 같은 접근자를 부른다
- 쿠키를 읽는 곳은 `lib/auth/request.ts` 하나다. core 에 처음 생기는 `next/headers` 의존을 이 파일에 가두고, 워커는 import 하지 않는다.
  `tsc -p packages/core` 가 `next` 타입을 찾는지 확인한다(지금 `next` 는 루트 `node_modules` 에 있다)
- 계약에 여는 것: **공개 읽기**(`core_public` 만 — 목록·글·댓글) · **화면용 회원**(`currentMember()` — 로그인 표시, 내 추천 여부) ·
  **회원 쓰기**(글·댓글 쓰기·수정·삭제, 추천, 신고)
- **관리자 함수(숨김·삭제·제재·공지)와 정기 작업은 쿠키를 보지 않고, 계약으로 열지 않는다.** 관리자 화면 액션이 `requireAdmin` 뒤에 접근자를 직접 부른다(편성표 관리자와 같다)
- 구현 때 함께 고칠 문서: ARCHITECTURE "무엇이 core 고" (core 가 회원·커뮤니티 기록을 가진다) · 계약 2조("모듈은 core 표에 직접 쓰지 않는다.
  core 가 계약으로 연 쓰기 함수만 부른다") · `contract/index.ts` 머리 주석("전부 `core_public` 만 읽는다" → 공개 읽기·회원 읽기·회원 쓰기 구분)

### 모듈 경로 — 편성표와 같은 모양

`/community`(목록)와 `/community/[id]`(상세) 둘이다. 글쓰기는 `/community?write=1`, 수정은 `/community/[id]?edit=1` — 화면은 값이 `"1"` 인지로 가른다.
★ 값을 비우면 주소 함수가 그 쿼리를 지운다(`site-paths.ts` 의 `withQuery`) — 그래서 `?write` 가 아니라 `?write=1` 이다.
★ 한 모듈 안에 파라미터 없는 경로가 둘이면 `verify:modules` 가 막는다(`scripts/verify-modules.ts:316`). **이번 출시에서는** 모듈 경로를 넓히지 않는다.
독립 화면이 늘면(내 활동·게시판 관리 등) 쿼리 분기를 늘리지 말고 이름 있는 경로를 지원한다(§단순함의 기준).

## 2. 회원

### 식별자 — ARCHITECTURE §1 표에 세 줄이 는다

| 식별자 | 주인 | 불변? | 무엇 |
|---|---|---|---|
| `member.id` | **우리** | ✅ 영구 | 내부 키 · 글 작성자 키 · 작성자 필터 주소 |
| `member_identity (provider, subject)` | **로그인 제공자** | ✅ 불변 | 로그인 판정 키 — `puuid` 와 같은 자리 |
| `member.nickname` | **회원** | ❌ 바뀜 | 표시용. **조인·주소에 쓰지 않는다**(Riot ID 와 같은 규칙) |

★ 이름이 `member`(회원)인 이유: `account` 는 이미 게임 계정이다(`streamer_account`·`riot_account`·`fco_account`). "계정" 에
세 번째 뜻을 붙이지 않는다. `user` 는 Postgres 예약어다.

### 로그인

- **소셜 로그인만.** 비밀번호를 저장하지 않는다
- 첫 제공자: **카카오 + 구글**, 둘 다 OpenID Connect 로 붙인다. 카카오는 [카카오 로그인] 사용 설정을 켠 뒤 [OpenID Connect] 를 켠다(공식 문서로 확인).
  네이버는 검수 조건과 함께 나중에 `[확인 필요]`
- SOOP 로그인: "SOOP Open API 는 제휴 후 키 발급" 이라는 기존 기록(PLAN §9)뿐이고 공식 문서는 확인하지 못했다 `[미확인]`.
  되면 스트리머 본인 인증의 가장 강한 근거라 따로 조사할 가치가 있다
- **받는 것은 제공자 고유 id(`sub`) 하나다.** 이메일·실명·프로필을 받지 않아 수집 범위를 줄인다(제공자 id 와 활동의 연결은 남는다)
  `[확인 필요: 동의항목 없이 회원번호만 받는 실제 응답 — 개발 앱으로 확인]`
- **프로토콜은 `openid-client`(6.8.8 고정)가 한다** — PKCE·`state`·`nonce`, 코드 교환, ID 토큰 검사.
  ID 토큰은 토큰 엔드포인트에서 TLS 로 직접 받으므로 서명 대신 TLS 서버 검증을 쓴다(OIDC 규격 — openid-client 기본값). 발급자·대상 앱·만료·`nonce` 는 검사한다.
  **회원·세션은 직접 관리한다** — 라이브러리는 "이 사람은 카카오의 sub X 다" 까지만 답한다
- 제공자 설정·로그인 흐름은 `core/lib/auth/oauth.ts` 한 곳(Next 를 모른다). 검증은 가짜 제공자의 메타데이터를 `Configuration` 에 넘기고
  HTTP 를 가짜로 보낸다(`customFetch`) — "가짜는 HTTP 경계뿐"(`scripts/fake-riot.ts`)이 그대로 지켜진다
- `state`·PKCE 검증값·`nonce` 는 **제공자 이름과 함께** 짧게 사는 httpOnly 쿠키(콜백 경로에만)에 담고 **한 번 쓰면 지운다** — 콜백 재사용과 제공자 혼동을 막는다
- 콜백의 `redirect_uri` 는 요청 주소가 아니라 **`SITE_ORIGIN` 기준으로 다시 만든 주소**에서 나온다 — openid-client 가 콜백 주소에서 쿼리를 뺀 값을
  토큰 요청에 쓰므로, 프록시 뒤에서 호스트·스킴이 달라지면 로그인이 실패한다
- 처음 로그인하면 가입 마무리 화면 — 닉네임 + 약관·처리방침·운영정책 동의(만 14세 이상 확인 포함). 동의 시각을 `member.agreed_at` 에 남긴다.
  닉네임이 없으면 읽기만 된다
- 로그인 뒤 돌아갈 주소(`?next=`)는 **내부 주소만** 받는다 — `adminReturn` 과 같은 검사(열린 리다이렉트 방지)

### 세션

- 쿠키에는 무작위 토큰, DB 에는 그 **sha256 만**(`member_session.token_hash`)
- HttpOnly · Secure(운영) · SameSite=Lax · **로그인부터 30일, 연장하지 않는다** — 화면을 그리는 중에 DB·쿠키를 쓰지 않으려고
- CSRF: 서버 액션은 POST 전용이고 Next 가 Origin ↔ Host(또는 `X-Forwarded-Host`)를 비교한다
  (`node_modules/next/dist/docs/01-app/02-guides/data-security.md` "Allowed origins"). SameSite=Lax 와 겹으로 막는다.
  ★ Caddy 뒤(M4)에서 `X-Forwarded-Host` 가 맞게 넘어가는지 배포 때 확인한다 — 틀리면 모든 쓰기가 막힌다
- 로그아웃 = 세션 행 삭제 + 쿠키 삭제

### 닉네임 규칙

- 2~12자. 정규화 키(NFKC · 소문자 · 공백과 기호 제거)로 중복을 판정한다
- ★ **스트리머 사칭 차단** — 등록 스트리머의 `display_name`·`aliases` 와 정규화 키가 같으면 거부한다. 스트리머 커뮤니티에서 가장 먼저 터지는 사고다
- 예약어: 운영자 · 관리자 · admin · SOOP …

### 탈퇴와 재가입

- 탈퇴: **회원 행을 잠근 뒤**(쓰기와 같은 잠금 — §3 쓰기) 세션 삭제, `nickname` NULL, `status='withdrawn'`. 회원 행은 남긴다 — 글의 작성자 키가 깨지지 않게
- 글·댓글은 기본으로 익명으로 남는다. 탈퇴 화면에서 **"내 글·댓글도 지우기"** 를 고르면 같은 트랜잭션에서 삭제한다(30일 뒤 파기)
- **로그인 연결(`member_identity`)은 바로 지우지 않는다.** 남겨 두는 기간은 **저장하지 않고 그때그때 계산한다** — 탈퇴 뒤에 걸리거나 풀린 제재도 바로 반영된다

  | 탈퇴 시각과 제재 기록 | 같은 소셜 계정으로 가입 못 하는 기간 |
  |---|---|
  | 제재 없음 | 탈퇴 + 30일 — 신고 중복 제한·쓰기 한도를 탈퇴로 초기화하는 것을 막는다 |
  | 기간 제재(탈퇴 전이든 뒤든) | 제재가 끝날 때까지(탈퇴 + 30일보다 짧으면 30일) |
  | 영구 제재 | 제재 시각 + 1년 — 무기한 보관하지 않는다 |

- 계산 함수는 `metrics/community.ts` 하나다. 로그인과 정기 작업이 같은 함수를 쓴다(원칙 6 — 두 군데서 따로 계산하지 않는다)
- 기간 안에 로그인하면 "탈퇴한 계정입니다 — ○월 ○일부터 다시 가입할 수 있습니다". **기간이 끝났으면 로그인 처리에서 옛 연결을 지우고 바로 새로 가입한다**
  (정기 작업을 기다리지 않는다). 정기 작업은 다시 오지 않는 사람의 연결을 지운다
- ★ 한계: **다른 소셜 계정**으로 새로 가입하는 것은 막지 못한다(휴대폰 본인확인 없이는). 그래서 신고 수로 자동으로 내리지 않는다(§3)

### 표

정본은 [`db/migrations/0081_member.sql`](../db/migrations/0081_member.sql) — 스키마의 출처는 마이그레이션 하나다(이 문서에 사본을 두지 않는다).

- `member` — 닉네임·정규화 키(UNIQUE)·상태·동의 시각·탈퇴 시각. 탈퇴해도 행은 남는다. 재가입 제한 기간은 저장하지 않는다
- `member_identity (provider, subject)` — 로그인 연결. 탈퇴해도 재가입 제한 기간이 끝날 때까지 남는다
- `member_session` — 토큰의 sha256 · 만료(로그인 + 30일)
- 모두 RLS ON(PostgREST 로 새지 않게 — SETUP §2)

### 화면

- 머리말 오른쪽: "로그인" / 닉네임(내 정보). ★ 머리말이 쿠키를 **먼저** 읽는다 — 그래서 머리말을 쓰는 화면은 전부 동적 렌더다.
  제공자 설정을 먼저 보고 빠져나가게 짰더니 빌드 때 설정이 없던 약관 화면이 정적(○)으로 굳었다 — 운영에서 설정을 넣어도 로그인 자리가 안 나오는 상태였다.
  쿠키가 없으면 DB 를 읽지 않으므로 비로그인 방문의 비용은 그대로다
- `/login`(제공자 버튼) · `/me`(가입 마무리: 닉네임·동의 / 그 뒤: 닉네임·로그아웃·탈퇴) · `/terms` · `/privacy` · `/policy`(운영정책 — 셋 다 **초안** 표시)
- 환경변수: `KAKAO_CLIENT_ID`·`KAKAO_CLIENT_SECRET`(선택)·`GOOGLE_CLIENT_ID`·`GOOGLE_CLIENT_SECRET`·`SITE_ORIGIN`(운영 필수). client id 가 없는 제공자는 버튼을 그리지 않는다
- **관리자 Basic 인증은 그대로 둔다.** 관리자를 회원 역할로 옮기는 건 자원봉사 운영자가 필요해질 때 따로 정한다

## 3. 커뮤니티 기록 (core)

### 분류 — 게임 × 말머리

- **게임**(`game_code`): `lol` · `fconline` · NULL(공통 = 게임 무관). ★ `platform`·`common` 같은 값을 **저장하지 않는다** —
  공간과 게임은 다른 축이다(PLATFORM-LAYER-PLAN). 공통은 "게임이 없음" 이다. 게임을 추가할 때 CHECK 를 같이 넓힌다(기존 결정)
- **말머리**(`topic`): 자유 · 질문 · 정보 · 경기 이야기 · 공지(운영자만). 게임과 독립 — 어느 게임에서든 같은 목록
- **게시판을 게임×주제로 쪼개지 않는다.** 글이 적은 초기에 칸이 많으면 전부 비어 보인다. 한 흐름에 필터 두 개로 시작하고, 칸이 필요해지면 말머리를 늘린다
- 주소 — **필터는 전부 URL 에 두고 서버에서 거른다**(편성표와 같다. 공유한 주소가 같은 화면을 연다)

  | 주소 | 보이는 글 |
  |---|---|
  | `/community` | 전부(공통 + 모든 게임) |
  | `?game=lol` · `?game=fconline` | 그 게임 글만 — 게임 머리말의 커뮤니티 메뉴가 여기로 온다 |
  | `?game=common` | 공통 글만. ★ 필터 값일 뿐 저장값이 아니다(저장은 NULL) |
  | `&topic=question` | 말머리 |
  | `&s=<slug>` | 그 스트리머가 태그된 글 — 프로필의 "이 스트리머 이야기" |
  | `&a=<slug>&b=<slug>` | 두 사람이 **모두** 태그된 글 — 상대전적의 "이 맞대결 이야기"(상대전적 주소와 같은 이름) |
  | `&author=<member.id>` | 그 회원의 글(닉네임은 바뀌므로 주소에 쓰지 않는다) |

- ★ `?game=lol` 의 목록에 **공통 글을 섞지 않는다.** 편성표의 `?game=` 과 뜻이 같아야 한다 — 좁히는 필터다
- 공지는 목록 위에 **최근 2개**를 보여 준다. 공통 공지는 모든 게임 필터에서, 게임 공지는 그 게임에서. 아래 목록(필터 결과)과는 섞지 않는다

### 글·댓글

- 글: 제목 1~100자 · 본문 1~10,000자 · 게임 · 말머리 · 스트리머 태그(최대 5명). 최신순만
- **본문은 일반 텍스트다.** 줄바꿈 + http(s) 주소 자동 링크(`rel="nofollow ugc noopener"`). HTML·마크다운 없음 — `dangerouslySetInnerHTML` 을 쓰지 않는다
- **이미지 업로드는 없다.** 저장소(S3)가 M4 에 준비된다. 그 전엔 링크
- 댓글: 1~1,000자. 대댓글은 **같은 글의 공개된 최상위 댓글에만** 단다. 같은 글은 DB 가 (글, 부모) 복합 FK 로 보장하고, 최상위·공개 여부는 접근자가 확인한다
- 수정: 작성자만, "수정됨" 표시. 수정 전 원문은 남기지 않는다
- 추천: **추천만, 비추천 없음.** 스트리머 이야기에서 비추천은 팬덤끼리 몰려가는 도구가 된다. 회원당 글 하나에 한 번 — 다시 눌러도 한 번만 센다
- **추천·댓글 수는 저장하지 않는다.** 공개 뷰가 셀 때마다 센다 — 숨김·해제·삭제마다 수를 맞출 일이 없다. 느려지면 그때 저장한다
- **조회수는 두지 않는다.** 새로고침으로 부풀고, 중복 제거 없이 띄우면 숫자로 거짓말하는 셈이다(원칙 3)
- 공지는 관리자 화면에서만 쓴다. 작성자는 "운영자"(`author_id` NULL). DB CHECK 는 '작성자 없음 = 공지' 짝을 지키고, 요청자가 관리자인지는 접근자가 지킨다

### 상태 — 공개 · 숨김 · 삭제 (글·댓글 같은 규칙)

- **공개는 `status = 'published'` 하나다**
- **작성자 수정은 공개 상태에서만 된다.** 수정은 상태를 바꾸지 않는다 — ★ 운영자가 숨긴 글은 작성자가 고쳐도 다시 공개되지 않는다
- **신고 당시 내용은 신고 행에 남는다**(제목·본문, 관리자만 본다). 신고 뒤 작성자가 고쳐도 운영자는 신고된 내용을 보고, 관리자 화면은
  `edited_at` 이 신고 시각보다 뒤면 "신고 뒤 수정됨" 을 표시한다. ★ **신고만으로는 수정을 막지 않는다** — 신고자 한 명이 남의 편집을 막을 수 있게 되기 때문이다.
  수정을 막아야 하면 운영자가 숨긴다
- 작성자 삭제는 공개·숨김 상태에서 된다 → `deleted`. 숨김이었다는 사실은 운영 기록(`community_moderation_log`)에 남아 있다
- 운영자: 숨김(공개 → 숨김) · 해제(**숨김 → 공개만** — 삭제된 글은 되살리지 않는다) · 삭제
- **임시조치**는 숨김의 한 종류다 — 운영 기록에 조치를 `blind` 로 남긴다. 30일이 지난 임시조치는 관리자 목록의 "다시 볼 것" 에 뜬다(기록에서 계산 — 자동 복구 없음)
- 숨김이 30일 넘게 그대로면 관리자 목록의 "확정할 것"(삭제 또는 해제)에 뜬다(역시 계산)
- 수정 충돌: 공개 뷰가 `version`(`updated_at::text`)을 내고, 수정 폼이 그 문자열을 그대로 돌려보낸다(편성표와 같다 — 시간 정밀도를 잃지 않는다).
  `updated_at` 은 **편집 폼이 저장하는 내용(제목·본문·게임·말머리·태그)이나 공개 상태가 바뀔 때** 바뀐다. 태그는 다른 표에 있어도 접근자가 글의
  `updated_at` 을 같이 바꾼다. 추천·댓글은 제외 — 추천·댓글이 달렸다고 쓰던 수정이 충돌하지 않는다
- 수정·삭제·운영 조치·신고 접수·파기는 대상 행을 `FOR UPDATE` 로 잠그고 소유·상태·version 을 같은 트랜잭션에서 확인한다(`saveScheduleEntry` 와 같은 방식, 잠금 순서는 §쓰기)

### 삭제와 파기

- **30일의 기준은 `deleted_at`** 이다(작성자 삭제든 운영자 삭제든)
- **파기**(정기 작업): 삭제 30일 뒤 제목·본문을 비우고(NULL) 스트리머 태그·추천을 지운다. 행의 뼈대(id·작성자 키·게임·말머리·시각)는 남긴다 —
  대댓글 자리와 신고 기록이 가리키는 대상이 사라지지 않게
- **글을 파기할 때 그 글의 댓글도 함께 파기한다**(상태를 삭제로, 본문을 비운다). 삭제된 글의 댓글은 이미 공개에서 빠져 있고, 따로 두면 원문이 영영 남는다
- **파기 보류**: 글이나 그 글의 댓글 중 하나라도 열린 신고가 있거나 최근 30일 안에 운영 조치가 있었으면 **글 전체를** 미룬다.
  따로 칸을 두지 않고 신고·운영 기록에서 계산한다. 권리침해 분쟁 중에 원문이 사라지면 판단할 근거가 없다
- **신고 당시 내용**은 그 신고를 처리하고 30일 뒤, 또는 대상이 파기될 때 비운다
- 위 기간을 처리방침에 그대로 적는다(§9)

### 표

정본은 [`db/migrations/0082_community.sql`](../db/migrations/0082_community.sql) — 이 문서에 사본을 두지 않는다. 표마다 지키는 것:

- `community_post` — 게임(NULL = 공통)·말머리·제목·본문·상태(공개·숨김·삭제)·삭제 시각·version(`updated_at`).
  CHECK: '작성자 없음 = 공지' 짝 · 삭제 ⇔ 삭제 시각 · 제목과 본문은 함께 비운다 · 비우는 것(파기)은 삭제된 글만
- `community_post_streamer` — 스트리머 태그(글 id 에 표로 연결 — 본문에 몰지 않는다)
- `community_comment` — (글, 부모) **복합 FK** 로 대댓글이 같은 글에만 달린다. 최상위·공개 부모인지는 접근자가 본다
- `community_post_vote` — (글, 회원) PK 라 두 번 눌러도 한 번
- `community_report` — 같은 대상 중복 신고 UNIQUE · **열린 신고는 신고 당시 내용(snapshot)을 반드시 갖는다** · 처리 ⇔ 처리 시각
- `community_sanction` — 쓰기 제한(NULL = 영구). 탈퇴 회원의 재가입 제한 기간도 여기서 계산한다
- `community_moderation_log` — 운영 조치와 사유(본문 없음). 임시조치(`blind`)·파기 보류·"확정할 것" 을 여기서 계산한다.
  `admin_audit` 에 넣지 않는다 — 행 전체(본문 포함)를 영구 보관해 파기 규칙이 깨진다
- 공개 뷰 `core_public.community_post`·`community_comment`·`community_post_streamer` — 누구나 읽어도 되는 것만. 하위 뷰는 부모 공개 뷰와 조인해 거른다.
  추천·댓글 수는 저장하지 않고 여기서 센다. 작성자 이름: `author_id` NULL 이면 운영자, `author_nickname` NULL 이면 탈퇴한 회원
- 모두 RLS ON

편성 일정·대회에 글을 붙이는 칸(`schedule_id`·`event_id`)은 3단계 마이그레이션에서 더한다.

### 쓰기 — 접근자 하나

- 권한·제재·검증·한도를 적용하는 **쓰기 경로는 하나**다 — 회원 화면·관리자 화면·정기 작업이 모두 이 경로를 지난다(파일은 기능별로 나눠도 된다).
  회원 쓰기 함수는 첫 인자로 **세션 토큰**을 받는다(§1 계약)
- **잠금 규칙 — 함께 판단하는 경로는 같은 행을 잠근다. 순서는 언제나 회원 → 글 → 댓글**(순서가 같아야 서로 기다리다 멈추지 않는다)
  - **회원 행**: 회원 쓰기(한도) · 탈퇴 · 제재 변경 · 로그인 연결 정리(정기 작업·로그인 때). 연결 정리는 잠근 뒤 재가입 기간을 **다시 계산**한다 —
    계산 직후 들어온 제재를 놓치지 않게
  - **대상 행**(댓글이면 글 → 댓글): 수정 · 삭제 · 운영 조치 · 신고 접수 · 파기. 신고는 공개 대상에만 받고, 파기는 잠근 뒤 열린 신고를 다시 확인한다 —
    신고와 파기가 겹쳐도 신고가 이기면 파기가 미뤄진다
  - 회원 쓰기의 순서: 토큰으로 회원 찾기 → 회원 행 잠금 → **잠근 뒤 세션·회원 상태·제재를 다시 확인** → (대상이 있으면) 대상 행 잠금 → 한도 → 저장.
    기다리는 동안 탈퇴가 끝났으면 다시 확인에서 거부된다
  - 행 잠금은 트랜잭션 안에서 끝나므로 Supabase 트랜잭션 풀러에서도 돈다
- 검증(폼 검증과 별개로 다시): 길이 · 게임과 말머리 값 · 태그 스트리머가 공개 명부에 있는지 · 쓰기 한도
- 수정·삭제는 **소유**를 확인한다 — 인증만으로는 부족하다(Next 16 `data-security.md` 감사 항목)
- 한도: 글 1분 1개·하루 20개, 댓글 10초 1개·하루 300개, 신고 하루 30개. 숫자는 출시 뒤 조정한다
- 신고·추천·닉네임 중복은 UNIQUE 제약이 막는다 — 동시 요청에도 하나만 들어간다

### 신고·운영 — core 관리자 `/admin/community`

- 신고 사유: 스팸 · 욕설/비하 · 개인정보 노출 · 명예훼손/허위사실 · 불법 · 기타(설명 필수)
- **자동으로 내리지 않는다.** 한 사람이 다른 소셜 계정으로 신고 수를 채울 수 있다(§2 한계). 대신 목록은 **개인정보 노출·명예훼손이 먼저**, 그다음 신고 수 순이다
- 신고마다 **신고 당시 내용과 지금 내용**을 나란히 보여 준다("신고 뒤 수정됨" 표시)
- 처리: 유지 · 숨김 · 임시조치 · 삭제 · 해제 + 작성자 쓰기 제한(1일 · 7일 · 30일 · 영구). 한 화면에서 하고, 처리마다 사유를 남긴다
- 공지 쓰기도 여기서 한다
- **임시조치**는 권리침해 주장(정보통신망법 제44조의2)에 쓴다 `[절차는 출시 전 확인 — §9]`
- 스트리머 본인 요청: 푸터의 "노출을 원하지 않으시면 문의해 주세요. 즉시 내립니다" 경로를 글에도 적용한다. 처리 사유에 '당사자 요청'
- 관리자 메뉴(`AdminShell` 의 `NAV`)에 "커뮤니티" 를 더한다 — 편성표와 같은 자리

### 정기 작업 — `worker -- community-housekeep`, 하루 한 번

- 삭제 30일이 지난 글·댓글 파기(글은 댓글과 함께, 보류 대상 제외 — 대상 행을 잠근 뒤 다시 확인)
- 처리하고 30일이 지난 신고의 당시 내용 비우기
- 재가입 제한 기간이 끝난 탈퇴 회원의 로그인 연결 삭제(회원 행을 잠근 뒤 §2 의 계산 함수로 다시 계산)

```json
}
```

편성표가 `navOrder: 10` 이라 머리말이 PLATFORM-LAYER-PLAN 의 그림대로 "편성표 · 커뮤니티" 가 된다. 자기 표·잡이 없다(편성표·대회 모듈과 같다).

- `ui/page.tsx` 가 `params.id` 와 `searchParams.write === "1"`·`searchParams.edit === "1"` 로 목록·글쓰기·상세·수정을 가른다(편성표 화면이 `params.id` 로 가르는 것과 같다)
- `server/actions.ts`(`"use server"`)는 폼 값을 계약의 쓰기 함수에 넘기기만 한다 — 판단은 core 하나. 편성표 모듈의 `server/load-window.ts` 와 같은 자리
- 목록: 위에 게임 칩(전체 · 공통 · LOL · FC) + 말머리 칩, 그 아래 공지 2개, 그 아래 목록. 행은 말머리 · 게임 표기 · 제목[댓글 수] · 작성자 · 시각 · 추천.
  편성표의 칩(`sched-chips`)과 낮은 채도 표 문법을 따른다. 페이지는 커서(`created_at`, `id`) — OFFSET 아님
- `?s=`·`?a=&b=` 목록의 머리에 그 사람(들)의 이름과 프로필·상대전적 링크. 비었으면 "아직 글이 없습니다 · 첫 글 쓰기"(태그가 채워진 글쓰기)
- 상세: 본문 · 스트리머 태그(`profileHref` 로 프로필 링크) · 추천 · 댓글. 숨긴 글·없는 id 는 404. **숫자가 아닌 id 도 404** — 캐스트 오류로 500 을 내지 않는다
- 글쓰기·수정: 로그인 안 했으면 로그인으로 보내고 돌아온다. 게임 기본값은 들어온 주소의 `game`(없으면 공통), `?s=`·`?a=&b=` 에서 왔으면 그 스트리머가 태그된 채로
- LOL·FC 표기는 편성표 막대의 표기와 같은 모양. 공통은 표기 없음
- 휴대폰: 가로 스크롤 없음, 16px 여백, 표 → 카드. CSS 는 모듈이 가진다(`ui/community.css`)
- 화면 하나의 질의는 순서대로 보낸다 — 팬아웃을 늘리지 않는다(편성표 결정과 같다, PLAN §M4-1)

## 5. 사이트와 엮기 — 차별점

**첫 출시(2단계)** — 들어오는 길이 없으면 차별점을 겪을 수 없다

- 프로필(core)에 **"이 스트리머 이야기 →"** — 롤 프로필은 `roleHref("community", {}, { game: "lol", s: slug })`, FC 프로필은 `game: "fconline"`.
  게임 문맥을 같이 넘겨야 글쓰기의 게임 기본값이 그 게임으로 잡힌다. 편성표의 "다가오는 일정" 처럼 커뮤니티 모듈이 없으면 그리지 않는다
- 상대전적 화면(`versus`·`fc_versus` 모듈)에 **"이 맞대결 이야기 →"** — host 가 넘기는 `roleHref("community", {}, { game, a, b })`.
  모듈끼리는 서로를 모르므로(3조) 링크만 그린다

**3단계**

- **편성 일정·대회** → 글에 `schedule_id`·`event_id`(경기 이야기 말머리). 편성표 상세·대회 화면에 "이 일정 이야기 →"
- **로비 "새 글"** — core 가 자기 표를 바로 읽는다. 커뮤니티 모듈이 없으면 그리지 않는다(`roleHref` 로 확인 — "다가오는 일정" 과 같은 방식)
- **검색** — 제목·본문 `pg_trgm`. 확장은 0001 에서 이미 켜져 있다(스트리머 이름 검색용)

## 6. 후속

- **승부예측** — 편성 일정의 대결에 회원이 승자를 고르고 실제 결과(연결된 `event`)와 대조한다. "누가 누구를 이겼나" 에 바로 붙는
  커뮤니티 기능이다. 표본이 작으면 작다고 쓴다("12명 참여" — 퍼센트만 쓰지 않는다, 원칙 3)
- **알림** — 내 글의 댓글, 태그한 스트리머의 새 일정. 편성표 3단계(로그인 이후 개별 알림)와 같은 기반을 쓴다
- **이미지** — S3(M4) 이후. 그때 불법촬영물 등 기술적 조치 의무 대상인지 확인한다
- **스트리머 본인 인증** — 회원 ↔ 스트리머 연결은 **근거 필수**(원칙 2). 후보: SOOP 로그인(제휴), 방송국 공지에 인증 문구. 인증되면 뱃지 · 사칭 차단 예외
- **필요해지면 붙일 것** — 추천순 정렬 · 추천·댓글 수 저장(셀 때 느려지면) · 신규 가입자 링크 제한 · 닉네임 변경 주기 · 공지 고정 ·
  신고 자동 내림(한 사람이 여러 명을 채우는 문제부터)
- **자원봉사 운영자** — 회원 역할. 그때 관리자 Basic 인증을 회원 역할로 옮길지 같이 정한다

## 8. 검증 — 돌려서 확인한다

1. **비로그인 글쓰기(유동닉)** — 추천: 받지 않는다. 받을 수는 있다(자동입력 방지·IP 기반 한도·IP 보관). 다만 운영자 한 명이 감당할
   비용(스팸 대응·IP 라는 개인정보 보관·제재 회피 대응)이 크다. 읽기는 누구나
2. **첫 로그인 제공자** — 추천: 카카오 + 구글
3. **탈퇴 때 글** — 추천: 기본은 익명으로 남기고, 탈퇴 화면에서 "내 글·댓글도 지우기" 를 고를 수 있게
4. **재가입 제한 기간** — 추천: 제재 없음 30일 / 기간 제재는 끝날 때까지 / 영구 제재는 제재 뒤 1년
5. **파기 기간** — 추천: 삭제 30일. 보류는 신고 처리가 끝나고 30일
6. **추천만 / 추천·비추천** — 추천: 추천만
7. **게임 필터에 공통 글을 섞나** — 추천: 목록에는 섞지 않는다(편성표 `?game=` 과 같은 뜻). 공통 공지만 목록 위에 보인다
8. **사이트 이름**(PLATFORM-LAYER-PLAN §미정) — 약관·처리방침에 서비스명이 들어가므로 **1단계 공개 전**에 정해야 한다
