# 화면 간 규칙 통일 계획 (2026-10-13)

> 전체 감사 결과(정렬·데이터 노출의 분기·중복)를 검증하고 사용자 결정을 반영한 계획이다.
> **구현 반영 완료.** 변경한 계약·소비 화면·제거한 경로·검증 결과·DB 적용 상태는 [구현 결과](SITE-CONSISTENCY-RESULT.md)에 기록한다.

## 0. 왜 갈라졌나 — 고칠 대상은 "구조"다

감사에서 나온 어긋남은 대부분 같은 원인 네 가지로 생겼다. 증상마다 한 곳씩 고치면 또 갈라진다.

| 원인 | 사례 |
|---|---|
| **규칙을 화면마다 다시 적었다** | 우승 수(목록만 `placement_rank=1`), FC 출전·평점 정의 3개, 맞라인 판정 화면 2곳, 구단가치 7일 계산 2개 |
| **이름표를 화면마다 따로 들고 있다** | CK·이벤트전 표기 5곳(내전/CK, 이벤트/이벤트전/이벤트 매치) |
| **같은 조건을 두 번 적었다** | 편성표 결과 링크 ↔ 상세 페이지가 열리는 조건 |
| **새 규칙을 넣고 옛 경로를 안 지웠다** | 랜드는 판 단위로 바꿨는데 결과 칸·요약·칩은 과반 판정. 연도(세트 단위)와 기간(다전제 단위) 두 자르기가 동시에 걸림 |

그래서 모든 단계는 다음 네 가지를 **한 묶음**으로 끝낸다.

1. **주인 하나** — 그 개념의 규칙은 `packages/core` 한 곳에만 있다(SQL 이 필요한 규칙은 뷰 하나 또는 SQL 조각 하나).
2. **옛 경로 삭제** — 새 규칙으로 옮긴 커밋에서 화면 쪽 계산·이름표·중복 조건을 지운다. "나중에 정리"는 없다.
3. **재발 방지 검사** — 계약을 우회하거나 알려진 옛 계산을 되살리면 `npm test` 또는 `verify:modules` 가 실패하도록 한다. 단순 문자열 금지 대신 import·계산 위치 검사와 소비 화면의 회귀 테스트를 함께 둔다. 정적 검사만으로 모든 중복 계산을 탐지할 수 있다고 보장하지 않는다.
4. **교차 검증** — 같은 데이터를 여러 화면 경로에 넣어 같은 숫자가 나오는지 확인한다. SQL 집계는 TS 함수를 못 부르므로 `verify:db` 에서 SQL 결과와 core 함수 결과를 대조한다.

## 2. 단계

### 선행 — 미커밋 작업 정리
⑥ site 처리(`site-paths.ts`·`schedule/ui/paths.ts`), ⑧ 타이포 토큰(`globals.css`), FC 메인의 최근 행사·7일 계산(`fc/page.tsx`·`club-value.ts` `valueChangeWithin`)은 **사용자가 다른 세션의 미커밋 작업이라고 전달한 코드**다.
요청한 선행 커밋을 확인한 뒤 구현에 착수한다. 착수 때 기준 커밋과 남은 diff를 확인하고, 다른 변경을 되돌리거나 이 작업에 일괄 커밋하지 않는다. 현재 git 상태만으로 다른 세션이 계속 수정 중인지까지 판단하지 않는다. 계획 문서 보완은 이 선행 작업과 독립적이다.

실행 기록: 이후 사용자의 “이제 수정 진행해” 지시에 따라 `637b531`과 착수 시 작업 트리 사본을 기준으로 기존 변경을 보존하며 구현했다. 선행 작업이나 이번 변경을 임의로 일괄 커밋하지 않았다.

### ① 행사 종류 — 이름표·목록·링크

**주인**: `packages/core` 에 행사 종류 모듈 하나.
- `eventKindLabel(kind)` — 표기 하나(CK / 대회 / 스크림 / 이벤트전). 지금 5곳(`fc_tournaments/ui/model.ts:172`, `fc/page.tsx:125`, `metrics/schedule.ts:15`, `admin-labels.ts:16`, `tournament-shared.tsx:26`)을 이것으로 바꾸고 지역 맵은 지운다.
- 상세 지원 종류는 롤 = tournament, FC = 모든 행사다. 다만 **game·kind만으로 실제 상세가 열린다고 판정하지 않는다.** 공개 여부·slug·공개 경기/참가자 등 상세 조회의 조건을 공유하는 core 접근자를 만들고, 상세 조회와 편성표 결과 링크가 같은 적격 행사 집합을 읽는다. 편성표는 연결된 행사 ID들을 일괄 조회해 `{page, slug}`를 받는다. 지금 `schedule-public.ts:149`는 대회 목록 조건을 빌려 쓰므로, 이를 먼저 분리하지 않으면 D1 이후 FC CK 결과 링크가 사라진다.
- `listedInTournaments(kind) = kind === 'tournament'` — 롤·FC 대회 목록 공통(D1). `listFcoEvents`(`fconline.ts:313`)에 적용.

**같이 할 것**
- FC 경기 조회(`FcoGame`/`gameSelect`)에 행사 kind 포함 → 경기 화면 링크 문구가 종류를 따른다("대회 기록으로 이동"이 CK 에도 붙는 문제).
- FC 목록 주석(`fc_tournaments/ui/index-view.tsx:2-3` "대회·이벤트")과 화면 문구를 D1 에 맞게 고친다.
- 롤 `tournamentCategory` 의 실행되지 않는 `"ck"` 분기 삭제.
- 구형 `fco:link-event` CLI 와 `docs/FCONLINE-SITE.md:54` 안내 삭제. `linkFcoMatchToEvent` 함수는 검증 스크립트 4개(`verify-fco`, `verify-bracket`, `verify-fco-context`(제외 거부 검증), `fco-public-snapshot`)가 쓰므로 **`fco:context apply` 의 내부 함수로 바꿔 붙인 뒤** 지운다.

**검사**: 행사 종류를 다시 번역하는 지역 맵과 목록·상세 접근 조건의 중복 구현을 검사한다. 설명문 속 "내전"이나 이미 판정된 종류에 따른 표시 분기까지 일괄 금지하지 않는다. 대회·CK·숨김 행사·기록 없는 행사로 목록/상세/편성표를 함께 검증한다.
**완료 기준**: FC 대회 목록에 대회만. FC CK 상세가 경기 화면·메인·편성표 결과에서 열린다. 롤 CK 로는 결과 링크가 생기지 않는다(404 없음).

**주인**: core 의 `isTitle(row)` / `isRunnerUp(row)` = 대회(`kind='tournament'`)의 `placement_rank` 1 / 2. SQL 쪽은 같은 조건의 SQL 조각 하나.

**검사**: 우승·준우승 집계가 공통 규칙을 사용하는지 검증한다. 메달 표시처럼 순위를 표현하는 비교는 허용하고, 별도 우승 계산만 제거한다. 기존 `counts_toward_titles=false` 사례의 kind·순위를 대조해 D2의 올스타전 우승이 실제로 포함되는지 확인한다. historical migration을 제외한 실행 코드에는 옛 필드가 남지 않는다.
**완료 기준**: 같은 스트리머의 우승·준우승 수가 목록·프로필·상대전적 사이드바에서 같다(올스타전 우승 보유자로 확인).

### ③ 경기 결과 — 판정 하나, 랜드는 판정 없음 (D3)

- 날짜 정밀도가 낮은 대회(`game_creation_precision`)의 연도 경계 처리를 core 에 한 번 정의.
- **선택 유지**: 롤·FC 상대전적의 모드·기간·정렬을 주소에 두고, 공통 scope 계약으로 파싱한다. 탭 전환·좌우 바꾸기·새로고침·뒤로 가기 모두 같은 scope를 복원한다. key만 바꾸는 것으로 끝내지 않는다.
  - 상대전적은 최초 조회에서 해당 쌍의 공개 경기 중 **필터·집계에 필요한 최소 자료 전체**를 받는다. 현재처럼 조회 단계에서 500/200건으로 먼저 자른 자료를 전체로 간주하지 않는다. 처음부터 URL의 선택 기간만 받아 두면 이후 필터를 넓힐 수 없으므로, 선택 가능한 범위 전체를 확보한다. 클라이언트에서 공통 core 규칙으로 필터 → 범위 전체 요약 → 목록 표시 상한 순으로 처리한다. 필터를 바꿀 때 `history.replaceState`로 주소만 갱신하고 서버를 다시 부르지 않는다. 선수·슛 상세 원본 JSON은 이 자료에 포함하지 않는다.
  - **FC 경기 지표·사용 선수 탭은 전체 맞대결 기준(D8).** 서버에서 만든 ReactNode라 클라이언트 필터가 닿지 않는데, 이것을 scope 별 서버 집계로 바꾸지 않는다. 대신 탭 링크가 고른 scope 를 주소로 넘겨 목록 탭으로 돌아왔을 때 복원되게 하고, 두 탭의 "전체 맞대결 기준" 표시를 유지해 고른 필터가 적용된 것처럼 보이지 않게 한다.
- **상한 — 모든 곳**: 과거 실측이 상한 미만이었다는 이유로 정확성을 보장하지 않는다. 기간·모드를 **목록 표시 상한 전에 적용**하고, 요약(승패·합계)은 상한과 무관하게 해당 범위 전체를 집계한다. 개인 경기 목록은 DB에서 필터 후 집계·목록 조회를 하고, 상대전적은 위의 전체 최소 자료에 클라이언트 필터를 적용한다. 상한은 목록 줄 수에만 걸린다. 다전제는 묶음 단위로 잘라 중간에서 끊지 않고, 개인 목록은 `limit + 1`, 전체 자료를 가진 상대전적은 필터 후 묶음 수로 잘림 여부를 판정한다.
- **상한 — 커서 페이지는 개인 목록에만**: FC 개인 경기(상한 1000, 감사 당시 최대 640)와 롤 개인 경기 목록에 안정적인 날짜+ID 커서를 둔다(롤 개인은 이미 다전제 단위 20개씩). 상대전적 한 쌍(감사 당시 롤 최대 129 / 상한 500, FC 66 / 200)에는 커서를 만들지 않는다. 요약은 전체 범위의 정확한 값이고, 목록이 표시 상한을 넘으면 일부 기록만 보인다는 사실을 표시한다. 커서 없는 목록의 완전성과 요약 수치의 정확성을 같은 것으로 설명하지 않는다.
- **상한 검증**: 상한을 넘는 합성 자료로 ① 요약 합계가 전체와 같은지 ② 과거 기간 필터가 상한 전에 걸리는지 ③ 다전제가 끊기지 않는지 ④ 잘림 표시가 나오는지를 확인한다(커서가 있는 목록은 이어 보기까지).
- **전송량**: 롤 프로필 상대전적 탭(`listOpponentGames`, 상한 없음, 최대 2,101줄)을 SQL 집계로 바꾸고 펼칠 때만 경기 목록을 받는다.
- **FC 대회 성적**(`fc/s/[slug]/page.tsx:43,71`)을 1000건으로 잘린 경기 목록에서 계산하지 않는다. 경기 성적은 선택한 scope 전체로 집계한다. 참가·수상처럼 통산으로 유지할 정보는 독립 질의로 계산하고 화면에 "통산"을 명시한다. 통산 정보와 기간 지표를 같은 범위인 것처럼 섞지 않는다.

**완료 기준**: 해를 넘긴 다전제가 연도 필터에서 반쪽으로 잘리지 않는다. 경기 목록과 기간 요약은 같은 필터 범위를 사용하고, 목록이 잘려도 요약은 전체 범위를 집계한다. **FC 상대전적의 지표·선수 탭은 예외로 전체 맞대결 기준을 유지하며 그렇게 표시한다(D8).** 상대전적 필터 변경으로 서버 요청이 생기지 않고, 탭 전환·좌우 바꾸기·새로고침·뒤로 가기 뒤에도 주소의 선택이 복원된다.

- 게임별 색·히어로 연출은 유지.
- **검사**: 새 하드코딩 `font-size`/`text-[Npx]` 가 늘지 않게 기준선 검사.
- **화면 검토**: FC 메인·구단가치·롤/FC 전적·대회를 같은 화면 폭으로 나란히 비교한다. 이름·금액·날짜·보조정보의 역할별 크기와 표 행 높이·패딩을 확인하고, 모바일에서도 정렬 화살표 잘림과 줄바꿈을 확인한다. 히어로 전용 크기는 일반 데이터 표의 기준으로 삼지 않는다.

## 3. 순서

1. 선행 — 미커밋 작업 정리
2. ①의 공통 행사 종류·상세 접근 계약을 먼저 정의한다. ② 우승 집계도 이 정의를 사용한다.
3. ③ 경기 결과 · ② 우승 · ④ 기간 — 단계별로 모든 소비처를 이관한다. 기간 조회·커서와 DB 칼럼 제거가 포함되므로 작은 화면 수정으로 취급하지 않는다.
4. ① 행사 목록·링크 이관 완료(편성표 판정 분리 → 목록 좁히기 순)
5. ⑤ 구단가치 — D7 조회 결과 저장과 공통 조회/계산을 함께 이관
6. ⑥ 이동·커뮤니티
7. ⑦ 남은 표시(D6 팀 분류 포함) · ⑧ 공통 UI

각 단계는 그 규칙을 쓰는 화면을 **전부** 옮기고 옛 경로를 지운 상태로 검토한다. 통합할 커밋에도 이 단위를 유지하며, 다른 세션의 변경을 끼워 넣지 않는다. 스키마·지표를 건드린 단계는 `npm test`·`verify:db`·`verify:modules`, FC 변경은 관련 `verify:fco*`, 수집 변경은 해당 수집 검증을 통과시킨다. 실데이터 대조는 읽기 전용, 경계 조건은 테스트 데이터로 한다.

## 4. 교차 검증과 완료 기록

함수 단위 테스트가 통과하는 것만으로 화면 통일을 완료 처리하지 않는다. 각 단계에 변경한 계약·전체 소비처·제거한 구현·검증 결과를 남긴다.

| 같은 자료로 대조할 경로 | 확인할 결과 |
|---|---|
| FC 대회 목록 ↔ CK 상세 ↔ 편성표 결과 링크 | 목록에서 빠진 CK도 공개 상세가 있으면 접근 가능, 숨김/미지원 상세는 링크 없음 |
| 롤 스트리머 목록 ↔ 프로필 ↔ 상대전적 사이드바 | 같은 범위의 우승·준우승 수, 올스타전 포함 |
| 경기 기록 ↔ 상대전적 ↔ 연도 요약 ↔ 최근 칩 | 랜드 5승 5패 유지, 묶음 승무패 없음, 보너스 명단 표시 |
| encounter ↔ 챔피언 맞라인 ↔ 개인 기록 ↔ 대회 맞라인 | 포지션 불일치 경기의 동일한 제외 |
| 기간 요약 ↔ 경기 목록 | 필터 scope 동일, 상한 초과·연도 경계에도 합계 정확, 잘림 표시, 개인 목록만 이어 보기 |
| FC 상대전적 목록 ↔ 지표·선수 탭 | 필터 변경 시 서버 요청 없음, URL 선택 복원, 지표·선수 탭의 값과 "전체 맞대결 기준" 표시 유지(D8) |
| 구단가치 메인 ↔ 순위표 ↔ 상세 | 같은 대표 계정·값의 기준 시각·최근 7일 변화, 급등락은 BP 증감 총액 기준, 비율은 표시만, 실제 비교 기간 표시 |
| 솔랭 도전 듀오 요약·흐름 ↔ 멤버별 개인 전적 | 같은 팀으로 함께한 판만 듀오에 포함, 한 명만 뛴 판·서로 상대인 판은 개인 기록에만 포함 |
| 대회 목록/상세 ↔ 개인 대회 이력 | 수집 경로와 무관한 성적, 같은 유효 날짜·팀 분류 |
| FC/롤 프로필 ↔ 편성표 ↔ 커뮤니티 | 메뉴 유지, 사람의 두 게임 일정 표시, 공통 공지·프로필 링크 일치 |

DB 변경은 테스트 DB에서 새 설치와 기존 스키마 업그레이드를 모두 확인한다. `counts_toward_titles` 제거 시 의존 뷰·권한 복원, 조회 결과 저장 도입 시 기존 성공 스냅샷 보존을 검증한다. 실제 DB 적용 여부와 적용한 마이그레이션은 구현 결과 보고에서 별도로 명시한다.
