# ck-local 결과창 판별기 학습 계획

작성: 2026-10-01. 상위: [CK-LOCAL-FIX-PLAN.md §9](CK-LOCAL-FIX-PLAN.md). 실험 폴더(`scripts/ck-local/`)와 함께 지울 수 있게 만든다.

## 0. 한 줄

로컬 모델에게 결과창을 **말로 설명하던 것**(프롬프트)을 그만두고, Claude 가 지금까지 직접 확인한 **실제 CK 결과창 사진으로 학습**시킨 작은 판별기를 쓴다.
판별기가 썸네일 모든 칸(3초)에서 결과창을 찾고, Claude 는 골라 준 원본만 읽는다.

## 1. 대상 — 스트리머 CK 결과창만

- **포함**: 스트리머 본인(또는 화면에 띄운) **롤 클라이언트 결과창** — 승리/패배 제목 + 점수판·그래프·룬 탭.
- **제외**: 공식 대회 채널(`lolbjmatch`, `afbjmatch`)의 사진 전부. 멸망전은 결과 화면을 방송 그래픽으로 만들고
  시즌마다 컨셉이 바뀐다. 우리가 모으는 건 CK 라서 학습에서 뺀다(정답으로도, 오답 예시로도 쓰지 않는다).
- 실측(2026-10-01): DB 의 결과창 표시 1,846장 중 1,602장이 공식 채널 방송 그래픽이었다. 스트리머 쪽은 약 250장.
  DB 의 `kind: result` 는 "결과를 읽은 근거 화면"이라는 뜻이라 클라이언트 결과창과 같지 않다 — **그대로 정답으로 쓰지 않는다.**

## 2. 정답 종류 (판별기가 고르는 것)

| 라벨 | 뜻 | 예 |
|---|---|---|
| `result` | **클라이언트 결과창** (찾을 대상) | 승리/패배 + 점수판·그래프·룬 탭. 창이 일부만 보이거나 일부 가려도 포함 |
| `ingame` | 게임 중 | 맵이 보이는 화면. Tab 점수판·상점·리플레이·남의 방송 속 게임 포함 |
| `client` | 롤 클라이언트 기타 | 로비, 사용자 설정 게임 방, 챔피언 선택, 로딩 |
| `other` | 롤 아님 | FC, 토크, 웹페이지, 다른 게임 |

헷갈리던 화면(Tab 점수판 = `ingame`, 챔피언 선택 = `client`)을 **따로 가르쳐** 경계를 잡는다. 로직은 `result` 확률만 쓴다.

## 3. 재료 — 결과창 주변의 실제 썸네일

- 스트리머 채널의 결과창 사진(약 250판)마다, 그 시각을 담은 **썸네일 시트 한 장**(5분 = 100칸)을 받는다(시간축: `vod-timeline.mjs`).
  한 장에 게임 끝 → 넥서스 폭발 → 결과창 → 로비가 다 들어 있어 가장 헷갈리는 순간이 모인다.
- `other` 재료: 이미 받아 둔 FC·토크 VOD 썸네일(시험용 VOD, 308장 세트).
- 원본을 줄여 흉내 내지 않는다 — 판별기가 실제로 볼 썸네일로 학습한다.

## 4. 정답 달기 — 자동 초벌 + 헷갈리는 칸만 검수

1. **초벌**: 결과창 사진 시각의 칸 = `result`. 나머지 칸은 비워 둔다(모름).
2. **1차 학습**을 초벌로 한다(결과창 칸 vs 결과창에서 1분 이상 떨어진 칸).
3. 판별기가 **자신 없어 하는 칸**과 **초벌과 어긋나는 칸**만 몽타주로 뽑아 Claude 가 4종 라벨을 단다(대화 안에서).
4. 다시 학습 → 3 반복(2~3번). 수만 칸 중 검수는 수백~천 칸이 되게 한다.
5. 수정한 정답은 `out/ck-detector/labels.jsonl` 에 쌓는다 — 다음 학습에도 쓴다.

## 5. 판별기 구조

- **특징 추출기(고정)**: 공개 이미지 모델 — SigLIP·CLIP·DINOv2 중 2~3개를 비교해 고른다. 학습하지 않는다.
- **판별기(학습)**: 그 위의 작은 4종 분류기(로지스틱 회귀 → 부족하면 작은 MLP).
- 이유: 결과창 판 수가 수백이라 큰 모델을 통째로 학습하면 외운다. 고정 추출기 + 작은 분류기는 적은 데이터로도 일반화되고,
  썸네일 한 칸에 몇 ms 라 5시간 방송 6,000칸을 1분 안에 본다.
- 입력: 썸네일 192×108 을 비율 유지(위아래 여백)로 추출기 입력 크기에 맞춘다.

## 6. 시험 — 처음 보는 스트리머, 판 단위

- **스트리머 단위로 떼어 시험**한다(예: 김민교로 배우고 이상호로 시험). 같은 스트리머는 VOD 가 달라도 화면 배치가 비슷해 점수가 부푼다.
  새 스트리머가 와치리스트에 들어와도 통하는지가 중요하다.
- **판 단위 채점**: 시험 VOD 20개 정도의 썸네일 전체를 실제처럼 돌려,
  (1) 알려진 판마다 결과창 후보가 잡혔나(재현율) (2) 시간당 가짜 후보 수 (3) 후보 원본 재확인 뒤 남는 가짜.
- 놓치는 쪽이 비싸므로 **놓침이 거의 없는 기준**에서 가짜가 얼마나 나오는지 본다. 합격선은 숫자를 보고 사용자와 정한다.

## 7. 적용 뒤 흐름

로컬: 모든 칸 판별 → 연속으로 걸린 칸을 후보로 묶음 → 후보마다 원본 1~2장(가장 잘 보이는 것) →
Claude: 원본 판독·같은 판 묶기 · 몽타주에서 "롤은 했는데 후보가 없는 구간" 점검 · 기록(ck-research 규칙).
Claude 의 후보 판정(진짜/가짜)은 새 정답으로 쌓여 재학습에 쓰인다.

## 8. 순서

| 단계 | 내용 | 확인 |
|---|---|---|
| 1 | 설치(uv 가상환경, PyTorch·추출기 약 3GB) + 결과창 주변 썸네일 수집 + 초벌 | 수집량·초벌 표본 |
| 2 | 학습 → 헷갈리는 칸 검수 → 재학습 (2~3번) | 검수 전후 점수 |
| 3 | 처음 보는 스트리머·VOD 로 판 단위 시험 | **숫자 보고 → 적용 여부 결정** |
| 4 | ck-local 에 붙이고 Claude 는 최종 검수만 | 새 VOD 로 기존 스킬과 비교 |

지우기: 코드 `scripts/ck-local/detector/`, 데이터 `out/ck-detector/`, 가상환경 `scripts/ck-local/detector/.venv`(gitignore).

## 12. 화면 종류 라벨과 토큰 절약 (2026-10-01)

### 라벨 (multi.py — 같은 SigLIP 특징 위의 8종 분류기, 확신 0.6 미만은 "모름")
검수 r7~r9 로 클라이언트를 밴픽·게임 방·그 밖으로 나누고, 그래프 탭·로딩을 유사도로 찾았다(로딩은 썸네일에 거의 없어 2칸 — 뺐다).
스트리머 하나씩 빼고 시험:

| 라벨 | 맞게 붙임 | 붙인 것 중 맞음 |
|---|---|---|
| 게임 중 | 98% | 100% |
| 밴픽 | 99% | 98% |
| 게임 방 | 100% | 94% |
| 결과창(점수판) | 91% | 97% |
| 롤 아님 | 94% | 95% |
| 종료 화면 | 95% | 76% |
| 결과창(그래프) | 100% | 66% |

## 18. 백필 장애 보완 (2026-10-04)

실제 1280×720 썸네일 시트를 1920×1080으로 가정해 자르는 결함을 확인했다.

검증은 합성 자료로 실제 학습을 실행해 운영 파일 보존 및 후보/시험 점수 일치를 확인했다.

## 19. 메모장 참고 화면 — 선택 VOD 시험 적용 (2026-10-05)

**최초 시험 당시 상태(아래 §20에서 일부 자동 수집 적용): 추가 학습과 검수큐 연결은 시험 가능. 전체 자동 수집은 미적용.** 기존 결과창 판별기,
`detect.py`, `scan.mjs`, 운영 가중치와 준비물 지문을 바꾸지 않았다. 기존 VOD를 자동 재준비하지 않는다.

`detector/memo-labels.json`은 에이전트가 화면을 보고 표시한 832장이다(학습 624, 개발 평가 208).
사람의 독립 검수 정답은 아니다. 학습/평가 채널은 분리했지만 평가 채널들이 같은 CK를 중계하므로
독립 표본으로 세면 안 된다. 반복해서 확인한 평가 묶음은 최종 블라인드 시험으로 취급하지 않는다.
학습에만 위치·크기·가림을 바꾼 합성 1,320장을 추가했다. 검수 화면에는 원래 썸네일만 표시한다.

| 방식 | 개발 평가의 메모장 45장 | 개발 평가의 비메모장 163장 | 추가 VOD 3개의 메모장 7장 | 추가 VOD의 비메모장 285장 |
|---|---:|---:|---:|---:|
| 기존 전역 특징 + 별도 선형 분류기 | 21장 발견 | 2장 오탐 | 1장 발견 | 0장 오탐 |

부분별 특징 실험은 기존 방식의 실패를 확인한 뒤 설계했으므로 추가 VOD 결과도 개발용 진단이다.

운영 `models/memo.json`은 설치하지 않았으며 백필에서 호출하지 않는다.

### 시험 실행과 산출물

기존 로컬 데이터와 특징 캐시를 사용하는 명령이며 영상 다운로드, OCR, Claude 호출이 없다.
연속 후보를 묶되 한 프레임만 잡힌 메모장도 버리지 않고, 묶음의 모든 후보 시각을 보존한다.


학습 결과/점수는 `out/ck-memo-training/`에 있다. 별도 `memo-refresh.py`는 캐시가 없는 VOD를
자동 추론하거나 결과창 준비를 다시 돌리지 않는다. 부분별 특징 모델(schema 2)은 연구용이며 이 게시 명령과 호환되지 않는다.

밤바팀 vs 오뀨팀 VOD `206156659`에 전역 특징 모델로 시험 수집한 **23묶음**을 표시했다.
기존 특징을 읽은 뒤 분류·썸네일 저장은 약 0.4초, 대표 이미지 합계 185,920바이트였다.
이는 캐시 재사용 1회의 측정이며 새 VOD의 전체 비용 증가율 측정이 아니다. 이 VOD 일부는 학습에 포함되어
23묶음이 나온 사실을 일반화 성능의 근거로 쓰지 않는다.

`verify-ck-memo-browser.mjs`는 시험 VOD에서 목록/대표 이미지/닫기/기존 경기 선택 보존을 확인한다.
브라우저의 GET/HEAD 이외 요청은 차단한다. 전체 적용 전에는 새로운 방송의 작은 실제 메모장·오탐 사례를 보강하고,
학습과 분리한 VOD의 메모장 구간 전체를 표시해 누락률과 오탐률을 다시 측정해야 한다.

## 20. 백필에 메모장 시험 수집 연결 (2026-10-05)

사용자 요청으로 **새로 준비하는 VOD의 25%**에 부분별 특징 모델을 적용했다.
`detector/models/memo-rollout.json`의 `enabled=true, percent=25`가 현재 설정이다.
VOD 번호의 해시로 고정 선택하므로 실행할 때마다 대상이 바뀌지 않는다. 이미 준비한 VOD는
메모장 수집만을 위해 다시 준비하지 않는다. 이번 변경으로 기존에 완료된 백필 전체를 재실행하지 않았다.

`detect.py`가 기존 SigLIP 추론 중 이미 계산된 14×14 특징을 관찰한다. 결과창·다중 라벨의 전역 특징과
출력은 그대로이며, 별도 이미지 추론·OCR·Claude·SOOP 호출이 없다. 부분별 선형 점수를 먼저 계산한 뒤
묶어 최대값을 취해 74×768 크기의 중간 특징을 만들지 않는다. 학습 때의 계산과 일치하는지 검사했다.
메모장 처리 오류는 별도 실패 기록을 남기고 결과창 판별을 계속한다. 원본을 자동 다운로드하지 않는다.

### 측정과 적용 확인

- VOD `208295391`, 10,503칸 전체: 변경 전 코드 46.90초, 수집 켬 43.96초, 수집 끔 44.40초, 수집 켬 42.22초.
  네 번의 결과창 후보·화면 분류 JSON이 완전히 같았다. 이번 한 VOD의 측정에서는 뚜렷한 지연이 관찰되지 않았다.
  다른 방송/장비까지 준비 시간 증가 5% 이하를 보장하는 결과는 아니다. 모델 로딩과 디스크 캐시의 변동도 포함한다.
- 후보 65묶음, 대표 이미지 513,784바이트. 이것은 정답 메모장 수가 아닌 후보 수다.
- 기본 `auto` 경로로 VOD `207333829`를 처리해 49묶음, 381,375바이트를 실제 검수큐에 게시했다.
  이 확인은 보관된 시트를 이용한 로컬 판별이며 경기 조사나 백필 전체를 다시 실행한 것이 아니다.
- 상세 측정: `out/ck-memo-training/activation/208295391/report.json`.
  `memo-run.json`의 관찰 함수 시간은 앞선 GPU 작업 대기까지 포함하므로 순수 추가 시간으로 해석하면 안 된다.

### 표시와 학습 피드백

검수큐의 후보를 열면 **메모장 맞음 / 메모장 아님 / 모르겠음**을 표시할 수 있다.
2026-10-06부터 별도 팝업 없이 기존 프레임창에 표시한다. 확대·VOD 이동 버튼을 공유하고,
좌우 키와 이전/다음 버튼으로 메모장 묶음 안에서 이동한다. 경기 항목을 선택하거나 돌아가기 버튼을 누르면
경기 프레임으로 복귀한다. 오른쪽의 **편집할 세트**는 참고 프레임 선택과 독립적이다.
메모장이나 다른 세트 사진을 보면서 고정한 세트의 경기·로스터·포지션을 입력할 수 있고 미저장 초안도 유지한다.
오른쪽 상단에 편집 중인 세트를 표시하며, 사진이 다른 세트 자료일 때는 차이를 안내한다.
새 경기 만들기는 미연결 프레임의 보조 메뉴로 둔다.
검수큐는 기본으로 **전체**를 표시하며 경기·미연결 프레임·메모장 후보를 시작 시각 순으로 섞어 보여 준다.
메모장만 따로 모은 목록은 없앴고, 같은 구간의 후보 화면 묶음은 유지한다. 위·아래 키도 이 시간순 목록을 따른다.
**경기** 필터에서는 경기 항목만 표시한다. 이 목록 변경으로 편집 대상이나 경기 연결을 바꾸지는 않는다.
지금 보이는 한 장에만 적용하며 전체 묶음을 일괄 라벨링하지 않는다. 사진 로딩 실패 시 표시를 막는다.
관리자 인증을 거쳐 `local/memo-feedback.jsonl`에 시각·모델 지문·원본 목록 지문과 함께 추가 기록한다.
정정해도 이전 기록을 지우지 않고 마지막 표시를 사용한다. 다른 원본 목록의 표시는 섞지 않는다.
DB·경기 연결·검수 잠금·scan.opened·done은 변경하지 않는다. 저장 자료가 바뀐 오래된 화면에서의 제출도 거부한다.
실제 서버 액션 저장/새로고침 후 유지 검사는 분리된 임시 폴더에서 수행했고 운영 자료에 시험 라벨을 쓰지 않았다.

이 피드백은 다음 학습용 자료이며 **자동 재학습이나 가중치 교체는 하지 않는다**.
후보에 오르지 않은 메모장은 이 버튼만으로 확인할 수 없으므로 별도 VOD 구간 표본 검수도 필요하다.
작은 메모장 누락과 오탐이 있는 실험 모델이라는 §19의 한계는 그대로다.

### 중지와 준비물 재사용

- `CK_MEMO_ENABLED=0` 또는 설정 파일의 `enabled=false`로 다음 판별부터 추가 수집을 끈다.
  이미 수집한 참고 화면과 사람의 표시는 보존한다. 모델 교체/수집 비율 변경만으로 결과창 준비 지문을 바꾸지 않는다.
- 이번 코드 연결은 준비 지문을 바꾸므로 검증된 변경 전/후 지문 한 쌍을
  `out/ck-detector/memo-preparation-compat.json`에 기록했다. 기존 지문이 정확히 일치하는 21개 준비물만 호환 대상이다.
  다른 코드나 결과창 가중치가 바뀌면 새 지문이 달라져 호환 처리는 적용되지 않는다.
  VOD `205886249`의 `--reuse`가 추가 작업 없이 반환하고 scan.json을 바꾸지 않는 것을 확인했다.
- 다른 환경에 배포할 때 이 호환 파일을 임의로 생성하지 않는다. 해당 환경의 코드/모델과 전후 동등성 확인이 먼저다.
  호환 파일이 없거나 손상되면 기존의 엄격한 지문 비교를 사용한다.

## 21. 남의 방송 화면 판별 — 시험 결과와 보류 (2026-10-09)

**정책(사용자 결정):** 남의 방송을 띄운 화면은 방송 주인이 그 경기·같은 시리즈·같은 대회의 참가자일 때만 경기 근거로 받는다.
무관한 방송(대기 중 시청, 남들끼리 CK 시청)은 경기를 만들거나 시점을 더하지 않는다. 이 검사는 **화면 판별 없이 저장 단계가 한다**
(`core/lib/db/ck-pov.ts` — `source: rebroadcast` 와, 본인 화면으로 새 경기를 만들 때 모두 방송 주인의 시리즈·대회 참가를 확인).

**판별기 시험:** 정답은 DB 시점 출처(`rebroadcast` 344장 · 본인 3,190장, 채널 21개)를 썼다(`scripts/ck-local/rebroadcast-seed.ts`).
정답 시각 근처 칸만 기존 전역 SigLIP 특징으로 계산(4,057칸, 159초)하고 선형 분류기를 채널 하나씩 빼고 쟀다(`detector/rebroadcast.py`).

| 문턱 | 남의 방송 찾은 비율 | 찾은 것 중 맞음 | 본인 화면 오탐 |
|---|---:|---:|---:|
| 0.5 | 74% | 52% | 704 |
| 0.7 | 49% | 69% | 225 |
| 0.9 | 5% | 80% | 12 |

틀린 사례를 열어 보니 두 가지였다.
- **전체 화면으로 띄운 남의 방송**(브라우저 틀 없음 — 깐숙 결과창·아바타 캠이 화면 가득)은 본인 화면과 겉모습이 같다.
  "이 캠·구성이 방송 주인 것인가"를 알아야 해서 일반 판별기로는 못 가른다.
- **정답 자체의 오류** — 최기명이 스맵임 방송을 본 화면이 `own` 으로 저장돼 있었다(오탐으로 잡힌 0.93 사례).

브라우저 창으로 띄운 경우(10/3 성훈 → 영재애애 방송)는 배치가 달라 학습 가능해 보이지만, 핵심 위험(무관한 방송으로 경기 만들기)은
저장 단계 검사가 이미 막으므로 **판별기는 조사 과정에 연결하지 않고 보류한다.** 다시 하려면 브라우저 창 사례만 정답을 손질하고
(전체 화면 사례는 빼거나 방송 주인 화면 구성과의 차이로 따로 다룬다), `rebroadcast-seed.ts` → `rebroadcast.py embed/eval` 순서로 돌린다.
