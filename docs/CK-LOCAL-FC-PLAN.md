# 로컬 준비 단계 공유 — 롤·FC 온라인 (C안)

작성: 2026-10-01. 상태: **구현 중**. 관련: [CK-LOCAL-DETECTOR.md](CK-LOCAL-DETECTOR.md)(롤 판별기) ·
[fco-match-context 스킬](../.claude/skills/fco-match-context/SKILL.md) · [MULTI-GAME-FCONLINE-PLAN.md](MULTI-GAME-FCONLINE-PLAN.md).

## 0. 한 줄

**화면을 보는 일(로컬 준비)은 하나로, 판단하는 일(스킬)은 게임별로 둘.**
한 VOD 의 썸네일은 한 번만 받고 한 번만 판별해 **롤·FC 가 함께 표시된 구간 지도**를 만든다.
롤 스킬(ck-local)과 FC 스킬(fco-match-context)은 그 지도를 각자 읽고, 각자의 규칙으로 판단한다.

## 1. 왜 C안인가

| | 롤 CK | FC 온라인 |
|---|---|---|
| 결과의 출처 | 화면뿐 — 사용자 설정 게임은 라이엇 API 에 없다 | **넥슨 API** — 승패·스코어를 이미 안다 |
| 경기가 언제였나 | 모른다 — 찾아야 한다 | **안다** — API 종료 시각 → VOD 초 |
| Claude 의 일 | 결과창을 찾아 **판독**(승패·이름·KDA·챔피언) | 그 경기와 같은 경기인지 대조하고 **맥락 판단**(친선·CK·대회) |
| 일의 단위 | VOD 하나(백필·자동 조사) | API 경기 하나(행사면 행사 묶음) |
| 남은 양 | 와치리스트 VOD 백필 | 스트리머 간 FC 경기 642개 중 620개 맥락 미조사(2026-10-01) |

- **한 스킬로 합치지 않는다(A안 기각)**: 목적·종료 조건·기록 창구(`ck:merge` vs `fco:context apply`)가 다르다.
  한 문서에 넣으면 두 규칙을 오가며 판단이 흐려진다 — ck-local 을 단순하게 만든 이유와 같다.
- **완전히 따로 두지도 않는다(B안 기각)**: 와치리스트 VOD 에 롤과 FC 가 섞여 있다(클리드1 9월 대부분).
  지금은 롤 조사가 썸네일을 다 받고 판별까지 하고도 FC 구간을 "롤 아님"으로 버리고, FC 조사가 같은 VOD 를 다시 연다.
  롤 조사 중 본 FC 는 `fco:context clue` 로 손으로 한 줄씩 남긴다.

## 2. 합치는 곳과 갈라지는 곳

```
                ┌───────────────── 공유 (로컬, DB 에 안 씀) ─────────────────┐
 VOD 번호 ──▶ │ ① 썸네일 시트 받기 (vod-timeline.mjs, 3초 칸)                   │
               │ ② 판별: 결과창 후보(롤) + 화면 종류 라벨(롤 + FC)              │
               │ ③ 산출물: out/ck/<vod>/local/  scan.json · map.txt · 몽타주    │
               └───────────────────────────────┬──────────────────────────────┘
                                                │  ← 여기서 갈라진다 (같은 파일을 읽는 두 소비자)
                     ┌──────────────────────────┴──────────────────────────┐
           롤 스킬 (ck-local)                                    FC 스킬 (fco-match-context)
   일의 시작: 백필·자동 조사가 VOD 를 고른다          일의 시작: fco:context list 가 API 경기를 고른다
   지도의 롤 구간 → 후보 → 원본 판독                  API 종료 시각 → 지도의 FC 구간·FC 결과 화면 → 원본 대조
   기록: ck:merge (경기·후보·scan)                    기록: fco:context apply (맥락·근거)
```

- **합치는 곳**: ①~③. 같은 VOD 면 어느 스킬이 먼저 부르든 한 번만 만든다(이미 있으면 재사용 — `scan.json` 의 run_id).
- **갈라지는 곳**: ③의 산출물을 **읽는 순간**. 두 스킬은 서로를 부르지 않는다. 같은 파일을 각자 읽을 뿐이다.
- **판단은 공유하지 않는다**: 로컬은 라벨만 단다. 롤 판독도 FC 맥락도 각 스킬의 Claude 가 원본을 보고 한다.

## 3. 바뀌는 것

### 공유 준비 (scripts/ck-local/)
- 화면 종류 라벨에 FC 3종 추가: `fc_match`(경기 중 — 잔디·스코어·시간) · `fc_result`(경기 종료 결과 화면) · `fc_menu`(스쿼드·이적시장·상점 등).
  롤 쪽 `other` 에 섞여 있던 것을 나눈다.
- 구간 지도에 FC 구간을 같이 싣는다. FC 결과 화면은 칸 단위로(경기마다 한 번, 짧다).
  ```
  0:17:50~1:12:05 FC 경기 중 (결과 화면 0:29:10 · 0:41:55 · 0:55:02 …)
  1:12:53~1:47:41 게임 중
  3:14:26~3:14:35 결과창(그래프) (후보 #1)
  ```
- 준비 명령은 그대로 하나: `npm run ck:local -- --vod N` (이름은 실험이 끝나면 정리).

### 롤 스킬 (ck-local) — 거의 그대로
- FC 구간은 지금처럼 롤 조사 대상이 아니다.
- **`fco:context clue` 손 기록을 없앤다** — 지도가 FC 구간을 이미 남긴다. (LoL 조사 중 FC 단서의 목적이 "FC 조사 후보 알림"이었는데 지도가 그 역할을 한다.)

### FC 스킬 (fco-match-context) — 찾는 부분만 바뀐다
- `locate` 가 API 종료 시각으로 VOD 초를 계산하는 것은 그대로.
- 그 VOD 에 준비 산출물이 없으면 만든다(`ck:local -- --vod N`), 있으면 재사용.
- 지금: 종료 −20초~+60초를 원본 5분할로 좁혀 결과 화면을 찾는다.
  바뀐 뒤: **지도의 `fc_result` 칸 중 API 종료 시각에 가장 가까운 것**의 원본을 바로 연다. 없으면 지금 방식(5분할).
- 지도는 FC 화면이 이어지는 **탐색 구간**을 준다(참가자·경기·행사 경계는 모른다 — API 와 원본으로 확인) → 맥락(친선·CK·대회)은 묶음의 시작(대기실·대진·공지)과 끝을 보고 판단하고,
  묶음 안 경기마다 결과 화면으로 matchId 대조. 기록은 지금처럼 경기마다(`apply`).
- 판단 규칙·기록 형식·검수 화면은 그대로다.

## 4. 구현 명세

### 4-1. 라벨 (scripts/ck-local/detector/)
| 라벨 | 화면 | `label.py` 글자 |
|---|---|---|
| `fc_match` | FC 경기 진행 화면(잔디·선수·상단 스코어·시간) | `F` |
| `fc_result` | FC 경기 종료 결과 화면(최종 스코어·득점자·평점) | `S` |
| `fc_menu` | FC 메뉴(스쿼드·이적시장·상점·대기실·카드팩) | `M` |

- `multi.py` 의 `CLASSES` 에 세 개를 더한다. 결과창 판별기(`train.py`)는 그대로 — FC 화면은 계속 "롤 결과창 아님"이다.
- 이미 `other` 로 단 칸 중 FC 인 것은 그대로 두면 학습이 충돌한다 → FC 라벨이 붙은 VOD 의 `other` 는 검수로 다시 단다.

### 4-2. 데이터
1. **시드**: DB `fco_context_evidence`(행사 VOD 205292057·205320949) — role `result`→`fc_result`, `start`·`end`→`fc_match`(22+~110장).
   `pre`·`post`·역할 없음은 화면이 섞여 시드로 안 쓴다.
2. **재료 VOD**: 시드 VOD 2개 + 클리드1 9월 FC 위주 VOD(이미 썸네일 캐시가 있다) → `collect.mjs --vods` → `embed.py`.
3. **검수**: 시드와 닮은 칸(유사도) + FC VOD 에서 고르게 뽑은 칸을 몽타주로 Claude 가 단다(F/S/M 및 기존 라벨).
4. **시험**: 스트리머 하나씩 빼고 — FC 3종의 전체 재현율·부여율·정확도, **롤 라벨 7종이 이전(§14)보다 나빠지지 않는지**.

### 4-3. 공유 준비 산출물 (scripts/ck-local/scan.mjs · detect.py)
- `detect.py` 의 `timeline` 에 FC 라벨이 그대로 나온다(종류 판별기만 바뀐다).
- `scan.json` 에 `fc` 블록 추가: `{ blocks: [{from, to}], results: [초…] }` — `fc_match` 구간(3분 안 끊김 잇기, 3분 이상) · `fc_result` 칸 덩어리의 가운데 시각.
- `map.txt` 에 FC 블록 한 줄씩: `0:05:00~0:20:10 FC 경기 (결과 화면 0:19:40)`. FC 메뉴는 지도에 안 싣는다(길어진다).

### 4-4. 롤 스킬 (.claude/skills/ck-local/SKILL.md)
- "실제로 연 FC 화면이 있으면 `fco:context clue`" 줄을 지운다 → "지도의 FC 구간은 롤 조사 대상이 아니다. FC 맥락은 fco-match-context 가 본다."
- 개요 몽타주는 그대로 본다(FC 라벨이 틀려 롤을 덮을 수 있다).

### 4-5. FC 스킬 (scripts/fco-context.ts · .claude/skills/fco-match-context/SKILL.md)
- `locate`: 경기마다 VOD 초를 계산한 뒤 `out/ck/<vod>/local/scan.json` 이 있으면 **API 종료 시각 −30초~+120초 안의 `fc_result` 시각**을 함께 찍는다:
  `지도: FC 결과 화면 1:19:40 → npm run ck:probe -- --vod N --at 4780`. 없으면 지금처럼 5분할 명령만.
  준비 산출물이 없으면 `ck:local -- --vod N` 을 먼저 돌리라고 안내한다(자동 실행은 안 한다 — SOOP 호출이 겹치지 않게).
- 스킬: "결과 화면 찾기"에 한 단계 추가 — 지도 시각이 있으면 그 원본부터, 없거나 아니면 기존 5분할.
  "FC 경기가 이어진 묶음"을 맥락 판단의 시작·끝을 고르는 데 쓴다(묶음은 어디를 볼지일 뿐, 결론은 경기마다 근거로).

## 5. 순서

| 단계 | 내용 | 확인 |
|---|---|---|
| 1 | 시드·재료 VOD 수집·특징 | 칸 수 |
| 2 | 검수(FC 3종) → `multi.py` 학습 | FC 3종 지표, 롤 7종 회귀 없음 |
| 3 | `scan.json`·`map.txt` 에 FC 블록 | 클리드1·시드 VOD 지도를 눈으로 대조 |
| 4 | 롤 스킬에서 FC 손 기록 제거 | 문서 |
| 5 | `locate` 에 지도 시각 | 시드 VOD 22경기 — 지도 결과 화면이 API 스코어와 같은 경기인지 |
| 6 | FC 스킬로 이미 결론 난 행사 경기 재조사(dry-run) → 미조사 경기 운영 | 같은 결론·원본 수·토큰 |

## 6. 위험

- FC 라벨을 넣다 롤 라벨이 나빠질 수 있다 → 같은 평가 자료에 옛·새 판별기를 함께 적용해 비교하고, 나빠지면 FC 를 별도 판별기로 분리한다(특징 추출은 그대로 한 번 — C안은 유지된다).
- FC 결과 화면은 짧다(수 초) → 3초 칸에 1~2번만 찍힐 수 있다. 못 찾으면 지금 방식(5분할)으로 — 판별기가 못 찾은 것은 "없음"의 근거가 아니다.
- 묶음 판단이 "같은 저녁이면 같은 행사"로 굳으면 안 된다(행사 중간 연습 경기 등) → 묶음은 **어디를 볼지**일 뿐, 경기마다 결론은 근거로.
- 남의 방송 시청(FC 중계)도 `fc_match` 로 보인다 → 화면 종류일 뿐, 본인 경기인지는 FC 스킬이 판단(지금 규칙 그대로).

## 7. 구현 결과 (2026-10-01)

### FC 라벨 (검수 r10~r13 + DB 근거 시드)
`fc_match` 268 · `fc_result` 73 · `fc_menu` 404칸. 처음 결과 화면이 거의 한 채널(galsa — 시드 행사 VOD)뿐이라 다른 채널 시험에서 0% 였고,
다른 채널 FC 경기 끝 구간을 따로 검수해 보탰다. ⚠ 팀 OVR 비교 팝업(154 vs 148 같은 숫자)은 결과가 아니라 경기 전 메뉴다(`fc_menu`).

스트리머 하나씩 빼고(전체 재현율 · 부여율 · 정확도):

| 라벨 | 재현율 | 부여율 | 정확도 |
|---|---|---|---|
| fc_match | 89% | 93% | 96% |
| fc_result | 62% | 79% | 92% |
| fc_menu | 91% | 95% | 95% |

롤 라벨은 나빠지지 않았다 — 결과창 70→73% · 밴픽 93→92% · 게임 방 89→95% · 게임 중 94→92%. 롤 아님(`other`)은 76→61% (FC 메뉴가 빠져나가 남은 것이 잡다해졌다).

### 지도와 locate
- `scan.json` 에 `fc: {blocks, results}`, `map.txt` 에 `0:13:24~0:52:15 FC 경기 (결과 화면 …)`.
  짧은 FC 결과 칸이 구간 묶기에서 앞 구간에 먹히던 것을 고쳤다(`SHORT_OK` 에 `fc_result`).
- `fco:context locate` 가 API 종료 −30~+120초 안의 지도 결과 화면을 함께 찍는다.
  미니 뿌챔스 21경기: 19경기에 지도 결과 화면 줄 · DB 의 결과 근거가 있는 18경기 **전부 15초 안**(대개 종료 +5~+20초).
  ⚠ 이 두 VOD 는 FC 시드로 학습에 들어갔다 — 처음 보는 VOD 의 성능은 다음 실제 운영에서 다시 잰다.
- `locate --from/--to` 경로가 Date 를 문자열처럼 정렬하다 죽던 기존 버그를 고쳤다(ISO 문자열로 맞춤).
- 스킬: ck-local 은 FC 단서 손 기록을 없앴다. fco-match-context 는 "먼저 지도, 아니면 5분할".

## 8. Codex 검토 반영 (2026-10-01)

| 지적 | 판단 | 조치 |
|---|---|---|
| 짧은 `fc_result` 가 구간 묶기에 먹힌다 | 수용(이미 고쳤음) + 보강 | 결과 시각을 묶기 전 **실제 검출 칸**으로 따로 낸다(`fc_result_cells`) |
| 평가가 `predict_proba` 열 번호를 라벨 번호로 썼다 — 한 채널에만 있는 종류를 빼면 어긋난다 | **수용(명백한 버그)** | `clf.classes_` 로 변환, 저장 라벨 목록도 실제 학습 순서로. FC 결과가 처음 0%였던 데 이 버그가 섞였을 수 있다 |
| DB 시드 role 과 썸네일 화면이 다를 수 있다 | 수용 | r14 검수: 113칸 중 22칸 틀림 → 고침. 시드 스크립트에 "붙인 뒤 검수" 명시 |
| 늘려 보기에 옛 라벨이 남는다 | 수용(절차) | 정답 파일이 늘려 보기보다 새로우면 학습·평가가 멈춘다 |
| `fc` 없음과 `fc.results: []` 를 같게 다룬다 | 수용 | `fc.supported`·모델 버전·`schema: 2`. locate 가 "옛 지도"·"실패 구간 있음"·"이 시간창엔 검출 없음"을 구별해 출력 |
| 지도는 FC 가 있는 VOD 를 **찾아 주지** 못한다 → clue 제거는 이르다 | **수용** | ck-local 의 clue 지시를 되살렸다 |
| "같은 두 사람·한 저녁" 표현이 과하다 | 수용 | 탐색 구간일 뿐, 경계는 API·원본으로 |
| locate 후보 정렬·시간축 불확실성 | 수용(작게) | 시간창 안 가까운 순, 원본 확인·5분할 복귀를 출력에 명시 |
| 캐시·잠금 체계, 지도에 메뉴 구간, 블록 병합 조건 세분 | 반려 | 지금 소비자는 locate 하나이고 준비가 1분이다. 운영(6단계)에서 필요가 보이면 |
