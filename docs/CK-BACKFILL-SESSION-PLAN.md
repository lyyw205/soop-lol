**로컬 모델이 영상을 훑는 구조는 유지한다. Claude가 사진을 너무 많이 쌓기 전에 저장하고, 새 세션에서 이어가게 한다.**

지금도 로컬 판별기가 썸네일을 분류하고 결과창 후보를 찾는다. Claude는 준비된 개요 사진을 확인하고, 후보의 원본을 읽고, 빠진 곳을 보완한다.
문제는 이 확인 작업이 한 대화에 너무 오래 쌓이고 실제 저장은 뒤로 밀린다는 것이다.

세션을 나누는 기준은 이미지 누적량이다. 한 경기도 사진이 많으면 여러 세션에 걸칠 수 있다.

## 확인한 원인과 아직 확인할 것

세 개의 실제 세션 로그와 해당 Claude Code 버전의 이미지 제거 코드를 대조했다.

| VOD | API 응답 수 | 이미지 열람 | 서로 다른 파일 | 재열람 | 재열람 중 앞 이미지가 이미 제거된 경우 |
|---|---:|---:|---:|---:|---:|
| 206719759, 임아니 | 112 | 437 | 91 | 346 | 343 |
| 208295391, 최기명 | 119 | 149 | 111 | 38 | 38 |
| 206994099, 다누리 | 107 | 169 | 119 | 50 | 50 |

- 설치된 CLI의 이미지 제거 함수를 기록된 이미지 크기로 재실행하자, 세 세션의 사고 블록 제거 발생 시점 **25회 모두**와 일치했다.
- 임아니 세션의 첫 실제 `ck:merge` 호출은 API 응답 110번째였고, 그 전에 이미지 437회를 모두 열었다. 읽은 것을 제때 저장하지 못한 사례다.
- 이 세 세션의 실행 설정은 모두 `session-games=0`이었다. 따라서 ‘5경기 제한을 모델이 무시했다’는 설명은 이 사례에 맞지 않는다. 기존 제한은 실행기에서 강제하는 상한도 아니었다.
- 확인한 CLI 2.1.285 구현에는 이미지의 base64 데이터 합계 **24 MiB**를 기준으로 오래된 이미지를 제거하는 경로가 있다. 일반적인 ‘원본 파일 25 MB 한도’로 해석하면 안 된다. 버전·실행 경로별 재확인이 필요하다.

관측한 흐름은 **이미지 누적 → 오래된 이미지 제거 → 이전 메시지 내용 변경 → 캐시 재작성과 사고 블록 제거 → 제거된 이미지 재열람**이다.
Claude Code도 이미지의 개수·용량 때문에 오래된 이미지를 제거하면 캐시가 무효화될 수 있다고 설명한다.
이전 메시지 변경은 사고 블록 유지에도 영향을 준다. [캐시 문서](https://code.claude.com/docs/en/prompt-caching#accumulating-many-images), [사고 블록 유지 문서](https://platform.claude.com/docs/en/build-with-claude/preserved-thinking).

이것은 Claude Code의 문맥 관리 방식과, 저장 없이 긴 판독을 허용한 실행 구조가 맞물린 문제다.
백필 쪽에서는 **이미지 제거 전에 저장하고 새 세션으로 넘어가는 구조**로 대응한다.
다만 모든 재열람의 의도나 전체 낭비가 이것 하나 때문이라는 점까지 증명한 것은 아니다. 과거 네트워크 요청 본문은 없어 로그와 설치 코드로 재구성했다.
이미지 제거 시점의 캐시 쓰기량을 그대로 예상 절감량으로 계산하지 않는다.

조사 산출물은 로컬의 [재현 스크립트](../out/ck/diagnostics/image-context-audit.py)와 [결과 JSON](../out/ck/diagnostics/image-context-audit.json)에 있다.
`out/`은 Git 추적 대상이 아니므로 주요 수치는 위에 남겼다. 구현 시 재현에 필요한 최소 자료와 검증 코드는 추적 가능한 테스트 자료로 정리한다.

## 1차 구현 순서

### 0. 훅의 실제 동작부터 시험한다

전체 VOD를 실행하기 전에 작은 고정 이미지로 확인한다.

- 정상 열람, 한도 초과 거부, 훅 예외·타임아웃·실행 파일 누락 때 실제로 이미지가 모델에 전달되는지 확인한다.
- 도구를 거부한 뒤에도 저장 명령이 가능한지, 저장·종료 단계에서 불필요한 도구 호출을 막을 수 있는지 확인한다.
- 동시에 여러 이미지를 열어도 합계가 상한을 넘지 않게 한다. 단순한 파일 잠금과 세션별 계수부터 사용하고, 복잡한 예약 체계는 먼저 만들지 않는다.
- 이 백필에서 이미지가 들어오는 경로를 확인한다. 필요한 경로는 계수하고 불필요한 MCP·자식 에이전트 등의 우회 경로는 실행 설정으로 제한한다.
- CLI 버전과 실제 전달 데이터의 크기 계산을 확인한다. 이미지 개수 제한도 함께 확인한다.

훅 함수 자체의 단위 시험과 실제 Claude Code를 통한 동작 시험을 구분한다. 작은 실호출 시험의 사용량도 기록한다.
오류 때 이미지가 통과하면 그 상태로 전체 VOD 시험을 시작하지 않는다. 최소 보완으로 막을 수 있는지 판단하고, 어렵다면 훅만으로 강제할 수 없다는 결과를 먼저 남긴다.
이 단계의 결과에 따라 구현 규모가 달라질 수 있으므로 ‘훅과 셸만 고치면 반드시 끝난다’고 확정하지 않는다.

### 1. 기존 저장 경로를 시험하고 필요한 부분만 보완한다

현재 프롬프트에는 이미 탐색 단계마다 `running`으로 `ck:merge`에 저장하라는 지시가 있다.
`scan.resume`, 후보의 관찰·미해결 질문, DB 재조회로 만드는 `resume.json`도 존재한다.
**중간 저장 기능을 새로 만드는 것이 아니라, 실제로 미리 사용하게 하고 끊긴 뒤 재개되는지 확인하는 작업**이다.

다음 세 경우를 기존 경로로 시험한다.

1. 한 경기를 읽은 뒤 저장하고 새 세션에서 이어가기.
2. 이름 일부처럼 모르는 값이 남은 상태에서 관찰·근거·질문을 후보·검토 기록으로 저장하고 이어가기.
3. 개요 사진만 확인했고 아직 원본을 열지 않은 상태에서 `running` 기록을 남기기.

현재 `ck:local --finish`는 원본 `opened`를 요구하고 기본 상태가 `done`이며, 범위 생략 시 준비 초안의 전체 요청 범위를 유지한다.
이 때문에 3번이 막히면 기존 `ck:merge` 입력을 이용하거나 초안 도구를 최소 보완한다.
새 작업 장부나 DB 스키마 확장을 먼저 만들지 않는다. 개요를 봤다고 원본 열람을 꾸미거나, 부분 기록에 전체 완료를 붙이지 않는다.
요청 범위·실제로 확인한 지점·실패 범위의 의미도 유지한다.

재개 요약에 세부 관찰이 부족하면 기존 `ck:record` 조회를 사용한다. 실제 누락이 확인된 정보만 요약에 추가한다.
짧은 다음 행동은 `scan.resume`에, 경기값과 상세 근거는 기존 DB 기록에 남긴다.

### 2. 8 MiB 안내와 12 MiB 차단을 붙인다

백필 자식 세션에만 적용하는 `PermissionRequest` 훅을 사용한다. 전역 설정은 변경하지 않는다.
0단계 시험 결과에 따라 초기 `PreToolUse` 안에서 바꿨다. 도구는 기본 승인 필요 상태로 두고, 훅이 정상 승인해야 실행된다.
승인 응답이 없거나 훅이 실패하면 자동 거부한다. 실제 전달량은 `PostToolUse`에서 별도로 확인한다.

| 상태 | 동작 |
|---|---|
| 누적 약 8 MiB 미만 | 기존 조사 진행. 경기·탐색 단계별 저장 지침 유지 |
| 누적 약 8 MiB 도달 | 지금까지 읽은 내용과 남은 질문을 저장하고 종료하도록 안내 |
| 다음 열람을 허용하면 12 MiB 초과 | 해당 이미지가 들어가기 전에 거부하고 저장·종료 단계로 전환 |
| 저장·종료 단계 | 기록 작성·필요한 텍스트 조회·DB 저장과 확인만 허용. 새로운 이미지와 탐색은 차단 |
| 저장·종료 상한 도달 | 외부 실행기가 중단하고 DB의 마지막 저장분 확인 |

**8 MiB 안내는 권고이고 12 MiB 차단이 강제 장치다.** 안내를 무시할 가능성은 남는다.
차단 뒤에도 저장을 자동으로 보장하는 것은 아니므로, 저장·종료 단계에는 별도의 시간 또는 호출 상한을 둔다.
상한에 걸려 종료되면 미저장분이 남았을 수 있음을 기록한다. [Claude Code 승인 훅](https://code.claude.com/docs/en/hooks#permissionrequest).

8·12 MiB는 확인한 CLI의 이미지 제거 지점보다 앞에서 끊기 위한 시험값이다. 원본 JPEG 파일 크기가 아니라 **실제로 전달되는 이미지 데이터 기준**이다.
정확한 전송 크기를 미리 알 수 없는 경우, 0단계에서 검증한 보수적 상한으로 선계수하고 실제 결과와 대조한다.
동시 요청은 잠금 아래에서 합계를 갱신한다. 계수 실패를 0바이트로 취급하지 않는다.
많은 작은 이미지가 개수 제한에 먼저 닿지 않도록 개수 상한도 설치 버전에 맞춰 둔다.

계수는 같은 세션에서 저장했다고 초기화하지 않는다. 새 세션에서만 초기화한다.
필요한 재열람은 허용하되 다시 사용한 용량으로 센다. 사진 자르기·화질 축소는 하지 않는다.
작업 트리의 기존 `--max-budget-usd` 변경은 비용 보호 장치로 통합한다. 이미지 제한과 역할이 다르므로 유지한다.

### 3. 기존 셸의 저장 확인·재개와 연결한다

새 작업 배정기 대신 기존 `next → Claude → after → next` 흐름을 사용한다.

- 이미지 한도로 종료되었는지, 비용 상한·오류·사용자 중단인지 구분해서 기록한다.
- 종료 후 기존 `after`가 DB를 재조회한다. 모델의 완료 답변, JSON 파일 생성, `--dry-run`은 저장 증거로 인정하지 않는다.
- 저장된 관찰·경기·남은 질문을 기존 재개 요약으로 전달한다. 긴 대화를 `--resume`하지 않고 새 `claude -p` 세션을 시작한다.
- 예산 때문에 미수행이 남았으면 `running`을 유지한다. 실제 저장이 없으면 앞으로 진행했다고 처리하지 않는다.
- 저장 직후 프로세스가 죽었어도 DB 기록을 재사용한다. 기존 저장·검수값 보호와 중복 제출 방지 규칙을 유지한다.

현재 `after`는 진척이 없으면 중단하며, 원본 열람 증가만 있는 경우에는 연속 3회 보류 규칙을 적용한다.
이를 그대로 활용하고, 메모 문구·시각 변경만으로 반복 제한을 초기화하지 않는다.
중간 관찰은 저장되었지만 현행 지표로 진척이 잡히지 않는 경우도 시험한다. 이것 때문에 정상 재개가 막히면 구체적인 사례에 한정해 보완하고, 무조건 성공 처리하지 않는다.

`done`은 필수 탐색 종료라는 기존 의미를 유지한다. 미해결이 남을 수 있으며, 예산이 끝났다는 이유로 완료하거나 `not_target`으로 닫지 않는다.
지도·후보에 없는 게임 구간, 썸네일 실패 범위, 필요한 파일 끝 확인을 포함한 기존 조사 규칙도 유지한다.
1차에서는 모든 조사 단계를 새 프로그램이 자동 검증한다고 주장하지 않는다. 저장 사실은 코드로, 탐색 누락과 오독은 시험 결과로 확인한다.

## 1차 진행 예시

작동 방식을 설명하는 가상 예시이며, 세션 수나 사진 수의 예측이 아니다.

1. **로컬 준비:** 기존 방식으로 개요·지도·후보·원본을 준비한다. 이후 세션에서도 준비물을 재사용한다.
2. **세션 A:** Claude가 개요와 후보를 확인한다. 누적 8 MiB 부근에서 저장 안내를 받고, 확인한 내용·남은 질문을 기존 DB 경로로 저장한 뒤 종료한다.
3. **세션 B:** DB 요약에서 남은 부분을 확인하고 이어간다. 저장 안내를 미루더라도 12 MiB를 넘기는 이미지 열람은 차단된다.
4. **차단 이후:** 추가 사진 없이 읽은 내용과 아직 모르는 항목을 저장하고 종료한다. 계속 다른 일을 시도하면 실행기의 상한으로 중단한다.
5. **다음 세션:** DB에 남은 것만 이어받는다. 저장이 없으면 기존 무진척 규칙으로 중단하고 원인을 확인한다.
6. **마무리:** 필수 탐색이 끝난 경우에만 완료한다. 전체 세션의 사용량과 저장 결과를 합산한다.

이 방식에서 같은 사진을 계속 다시 열거나 저장을 미루면 그 자체가 1차의 실패·추가 개선 근거다.
그때 필요한 부분에만 2차 작업 배정을 추가한다.

## 1차 수정 대상

| 범위 | 변경 |
|---|---|
| 백필 전용 훅·계수 모듈 | 이미지 크기·개수, 8 MiB 안내, 12 MiB 차단, 저장·종료 상태 |
| `scripts/ck-backfill.sh` | 세션 설정, 종료 상한·사유, 기존 DB 확인·재개 연결 |
| `scripts/ck-backfill-par.sh` | 필요한 실행 옵션 전달만 반영 |
| `scripts/ck-backfill.ts`, 기존 저장·요약 도구 | 시험에서 확인한 저장·재개 빈틈만 보완 |
| 기존 백필 테스트·임시 DB 검증 | 훅·상한·중단·재개 회귀 시험 |
| 백필·ck-local 지침 | 안내 후 저장, 차단 후 종료, 원본·기존 탐색 규칙 명시 |

새 작업 ID, 작업 종류별 배정, 작업 완료 장부, 매 이미지 묶음의 저장 확인은 1차 범위에서 제외한다.
기존 DB 정본과 `ck:merge` 저장 창구를 유지한다. 진행 중인 다른 세션의 비용 상한 변경은 덮어쓰지 않고 통합한다.
첫 대상은 LoL `ck-local` 백필이다. 공용 셸의 FC 경로는 회귀 확인한다.
로컬 준비 실패로 `ck-research`로 전환될 때 제한이 조용히 빠지지 않도록 적용 범위도 시험한다.

## 1차 검증

### 작은 시험으로 먼저 확인할 조건

- 8 MiB 안내, 12 MiB 초과 사전 차단, 이미지 개수 제한, 재열람·동시 열람 계수가 작동한다.
- 훅 오류·누락·타임아웃과 허용한 다른 이미지 입력 경로에서 한도를 우회하지 않는다.
- 차단 이후 저장은 가능하고, 저장·종료가 무한 반복되지 않는다.
- 개요만 본 상태·일부 값만 읽은 상태를 거짓 완료 없이 저장할 수 있다.
- DB 저장 실패, 저장 직후 종료, 동일 `after` 재실행에도 결과를 건너뛰거나 중복 저장하지 않는다.
- 비용 상한과 사용자 중단, 무진척 중단, 기존 잠금·FC 경로가 유지된다.

관련 단위·셸 시험과 타입 검사를 수행한다. 저장 코드를 바꾸면 해당 임시 DB 수집·백필 검증도 실행한다.
이 단계가 통과해야 전체 VOD 시험으로 넘어간다.

### 새 방식만 VOD 하나를 끝까지 실행한다

**임시 DB 하나에서 206719759 전체를 새 방식으로 처리하고, 과거 실행을 기준선으로 사용한다.**
기존 방식을 다시 실행하거나 두 개의 비교용 DB를 만드는 것은 1차의 전제 조건이 아니다.

- 과거 기준선은 확인된 이미지 열람 437회·고유 파일 91개·재열람 346회와 기존 경기 결과다.
  검토에서 제시된 약 $23.8·5경기는 원본 사용량·저장 기록과 대조해 비교표에 확정한다. 비용은 동일한 환산 기준을 사용한다.
- 임시 DB에는 평가용 정답과 이 VOD의 기존 완료·관찰·재개 결과가 세션에 노출되지 않도록 한다.
  `done`만 지우고 저장 경기·후보·관찰을 그대로 둔 실행을 처음부터 처리한 시험으로 계산하지 않는다.
- 정답은 평가용으로 별도 보관한다. 다른 VOD의 기존 정보 등 시작 조건을 과거와 맞추기 어려운 부분은 기록한다.
- 가능한 범위에서 모델·effort·CLI 버전·준비물을 맞추고 차이를 표기한다. 시작 조건의 차이 때문에 기존 방식 재실행을 자동으로 추가하지 않는다.
- 모든 세션과 중단·재시도 비용을 합산한다. 초기 훅 시험 비용과 VOD 처리 비용은 각각 기록하고 전체 실험 비용도 표시한다.
- 시험 전체의 비용·세션 상한도 실행 전에 설정한다. 상한으로 끝내지 못하면 미완료로 보고하며, 저비용 성공으로 계산하지 않는다.
- 기존 검수 결과와 원본 근거를 대조해 경기 누락·중복·이름·챔피언·KDA·승패 오독을 확인한다.
  미확인 이름을 추측해 채웠는지도 확인한다. 일부 칸이 같다는 것만으로 전체 품질을 통과시키지 않는다.

과거 기록과의 비교는 **1차 개선 여부를 판단하는 근거**로 사용한다.
동시 조건을 맞춘 대조 실험보다 불확실성이 크다는 점을 표시하되, 그 이유로 비교 자체를 배제하지 않는다.
기존 방식 재실행은 결과가 애매하고 그 비교가 다음 결정에 필요한 경우에만 후속으로 검토한다.

| 항목 | 비교 내용 |
|---|---|
| 사용량 | 입력·캐시 쓰기·캐시 읽기·출력 토큰, 전체 환산 비용, 처리 시간 |
| 세션 | 세션 수, API 응답 수, CLI의 `num_turns`를 별도 기록 |
| 이미지 | 총 열람·고유 파일·재열람, 제거된 이미지 재열람, 최대 누적 데이터·개수 |
| 캐시 | 이미지 제거와 그에 따른 캐시 재작성·사고 블록 제거 발생 |
| 저장·재개 | 저장 시점, 미저장 종료, 같은 구간 반복, 보류·재시도 |
| 품질 | 필수 탐색 누락, 경기 누락·오탐·중복, 판독값 차이와 미해결 사유 |

| 전체 처리를 마치고 비용·재열람이 줄며 품질 유지 | 큰 작업 배정 체계 없이 유지. 짧은 VOD·720p·0경기 등 소량 표본으로 적용 범위 확대 |
| 이미지 제거는 막았지만 저장을 계속 미룸 | 저장 확인을 더 이른 시점에 요구하는 최소 보완부터 검토 |
| 재개 때 같은 개요·후보를 반복해서 봄 | 반복되는 단계부터 작은 작업 배정과 완료 기록 추가 |
| 후보 밖 구간 누락·거짓 완료·오독 증가 | 비용과 무관하게 확대 중단, 탐색·재개 누락 수정 |
| 개선 폭이 작거나 과거와 조건 차이가 커 판단 곤란 | 임계값·재개 자료를 점검하고 필요한 경우에만 통제된 추가 비교 |

1차를 통과해도 VOD 하나의 결과를 모든 영상의 절감률로 일반화하지 않는다.
필요해진 경우에만 2차에서 개요·후보·보완 작업을 구분하고 안정적인 작업 ID·준비물 지문·DB 확인 기록을 설계한다.
이미 충분하면 그 체계는 만들지 않는다.

MCP 축소에 따른 시작 문맥 절감은 별도 후속 실험으로 둔다. 1차에 꼭 필요한 이미지 경로 제한과 구별한다.
새 구조는 명시적 실행 옵션으로 검증하고, 문제가 생기면 옵션을 끄되 저장된 경기·관찰·미해결 기록과 비용 상한은 보존한다.
CLI 버전 변경 시 이미지 계산과 훅 동작을 다시 확인한다.

이 계획은 [기존 안정성 개선 계획](CK-BACKFILL-HARDENING-PLAN.md)의 저장·완료·검수 원칙을 유지하며,
먼저 이미지 누적 제한의 효과를 작게 검증하도록 범위를 줄인 후속 계획이다.
