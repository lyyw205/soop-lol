### B1. [P1] 미완료 경기의 새 불일치를 오래된 화면에서 검수 완료할 수 있다

- **문제:** 다시점 관측만 바뀌면 경기 값이 그대로이므로 DB의 경기/참가자 변경 트리거는 실행되지 않는다. 그런데 시점 저장은 이미 완료된 경기에서만 `review_version`을 올린다. 미완료 화면을 보고 있던 검수자가 새 불일치를 보지 않고 완료할 수 있다.
- **근거:** `packages/core/lib/db/ck-pov.ts:200` 및 `:207`의 완료 상태 조건, `packages/core/lib/db/ck.ts:1264`의 버전 기반 완료 검사, `packages/core/lib/metrics/pov.ts:192` 부근의 완료 시각 기반 불일치 판정.
- **재현 확인:** 폐기 가능한 DB에서 킬 3인 경기의 버전 1을 읽음 → 새 시점이 킬 8 제출 → 버전 여전히 1 → 이전 버전으로 완료 성공 → 새 불일치가 `mismatch_reviewed: 1`, `mismatch_open: 0`으로 바뀜. 실제 경쟁 실행이 없어도 이 요청 순서로 재현된다.
- **수정 방향:** 검수 대상 관측의 의미 있는 변경도 경기의 검수 버전에 반영한다. 완료 상태와 무관하게 적용하고, 동일 관측의 재전송은 버전을 올리지 않는다. 기존 경기 행 잠금 안에서 관측 병합·버전 갱신을 함께 처리한다. 버전과 완료 시각의 역할은 유지해 별도 승인 테이블을 만들 필요가 없다.
- **필요한 테스트:** 미완료 화면 열기 → 새 불일치 → 이전 버전 완료 거부; 완료 후 새 불일치의 재개방; 같은 관측 재전송은 버전/완료 유지; 관측 철회·수정 후 오래된 완료 요청 거부.

### B2. [P1] 기존 0026 마이그레이션의 빈 줄 변경이 업그레이드를 막는다

- **발생 조건:** 변경 전 0026을 적용하고 해당 지문을 기록한 DB에서 현재 파일로 `db:migrate` 실행.

- **필요한 테스트:** 실제 PostgreSQL 두 연결로 두 번째 시점 추가와 원본 재작성을 교차시켜 원본 덮어쓰기 및 보충값 유실 차단; 관리자 저장과의 경쟁; 동일 ID 동시 생성·재전송의 일관성.

### B4. [P2] CK 다시점 화면으로 이동하면서 로스터 부족 항목 딥링크가 사라진다

- **필요한 테스트:** 목록 부족 항목 → 해당 경기/로스터 → 다른 시점 전환 → 새로고침을 데스크톱·모바일에서 확인. 대상 시점에 경기가 없는 경우의 선택도 확인한다. 이번 확인은 코드 추적이며 실제 브라우저 재현은 미실행이다.

### B5. [P2] 대회 검수 화면에서 경기별 POV 전체 조회를 두 번 반복한다

- **문제:** 시점 칩 집계를 위해 대회의 모든 경기별 상세를 읽고, 선택한 VOD의 불일치 표시를 위해 다시 읽는다. 요약만 필요한 첫 단계에서도 프레임까지 읽는다.
- **근거:** `packages/core/lib/db/ck-pov.ts:310`의 경기별 `getMatchPovViews`, `:328`의 동일 상세 재조회. `getMatchPovViews`는 경기·참가자·POV·프레임 4개 질의를 수행한다(`:230` 부근). 대회 페이지가 두 함수를 순차 호출한다. 기존 `getLeadWorkspace`는 이미 같은 N+1을 없애기 위해 일괄 조회한다(`packages/core/lib/db/ck.ts:1433`).
- **발생 조건/비용:** 대회 경기 N개, 선택 시점 경기 K개이면 이 두 함수만 `2 + 4N + 4K`개 질의. N=K=20이면 162개이며 다른 대회/검수대 조회는 별도다. 이는 코드상 질의 수 계산이고 운영 응답시간 측정은 아니다.
- **수정 방향:** 대회 경기·참가자·시점 관측을 묶어 읽고 동일 스냅샷으로 칩 요약과 선택 시점의 차이를 계산한다. 프레임은 선택 VOD 검수대의 기존 조회를 사용한다. 비교 결과를 별도 정본 테이블이나 캐시에 복제할 필요는 없다.
- **필요한 테스트:** 1/20/100경기 fixture에서 질의 수가 경기 수에 비례해 늘지 않음; 리팩터링 전후 시점 수·미해결 수·참가자 대응·순서 동일; 다른 시점 편집 후 다음 읽기에 반영.

## C. 권장 개선사항

1. **동일 재가져오기의 전체 삭제/재삽입과 행별 revision 증가를 줄인다.** `ck.ts:851`, `db/migrations/0043_match_review_completion.sql:27` 부근. 참가자 한 명인 동일 경기 입력을 다시 저장했을 때 revision이 `1 → 3`으로 증가하는 것을 재현했다. 10명은 삭제/삽입만으로 20번 증가할 수 있다. 9월 27일 통합 변경에 이미 있던 구조이며, 추가 시점 경로에서는 개선됐지만 원본 시점 경로에는 남았다. 값 기반 upsert/diff로 동일 재전송을 무변경 처리하고, 논리 변경 단위의 버전 관리를 검토한다.
2. **FC 추천 정책의 소유권을 정리한다.** `packages/core/lib/db/fconline.ts:214`, `:237`의 최다 맞대결 추천과 상위 쌍 선정은 단순 경기 사실 조회보다 기능 정책에 가깝다. 홈과 상대전적에서 공유하지만 `getFeaturedFcoPair`와 `listFcoTopPairs`가 유사한 SQL을 중복한다. `docs/ARCHITECTURE.md`에도 알려진 부채다. 공개 범위 판정은 코어에 유지하고, 추천 선택/노출은 모듈 역할과 화면으로 옮기거나 정책 소유권을 명시한다. 코어의 모든 FC 집계를 모듈로 옮길 필요는 없다.
3. **검증 하네스의 연결 설정을 자체 고정한다.** 기본 `verify:db`는 실행 도중 진행이 멈춰 종료 후 `DATABASE_POOL_MAX=1`로 재실행했다. `scripts/verify-db.ts:42`는 PGlite 소켓을 만들지만 pool 상한을 고정하지 않고, 코어 기본값은 20이다. 다른 하네스처럼 시험용 연결 수를 명시하고 전체 타임아웃을 둔다. 멈춤의 정확한 내부 원인은 별도 진단이 필요하다.
4. **문서와 미래 상태를 현재 구현에 맞춘다.** 계약 파일 첫머리의 “모두 core_public만 읽는다”와 아키텍처 문서의 FC 비공개 계약 설명은 현재 FC 함수 재수출(`contract/index.ts:305`)과 맞지 않는다. `match_pov.mode='full'`은 현재 분기를 만들지 않는 미래용 필드다. 기존 마이그레이션을 고쳐 제거할 사안은 아니지만, light 단계 전까지 큐/복사본/승인 상태를 더 만들 이유는 없다.
5. **백필 목록에서 사라진 VOD의 완료 표현을 구분한다.** `ck-backfill.ts`의 `missing`은 보고용이며 실행 `queue`에 포함되지 않는다. `ck-backfill.sh`는 큐가 비면 “요청 기간을 끝까지 처리”라고 출력한다. 스킬은 최종 `missing` 확인을 요구하므로 정보가 사라지지는 않지만, 셸 종료 메시지도 “목록에 남은 대상 처리 완료, 목록 누락 X건 별도 확인”처럼 표현하면 오해를 줄인다.

## E. 변경 파일과 작업 순서

1. **마이그레이션 원문 복구:** 0026의 불필요한 EOF 변경만 제거한다. 적용 장부를 일괄 재채택하지 않는다.
2. **실패 회귀부터 추가:** `scripts/verify-ck-pov.ts`에 B1; `scripts/verify-ck-concurrency.ts`에 B3 경쟁 순서; 브라우저 검사에 B4의 대회/시점/부족 항목 이동을 추가한다.
3. **코어 저장 경계 수정:** `packages/core/lib/db/ck-pov.ts`, `packages/core/lib/db/ck.ts`, `scripts/ck-merge.mjs`. 원본 재작성 정책을 잠금 아래 코어로 모으고 의미 있는 관측 변경을 검수 버전에 반영한다.
4. **검수 조회 묶기:** `ck-pov.ts`에서 대회 단위 일괄 조회 결과를 공유하고 대회 페이지에서 중복 호출을 제거한다.
5. **UI 상태 전달 수정:** `apps/web/app/admin/ck/event/[slug]/page.tsx`, `apps/web/app/admin/ck/match/[matchId]/page.tsx`, `PovChips.tsx`, 필요 시 `CkReviewer.tsx`. 경기 ID·탭·focus를 같은 규칙으로 유지한다.
6. **검사:** 단위/타입 → POV/CK/백필 → DB 신규 설치/기존 장부 업그레이드 → FC/수집/모듈 제거 → 실제 PostgreSQL 동시성 → 데스크톱·모바일·키보드/딥링크.
7. **운영 반영 전:** 실제 적용 버전을 읽기 전용으로 확인하고 백업한다. `0046`은 옛 진척 표를 제거하므로 옛 표와 `event_lead.raw`도 백업 대상이다. 0044→0045→0046 순서를 유지하고, 요청 기본 기간이 새로 필요할 수 있음을 확인한다. 경기/참가자/프레임/연결 ID·건수, 공개 경기/사람 수, 대회 순서를 전후 대조한다. 실패 시 변경 단위 롤백 또는 백업 복원 절차를 준비한다. 이번에는 운영 이관을 수행하지 않았다.

필수 문제는 대부분 기존 모델과 저장 경계를 고치면 해결된다. 새 큐·승인 테이블·공개 사본을 추가하는 재설계는 필요하지 않다. 트리거 수정이 필요해지면 이미 적용된 0043을 편집하지 말고 새 번호 마이그레이션으로 작성한다.
