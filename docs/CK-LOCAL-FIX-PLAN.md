# ck-local 실험판 수정 계획

작성: 2026-09-30. 대상: `scripts/ck-local/`, `.claude/skills/ck-local/`. 상위 계획: [LOCAL-VLM-PLAN.md §5-A](LOCAL-VLM-PLAN.md).
출발점: Codex 검토 6건 + ck-research SKILL.md·ck-probe·ck:merge 병합 규칙을 줄 단위로 대조한 결과.

## 0. 요약

첫 구현은 **기존 도구에서 보조(거름망)였던 썸네일 시트를 조사의 뼈대로 올리면서, 뼈대에 필요한 계약을 만들지 않았다.**
시간축·커버리지 지점·시트 수신 완료 판정이 ck-probe 안에만 있거나(시간축·지점) 아예 없었다(수신 완료).
그래서 고치는 방향은 ck-local 에 같은 로직을 한 번 더 쓰는 것이 아니라, **그 계약을 공용 모듈 하나로 빼서
ck-probe·거름망·ck-local 이 같이 쓰게 하는 것**이다. 조사 중 기존 도구에도 같은 결함이 있는 것을 실측으로 찾았다(§1).

## 1. 새로 확인한 사실 (실측, 2026-09-30)

VOD 3개·파일 7개(205676943, 207602969 f1~f4, 206431267 f1~f2).

| 사실 | 근거 |
|---|---|
| **시트 `column=0` 과 `column=1` 은 같은 이미지다** | 205676943 f1: md5 동일(697,435B). 7개 파일 전부 칸 수가 `ceil(길이/3) + 99~100` — 앞 한 장이 중복이다 |
| **칸 간격은 3초 고정이다** (`길이 ÷ 칸 수` 가 아니다) | 중복 한 장을 빼면 7개 파일 모두 칸 수 = `ceil(길이/3)` ±1. 46초 파일도 16칸 |
| 위 대응이 원본과 맞다 | 207602969 의 3600·7200초 원본(g0003600·g0007200)과 비교: 새 대응(`1 + t/3` 번째 칸)은 같은 화면, 옛 대응(`t ÷ (길이/칸수)`)은 다른 화면 |
| **정상 끝 응답 = HTTP 500, 본문 0바이트** | 7개 파일 모두. 오류와 끝이 **같은 모양**이라 응답만으로는 구분할 수 없다 |
| API 길이와 HLS 길이 | 이 3개 VOD 는 같았다. 다만 CK-COLLECTION.md 에 API 4.00h / HLS 2.18h 사례가 있다 — 축은 HLS 가 정본 |

### 기존 도구에 미치는 영향 (ck-local 과 별개)

`scripts/lib/soop-vod.mjs` 의 `scanSheets` 는 column 0 부터 받고 `sec = 길이 ÷ 칸 수` 로 시각을 낸다.
그래서 **파일 앞쪽일수록 최대 약 5분 늦은 시각**을 보고한다(뒤로 갈수록 줄어 끝에서 0).
쓰는 곳: `ck-probe`(거름망 추천 지점), `collect-leads`, `prep-ck-frames`(2026-10-01 삭제), `scan-vod-frames`.
ck-probe 에서는 30분 격자가 따로 있어 위험이 줄었지만 **누락이 없었다고 단정할 수는 없다** — collect-leads·prep-ck-frames 는 거름망 결과에 직접 기댄다.
끝 판정(`길이 < 1000B → 끝`)도 같아서 중간 500 오류가 조용히 "끝"이 된다.

## 3. 해결 구조

### 변경 분리

| 변경 | 실험을 지우면 |
|---|---|
| 시트 중복·시간축·수신 완료·커버리지 지점 (A·B·C) | **유지** — 기존 도구의 결함 수정. Ollama·ck-local 경로를 넣지 않는다 |
| 로컬 모델·몽타주·검산 기록·장부 (D·F·G·H·I) | 삭제 (`scripts/ck-local/`) |
| 백필 준비 단계 연결 (E) | 환경변수를 안 주면 꺼진 상태. 남겨도 무해 |

### 공용 (실험을 접어도 남긴다 — 기존 도구의 결함 수정이다)

**A. `scripts/lib/vod-timeline.mjs` — 시간축 단일 출처 (R1·R3)**
- `timeline(detail)` → 파일별 `{ index, offset, length(HLS), measured, snapshotRowKey }`. ck-probe 의 ① 을 그대로 옮긴다.
- `sheetIndex(part)` → 시트 수신 + 대응:
  - **완료는 시트 수가 아니라 칸이 덮는 시간으로 판정한다.** 조건 전부:
    ① 그 파일과 **앞 파일 전부**의 HLS 길이를 쟀다(앞 파일이 미측정이면 뒤 파일 시작 위치가 불확실하다 — `axis_reliable: false`)
    ② column 0 과 1 이 같은지 **해시로 확인**했다(다르면 대응을 가정하지 않고 파일 전체를 미확인으로)
    ③ 받은 시트가 전부 JPEG 로 해석됐다 ④ 마지막 시트의 유효 칸(빈 칸 제외)을 셌다
    ⑤ `유효 칸 × 3초` 가 파일 끝까지 덮는다
  - 실측의 ±1칸은 **끝 3초 허용**으로 다룬다. 덮은 끝이 `길이 − 3초` 보다 앞이면 그 뒤를 `failed`(원본으로 확인) — 시트 수로 보정하지 않는다
  - 덮기 전에 온 500·비JPEG → 재시도 3회 → 그래도면 그 시트 시작부터 끝까지 `failed`. 덮은 뒤의 500 만 정상 끝
  - 반환 계약: `frames[i]` = 파일 로컬 `i × 3`초의 칸(중복 시트 제외), `sec = 3`, `total` = 파일 길이(HLS, 없으면 API), `failed` = 파일 로컬 초 범위
  - `cellAt(t)` → `{ sheet, cell, at }` = column `1 + floor(i/100)`, 칸 `i % 100`, `i = floor((t - offset)/3)`
- `scanSheets` 는 이걸 써서 통계를 내도록 바꾼다 → 거름망 시각 5분 오차와 조용한 중단이 같이 고쳐진다.

**B. `coveragePoints(parts, interval)` — 커버리지 지점 단일 출처 (R2)**
- ck-probe 의 규칙을 그대로 옮긴다: 전역 격자 + **파일마다 없으면 가운데 한 장** + **파일마다 끝-30초**
  (ck-probe 는 끝-30초를 VOD 전체 끝에만 둔다. 파일 끝마다로 넓히는 것은 두 도구 모두에 이득이다).
- ck-probe 와 ck-local 이 같은 함수를 부른다.

**C. 축 검증 명령 (R1 을 한 번 확인하고 끝내는 게 아니라 재확인 가능하게)**
- `node scripts/verify-sheet-axis.mjs --vod <번호>`: 이미 받아 둔 원본(`out/ck/<번호>/g*.jpg`)을 192×108 로 줄여
  대응 칸 주변과 픽셀 차이를 비교해 세 가지로 나눈다.
  **정상**(최적이 대응 칸 또는 바로 다음 칸 — 3초 샘플 간격으로 설명된다) · **판단 불가**(여러 칸이 비슷 — 로비처럼 정지 화면) ·
  **어긋남**(분명히 다른 칸이 최적이고, 파일 안에서 같은 방향으로 수십 칸 이상 반복). 합격 조건은 "어긋남 0".
- 원본이 수백 장 있는 VOD 가 이미 여럿이다(207602969 에 313장). 새로 받지 않는다.

### ck-local 전용 (실험을 접으면 같이 지운다)

**D. 캐시 이름표 (R4)** — `모델 digest | 프롬프트 버전 | 이미지 처리 버전 | 시트 해시 | 칸 번호`.
시각은 이름표에 넣지 않는다. 대응을 고쳐도 같은 이미지면 판정을 재사용하고, 다른 이미지면 새로 분류한다.
`runs[]` 에 **새로 분류한 수·캐시 재사용 수·전체 경과 시간**을 따로 적는다.

**E. 실행 위치 (R7)** — 로컬 훑기는 **Claude 세션 밖의 준비 단계**다.
- 백필: `ck-backfill.sh` 에 `CK_BACKFILL_PREP` (VOD 마다 Claude 세션 **전에** 실행할 명령)을 둔다.
  `CK_BACKFILL_SKILL` 과 같은 방식이고, 기본값이 없으면 지금과 같다. 순서가 직렬이라 SOOP 병렬도 생기지 않는다.
- 단일 VOD: 사용자가 돌리거나 Claude 가 백그라운드로 돌리고 끝난 뒤 이어간다.
- 준비 단계가 실패하면 그 VOD 는 ck-research 규칙대로 조사한다(없던 일로 두지 않는다).
- 준비 작업도 백필과 같은 잠금 안에서, 같은 중단 처리(프로세스 그룹 종료)로 돈다.
- **이번 실행의 성공한 결과만** Claude 에 넘긴다: 셸이 준비 명령의 종료 코드와 `scan.json` 의 run_id 를 확인해 프롬프트에 run_id 를 적는다.
  실패하면 "준비 실패 — ck-research 방식"이라고 적는다. 스킬은 run_id 가 다른 산출물을 쓰지 않는다.
- 단일 VOD 를 백그라운드로 돌릴 때도 끝나기 전에는 다른 SOOP 조사 도구를 시작하지 않는다.
- 예산: `--max-calls`(기본 3000)·`--max-minutes`(기본 90). 넘으면 정밀 분류를 멈추고 남은 롤 구간을 `unexamined` 로 적는다 — Claude 가 ck-research 방식으로 본다.

**F. 기록 의미 (R6)** — **이 실험의 정책**으로 `opened` 에는 원본만 넣는다(ck-research 는 "실제로 연 시각"이라고만 정의한다 — 원본 한정은 뜻을 분명히 하려는 이번 선택이다).
썸네일 검산은 `probes.planned` 가 아니라(계획이지 본 것이 아니다) **실제로 연 몽타주 파일과 그 범위**를 `local/review.json`(run_id 포함)과 `note` 에 남긴다.
그래서 롤이 없어 보이는 VOD 도 **파일마다 원본 1장 이상**(B 의 파일 끝 지점)을 연다.
- 이유: `opened` 는 "원본을 열어 봤다"는 근거로 쓰여 왔다(ck-research §기록의 뜻). 썸네일 150칸을 거기 넣으면
  완료 판정은 통과하지만 뜻이 바뀐다. 썸네일 열람 칸을 새로 만드는 건 core 변경이라 실험 단계에선 하지 않는다.
- 비용: VOD 당 원본 1~4장. 기존 30분 격자(5시간에 11장)보다 적다. 파일 끝 원본은 검산을 **대신하지 않는다** — 몽타주 검산은 따로 필수다.

**G. 결과창 후보 (4)**
- `result-hits-N.jpg` 로 페이지를 나눈다. 묶음마다 번호(`#1`, `#2`…)를 칸 밑에 찍는다. 스킬에서 전부 연다.
- 원본 지점: 묶음의 처음·가운데·끝 + **첫 결과창 직전의 마지막 롤(비결과창) 칸 = 경계 후보**.
  LOL 에는 로비도 들어 있어 이미 결과창이 지나간 뒤일 수 있다. **Claude 가 원본을 열어 같은 경기의 진행·종료 화면인지
  확인한 뒤에만** 「앞쪽 보완 탐색」의 왼쪽 경계로 쓴다.
- 한 칸짜리 묶음도 원본으로 본다(짧게 지나간 결과창일 수 있다).
- Claude 의 묶음별 판정(진짜 결과창·헛봄·다른 화면)을 `ck:local -- --review <vod> --run <run_id> --cluster N --is result|false --note …`
  로 `local/review.json` 에 남긴다. 재실행하면 묶음 번호가 바뀌므로 **run_id 와 함께** 적는다. 프롬프트 개선 자료다. DB 후보(`candidates`)에는 넣지 않는다 — 후보는 경기 단위다.

**H. 실험 장부 (R5)** — `out/ck/local-ledger.jsonl`: VOD, run_id, 모델 digest, 판정, 산출물 경로,
Claude 조사 결과(ck:merge 저장 여부·status). 스킬 문서의 「지우기」는 이 장부로 대상을 고른다.
`scan.version = ck-local/1` 은 보조 표시로 남긴다.

**I. 썸네일 정확도 먼저 재기 (R8)** — 새 VOD 를 돌리기 전에 두 가지를 따로 잰다.
- **분류 성능**: 결과창 시험 세트 시각의 썸네일을 A 의 대응으로 꺼낸다. 원본 정답을 그대로 붙이지 않는다 —
  3초 차이로 아직 게임 화면일 수 있고, 원본 세트에도 잡음이 있었다. **꺼낸 썸네일을 Claude 가 몽타주로 직접 보고 정답을 다시 단 뒤** 모델과 비교한다.
- **탐색 성능**: 결과창이 있던 경기마다, 그 결과창 순간이 10초 정밀 분류 지점의 썸네일에 실제로 잡히는가(샘플 사이로 지나가지 않는가).
- 원본 960px 결과(Qwen2.5 152/158)와 비교한다. 크게 떨어지면 확대 배율·프롬프트를 여기서 고친다.

## 4. 기존 스킬(ck-research) 줄 단위 대조

| ck-research 규칙 | ck-local 현재 | 조치 |
|---|---|---|
| 1단계: `ck:record --lead`, `--find-match --vod` | 참조 | 유지 |
| **예측 위치**(`--between … --divide 5`)부터 결과창을 찾는다 | 없음 | **추가.** 예측 줄이 있는 경기는 로컬 후보와 관계없이 예측 위치를 본다. 로컬 후보가 예측과 맞으면 그 원본부터 |
| 기존 경기라도 처음부터 읽는다 | 참조 | 유지 |
| 짧은 꼬리·잔여 범위에도 대표 지점 | 없음 | B |
| VOD 전체 초, HLS 불일치면 투영하지 않는다 | API 길이 사용 | A |
| 맥락 확인 → 경계 → **판마다 결과창 탐색 종료 사유** | `LOL_NO_RESULT` 에서만 5분할 | **모든 판**에 적용. "로컬이 못 찾음"은 네 종료 사유 중 무엇도 아니다 — 원본 5분할→2~3초까지 해야 미발견 |

인게임 Tab 점수판은 인게임 구간 **안**이라 자연히 빠진다.

## 8. 2차 설계 — 로컬은 "판 끝 위치"만, 판단은 전부 Claude (2026-09-30 결정)

§7 의 결론(후보 = 인게임 끝 전환)을 채택하되, 점수·합격선을 더하지 않는다. 기존 ck-research 로 결과가 잘 나왔으므로
**로컬은 어디를 먼저 볼지만 좁히고, 무엇이 결과창인지·몇 판인지는 Claude 가 기존 규칙대로 정한다.**

### 로컬이 하는 일 — 로직에 쓰는 판단은 "게임 중인가" 하나

질문 두 개(`scripts/ck-local/vlm.mjs`): **stage** `LOL_RESULT · LOL_CLIENT · LOL_GAME · FC · OTHER · UNSURE` — 로직은 `LOL_GAME` 만 쓴다.
**kind**(p1, 결과창 128/128) — 끝 띠의 분홍 표시(B)에만 쓴다.
stage 실측(썸네일, 정답은 Claude): 게임 중 73 → LOL_GAME 65 · 클라이언트 34 → 0 · 결과창 128 → 0. 끝난 판을 게임 중으로 보지 않는다.
실패한 질문: 6라벨에 LOL_INGAME 을 맨 앞에 둔 p2(265/308 이 게임 중), "미니맵이 보이나" 예/아니오(결과창 126/128 이 예).

1. **2분 칸 분류** — 기본 지점(격자 2분 + 파일마다 가운데·끝) 전부.
2. **D. 애매한 칸 재확인** — `UNSURE`·분류 실패 칸은 앞뒤 30초를 한 번 더 분류한다. 둘 다 `LOL_GAME`·`UNSURE` 가 아니면
   "재확인 — 롤 아님"으로 회색 표시, 아니면 노란색 그대로(Claude 가 본다). 라벨 자체는 바꾸지 않는다.
3. **판 끝 후보** — `LOL_GAME` 칸 다음 기본 지점이 `LOL_GAME` 이 아니면 후보. 영상이 게임 중으로 끝나면 영상 끝.
4. **A. 판 끝 확인·정밀화** — 후보에서 10초 간격으로 앞으로 본다. 게임 아님이 **2분** 이어지면 판 끝(직전 게임 칸이 마지막 게임 칸),
   그 전에 게임 화면이 다시 나오면 후보 취소. 근거: 판과 판 사이는 결과창→로비→챔피언 선택→로딩이라 2분 이상이다.
   Tab 점수판·상점은 몇 초다. (실측: 이 확인 없이 207588653 의 4판이 Tab 점수판 때문에 12조각 났다.)
5. **끝 띠** — 마지막 게임 칸부터 5분을 10초 간격 30칸 몽타주로.
6. **B. 결과창 표시** — 띠 30칸을 kind 질문으로 분류해 `LOL_RESULT` 칸에 분홍 테두리. **표시일 뿐** — 분홍이 없어도 Claude 는 띠 전체를 본다.

없애는 것: 롤 구간 전체 10초 정밀 분류, 결과창 묶음·경계 후보·묶음별 검산 기록, 결과창 몽타주.
비용: 5시간 VOD·3판 ≈ 150 + 판당 42 + 애매 칸당 2 회 ≈ 10분.

### Claude 가 하는 일 (순서 고정, 앞 단계가 뒤 단계의 입력)
