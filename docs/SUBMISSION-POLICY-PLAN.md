# 제보 판정 — 기준을 갈아 끼울 수 있는 뼈대 + 2단계(빠진 경기 등록·VOD 단서)

> 2026-10-17 설계 · **결정 완료**(§9, 같은 날 사용자) · **§8 다섯 단계 전부 구현·운영 DB 적용(0095~0098 2026-10-17 · 0099 2026-10-18)** — 한눈에 보는 결과는 **§10**. **2026-10-18 반영 방향을 바꿨다(§11): 경기 고치기는 운영자 확인 대기, 편성표 제보는 바로 반영.**
> 앞 문서: [USER-SUBMISSION-PLAN.md](USER-SUBMISSION-PLAN.md)(1단계 경기 고치기·3단계 편성표 — 지금 기준이 코드 곳곳의 if 로 박혀 있다).

## 1. 왜

사용자 결정(2026-10-17):

- 2단계는 **둘 다** 한다.
  - **가. 직접 입력**: 중복 경기가 없으면 **곧바로 공개**한다. "검증 전 · 곧 VOD 확인" 표시를 달고, **집계에서는 빠진다**.
  - **나. VOD 단서**: 공개하지 않는다.
  - 둘 다 **VOD 판독 대기열 맨 앞**에 넣는다. 판독 결과가 나오면 집계에 들어간다.
- **검증 기준은 언제든 바뀐다.**
  - 예: "3명이 같은 값을 보내면 검증", "특정 계정에 권한".
  - 기준이 바뀌어도 분기·예외가 코드 곳곳에 퍼지지 않아야 한다.
  - **이미 만든 제보(경기 고치기·편성표)도 같은 틀**로 판정한다.

지금 기준이 박혀 있는 곳은 아래와 같다. 기준 하나를 바꾸려면 이 넷을 다 찾아 고쳐야 한다.

- `holdReasonInTx`(경기 고치기 보류 이유 5종)
- `submitScheduleReport`(편성표는 언제나 보류)
- `verifySubmission`·`rejectSubmission`(운영자만 상태를 바꾼다)
- 화면의 버튼 문구

## 2. 뼈대 — 사실 → 판정 → 실행

```
 접수·+1·VOD 판독 결과·운영자 처리·권한 변경·기준 변경
        │  (무슨 일이 있었나 — 사실만 쌓는다)
        ▼
  ① 사실 모으기  gatherFacts(tx, 제보)        ← DB 를 읽는 곳은 여기 하나
        │  Facts (순수 값)
        ▼
  ② 판정        decide(Facts, 기준)          ← 순수 함수. 기준 = 규칙 목록 + 설정값
        │  Verdict { 보임, 믿음, 할 일, 이유 }
        ▼
  ③ 실행        enact(tx, 제보, 이전 판정, 새 판정)  ← 쓰기는 여기 하나(기존 쓰기 길만 부른다)
```

- **기준을 바꾸는 일은 ②만 고치는 일이다.** ①·③은 기준을 모른다.
- ②는 DB 를 모르고 순수 함수라서 단위 시험만으로 기준을 바꿀 수 있다.
- **새 사실 종류**(예: "다른 사이트 기록 일치")가 생기면 ①에 칸 하나, ②에 규칙 하나를 더한다.
- **새 동작**(예: "알림 보내기")이 생기면 ③에 동작 하나를 더한다.

### 판정(Verdict)은 두 축이다

지금의 `state` 한 칸(applied·held·verified·reverted·rejected·duplicate)에는 두 가지 뜻이 섞여 있다. 섞여 있으면 기준이 늘 때마다 조합이 늘어난다. 그래서 둘로 나눈다.

| 축 | 값 | 뜻 |
|---|---|---|
| **보임**(visibility) | `shown` · `hidden` | 제안이 공개 기록에 들어가 있나(목록에 보이나) |
| **믿음**(trust) | `pending` · `verified` · `rejected` | 집계에 넣어도 되나 |

- 공개 화면 규칙은 하나로 끝난다: **보이고(shown) 아직 믿지 않으면(pending) "검증 전"**. 집계는 `verified` 만 센다. 지금의 `pending_match` 뷰 정의 하나를 이 뜻으로 바꾸면 된다.
- 옛 `state` 는 두 축에서 계산되는 이름표로 남긴다(화면 호환).

| 옛 이름 | 보임 | 믿음 |
|---|---|---|
| applied | shown | pending |
| held | hidden | pending |
| verified | shown | verified |
| reverted | hidden | rejected(보였다가 되돌림) |
| rejected | hidden | rejected |

- `duplicate` 는 판정이 아니라 **합침**이다(제보 A → B). 판정 축 밖의 칸 `duplicate_of` 로 남긴다.

### 할 일(effects)

판정이 함께 내놓는 요청 목록이다. ③이 실행한다.

- `vod_priority`: 그 VOD 를 판독 대기열 맨 앞으로
- `admin_review`: 운영자 대기열에 올림
- `notify_reporter`: 보낸 사람에게 알림(나중)

## 3. 사실(Facts) — 판정이 볼 수 있는 것 전부

```ts
interface Facts {
  kind: "match_correction" | "schedule_report" | "match_addition" | "vod_hint";
  intake: {                       // 접수 때 본 대상의 상태(종류별)
    review_completed?: boolean; api_observed?: boolean; account_identity?: boolean;
    contested?: boolean; not_public?: boolean; duplicate_of_match?: string | null;
  };
  reporter: { roles: Role[]; sanctioned: boolean };
  agreement: { members: number; trustedMembers: number };   // 같은 지문의 서로 다른 회원 수(보낸 사람 + +1)
  vod: { state: "none" | "queued" | "agree" | "mismatch" | "not_found" | "unavailable"; mismatchCells: string[] };
  admin: { decision: "verify" | "reject" | null };
  age: { hours: number };
}
```

- `vod` 는 판독 대기열과 판독 결과에서 온다(§6).
- `agreement` 는 지금의 `submission_supporter` 를 센다.
- `reporter.roles` 는 새 권한 표에서 온다(§5).

## 4. 기준 = 규칙 목록 + 설정값

```ts
type Rule = { id: string; when: (f: Facts, c: Config) => boolean; then: Verdict };
const POLICY = { version: "2026-10-17.2", config: { trustedReporter: false, consensusMembers: null }, rules: [ /* 위에서부터 처음 맞는 것 */ ] };
```

v1 규칙은 **지금 동작을 그대로 옮긴 것**에 2단계를 더한 것이다(굵은 것이 새 규칙).

| 순서 | 규칙 id | 조건 | 판정 |
|---|---|---|---|
| 1 | `admin` | 운영자가 확인/반려 | 그대로(확인 → 보임·믿음, 반려 → 숨김·거부) |
| 2 | **`vod_agree`** | VOD 판독이 같은 판을 찾았다 | 보임·믿음(판독 값 우선) |
| 3 | **`vod_mismatch`** | 판독이 같은 판인데 값이 다르다 | §9-2 결정 |
| 4 | `sanctioned` | 보낸 사람이 제재 중 | (접수 자체를 막는다 — 지금과 같다) |
| 5 | `hold_*` | 경기 고치기의 보류 이유 5종 | 숨김·대기 + 운영자 |
| 6 | `schedule` | 편성표 제보 | 숨김·대기 + 운영자 |
| 7 | **`trusted`** | 경기 고치기 + 보낸 사람에게 `trusted_reporter` 권한(설정 `trustedReporter`) | 보임·믿음 |
| 8 | **`consensus`** | 경기 고치기 + 서로 다른 회원 N명(설정 `consensusMembers`)이 같은 값 | 보임·믿음 |
| 9 | **`addition`** | 빠진 경기 직접 입력(중복 없음) | **보임·대기 + VOD 우선** |
| 10 | **`hint`** | VOD 단서 | 숨김·대기 + VOD 우선 |
| 11 | `default` | 경기 고치기 | 보임·대기(지금의 applied) |

- **기준을 바꾸는 방법은 셋뿐이다.**
  - 줄의 순서·조건을 바꾼다.
  - 설정값을 바꾼다(예: `consensusMembers: 3`).
  - 줄을 더하거나 뺀다.
- 판정마다 `rule_id` 와 `policy.version` 을 남긴다. 그래서 "이 판은 어떤 기준으로 검증됐나"를 언제든 보여 줄 수 있다.
- **기준이 바뀌면 열린 제보를 다시 판정한다.** `reconsiderAll()` 을 돌린다. ③은 판정이 그대로면 아무것도 하지 않으므로(멱등) 몇 번 돌려도 안전하다.
- 사람이 내린 결정은 기준이 바뀌어도 뒤집지 않는다. 규칙 1(`admin`)이 언제나 맨 위에 있기 때문이다.
- **신뢰 계정·합의는 보류 아래에 둔다(구현 때 정함, 2단계 ②).** 처음 표에서는 보류 위였다. 하지만 그러면 신뢰 계정 한 명이
  공식 기록(`api_observed`)·다툼(`contested`)·검수 끝난 판을 운영자 없이 바꾼다. 그래서 이 두 규칙은 "바로 반영(확인 전)"이 될 제보를
  검증으로 올리기만 한다. 편성표 제보에도 쓰지 않는다 — 편성표는 운영자가 저장해야 바뀌므로, "검증"만 하면 반영 없이 닫혀 버린다
  (편성표용 권한은 따로 `schedule_editor` 같은 역할 + 그 반영 길을 만들 때 더한다). 바꾸려면 규칙 순서만 옮기면 된다.
- 판정이 보는 "같은 내용 회원 수"는 보낸 사람 + 같은 내용이에요(+1)다. 반영된 제보에 같은 값을 다시 보내면 "이미 그 값"이라
  거부되므로, 확인 전 제보에 동의하는 길은 +1 버튼 하나다.

## 5. 권한 — 계정에 붙는 역할

```sql
member_role (id, member_id, role, note, granted_by, granted_at, revoked_by, revoked_at)   -- 0096
-- 지금 유효 = revoked_at IS NULL, (member_id, role) 마다 하나(부분 UNIQUE). 주고 거둔 기록은 지우지 않는다(제재 표와 같은 모양).
```

- 구현 때 바꾼 것: 처음 설계의 `PK (member_id, role)` + `expires_at` 대신 기록을 남기는 줄 + 거두기 칸으로 했다.
  "누가 언제 왜 주고 거뒀나"가 남아야 권한으로 검증된 제보를 나중에 설명할 수 있다. 기한은 쓸 곳이 생기면 더한다.
- 주기·거두기는 `db/submission.ts` 의 `grantMemberRole`·`revokeMemberRole` 하나 — 회원 → 판 → 제보 순서로 잠그고
  그 회원이 보냈거나 +1 한 열린 제보를 다시 판정한다. 이미 검증된 제보는 거둬도 그대로다(그때의 기준으로 닫혔다).
- 운영 화면: 커뮤니티 운영의 회원 카드(`/admin/community?member=`)에 권한 기록·주기(사유 필수)·거두기.
  지금 기준에서 꺼진 역할은 "효과 없음"으로 알린다(`roleInEffect`). 제보 상세에 보낸 회원의 권한과 회원 카드 링크.

- 역할의 예: `trusted_reporter`(제보가 바로 검증), `schedule_editor`(편성표 제보가 바로 반영) 등.
- 역할 목록은 `metrics` 상수 하나에 둔다. DB CHECK 도 같은 목록이다.
- 역할은 **판정의 사실일 뿐**이다. 역할마다 화면이나 코드를 따로 만들지 않는다. 권한을 주거나 거두면 그 회원의 열린 제보를 다시 판정한다.
- 운영자(최고 관리자)는 지금처럼 인증 쪽에 남는다. 운영자의 확인·반려는 사실(`admin`)로 들어간다.

## 6. VOD 판독과 잇기 — 웹 ↔ 이 PC

ck-auto 의 대기열은 이 PC 의 파일(`out/ck/auto/queue.json`)이다. 배포하면 웹은 서버에서 돈다. 그래서 둘 사이를 **DB 의 요청 표 하나**로 잇는다.

```sql
vod_request (id, title_no, channel_id NULL, priority, reason: submission|admin, submission_id NULL, note, requested_by,
             state: queued|claimed|done|unavailable|cancelled, outcome_note, requested_at, claimed_at, closed_at)   -- 0097
```

- **구현 때 정한 것(③, 2026-10-17):** 줄은 **(VOD, 제보)마다** 하나이고, "같은 VOD 는 한 줄로 모은다"는 읽는 쪽(`listOpenVodRequests`)이
  VOD 번호로 묶는다. 그래야 제보마다 "내 VOD 는 어디까지 왔나"(사실 `vod`)를 바로 읽는다. 같은 VOD 의 열린 줄은 claim·close 가 함께 옮긴다.
- 상태: `queued`(이 PC 가 아직 못 봄) → `claimed`(대기열에 넣음 — 끝난 조사였으면 다시 열었다) → `done`(판독 끝) | `unavailable`(영상 없음).
  `cancelled` = 요청한 쪽이 거둠(운영자 요청은 운영 화면에서, 제보의 요청은 ④⑤의 판정이).
- 우선순위(`metrics/vod-request.ts`): 회원 제보 100 > 운영자 50 > 요청 없는 매일 조사 0. 대기열은 우선순위 → 오래된 VOD.
- 채널을 모르는 요청(링크만)은 이 PC 가 SOOP 상세(`vodDetail`)에서 채널·방송 끝·길이를 읽는다. 못 읽으면 지어내지 않고 다음 회차까지 둔다.

**흐름**

1. 판정의 할 일 `vod_priority` 가 요청 표에 한 줄을 쓴다(`requestVodInTx` — 제보 접수와 같은 트랜잭션, ④⑤). 운영자는 제보 화면의 "VOD 판독 요청"으로 쓴다.
2. ck-auto 가 매시간 목록을 갱신할 때(`ck:queue plan`) 요청 표를 읽는다. 할 일은 순수 함수 `scripts/lib/ck-vod-request.ts` 가 정한다(단위 시험).
   - **감시 목록 밖 채널이어도** 대기열에 넣는다. 제목 제외 규칙도 건너뛴다(사람이 콕 집은 VOD 다).
   - **이미 끝난 VOD 면 다시 연다** — `ck:queue reopen` 과 같은 함수(`reopenDone`). 인계에는 "이전 결론은 유지하고 요청 뒤 들어온 경기를 확인,
     같은 판이면 그 경기 번호로" + 요청 메모를 남긴다(품질 의심으로 다시 여는 reopen 과 문장이 다르다). 다시 열기는 처음 본(queued) 요청에서만.
   - 접근 불가로 기록된 VOD 는 `unavailable` 로 닫는다. 대기열에 넣은 뒤 끝났으면(`claimed` + 끝) `done` 으로 닫는다.
   - 요청 상태를 쓰는 것은 `--enqueue`(시간별 조회)뿐 — 미리보기·`--dry-run` 은 읽기만.
3. 대기열의 `claim` 정렬에 `priority` 를 더한다. 요청된 VOD 가 오래된 순서보다 앞선다(같은 채널은 여전히 하나씩).
4. 조사가 끝나면 `ck:queue finish` 가 `done`, 접근 불가 기록(`ck:queue access --status unavailable`)이면 `unavailable` 로 닫는다.

**판독 결과 → 사실**

- 판독 세션의 프롬프트에 "이 VOD 에 회원이 등록한 경기 X(사람·시각)가 있다"를 넣는다.
- 같은 판이면 세션이 **그 경기 번호로 기록**한다(기존 `submitMatchPovInTx role:'added'` — 칸마다 일치·불일치가 남는다). 다른 번호로 새 판을 만들지 않는다.
- 이 기록을 사실 `vod.agree`·`vod.mismatch` 로 읽는다.
- VOD 에 그 경기가 없으면 `vod.not_found`, 파일이 없으면(-6303) `vod.unavailable`.

**VOD 가 없는 직접 입력** — 회원이 VOD 링크를 안 줬을 때(§9-1):

- 그날 참가 스트리머들의 VOD 를 찾아 요청 표에 넣는다.
- 찾을 VOD 가 없으면 `vod.none` 으로 남는다. 판정은 "검증 전 + 운영자"다.

## 7. 2단계 두 종류

### 가. 빠진 경기 직접 입력 (`match_addition`)

**입력**: 행사(있는 행사 고르기 또는 이름) · 날짜·시각 · 블루/레드 사람 · 세트별 승리 팀 · (선택) 챔피언·KDA · VOD 링크 · 메모.

**중복 검사(접수 때)**

- 지금의 중복 판정은 챔피언·KDA 로 한다. 회원 입력에는 그 값이 없을 수 있다.
- 그래서 **사람·날짜 규칙**을 새로 둔다(metrics, 단위 시험): 같은 KST 날짜 ±시간 창, 같은 편 사람이 N명 이상 겹치면 같은 시리즈 후보.
- 후보가 있으면 받지 않는다. "이미 있는 경기입니다 → 그 경기 고치기"로 보낸다.
- 같은 규칙을 판독 결과를 이을 때도 쓴다(§6). 그래서 같은 게임이 두 개 생기지 않는다.

**공개**

- 기존 쓰기 길(분류 쓰기 `placeSetInTx` + 경기 쓰기)로 만든다.
- 쓰는 이를 `member` 로 넓힌다. 분류 쓰기는 지금 `auto`·`admin` 만 안다. `member` 는 `auto` 처럼 사람의 행사 제외를 넘지 못한다.
- `collected_via='manual'`.
- 판정이 보임·대기라서 "**검증 전 · VOD 확인 예정**" 표시가 붙고 집계에서는 빠진다.

**검증**

- VOD 판독이 같은 판을 찾으면 판독 값이 들어가고 집계에 포함된다.
- 반려되면 숨긴다. 만든 판이라 되돌릴 이력이 없다. 그래서 반려 = 판 숨기기(기존 `visibility`)다.

**구현(⑤, 2026-10-17, 0099)에서 정한 것** — 사용자 결정(10/17): 행사는 "있는 행사 + 모름", 챔피언·KDA 선택 입력, 표시는 하나로 "검증 전".

- **입력** = 행사(있는 실제 행사 또는 모름) · 날짜 · 첫 세트 시작 어림 · 맵(협곡/칼바람) · A·B팀 사람(등록 스트리머 또는 이름, 등록 스트리머 2명 이상)
  · 세트마다 A팀 진영·승리 팀 · (선택) 사람마다 챔피언·KDA · (선택) VOD 링크 · 메모. 정규화는 `metrics/addition.ts`.
  - 행사 모름 → 그날의 회원 등록 미분류 묶음(자동 묶음 `lol-member-auto-<날짜>`) — 회원이 쓴 행사 이름이 검증 없이 공개되지 않는다.
  - 시각은 회원의 어림이라 **날짜 정확도**로 저장한다(세트 시각 = 시작 + 40분씩 — 판독 후보 조회가 방송 안에서 찾게 하는 자리일 뿐).
- **중복** = 같은 KST 날짜의 공개 내전 세트 중 같은 편 등록 스트리머가 min(3, 고른 수) 이상 겹치면 후보(진영이 뒤집혀도 같은 편).
  후보가 열린 직접 입력이면 그 제보에 +1, 아니면 받지 않는다("그 경기 고치기"). 판 쓰기 잠금(`lockCkMatchWritesInTx`)으로 동시 등록·판독 저장과 줄을 세운다.
- **공개** = 판 `sub:<제보>:<세트>` · 시리즈 `sub:<제보>`, 분류 쓰기 `placeSetInTx`(새 판이라 사람의 제외가 있을 수 없어 actor auto — 분류 쓰기의
  쓰는 이를 넓히지 않았다) · `collected_via='manual'` · 확인 전 흔적 `submission_effect`(판마다) → 목록에 "검증 전", 집계에서 빠짐.
- **표시** = 고친 판·등록한 판 모두 "검증 전"(하나의 표시 `PendingBadge`, 설명은 "VOD 판독·운영자 확인 전"). 상태 이름 "반영됨 · 검증 전".
- **판독 잇기**
  - 판독할 VOD = 링크 또는 그날 참가 등록 스트리머 채널의 VOD 단서 행(VOD 끝이 시작 뒤 18시간 안, 4개까지). 없으면 사실 `no_vod` → 검증 전 + 운영자.
    시간별 조회(`ck:queue plan --enqueue`)가 먼저 열린 제보를 다시 판정하므로, 단서 행이 생기면 그때 요청이 나간다.
  - 요청 메모 = 만든 경기 번호·날짜·등록 이름 + "같은 판이면 이 번호에 시점을 더한다(pov added)" — 자동 판독 세션의 대상 사유로 넘어간다(회원 글 없음).
  - **찾음** = 만든 판 **모두**에 판독 시점(`match_pov`)이 붙었다. 일부만이면 운영자(`addition_unverifiable`).
  - 찾으면 규칙 `addition_found` 의 할 일 `adopt_vod` → `adoptPovValuesInTx`(ck-pov.ts): 대응이 확실한 불일치의 승리 팀·챔피언·KDA·포지션을 판독 값으로
    (검수 길 하나, 새 쓰는 이 `auto` — 사람 칸이 아니고 검수 표시를 남기지 않는다). 사람의 편(team)과 시점끼리 다른 값은 덮지 않고 운영자 화면에 남긴다.

### 나. VOD 단서 (`vod_hint`)

- **입력**: SOOP VOD 링크(필수) · 대략의 시점(선택) · 누가 나왔나(선택) · 메모.
- VOD 번호로 정규화한다. 같은 VOD 의 단서는 +1 로 모은다(지문 = VOD 번호 + 시점 구간).
- 판정은 숨김·대기 + VOD 우선이다. 판독이 경기를 기록하면 그 경기는 판독 경기로 바로 집계에 들어간다. 회원 값이 없으니 비교할 것이 없다.
- 단서 자체는 `vod.agree`(경기를 찾음)면 확인, `not_found` 면 "찾지 못함"으로 닫는다.
- **구현(④, 2026-10-17, 0098)에서 정한 것:**
  - 규칙 `hint_found`(확인) · `hint_not_found` · `hint_unavailable`(둘 다 숨김·대기 + 운영자) · `hint_pending`(숨김·대기 + 할 일 `vod_priority`).
    못 찾음을 바로 닫지 않고 **운영자 대기**로 둔다 — §9 "VOD 로 검증 불가 → 검증 전 유지 + 운영자"와 같은 결정(판독이 놓쳤을 수 있다).
  - "찾음" = 요청한 판독이 끝났고 그 VOD 에 판독이 기록한 경기(`match_pov`)가 있다. 시점을 줬으면 그 앞뒤 30분 안의 근거 화면
    (`match_evidence_frame`)이 이은 경기만. 경기가 나중에 이어지면 다시 판정(`reconsiderOpenSubmissions`)이 확인으로 옮긴다.
  - 사실 `vod` = 그 제보의 요청 줄 상태 + 그 경기 유무(`vodFactInTx` 하나). 판정의 할 일은 실행이 옮긴다(`syncEffectsInTx`):
    열린 제보에 `vod_priority` 면 요청 줄을 두고(이미 있으면 그대로 — 끝난 줄도 다시 만들지 않는다), 제보가 닫히면(반려·확인·중복) 열린 요청을 거둔다.
  - 판독이 끝나 요청이 닫히면 `settleVodRequests` 가 **같은 트랜잭션에서** 요청한 제보들을 다시 판정한다(ck:queue finish·access·plan 이 부른다).
  - ★ 요청 메모는 자동 판독 세션의 지시문(대상 사유)으로 넘어간다. 그래서 **회원이 쓴 글을 넣지 않는다** — 시점(숫자)과 등록된 스트리머 이름으로
    맞춘 사람만 적는다(지시문 주입 막기). 회원 메모는 운영자 화면에만 보인다.
  - 지문 = VOD + 시점(누가 나왔나는 빼고) · 같은 요청·+1·하루 한도·제재는 다른 제보와 같은 길(`twinOrLimitInTx` 하나로 모았다).
  - 화면: `/submit/vod`(로그인), 내 제보에 들어가는 링크·"VOD 판독 대기" 상태, 운영 상세에 요청 상태와 판독이 기록한 경기.

## 10. 구현 결과 요약 (2026-10-17~18)

§1~§9 의 설계를 다섯 단계(§8)로 만들었다. 이 절은 **실제로 무엇이 바뀌었나**를 한곳에 모은 것이다. 설계와 달라진 점은 §10-6.

### 10-1. 회원·운영자가 보는 것

| 제보 종류 | 보낸 순간 | 공개 화면 | 검증하는 쪽 | 검증 못 하면 |
|---|---|---|---|---|
| 경기 고치기(1단계) | **운영자 확인 대기**(§11, 10/18) | 바뀌지 않음(표시 없음) | 운영자 — 확인하면 운영자 이름으로 반영(신뢰 계정·합의는 꺼 둠) | 반려(바뀐 것 없음) |
| 편성표(3단계) | **바로 반영**(§11, 10/18) · 같은 일정의 열린 제보·방송 칸 여럿이면 운영자 대기 | 반영됨 + "확인 전" | 운영자 — 확인 = 표시 떼기 · 보류는 편성표 편집 저장 | 반려 = 되돌리기(고친 일정은 전으로, 만든 일정은 숨김) |
| **VOD 단서**(2단계 나) | 숨김 · 판독 대기열 맨 앞 | 바뀌지 않음 | VOD 판독(그 VOD·시점에 경기를 기록하면 확인) | 운영자 대기(못 찾음·영상 없음) |
| **빠진 경기 직접 입력**(2단계 가) | 사람·날짜 중복 검사 → 바로 공개 · 판독 대기열 맨 앞 | "검증 전"(목록에 보이고 집계 제외) | VOD 판독(만든 판 모두에 시점이 붙으면 판독 값으로 덮고 검증 → 집계) | 검증 전 그대로 + 운영자 · 반려 = 판 숨기기 |

### 10-2. 구조 — 기준은 한 파일, 처리는 한 길

```
사실 모으기 factsInTx            판정 decide(POLICY)                 실행
 접수 사실(intake)·운영자 결정  →  규칙 목록에서 처음 맞는 것   →  보임이 바뀌면 종류별 어댑터 show/hide
 보낸 사람 권한·같은 내용 회원 수    (보임 × 믿음 + 보류 이유          할 일 syncEffectsInTx: vod_priority(요청 줄) ·
 VOD 판독 사실(vod)                   + 할 일 effects + rule id)        adopt_vod(판독 값으로 덮기) · 닫히면 요청 거둠
```

- **기준의 단일 출처** `packages/core/lib/metrics/submission-policy.ts` — 규칙 목록 + 설정값 + 기준 버전. 기준을 바꾸는 일은 이 파일만 고치는 일이다.
- **처리의 단일 길** `packages/core/lib/db/submission.ts` — 접수(`admitInTx`)·다시 판정(`settleInTx`)·운영자 확인/반려·편성표 반영·+1·권한 변경·판독 결과가
  모두 "사실을 남기고 다시 판정한다"로 끝난다. 종류마다 다른 것은 어댑터(`ADAPTERS[kind]`: show/hide, VOD 어댑터 vods·found·matches·note, adopt)뿐이다.
- 판정마다 `rule_id`·`policy_version` 이 남는다 → "어떤 기준으로 검증됐나". 운영자 결정은 규칙 맨 위라 기준이 바뀌어도 뒤집히지 않는다.
- 기준이 바뀌면 `reconsiderOpenSubmissions()` — 열린 제보만 다시 판정, 판정이 그대로면 아무것도 안 바뀐다(멱등).

### 10-6. 설계에서 달라진 것(구현 때 정함)

- 신뢰 계정·합의 규칙은 **보류 아래**에 두고 **경기 고치기만** 쓴다(§4 의 처음 표는 보류 위였다) — 신뢰 계정 하나가 공식 기록·다툼·검수 끝난 판을 운영자 없이
  바꾸지 못하게, 편성표는 검증만 되면 반영 없이 닫혀 버리므로. 바꾸려면 규칙 순서만 옮긴다.
- 권한 표는 `PK(member_id, role)` + 기한 대신 **기록을 남기는 줄 + 거두기 칸**(누가 언제 왜 주고 거뒀나). 기한은 쓸 곳이 생기면 더한다.
- VOD 요청 표의 줄은 **VOD × 제보**이고 묶음은 읽는 쪽이 한다(제보마다 진행을 바로 읽으려고).
- VOD 단서가 못 찾으면 바로 닫지 않고 **운영자 대기**(§9 "검증 불가 → 검증 전 + 운영자"와 같은 결정).
- 직접 입력: 행사는 "있는 행사 + 모름"(모름 = 그날의 회원 등록 미분류 묶음), 시각은 날짜 정확도, 분류 쓰기의 쓰는 이를 넓히지 않고 새 판이라 auto 로 둔다,
  "찾음"은 만든 판 **모두**에 판독 시점이 붙었을 때, 덮는 칸은 승리 팀·챔피언·KDA·포지션(사람의 편과 시점끼리 다른 값은 운영자에게 남긴다).
  시점끼리의 충돌은 **모든 시점의 관측(경기 값과 같은 것까지)**을 칸마다 모아 가린다 — 처음 구현은 경기 값과 다른 관측만 모아,
  "경기 3킬 · A 3킬 · B 9킬"에서 B 의 9킬로 덮었다(10/18 외부 검토로 발견, 같은 날 고침 · 단위·verify:db 회귀 검사).
- 판독 값으로 덮는 쓰기를 위해 검수 길(`applyMatchReviewInTx`)에 쓰는 이 **auto** 를 더했다 — 사람 칸이 아니고, 검수 표시(`reviewed_at`)를 남기지 않고, 그 판의 칸만 고친다.
- 표시 문구는 종류별로 나누지 않고 하나("검증 전")로.

## 11. 반영 방향 바꾸기 (2026-10-18 사용자 결정, 0100)

> "경기 고치는 건 반영 안 되고 운영자가 확인하고 고쳐야 할 것 같고, 오히려 편성표 제보를 했을 때 바로 적용이 되는 게 좋을 것 같아."

| 질문 | 결정 |
|---|---|
| 편성표가 바로 바뀔 때 표시 | **확인 전 표시** — 운영자가 확인하면 떨어지고, 반려하면 제보 전 값으로 되돌린다 |
| 바로 반영 범위 | **고치기·새 일정 모두** |
| 경기 고치기 대기 중 공개 표시 | **표시 없음** — 회원은 내 제보에서 "운영자 확인 대기"를 본다 |

**판정 기준(코드 한 파일만 바뀌었다 — 뼈대 덕분)** `submission-policy.ts` 기준 `2026-10-18.1`

- 경기 고치기: 마지막 규칙 `apply_pending`(보임·확인 전) → **`correction_review`**(숨김·대기, 보류 이유 `correction_review`). 운영자가 확인하면 검수 길로
  운영자 이름으로 반영된다(기존 "보류 제보 확인" 길 그대로). 보류 사실 5종·신뢰 계정·합의 규칙은 그대로 — 신뢰·합의를 켜면 대기 대신 바로 반영 + 검증.
  - 접수 사실 "다툼(contested)"은 이제 확인 전뿐 아니라 **운영자 대기 중인** 같은 칸 제보도 센다(둘 다 열린 제보).
- 편성표: `schedule_review`(언제나 대기) → **`schedule_contested`**(같은 일정에 열린 제보가 이미 있음 → 운영자, 보류 이유 contested) ·
  **`schedule_multi_slot`**(방송 칸이 여럿인 일정의 날짜 → 운영자, 어느 칸인지 모른다) · **`schedule_apply`**(보임·확인 전).

**편성표 바로 반영의 실행(편성표 어댑터)**

- 반영 = 편성표 쓰기의 단일 출처 `saveScheduleEntryInTx` 하나. 저장할 입력은 순수 함수 `scheduleInputFromReport`(metrics/submission.ts)가 만든다 —
  고치기는 바꾼 칸만(시작을 옮기면 끝도 같은 길이, 참가자는 이름이 맞은 등록 스트리머로 — 있던 사람 역할·팀 유지, 새 사람 선수, 근거 링크는 출처에 더함),
  새 일정은 미분류·예정·공개 + 근거 링크 출처.
- 되돌리기 원본 = **`submission_schedule_effect`**(0100): `changed`(고치기 전 저장 입력 + 저장 직후 version) · `made`(만든 일정) · `admin`(운영자가 편성표 편집으로 반영).
  - 반려 = 고친 일정은 고치기 전 입력으로, 만든 일정은 숨김. **그 뒤 누가 또 저장했으면(version 이 다르면) 아무것도 바꾸지 않고 거부**(경기 되돌리기의 충돌과 같은 원칙).
  - 흔적이 이미 있으면 다시 쓰지 않는다 — 보류였던 제보를 운영자가 편성표 편집으로 저장하면(`applyScheduleReport`) 흔적 admin 을 남기고 확인으로 닫는다.
  - 방송 칸이 여럿인 일정의 날짜 제보는 "확인" 버튼으로 자동 반영하지 않는다(거부 문구로 편성표 편집을 가리킨다).
- 확인 전 = **`core_public.pending_schedule`** 뷰 하나(applied 제보의 흔적이 있는 일정). 공개 편성표 읽기(`schedule-public.ts`)가 `pending` 으로 내고,
  편성표 모듈이 목록·상세에 "확인 전" 표를 단다(제목에 마우스: "회원 제보로 바로 바뀐 일정입니다. 운영자가 확인하기 전입니다.").
- 잠금 순서: 일정 → 제보(접수·운영자 처리 모두 — `tryLockOpen` 이 편성표 제보의 일정을 먼저 잠근다).

**화면**: 경기 제보 화면 "운영자가 확인한 뒤 경기 기록에 반영됩니다" · 편성표 제보 화면 "바로 편성표에 반영되고 … 확인 전" · 운영 상세는 편성표 제보가
보류일 때만 "편성표 편집에서 반영 →", 반영된 것은 "반영된 일정 →" + 확인(표시 떼기)·반려(되돌리기).

**검사**: 판정 단위(새 기준) · `scheduleInputFromReport` 단위 · verify:db — 편성표 절을 새로 씀(바로 반영·되돌리기 원본·다툼·새 일정·반려 되돌리기·충돌이면 거부·
만든 일정 숨김·보류는 편집 저장·여러 칸은 확인 거부) + 제보 절(바로 반영 기계는 옛 규칙의 시험 기준으로 계속 검사, 기본 기준은 운영자 대기 → 확인하면 운영자 이름으로 반영,
기준을 바꾸고 다시 판정하면 바로 반영돼 있던 열린 고치기를 되돌려 운영자 대기로) · 브라우저 13단계(고치기 대기 → 운영자 "확인하고 반영", 편성표 바로 반영·확인 전·다툼 보류·
편집 반영·새 일정 반려 숨김).
