# FC 경기 맥락 조사

경기 사실(누가 이겼나)은 **넥슨 API가 이미 안다.** 여기서 알아내는 것은 **무슨 판이었나**다 —
어느 진행 방식의 행사 소속인가 — 대회·CK·컨셉(정해진 형식 밖의 특별 컨셉 경기)·친선. VOD 화면으로 API 값을 다시 판독하지 않는다.
**친선은 사람이 확인해서 정한다**(2026-10-16 사용자 결정 — 확인된 것만 라벨). 자동 조사는 친선 결론을 내지 않는다 — 행사 단서가
없으면 `unresolved` 로 무엇을 보면 풀리는지 남긴다. 보상 여부는 분류 기준이 아니다.

**단, API 는 최근 30일만 준다.** 그 이전 경기, 등록 계정의 API 기록에서 빠진 경기는 **VOD 결과 화면으로만** 안다 —
그때는 아래 [VOD 에서 출발하기](#vod-에서-출발하기--api-에-없는-경기)로 경기 자체를 기록한다. 출발점이 둘이고 규칙은 같다.

> **반드시 정해진 것은 「무엇을 수행하고 무엇을 기록하나」뿐이다.**
> 그 자료가 무슨 뜻인지, 어떤 결론을 내릴지, 더 조사할지는 **네가 판단한다.**

## 반드시 하는 것 / 네가 정하는 것

| 자리 | 반드시 수행·기록 | 네가 정한다 |
|---|---|---|
| 대상 | `fco:context list` 로 API 경기·기존 판단·행사 연결을 조회한다 | 어느 경기·VOD·시점부터 볼지 |
| 탐색 | 실제로 연 VOD 지점과 사용한 공지, 못 연 범위를 남긴다 | 후보 시간창, 프레임·채팅·음성의 범위 |
| 대조 | 후보 VOD 가 그 `matchId` 경기인지 화면 사실로 확인한다 | 같은 경기인지의 판단과 그 이유 |
| 기록 | 경기마다 결론(`event`) **또는 미해결 사유**(`unresolved`)를 `apply` 로 반영한다. **실제로 연 프레임은 `frame_path` 로 근거에 건다** | 행사 분류·메타데이터·시리즈 경계 |
| 마무리 | 저장 결과와 ⏭(충돌·검수 보호) 항목을 구별해 보고한다 | 조사 중단 위치 |

**검수자는 입력하지 않는다 — 승인한다.** `/admin/fco` 는 네가 남긴 제안과 프레임을 대조해
도장을 찍는 자리다. 그래서 조사 대상마다 **결론 제안과 근거를 완결해서** 반영해야 한다 —
좌표만 남기고 프레임을 안 걸면 검수자가 화면을 다시 찾아야 하고, 그건 조사를 두 번 하는 것이다.

**행사 결론은 행사 단위로 검수된다.** 검수 화면은 그 행사의 전 경기를 한 묶음으로 놓고
프레임을 시간 순으로 넘긴다. 그래서 행사로 결론 내릴 때는 **대회의 시작부터 끝까지의 서사**가
프레임으로 따라와야 한다 — 시작(안내·브래킷·오버레이), 경기마다 그 matchId 경기임을 확인한
장면, 종료(최종 결과·시상·마무리 발언). 몇 장인지는 네 판단이지만, 검수자가 프레임만 넘겨도
"이 경기들이 정말 이 행사였다"를 따라갈 수 있어야 한다. 각 근거는 해당 경기의 `evidences` 에
건다 — 행사 공통 장면(개막 화면 등)은 시간상 가장 가까운 경기에 건다.

**모드와 맥락은 별개다.** `mode_key`(매치 타입)는 친선의 증거가 아니다 — 친선 모드로도
컵·CK 를 한다(실측: 피온시식컵이 모드 40 이었다). **VOD 가 없어도 API 경기는 남는다** —
그건 `맥락 미확인`이지 `경기 없음`도 `친선`도 아니다. `N장 확인` 같은 합격선은 없다.
없는 행사명·주최자를 지어내지 않고, 근거가 부족하면 `unresolved` 로 남긴다.

## 흐름

```
fco:context list --vods        미조사 경기 + 후보 VOD 시간창
  → fco:context locate          경기마다 VOD 몇 초인가 + 뽑을 명령 (4종 · 결과 화면)
  → ck:probe --vod … --at/--between  프레임      (네가 연다)
  ↔ ck:listen · 채팅 !공지       필요한 구간만 (음성 기능을 켠 VOD 는 아래 「음성 원문」의 필수 열람)
  → fco:context draft --vods …  **뽑은 프레임 전량이 열거된 초안**
  → 초안을 채운다               연 것은 observed 를 쓰고, 안 연 것은 줄을 지운다
  → fco:context apply --file    반영 (유일한 창구, --dry-run 지원)
  → fco:context show            저장 결과 확인 → 사람이 /admin/fco 에서 프레임 대조 후 승인
```

**초안부터 시작한다 — 빈 파일에서 근거를 떠올려 적지 마라.** 빈 배열에서 시작하면 기록이
기억에 의존하고, 실제로 그렇게 **26장을 읽고 2장만 걸었다**(2026-08-25 뿌챔스 조사).
`draft` 는 `out/ck/<vod>/` 의 프레임을 전부 열거하고 `observed` 를 비워 둔다.
빈 `observed` 는 저장이 거부하므로 **읽은 것은 채우고 안 읽은 것은 지워야** 반영된다 —
그 지점이 「뽑음」과 「읽음」을 가르는 자리다(`ck-research` 의 `scan-draft.json` 과 같은 구조).

시간창 초기값은 실측(docs/FCO-TIME-SAMPLES.md)에서 온다: **matchDate 는 경기 종료 시각**,
경기 구간 ≈ [matchDate−12분, matchDate]. 판정 규칙이 아니라 탐색 시작점이다.
프레임·전사의 시각은 전부 **VOD 전체 초** 하나로 쓴다(ck:probe 와 같은 축).

## VOD 에서 출발하기 — API 에 없는 경기

API 경기 목록이 아니라 **VOD 를 받아** 그 안의 FC 경기를 찾는 흐름이다(과거 백필·대회 VOD). 설계: docs/FCO-SCREEN-MATCH-DESIGN.md.

1. **지도** — `npm run ck:local -- --vod <번호>`(롤·FC 공용 준비, 6시간 VOD 약 1분) 다음
   `out/ck-detector/venv/bin/python scripts/fco-local/fc_detect.py --vod <번호>`(FC 전용 판별기, 약 1분).
   `out/ck/<번호>/local/fc.json` 의 `results`(결과 화면 후보 초)와 `blocks`(FC 구간)가 찾을 곳이다 — `locate` 도 이걸 보여 준다.
   처음 보는 채널에서 경기 단위로 약 91% 를 짚지만 **위치 안내일 뿐이다** — 후보가 없는 FC 구간은 결과 화면을 직접 찾는다
   (아래 「결과 화면을 찾는 기본 방법」, 구간 끝에서 시작). 후보 원본을 열어 결과 화면이 아니면 버린다.
2. **읽기** — 결과 화면 원본에서 두 닉네임·스코어(·보이면 모드·승부차기)를 읽는다. 보이는 것만 적는다 — 스쿼드·통계는 비운다.
   **닉네임은 확대해서 한 글자씩 확인한다** — 검증(2026-10-01)에서 27경기 중 11경기가 자모 하나를 잘못 읽었다
   (뀨뀨rr→꾸꾸rr, 걍하리→강하리, 잉유진→임유진: ㅠ/ㅜ·ㅑ/ㅏ·ㅇ/ㅁ). 스코어는 전부 맞았다. 한 글자가 틀리면 같은 경기를
   자동으로 못 잇고 검수 대기로 간다(틀린 연결은 안 생기지만 사람 일이 는다). 같은 사람이 여러 판이면 판마다 같은 철자인지 맞춰 본다.
   같은 점수(승부차기 가능)·못 읽은 점수는 적지 않으면 도구가 `unknown` 으로 둔다. 승부차기 승자를 봤으면 `outcome` 으로 적는다.
3. **저장** — `npm run fco:context -- screen --file out/fco/<이름>.json [--dry-run]`
   ```json
   [{ "vod": 207643193, "at_sec": 5310,
      "sides": [{ "nickname": "알파감독", "score": 2 }, { "nickname": "상대감독", "score": 1 }],
      "observed": "결과 화면 2:1, 알파감독(홈) vs 상대감독" }]
   ```
   - `at_sec` 는 **연 결과 화면 프레임의 VOD 전체 초**다(`out/ck/<vod>/g<초>.jpg` 가 있어야 한다 — 그 프레임이 근거로 걸린다).
   - 사람: 등록 계정 닉네임과 **정확히 하나만** 맞으면 도구가 붙인다. 방송 주인 본인 칸은 `"streamer_slug": "…", "basis": "vod_owner"`.
     그 밖의 추정으로 slug 를 적지 않는다 — 모르면 닉네임만 둔다.
   - 결과: `created`(새 화면 경기, 숨김) · `linked`(같은 경기의 API·다른 화면 기록에 연결, 근거 복사) ·
     `needs_review`(후보가 둘 이상이거나 조건 부족 — **그대로 둔다**, 검수가 정한다) · `protected`(검수된 경기).
     관측은 어느 경우든 먼저 저장된다 — "API 가 곧 가져오겠지"로 저장을 건너뛰지 않는다.
4. **맥락 — 경기마다 결론을 남긴다(백필에서도 필수).** 저장한 경기와 이 VOD 시간대의 API 경기
   (`fco:context list --from <VOD 날짜> --to <VOD 날짜> --streamer <방송 주인 slug>` — 결과 화면을 못 찾은 판도 API 에는 있다)마다
   `apply` 로 `event`·`unresolved` 중 하나를 남긴다(`casual` 은 없어졌고 `friendly` 는 사람만 낸다 — 자동 반영이 거부한다). 대상 id: `linked` 면 연결된 API 경기, `created` 면 `screen` 이 찍은
   화면 경기 id(`fcs:<VOD>@<초>`). `needs_review` 는 검수가 연결을 정하기 전이라 미루고 근거를 `observed` 와 보고에 남긴다.
   음성 기능이 켜져 있으면 결론 전에 아래 [음성 원문](#음성-원문--기능을-켠-vod)을 읽는다.
   - **대회·CK 는 행사로 묶는다 — 먼저 기존 행사를 찾는다.** `npm run fco:context -- events [--search <이름 일부>]` 로 같은 대회가 있는지 보고,
     이름·날짜·참가자가 맞으면 그 slug·name·format 을 **그대로** 쓴다(하나라도 다르면 apply 가 거부한다). 앞선 VOD 세션이 이미 만들었을 수 있다.
   - 새로 만들 때: slug 는 `fc-<대회를 가리키는 영문·숫자>-<첫 경기 KST 날짜>`(예: `fc-tier3-cup-2026-10-11`), name 은 방송·공지에 나온 대회명
     그대로(회차·날짜를 붙여 구별), format 은 `tournament`(티어 대회·승격전·리그·컵) · `ck`(스트리머끼리 정해서 겨룬 승부 — 보상 무관) ·
     `concept`(벌칙·미션·특수 규칙 등 정해진 형식 밖의 특별 컨셉 경기 — 확인될 때만). 대회 대비 연습은 행사로 묶지 않고 `unresolved` 로 남긴다
     (FC 에는 스크림 분류가 없다). 옛 `kind` 키는 거부된다.
     `source_url` 은 공지·대진표 URL 이 있으면 그것, 없으면 근거를 본 VOD URL(`https://vod.sooplive.com/player/<번호>`).
   - **여러 날·여러 방송에 걸친 한 대회는 한 행사다**(예선·본선·승격전 전체). 회차가 다르면(이번 주 대회와 다음 주 대회) 다른 행사다.
     대회 대비 연습 경기를 대회 행사에 넣지 않는다.
   - **방송 주인이 참가한 대회면 다른 참가자끼리의 경기 결과 화면도 저장하고 같은 행사로 묶는다.** 대회와 무관한 남의 경기 시청(프로 경기 등)은 저장하지 않는다.
   - 제목·분위기만으로 `event` 로 묶지 않는다. 근거가 모자라면 `unresolved` 에 무엇을 보면 풀리는지 남긴다.
5. **도장** — VOD 를 다 봤으면 `npm run fco:context -- scan --vod <번호> --status done --requested 0-<길이> --opened <연 초,…>`.
   못 끝냈으면 `--status running`. **롤 도장과 따로다** — 롤 조사가 끝난 VOD 도 FC 로는 따로 끝내야 한다.

## 음성 원문 — 기능을 켠 VOD

`npm run ck:listen -- status --vod <번호>` 가 `active:true` 면 적용한다(롤 조사와 같은 스위치). 백필 실행기가 Claude 시작 전에
**첫 FC 활동 30분 전부터 마지막 경기 끝까지**(`prepare --plan fc`, +5분 여유) 전사해 둔다 — 그 사이는 경기 내부까지 통째로라
아래 필수 창은 항상 들어 있다. 그 밖(방송 앞부분 잡담·마지막 경기 뒤)이 필요하면 `npm run ck:listen -- prepare --vod N --between a:b`
로 그 범위만 더 준비한 뒤 읽는다(차례를 기다릴 수 있다). 롤이 이미 전사한 VOD 는 같은 원문을 그대로 쓴다.
**명령(read·페이지·ack·search)과 해석 원칙은 [공통 절차](../ck-local/listen.md)를 따른다.** 읽는 시점과 기록만 아래 FC 규칙이다.

1. **필수 — 경기 앞 대화와 경기 사이 대화.** 첫 경기는 시작 전 30분(`read --vod N --before <첫 경기 시작초>`), 다음 경기부터는
   직전 경기 결과 화면부터 그 경기 시작까지(`--before <시작초> --previous-end <직전 결과 화면초>`). 창이 여럿이면
   `--between a:b,c:d,…` 로 묶어 한 번에 읽는다. 시작초는 킥오프를 봤으면 그 초, 아니면 결과 화면 −12분(실측 경기 길이, docs/FCO-TIME-SAMPLES.md).
   경기 맥락 결론(`apply`) 전에, 늦어도 `scan --status done` 전에 읽는다. 판별기 지도의 FC 구간(`fc.json` 의 `blocks`)은 대기실 잡담까지
   묶어 여러 경기를 한 구간으로 잡으므로 이 기준에 쓰지 않는다(2026-10-13 시험: 구간 기준으로는 39초만 읽고 첫 경기 앞 "3티어 대회" 대화를 놓쳤다).
2. **행사·시리즈 결론은 그 범위를 읽은 뒤.** `event`·`series` 로 묶을 때는 첫 경기 앞 안내부터 마지막 경기 뒤 마무리까지
   `read --between` 으로 읽는다. 구간 앞 대화에서 행사·내기 단서가 나오면 친선으로 닫기 전에 그 앞뒤를 더 읽는다.
3. **무엇을 듣나** — 친선/CK/대회, 대회명·주최, 몇 판 몇 선승, 상대 교체, 보상·벌칙, 본인 경기인지 남의 방송 시청인지.
4. **덮지 않는다** — 닉네임·스코어·승부차기 승자는 결과 화면이 정본이다. 음성의 이름은 화면 철자를 확인하는 단서일 뿐이다.
   **`best_of` 는 여전히 화면·공지 근거로만 넣는다** — 음성의 "3판 2선승" 은 `audio` 근거로 걸고 `best_of` 는 비운다.
5. **결론에 쓴 발언은 그 경기 근거로 건다** — `kind: "audio"`, `frame_path` 없음, `observed` 는 원문 그대로(고쳐 쓰지 않는다):
   ```json
   { "evidence_key": "audio:<vod>@<청크 시작초>", "kind": "audio", "vod_title_no": 207643193, "at_sec": 1440, "end_sec": 1470,
     "observed": "<원문 그대로>", "why": "<해석 — 왜 이 경기의 맥락인가>" }
   ```
6. **도장** — `fco:context scan … --listen-read <ack 한 패킷ID,…>` 가 읽은 범위를 `transcript_read` 에, `asr` 를 `signals` 에 넣는다
   (ack 안 한 패킷이면 저장 전에 거부한다). 못 읽은 범위·사유는 `--listen-note "구간과 사유"`.
   **`--status done` 은 관문을 거친다**(2026-10-14) — 이 VOD 의 화면 경기(`fcs:<vod>@<결과 화면초>`)로 필수 창의 바닥을 계산해
   (`requiredFcWindows`: 킥오프가 결과 화면 9~15분 전 어디든 반드시 읽게 되는 부분, 경기가 없으면 `fc.json` 첫 FC 구간 앞 30분),
   지금까지의 `transcript_read` 가 덮지 않으면 DB 에 쓰기 전에 거부하고 읽을 `--between` 을 알려 준다(아직 전사 전인 자리면
   먼저 `prepare --between` 할 범위도 알려 준다). 전사에 실패한 자리만
   `--listen-note` 를 붙여 넘어간다. 키워드 검색·샘플은 읽은 것으로 치지 않는다 — 경고만 하던 때 음성을 건너뛰고 done 을 찍은 VOD 가 나왔다.
7. **준비 종료 코드가 실패여도 이미 전사된 원문은 읽는다.** 실패는 "이번에 새로 전사하지 못했다"는 뜻이지 원문이 없다는 뜻이 아니다.
   `status` 의 `coverage` 안에 든 필수 창은 위 1·2 대로 읽고, `missing` 에 걸린 부분만 확인 불가로 `--listen-note` 에 적는다.
   `missing` 은 무음이 아니다. 필수 창이 전부 `missing` 이면 사유를 남기고 화면 조사로 진행한다 — 음성이 없다고 FC 조사를 멈추지 않는다.
   **경기가 없는 VOD(남의 경기 시청 등)도 `done` 전에 FC 화면이 처음 나오는 지점 앞 30분을 읽는다** — 화면만으로 시청이라고 닫지 않는다.

## 경기마다 뽑는 장면 — 4종 + 결과 화면

경기 시작은 넥슨 `matchId` 앞 8자리(16진 유닉스 초), 종료는 `matchDate`, VOD 0초는
`broad_start` 다. `locate` 가 이 셋으로 경기마다 VOD 초를 계산해 명령을 찍어 준다.

| role | 장면 | 무엇을 보여주나 |
|---|---|---|
| `pre` | 경기 전 (대기실·브래킷·대진 안내) | 이 대진이 예정돼 있었다 |
| `start` | 킥오프 직후 | 그 두 사람이 그 경기를 시작했다 |
| `end` | 종료 직전 경기 화면 | 경기가 끝까지 갔다 |
| `post` | 종료 후 (반응·다음 안내) | 끝난 뒤 흐름 |
| `result` | **결과 화면** (최종 스코어·득점자) | API 스코어와 같은 경기다 |

**결과 화면은 모든 포함 경기에 필수다.** 검수 화면은 경기를 고르면 `result` 프레임을 먼저
띄운다 — 검수자는 스코어를 API 값과 대조하는 것으로 판단을 시작한다. 무승부·연장·승부차기는
API 가 승자를 못 가리는 경우가 있어 결과 화면이 **유일한 근거**가 된다. `apply` 는 결과 화면
근거가 없는 경기를 경고로 찍는다. `locate` 의 4종 지점은 보정한 초기값이지 정답이 아니다 —
열어 보고 그 장면이 아니면 앞뒤를 더 본다. 연 프레임에는 본 장면대로 `role` 을 단다
(장면이 아니면 비운다. 추측해서 채우지 않는다).

### 결과 화면을 찾는 기본 방법

**먼저 지도.** 그 VOD 에 롤·FC 공유 준비 산출물(`out/ck/<vod>/local/scan.json`)이 있으면 `locate` 가
`지도  FC 결과 화면 …s → ck:probe --at …` 줄을 함께 찍는다 — 판별기가 결과 화면으로 본 칸이다. 그 원본부터 연다.
산출물이 없으면 `npm run ck:local -- --vod <번호>` 로 만든다(약 1분, 다른 SOOP 도구와 동시에 돌리지 않는다).
지도는 위치 안내일 뿐이다 — 연 원본이 결과 화면이 아니거나 지도 줄이 없으면 아래 기본 방법으로 간다.
지도(`map.txt`)의 **FC 경기 구간이 이어진 묶음**은 맥락 판단에서 어디를(묶음의 시작·끝) 볼지 고르는 데 쓴다. 결론은 여전히 경기마다 근거로.

`locate` 가 주는 첫 구간 [종료−20초, 종료+60초] 을 `--divide 5` 로 나누고, **뽑은 지점을
모두 연다.** 결과창이 없으면 마지막으로 확실한 **경기 진행 화면**과 처음으로 확실한 **종료
후 화면**(다음 대기실·방송 화면)을 새 기준점으로 삼아 그 사이를 다시 `--divide 5` 한다.
더 좁힐 수 없는 마지막 짧은 구간만 `--step 1` 로 소진한다. 채팅·음성이 정확한 시각을 주면
거기서 시작해도 된다. 로딩·다른 창·리플레이는 기준점이 아니다.

다음 경우에만 탐색을 닫는다.

- 결과 화면을 읽음 → `role: "result"`, observed 에 **읽힌 스코어·이름 그대로**
- 좁혀진 구간의 모든 초를 열었으나 없음 → **결과 화면 미발견** (note 에 연 범위)
- 다른 참가자 VOD 에서 같은 경기의 결과 화면을 확보함
- VOD 끝·조각 누락·가림으로 확인할 수 없음 → **확인 불가** (못 연 범위를 note 에)

미발견과 확인 불가는 다르다. 결과창이 여러 장이면 가장 잘 읽히는 것을 `result` 로, 나머지도
연 것이면 근거로 건다(역할은 같게 둬도 된다). 뽑고 안 연 프레임으로 탐색을 닫을 수는 없다.

## 명령

```bash
npm run fco:context -- list [--from 2026-09-20 --to 2026-09-23] [--streamer slug] [--vods]
npm run fco:context -- locate --vods 205292057,205320949 (--event slug | --match-id id,… | --from/--to)
npm run fco:context -- draft  --vods … (--event slug | --from/--to) [--out out/fco/x.json]
npm run fco:context -- draft --vods 205292057,205320949 --event <행사slug> [--out out/fco/x.json]
npm run fco:context -- show --match-id <넥슨matchId>
npm run fco:context -- apply --file out/fco/0923.json [--dry-run] [--admin]
npm run fco:context -- screen --file out/fco/<이름>.json [--dry-run]   # API 에 없는 경기 — VOD 결과 화면으로 기록
npm run fco:context -- scan --vod <번호> --status done|running [--requested 0-<길이>] [--opened …] [--listen-read <패킷ID,…>] [--listen-note "…"]   # FC 조사 도장
npm run fco:context -- events [--search <이름 일부>]   # 기존 FC 행사(경기 수·기간·참가자) — 새 행사를 만들기 전에 같은 대회를 찾는다
npm run fco:sync -- --streamer slug --nickname 감독명   # 계정 연결·경기 수집 (일일은 워커 engine_e_fco)
```

`ck:probe`/`ck:listen` 은 그대로 쓴다 — DB 에 아무것도 쓰지 않고, 추출한 프레임은 읽은
프레임이 아니다. **연 것만** 근거다.

## 반영 파일 — `apply` 입력

```jsonc
[{
  "provider_match_id": "6aafaa2f3d823566b1f0cca9",
  "conclusion": "event",              // "event" | "unresolved" | 생략(근거만 추가). "friendly" 는 사람(--admin)만
  "note": "…",                        // unresolved 일 때 필수 — 무엇을 보면 풀리는가(남은 질문)
  "event": {                          // conclusion=event 일 때
    "slug": "fc-sisik-cup-2026-09",
    "name": "고세구 피온시식컵",
    "format": "ck",                   // ck | tournament | concept 만
    "source_url": "https://…"         // 확인 근거 URL 필수
  },
  "evidences": [{
    "evidence_key": "vod:207643193@1479",   // 멱등 키 — 네가 정한다
    "kind": "vod_frame",                     // vod_frame | chat | audio | notice | url
    "vod_title_no": 207643193, "channel_id": "phonics1", "at_sec": 1479,
    "frame_path": "out/ck/207643193/g0001479.jpg",  // 네가 실제로 연 파일 — 검수 화면이 띄운다
    "role": "end",                                   // pre|start|end|post|result — 본 장면. 아니면 생략
    "observed": "인게임 88:23, 교로텔리 3:4 호날두",   // 본 것
    "why": "matchDate 16초 전 88분 — 이 matchId 경기다"  // 해석. observed 와 섞지 않는다
  }]
}]
```

- **다전제(시리즈)**: 같은 두 사람이 연속 세트로 한 판의 승부를 가렸으면 세트마다 `series` 를 붙인다.
  ```jsonc
  "series": {
    "id": "fc-sisik-cup-2026-09-20:kimmingyo-doochiwa",  // 시리즈 정본 키
    "game_no": 2,                                         // 몇 번째 세트인가
    "best_of": 3,                                         // 모르면 비운다
    "best_of_evidence": "방송 공지 '3판 2선승'"            // best_of 를 줄 때만 필수
  }
  ```
  **상대가 바뀌면 시리즈가 아니다** — 그건 대회 안의 다른 매치업이라 `event` 로 묶는다(저장이 거부한다).
  `best_of` 는 화면·공지에서 읽은 근거 없이는 못 넣는다(음성 발언만으로도 넣지 않는다). **「연속 3경기니까 Bo3」는 추측이다** —
  형식을 모르면 비우고, 그래도 세트는 시리즈로 묶인다. 시리즈 승패는 저장하지 않고 세트에서 파생한다.
- **근거는 「실제로 연 것 전부」다.** 결론을 설득할 최소한이 아니다. 판단에 쓴 화면, 쓰지 않았지만
  열어서 확인한 화면, 어긋나 보였던 화면까지 전부 건다 — 검수자는 네 결론이 아니라 **네가 본 것**을
  대조한다. 뽑아 놓고 안 건 프레임이 있으면 `apply` 가 ⚠ 로 알린다.
- **결론과 근거의 뜻**: `unresolved`(모름 — 판은 그날 두 사람의 미분류 묶음에 남는다, 남은 질문 필수) ·
  `event`(행사를 찾거나 만들어 판을 그 행사의 시리즈로 옮긴다 — CK 면 `format: "ck"`). 분류는 문자열이 아니라 **행사 소속**이다.
  친선은 사람이 검수 화면에서 확정한다(자동 조사는 친선 결론을 낼 수 없다).
  결론 없이 `series` 만 주면 그날 두 사람 묶음 안에서 세트를 묶는다.
- 재전송은 중복을 만들지 않는다. 판단 메모는 이력으로 쌓이고, 근거는 `evidence_key` 로 합쳐진다.
- **admin 판단은 자동 반영이 못 덮는다** — 사람이 그 행사에서 뺀 판은 자동이 다시 넣지 못한다. ⏭ 로 알려주며 성공으로 세지 마라.
- 같은 slug 다른 이름·다른 format 의 행사는 **거부된다**. 덮어쓰지 말고 확인하라(`fco:context events` 출력 칸도 `format`).
- 판의 행사는 언제나 그 판의 시리즈를 거친다(행사 → 시리즈 → 세트). 시리즈를 옮기면 그 시리즈의 모든 세트가 함께 간다.
- 여러 POV 근거는 전부 남긴다. 경기당 하나로 관리되는 것은 **현재 최종 판단**뿐이다.

## LoL 조사와의 경계

- LoL 전량 조사 중 FC 화면을 **실제로 열어** 봤다면: `npm run fco:context -- clue --vod … --at … --observed "…"`.
  단서일 뿐 FC 경기 연결이 아니다. LoL 탐색의 나머지 범위를 생략할 이유도 아니다.
- FC 조사 대상은 LoL 스캔 결과로 제한되지 않는다 — API 에만 있는 경기도 후보다.
- VOD 화면에 FC 가 보여도 API `matchId` 와 대조하기 전에는 그 경기로 묶지 않는다.

## 갈리는 판단 — 정답을 정해 두지 않는다

- 이 화면은 본인 플레이인가, **남의 방송 시청/중계인가**? (실측: 김민교가 고세구 방송을 보던 화면이 있었다)
- 연속된 경기들이 같은 행사인가, 행사 중간의 연습인가? CK 안의 연습 경기와 행사 경기를 구별할 근거가 있나?
- 채널이 미등록이면 `VOD 없음`이 아니라 `조사 불가`다 — 채널 등록이 먼저인지 판단하라.
- 더 보면 결론이 바뀔 가능성이 있나? 낮으면 어디서 멈출지.

## 끝내기

`apply` 출력의 **남은 일**(미조사·미해결 수)을 그대로 전한다. 수를 지어내지 않는다.
`npm run verify:fco-context` 는 스키마·계약을 건드렸을 때만 돌린다.

⚠ **FC 화면 부재는 부정 증거가 아니다.** 방송을 안 켰거나, VOD 를 안 남겼거나, 다른 채널에서
했을 수 있다. 그 결론은 숫자가 아니라 네가 남기는 것이다.
